# 会话目标

目标（goal）是会话持续朝向的一个条件。用 `/goal` 设定一次；此后每轮结束时运行时都会判定条件是否已经成立，未成立就自动续一轮——每个续轮都是普通的一轮，你可以旁观、插话或停止。模型不再说话，会话也不会就此自然停下。

```
/goal 所有单元测试通过，且 README 写明了新参数
```

这条命令把目标写到会话上，并立即以条件文本为指令发起第一轮。之后每当一轮结束而目标未达成，运行时就发出一条续轮消息（`[goal] 未达成：<原因>。继续。`），带上判定者给出的未完成原因。

## 两种判定方式

**带检查命令**（能写出来就优先用它）：

```
/goal --check "cd /path/to/repo && python -m pytest -q" 所有测试通过
```

引号里的命令在每轮结束后于会话工作目录执行（120 秒超时）。退出码 0 即达成；非 0 则继续循环，命令输出的尾部会作为原因喂给下一续轮。判定完全确定性，零 LLM 成本。

**不带检查命令**时由 LLM 判定。每轮结束后，用会话模型发起一次无工具调用，读目标文本加对话尾部（最后的助手输出和最近的工具结果），输出严格的是/否加原因。判定者刻意不是干活的 agent 自问"我做完了吗"——自报式判定普遍偏乐观；结论来自一次只看证据的独立调用。

## 怎样写出有效的条件

把条件写成对话记录能证明的事，而不是一种感觉：

- 好：`tests/unit` 全部通过，且新页面登记进了 `nav.py`——判定者能看到测试输出和文件改动。
- 好：脚本对全部 12 个输入都打印 `OK`——输出可证明。
- 弱："代码要干净"、"功能要好用"——记录里没有能裁决它的东西，判定者只能猜，循环会漂。

条件能写成 shell 命令就用 `--check` 挂上——一套会失败的测试比任何模型都是更好的判定者。

## 查状态、解除、停止

```
/goal            # 显示目标、状态、已用轮数和最近一次原因
/goal clear      # 解除（别名：stop / off / cancel）
```

续轮期间 Stop 按钮（以及任何取消）与你自己的轮次完全一样有效——续轮就是普通一轮。停止不会清除目标；它保持 `active`，你下一条消息之后继续判定。要真正移除用 `/goal clear`。

Web 界面里，活跃目标显示为输入框上方 chip 行的 `◎ goal · N/20`（N 为已用轮数）。循环结束时变为 `goal achieved` / `goal capped` / `goal error`。

## 循环何时自行停止

| 结果 | 含义 |
|---|---|
| `achieved` | 检查命令通过，或判定者回答已达成。 |
| `capped` | 用完轮数预算（默认 20；设置项 `goal.max_turns`）。调大预算或拆分目标。 |
| `error` | 某个续轮在目标未达成的情况下没有任何工具调用（空转），或判定连续失败三次。目标状态和最近原因仍可用 `/goal` 查看。 |
| `cleared` | 你解除了它。 |

失败的一轮（provider 报错、取消）只是暂停循环，不消耗目标——目标保持 `active`，下一次完整的一轮之后恢复判定。

## 在哪些入口可用

`/goal` 是内建命令：Web 输入框、TUI、Rich REPL 都接受，而续轮循环跑在 worker 里，关掉页面它也继续。一个入口设定的目标在所有入口可见——状态存在会话上。
