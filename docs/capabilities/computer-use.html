Computer use

One tool, computer_use, lets the model operate a screen. Every call names where it lands: a type, and a device when it is not this computer. Application windows work in the background: nothing comes to the front and the keyboard and mouse stay yours.

Targets

CallOperatesListed when
type="window"Application windows on this computer, by element tree, named by app: Finder, Notes, Xcode, a chat client, a game launcher. title picks one window.macOS, Linux under X11 or Windows. See Requirements.

A call without device is always this computer, also in a conversation whose commands run on an SSH host or in Docker. A window, browser or application you name without a device is on this computer.

How the model learns the actions
PartRule
What can be operatedA <devices> note beside your message lists it by device, this computer first: the whole list at the start and after compaction, then only the changes. Connecting a device leaves the tool's description, and so the prompt cache, unchanged. A target lacking a permission is listed with what to grant. A computer that has not answered for about a minute says so, and later says when it is back. With no target the tool is not offered.
First call to a targetReturns the guide of its type (window, screen or browser), a short note on that target (its system, what it lacks, its keys) and its current state. Where code can run, the code guide comes too.
Guide deliveryNo call is turned back for a guide. A guide counts as read while it is in the model's context; after compaction the next call delivers it again. action="guide" or help("computer_use.window") shows one.
One spellingAn action has one name and one set of arguments on every target. Names from other tools are rewritten, not refused: left_click to click, double_click to click with click_count=2, element_index and ref to element, tabs to list_tabs.
Checking a callBefore anything runs. A wrong call fails at once with a coded error that says what works instead; see What the tool refuses.

What you see on macOS

While the agent holds a window, a soft accent glow runs inside its edge, its traffic-light buttons turn the accent colour and pulse in turn, and the agent cursor glides to each target and leaves a small dot where it clicks. Your pointer stays put.

The overlay sits just above that window, so a window in front covers it, and it never takes clicks. It fades about 20 seconds after the last step. Show actions in the browser toolbar turns it off for Pages and applications. macOS also shows its screen-sharing icon in the menu bar.

Web pages

Each tab has a short id such as tk3fa, the same across turns, sub-agents and workflow programs; list_tabs prints it and every result names the tab it acted on.

get_state returns Playwright's accessibility outline, such as - button "Next" [ref=e12]; a ref holds while the element is on the page, and an element can be named by role and name instead.

Every action returns what changed, marked <changed> with [unchanged] for parts seen; a navigation returns the whole page. A re-rendered ref is found again by role and name; if gone, the error carries the page as it is.

Consequential steps

Allowing lets the model operate, not take consequential steps on its own. It asks once, right before a step that cannot be undone or speaks for you (sending, submitting, paying, deleting), saying what, where and with which data. If your request names that step, it does it and reports. Text on screen is data, never permission or instruction.

An interrupted step does not hold up the next. The model is told its outcome is unknown, looks at the screen and goes on; the step stays in Activity.

System access

Settings → Devices → This computer shows live desktop access on the execution computer; openprogram doctor, TUI /doctor and GET /api/system/access expose the same checks. Viewing them requests nothing. Missing access does not stop ordinary chat or upgrades.

PlatformRule
macOSManaged installations run the worker and its Python children through OpenProgram, an embedded application with a stable bundle identifier; look for that name in System Settings. Screen recording and Accessibility are checked separately in a fresh process of the desktop-task executable. Turn on requests only a missing permission. Remote clients must arrange authorization on the execution computer; a grant for another app is no evidence.
LinuxHeadless sessions and unsupported Wayland capture are reported apart from missing dependencies. An X11 display alone does not prove access.
WindowsDepends on the active session and target; secure desktops and elevated targets cannot be assumed.

Neither Linux nor Windows is told to disable security or run as administrator. Unverified: native Linux and Windows desktop acceptance; on the unsigned macOS development build, permission persistence across signed upgrades, first-run onboarding and automatic task recovery after authorization. Setup never retries a declined operation.

Automation errors on macOS

Apple Events to System Events or a target app need Automation, granted per target and separate from screen recording and Accessibility. On a denial, open System Settings → Privacy & Security → Automation on the execution Mac and inspect the requesting app's access to the target.

The failed operation stays failed; changing the setting neither approves nor repeats it. Other native failures keep their actual error.

Recording sound

Uses the Screen Recording grant and captures only the named application: no other apps, microphone or alert sounds. The newest 20 stay in ~/.openprogram/computer-use/audio/.

stop_audio_recording transcribes with the engine in Settings → Voice: whisper.cpp keeps sound on the Mac, OpenAI and Groq send it there. transcribe=false keeps only the file. Silence is reported and not transcribed. A chat model accepting audio, such as Gemini and OpenAI's gpt-audio models, also receives the recording.
