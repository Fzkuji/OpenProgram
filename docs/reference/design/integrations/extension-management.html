One management grammar for Plugins, Skills, and MCP

This document defines how an OpenProgram owner discovers, adds, configures, enables, diagnoses, and removes the three extension types in the Web UI. The audience is the Web and runtime maintainers. Programs, agent-specific allowlists, third-party marketplace governance, and new package formats are outside this task.

Current implementation and verified gaps

Different task words

Plugins use Installed / Marketplace / Errors and “Install”; Skills use Browse / Discovery and “New skill”; MCP uses a server rail, “Browse catalog,” and “Add server.” The same user intent changes name and location.

Different failure behavior

Skills have a page error bar. Plugin initial load can reject without a page-level error. Several MCP mutations ignore non-2xx responses, leaving the visible state unchanged with no explanation.

Different status density

Plugins expose trust and load errors, Skills expose enabled state, and MCP exposes live readiness and tool count. The page chrome does not state which count means installed, enabled, ready, or failed.

Duplicated MCP discovery

MCP exposes Discover as both a secondary tab and a top-level action. The tab only opens a modal while Installed remains active, so navigation state and visible content disagree.

State and failure flow

Public page action

Add, enable, refresh, test, update, or remove. The control enters a busy state and remains named after the action.

→

Typed JSON request

One client parses error and FastAPI detail, preserves status/code, and throws one error type.

→

Observable result

Success refreshes the affected collection and selection. Failure stays visible near the collection or dialog and explains the recovery action.

Adopted, modified, and rejected choices

Adopt

Reuse ManagePageHeader, ManageSubnav, ManageRow, existing dialogs, existing routes, and native fetch. Preserve each subsystem’s backend and security boundary.

Modify

Standardize task vocabulary, summary placement, loading/error feedback, and request error parsing. The top toolbar contains only search and refresh. Secondary tabs own the body and the single Add action. MCP Discover renders the catalog inline and becomes the active tab.

Reject

No duplicated Discover action in the top toolbar, no Discover modal, no universal extension backend, no merged persisted schema, no new state library, and no automatic remote installation from search results.

Reference comparison: Claude Code’s plugin manager supports installed/discover/error tasks but does not define OpenProgram Skills or MCP runtime readiness; opencode’s MCP and plugin surfaces do not provide one cross-type management model; Hermes groups skills but lacks the three-type availability summary. The target therefore adopts the shared task vocabulary while retaining OpenProgram-specific live MCP state and Skill hierarchy.
