屏幕审批

审批与访问

一块屏幕整体授权，一次：一个应用、整个屏幕，或用户自己的浏览器，连同在里面做的一切（点击、输入、页面脚本、往里上传）。一次调用问什么由目标的 provider 回答（Provider.approval）：显示的那句话，以及回答记在哪个规则键下。

调用授权
type="window"（list_apps 除外）按应用：“computer_use controls <application>”，规则 computer_use(window <application>)，这里是应用的显示名（AppProvider._rule_name，见下）
type="screen"（list_displays 除外）“computer_use controls the whole screen of this computer”，规则 computer_use(screen)：包含所有应用的那块表面上的授权
type="browser", app="chrome"、"safari"、"firefox" 等“computer_use controls your Google Chrome”，规则 computer_use(browser chrome)（或 browser safari、browser firefox，每个浏览器名一条），从不使用 Page 授权；它覆盖那里的页面脚本和上传
type="browser"对话有 Page 时不需要（本轮的 Page 授权）：打开网站、在上面操作、在里面运行脚本都不询问。upload_file 把本地文件发出去，所以 Page 授权从不覆盖它：会询问的模式每次都询问，Auto 每次都审查；它没有规则键
带设备的调用（device="lab", type="screen"）不需要：设置好这台设备就是同意。它的键 <device> <type>（lab screen）仍会被所有者的 deny 和 ask 规则匹配
action: "guide"不需要

AppProvider._rule_name 调用后端的 app_name：精确匹配，不启动也不画图标，保留 5 秒，所以审批、保存的规则和之后的调用拿到同一个键。

macOS 上任何精确写法（显示名、文件名、bundle id、.app 路径、运行时用的名字、运行中的 pid:N）都得到显示名，不管运行与否。

Linux 上桌面 id、条目名、可执行文件或 pid 得到条目的名字；Windows 上 pid 或 exe 得到去掉 .exe 的文件名。其他名字，包括名字的一部分和开始菜单里的名字，按原样保留。

权限与审批

项
审批文案requires_approval 返回 provider 显示的那句话，或者什么也不返回；带 code 或不带动作的调用，按在它所指主体内打开目标来审批。
规则parse_command 把一次调用归约为 provider 给的规则键（window Calculator、screen、browser chrome、lab screen，内置浏览器没有），于是 exact_rule_for_call 得到 computer_use(window Calculator)，rule_to_string 以常规形式打印。含 *、? 或 [，或以 :* 结尾的键得不到规则，所以这样的应用只能允许一次。
宽规则以 :* 结尾的 deny 或 ask 规则也把键当作普通词语读，不分大小写，所以 computer_use(window:*) 能覆盖 shell 解析不了的名字（“Grandma's Notes”），browser:* 覆盖用户的两个浏览器，lab:* 覆盖一台设备上的一切。

审批卡片提供四个范围：

范围规则保存在哪
once不保存
session会话的 run config（permission_rules.allow）——computer_use 在 _SESSION_SCOPE_TOOLS 里
always项目规则
deny不保存
项
授权类工具permission_decision 把 computer_use 当作按屏幕授权的工具：该工具登记了一份回答 approval 的档案（runtime/permissions/tool_profiles.py）。
判定：询问在会询问的模式下，当工具自身的 requires_approval 表明这次调用需要授权、且没有允许规则点名这块屏幕时，走模式判定，所以决定是 ask，理由 MODE_APPROVAL；因此无人值守的来源得到 NO_ONE_TO_APPROVE，允许规则和其他工具一样能结束询问。
判定：BypassBypass 直接放行。带 code 的调用，每一步都像一次单独的动作调用那样过同一个判定（code._as_action_calls），所以落在所有者拒绝或询问规则所写对象上的步骤会被拒绝。
判定：AutoAuto 在本对话此前的审查已放行同一块屏幕时返回 AUTO_APP_GRANT（app_grants.held），否则把调用交给自动审查，放行的结论由 auto_review 用 app_grants.grant 保留下来。
不询问provider 什么也不问的调用（list_apps、list_displays、guide、任何带设备的调用）在所有模式下、匹配完所有者的规则之后，以 APP_GRANT_FREE 放行，前提是那一刻它的目标能解析（policy._resolved）。解析不出的目标在此之前已由工具的预检（tool._unknown_target）以 UNKNOWN_TARGET: 退回，先于任何卡片、审查或 NO_ONE_TO_APPROVE；之后才变得解析不出的目标，或读不到目标列表，走模式判定。
内置浏览器内置浏览器没有自己的规则：有 Page 的对话得到本轮的 SURFACE_GRANT（tool.page_surface），只有 provider 要问的调用即上传文件除外，它每次都由模式决定（policy.surface_grant_applies）：会询问的模式询问，Auto 审查；没有 Page 时由模式决定。

权限规则在每个操作边界重新加载（全局 < 项目 < 会话），所以会话规则对下一次调用立即生效，无需重启。

项
系统权限系统访问：computer_use:desktop 同时是 accessibility 和 screen_recording 两项能力的操作；provider 的 system_access 把本机除列表和 guide 外的每次窗口和整屏调用映射到它（统一系统访问），于是缺少授权时调用进入标准的"等待"状态并走设置 → 系统访问流程；等待请求写明 computer_use。
探测这项检查要启动一个新进程（约 0.4 秒），所以只在一个回合的第一个应用步骤之前运行：wrap_live_permission 记住已查到授权的操作，required_access_state 对它们跳过探测，回合里之后的步骤前面就没有等待。
缺少授权授权缺失期间每次调用都重新探测。
中途撤销回合中途被撤销的授权会让该步骤在后端失败（_frameworks 会指明辅助功能这项设置）。

工具在 DEFAULT_TOOLS 里且常驻：schema 很短，不延迟加载。只要设置了任何目标，_configure_screen_tool 就会把它加进原本没有它的轮次；按名字给定工具的轮次，只有名单里写了它才会有。unsafe_in 在微信、Telegram 渠道和规划模式下隐藏它。

实现状态

状态范围
已实现每块屏幕一次授权（Auto 保留的审查结论、页面脚本随浏览器授权）、来自 provider 的规则键、已设置的机器不询问即可操作、写在工具描述里的确认规则、被打断的屏幕步骤只作记录、一个应用同一时间只归一个 agent 的调用，以及被替换的元素按原序号重新对上；每项都有单元测试和组件测试。元素修复在 macOS 上运行过；Linux 和 Windows 共用 tree.rebind，尚未在那里运行。
