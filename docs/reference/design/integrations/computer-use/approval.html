Screen approval

Approval and access

A screen is granted whole, once: an application, the whole screen or the user's own browser, with everything done in it (clicks, typing, page scripts, uploads to it). The target's provider says what a call asks (Provider.approval): the sentence shown and the rule key its answer is remembered under.

CallGrant
type="window" (except list_apps)per application: "computer_use controls <application>", rule computer_use(window <application>), where the application is its display name (AppProvider._rule_name, below)
type="screen" (except list_displays)"computer_use controls the whole screen of this computer", rule computer_use(screen): the grant on the surface that contains every application
type="browser", app="chrome", "safari", "firefox", …"computer_use controls your Google Chrome", rule computer_use(browser chrome) (or browser safari, browser firefox, one per browser name), never the Page grant; it covers page scripts and uploads there
type="browser"none where the conversation has Pages (the turn's Page grant): opening a site, acting on it and running a script in it ask nothing. upload_file sends a local file, so the Page grant never covers it: the modes that ask ask each time and Auto reviews it each time; it has no rule key
a call with a device (device="lab", type="screen")none: setting the device up is the consent. Its key <device> <type> (lab screen) is still matched by the owner's deny and ask rules

AppProvider._rule_name asks the backend's app_name, an exact match that launches and draws nothing, kept 5 s, so approval, the saved rule and later calls get one key.

On macOS any exact spelling (display name, file name, bundle id, .app path, the name it runs under, pid:N while it runs) gives the display name, running or not.

On Linux a desktop id, entry name, executable or pid gives the entry's name; on Windows a pid or exe gives the exe's file name without .exe. Any other name, part of a name or a Start menu name included, stays as written.

System access (Accessibility, Screen Recording) gates the window and screen calls of this computer other than list_apps and list_displays.

Permissions and approval

Item
Approval textrequires_approval returns the sentence the provider shows, or nothing; a call with code or no action is approved as opening the target within the subject it names.
Ruleparse_command reduces a call to the provider's rule key (window Calculator, screen, browser chrome, lab screen, none for the built-in browser), so exact_rule_for_call yields computer_use(window Calculator) and rule_to_string prints it in the usual form. A key that contains *, ? or [, or ends in :*, yields no rule, so such an application can be allowed once only.
Wide rulesA deny or ask rule ending in :* also reads the key as plain words, without regard to case, so computer_use(window:*) reaches names a shell cannot parse ("Grandma's Notes"), browser:* both of the user's browsers and lab:* everything on one device.

Grant toolpermission_decision treats computer_use as an app-grant tool (_APP_GRANT_TOOLS).
Decision: askIn the modes that ask, when the tool's own requires_approval says the call needs a grant and no allow rule names the screen, the mode decision applies, so the decision is ask with MODE_APPROVAL; unattended sources therefore get NO_ONE_TO_APPROVE, and an allow rule ends the question as for any tool.
Decision: BypassBypass allows the call. A call with code runs each step past the same decision as an action call of its own (code._as_action_calls), so a step on a subject the owner's deny or ask rules name is refused.
Decision: AutoAuto returns AUTO_APP_GRANT when an earlier review of the conversation allowed the same screen (app_grants.held), and otherwise sends the call to the Auto review, whose allowing verdict auto_review keeps with app_grants.grant.
Nothing askedA call whose provider asks nothing (list_apps, list_displays, guide, any call with a device) is allowed as APP_GRANT_FREE in every mode, after the owner's rules, when its target resolves at that moment (policy._resolved). A target that does not resolve already went back as UNKNOWN_TARGET: from the tool's precheck (tool._unknown_target), before any card, review or NO_ONE_TO_APPROVE; one that stops resolving after that, or a target list that fails to read, goes through the mode decision.
Built-in browserThe built-in browser has no rule of its own: a conversation with Pages gets the turn's SURFACE_GRANT (tool.page_surface), except a call its provider asks about, an upload, which the mode decides each time (policy.surface_grant_applies): the modes that ask ask, Auto reviews it; without Pages its calls are decided by the mode.

Permission rules are reloaded at every operation boundary (global < project < session), so a session rule applies to the next call without a restart.

The tool is in DEFAULT_TOOLS and resident: its schema is short, so it is not deferred.
