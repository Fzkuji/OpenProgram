Decisions

DecisionWhy
One tool for every screenOne small schema stays in context and never changes, so the prompt cache survives a device connecting. The actions arrive in the type's guide with the first result, so the model needs no extra call and no memory of them.
A target is a provider behind one contractA connection kind opens one provider per target it yields. The tool, the permission code and code mode ask the provider and name no target, so a new kind is one module and adds a line to <devices>, not to the tool.
Backends share result types and action namesdesktop/base.py. The guide and the tool read the same on each platform, and a platform that lacks something says so in its target note instead of differing silently.
The caller operatesAs in Codex, the agent that knows the task holds the screen. Nothing in the tool starts another agent, so no context is lost in a handover.
State per agent, tabs per conversationAgents running beside each other must not replace each other's element ids (state_scope). A browser tab keeps one id for every turn and agent, so it is shared on purpose.
Locks are filesA call and a step of code take the same keys from locks.py, and every worker process sees them, so two agents never act on one application or one whole screen at once.
Pages belong to the conversation; other windows to nobodyA page was opened for this work and stays until closed. Another application's window is the user's and every conversation may use it, so it is shown only while operated.
One preview frame for every kindA page, a window, a terminal and an application share the frame, gestures and header. A new kind adds only what is inside.
Open in tab shows the same objectNever a copy: the tab and the preview are two holders of one page or window, so nothing reloads and nothing diverges.
Frames live in memory onlyThey are what the Agent saw, not a record. Nothing of the user's screen is written to disk for display.
Display never blocks a stepThe marker stream opens on its own thread and a failed broadcast is dropped. A step neither waits on nor fails because of what is shown.
Code reaches the screen only through the brokerGenerated Python gets opaque resource names with the call's approval scope, and every primitive is recorded as an effect of the execution.

Why the definition is fixed
  • A request is sent as tools, then system prompt, then messages, so a tool definition that changes when a device connects or a grant changes re-reads the whole prompt. The description and schema of computer_use are therefore constants in tool.py, with no enum of targets.
  • What is set up goes in <devices> beside the user's message: the whole list when no earlier note is in view, then what was added, changed or removed (Machines and targets). It lists:
    • type="window" where the platform backend loads, and type="screen" on macOS once the owner turns on computer_use.whole_screen
    • type="browser" while the browser application is enabled
    • the user's own browsers (app="chrome", "safari", "firefox", …) where they are installed, a Chromium browser only with the Playwright Extension (extension.installed_browsers, which reads the data directory and never touches the browser; User browsers)
    • whether calls may send code, where the sandbox runs
  • A target whose operating-system grant is missing stays listed with a note saying where to grant it.
  • With no target at all, check_fn hides the tool.

action, actions and code are exclusive. Arguments are checked against the vocabulary, and an error names the right spelling, since the schema does not list every action's arguments.

Guide delivery and the user's browser
Item
GuidesEach type has a guide (guides/<type>.md: window, screen, browser): its actions, their arguments and how results look. Each target adds a note of a few lines (Provider.note): its machine, operating system, what it lacks, its shortcut keys.
Deliverytool.py registers them as included tool guides: computer_use.<type> arrives with the first result of a call that operates a target of that type, computer_use.note.<target> with the first call to that target, and computer_use.code with the first call that operates any target, on hosts where code runs, so the model has read how code works before it sends any.
No waitingNo call waits for a guide: a call that sends code before either guide was seen runs, and the guides come back with its result.
Known guidesWhether a guide is known is read from the request the agent loop last sent, so compaction, cleared tool results and a worker restart all lead to the guide being sent again; a guide inside a prompt that another agent wrote reaches the model inside the speaker's JSON envelope, so guides.known also matches the marker with its quotes escaped.
On requestaction: "guide" returns the target's type guide, note and code guide; help("computer_use.<type>") returns one.
Item
ActionsOpenProgram's browser and the user's own browsers take the browser type's actions with the same arguments (Machines and targets); only the built-in browser has panes and video.
Browser firstAs in Codex, the browser is chosen first, by app, and the actions do not change with it.
ListingThe user's Chromium browsers are listed whether or not the extension is connected now; a call to one that does not connect answers with its code. Without the extension, a page in that browser is part of its window, reached with type="window".
Serverproviders/user_browser.py hands each step to extension.py of the browser application, which runs a pinned @playwright/mcp --extension with --browser set to the channel, or --executable-path for a browser without one through its own MCP client, one server per conversation and browser, kept between calls and while any agent that used it, if only to list tabs, is still running; the connection and its tab table end with the last of them.
ClosingAn agent's end never waits: the connection closes in the background, after any step still running in it, and only if no agent started using it meanwhile.
ConnectionThe server opens chrome-extension://<id>/connect.html in that browser with the address of its relay, and the Playwright Extension connects back and relays CDP for the tab the user shares; with computer_use.chrome_extension_token set, the server passes PLAYWRIGHT_MCP_EXTENSION_TOKEN and the extension connects without asking.
Action mappingextension.py translates each action into Playwright MCP's tools from the same arguments the tab driver reads; an element is a ref of the server's snapshot, or role and name, which reach it as getByRole(role, { name, exact: true }).
The windowThe provider claims a browser window whose page is a tab this conversation's connection has attached and that was in its latest listing, never one that has since gone: type="window" leaves the page out of its tree and names the call type="browser", app="chrome" (or "edge"), while the tab strip, toolbar and menus stay there. A window that does not report its address (Linux, Windows), and any other page, stays whole with type="window".

Code
Item
Interpretercode runs in the persistent sandboxed interpreter of computer_use/sandbox/runner.py (seatbelt on macOS, no file, network or process access).
Namespacecu is the call's target: await cu.click(element=3) is the step click with that argument on that target, dispatched by the host through the same checks and locks (dispatch.run_steps), one effect receipt per step (computer_use/sandbox/broker.py).
DocstringsThe prelude gives each cu method its action's line from the type guide as its docstring, else its signature, so dir(cu) and help(cu.click) work inside the interpreter.
Parameter textThe code parameter's own description shows await cu.get_state() and await cu.click(element=3), so a model that no longer has the code guide in view still writes cu.click(...) and not a bare click(...).
Item
SubjectA code call acts within what its call names in args (the application, the tab, the display): a step may leave it out and may not name another.
GrantThe call's grant covers that subject, so code._validator refuses a step that would ask anything else and lets everything else the target offers through, page scripts and opening sites included. In Bypass, where the call has no grant to stay inside, each step gets the decision an action call of its own would get (code._as_action_calls) and runs only when that is allow, so the owner's deny and ask rules still hold.
UploadRefused in code: an upload from the built-in browser sends a local file and asks each time, so it is made as an action of its own.
Page scriptA page script does not run where nobody attends the turn, or where the turn works from text the owner did not write (a handoff, an automatic Goal turn), from code as from an action: code.run reads that from the turn's request when the call starts.
Item
LifetimeOne interpreter serves one execution attempt, so variables persist for the rest of the turn, whatever the targets of its calls; it is replaced when it fails or times out.
Held byInterpreters are held per conversation and execution, and element ids and window states per conversation and job (tool.operator, from the job the call runs in).
Shared keyThe conversation's own turns share one key, so a turn acts on the window the turn before it read. An agent the conversation starts runs as its own job, whose reads and code never replace what the main turn or another agent is acting on.
Item
LimitsEach call may run 120 seconds and 100 steps.
Printed textPrinted text is kept up to 256 KB and the rest is dropped with a note in the result; what a step returns goes to the code and is not counted against that.
Not dispatchedA step that stops before input reaches the target (a coded refusal, an element that is gone, an app not found, a stop while it waits for a lock: the deadline, a stop or a revoked grant, which answers TIMEOUT: stopped while waiting for <target>: …; nothing was sent) returns action_dispatched: false, so the broker records it as not committed.
Failed after inputA step that fails after input may have been sent raises in the code with the target's message, and the steps before it stay made.
Timed outA call that outruns its time, or whose interpreter stops, comes back as an error result: the steps already made stay made, the step that was running may or may not have applied, and the next code call starts a new interpreter without this one's variables.
Open receiptsWhen a call returns, the broker closes the receipts of the steps whose outcome it never learned (GuiBroker.settle, receipt state unknown): the result is what tells the model, and no open receipt outlives the call.
PlatformCode mode needs the macOS sandbox; elsewhere a code call reports that the sandbox is unavailable.
Who operates
Item
CallerThe agent that calls the tool operates the screen and carries the task through. The tool takes no argument that passes the task to another agent, so a failed step is retried where it failed.
Long taskscode runs many steps in one call and returns only what it prints, which keeps intermediate screens out of the conversation.
Several screensWork on separate screens at once goes through the agent tool, which the base instructions allow only when the user or project instructions ask for sub-agents. Each agent keeps its own window states, element ids and code interpreter, and the locks keep two of them off one application at a time.
Time limitThe tool has no overall time limit. An action call stops at its deadline, 300 s (registry.FINISH_SECONDS, the time a release waits for running calls), with TIMEOUT:; code stops at its own timeout.
