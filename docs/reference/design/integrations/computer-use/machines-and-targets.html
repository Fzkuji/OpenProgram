Machines and targets

Three rules

RuleMeans
The call says wheredevice names the machine and type what on it: window, screen or browser. Without device it is this computer, where the worker and the App run, in every conversation. No environment or earlier call changes where a call lands.
The tool never changesThe tool's description and parameters are the same for the whole conversation. What can be operated now goes in a <devices> note beside the user's message (What the model reads).
One spelling per meaningThe same act has one action name and one set of argument names on every target. Names a model carries over from another tool are rewritten, not refused.

Concepts

ConceptIs
MachineA computer with its own operating system: this computer, an SSH host, a Docker machine, a virtual machine, another computer with its own OpenProgram. One registry. A machine is an id, a name, an enabled switch and one connection.
This computerBuilt in, with the method local, never stored; a call names it by leaving device out.
DeviceHow a call names a machine: its id (its name is accepted too). The operating system is a property of the device, shown in <devices>, never a call argument.
ConnectionHow a machine is reached: one method (its kind) and that method's settings (Connection methods). It says nothing about what is done there.
ProjectA folder on one machine: (machine, folder). Its conversations run on that machine, in that folder.
EnvironmentA role: the machine a conversation's commands and file tools run on, its project's machine. Its method must be one commands run through: local, ssh or docker.
TypeWhat kind of thing is operated; it fixes the vocabulary. window: application windows by element tree. screen: a whole display. browser: web pages; without app a browser OpenProgram runs, with app="chrome", "safari", "firefox" or another of the user's own (User browsers). Types belong to computer_use, not to machines.
TargetWhat a call's device, type and, for a browser, app name. Its key joins the three, leaving out this computer and OpenProgram's own browser: window, browser chrome, lab screen. Locks, permission rules and Resources use the key; the model never writes it.
SubjectWhat inside the target: app and title (a window title, or a window_id when it is digits) for a window, title (a tab id or title) for a browser, display for a screen.
ProviderThe module that yields one kind of target over a method.

RuleDetail
The device layer knows no featureA method registers a name, a label, a settings schema, a reachability check, what tells two connections apart and the address it reaches. Nothing in host/machines says what is done over it.
Each feature maps methodsThe shell feature: host.backend.SHELLS, from local, ssh and docker to how commands run. computer_use: registry.offer(method, opener), one opener per provider module; a method nobody offers yields no target. A new feature adds its own mapping and touches no device.
This computerHas no settings to edit. Whether it gives a screen is the setting computer_use.whole_screen, not part of its connection.
SecretsA setting marked secret (the pairing credential token) is stored in state/auth/machines/<id>.json under the setting's name.

A virtual machine is a machine: vm is not a type and computer_use.vm_url is gone.

Machines and environments

QuestionDecision
RegistriesOne, machines. It replaces the environments registry. Identity, configuration and the connection are shared by every feature.
BindingsTwo, kept apart. The environment comes from the project (machine_id on the project record, resolve_for_project), never from the conversation: a conversation's project is frozen once it has a session, so its machine never changes and it promises where commands take effect. Targets are listed per turn and chosen per call.
In an SSH or Docker conversationA call without device still acts on this computer. The tool description, <devices> and the <environment> block say so, and the built-in browser's line says its localhost is this computer's.
A machine that runs commands and is operatedOnly this computer. An SSH host or Docker machine is an environment and gives computer_use nothing; another computer's OpenProgram is operated with device="<m>" and runs no commands here. Being the environment never makes a machine the default.
InstancesA shell declares instance_scope. machine: one instance. conversation (Docker): one per conversation, created on first use and removed with the conversation. State, locks and screen-server processes are keyed by the instance.
IdentityA machine id never changes; only its name is edited. A machine added without an id gets one made from its name (Dev Box becomes dev-box, then dev-box-2). Deleting or disabling a machine lets running calls finish, then closes its providers and removes its instances by label.
Choosing the machineWhen a project is opened: Open folder on… picks the machine, then the folder on it. This computer and a Docker machine (which mounts this computer's folders) use the folder picker; an SSH host is browsed through its shell (list_machine_folder), starting at its remote folder setting, and the folder is made absolute there (resolve_folder).
One folder, one projectOne folder on one machine is one project; a folder on this computer belongs to one project whatever machine runs it. The home project is always this computer. There is no default environment and no per-conversation choice.
A project's machine is goneSwitched off, reached by a method commands do not run through, or removed: its conversations' commands and file calls are refused, never replaced by this computer. The picker greys its projects.
Connection statehost/machines/status.py: connected, connecting (no answer yet), disconnected (switched off) or error. A listing checks a machine behind its answer when the last word is over 60 s old; every shell file call on it reports what it saw. Each machine in the machines frame carries its status, and a change broadcasts the frame. The App shows it as a dot on the machine's icon: green, a turning ring, grey, red.
Where the App shows the machineThe project picker groups projects under machine headers, this computer first. The sidebar's project header shows a project on another machine with that machine's icon (Solar server-2 for a machine on another computer, drawn at the folder icon's size), dot and name; chat rows never show a machine. The composer's machine chip shows the project's machine and cannot switch it; its menu says it is set by the project.
A project's folder on an SSH hostRead and changed on the host: the Files panel, its search, @ file search and the file tools go through its shell; a deleted entry moves into ~/.openprogram/trash on the host. Snapshots, automatic commits, worktrees and the branch pill need the folder on this computer, so they are not offered for it.
Never this computerRefused: an SSH target that resolves to this computer on port 22 (a loopback address on another port is a forwarded virtual machine or container, and is accepted), a screen server or cua-driver that reports this computer's identity, and a loopback address whose screenshot, taken when the machine is added, is this computer's own display. This computer is reached by leaving device out.
One address, one machineTwo machines may not share one address their method reaches, such as one OSWorld server's URL.
WordsSettings → Devices uses the word the model writes in device. openprogram machines (list, add, remove, enable, disable, test) and the configuration key machines keep their names. add ID [--name NAME] METHOD [KEY=VALUE ...]; list --kinds prints the methods and their settings. Settings → Devices shows one Connection per device: a method picker, then its fields. The project picker says Open folder on….
Codehost/environments becomes host/machines. Connection methods register there (kinds.py); the parser, validator, Settings and CLI name no method.

Rules for the list

RuleDetail
Listed means set upThe list changes when the set-up changes: settings, an installed extension. Capabilities are declared per provider and never probed. A machine that is off stays listed and the call answers MACHINE_UNREACHABLE:; one the checks cannot reach says so in its block (What the model reads). No network probe delays a turn.
A paired computerIts window, screen and browser are listed while it is switched on, without asking it. Asking would cost a round trip to every paired computer on every turn, often to a laptop that is asleep; and the other computer already refuses precisely, with the targets it does have: a type it lacks, a browser it cannot reach, a screen it keeps off.
NamesA configured machine is named by its id; its name is accepted too, without regard to case. local, localhost and this computer as a device mean this computer.
Window titlestitle picks a window by part of its title, or by its window_id when it is digits. A title that matches several windows is refused with the candidates and their ids, so a call never lands on a window it did not mean. A tab title that matches several tabs is refused the same way.
One routeA surface with its own target is not also operated through the local window that shows it. A provider may claim such windows for the conversation that asks: a Chrome or Edge page whose tab this conversation's connection has attached (a window that does not report its address, as on Linux and Windows, stays with type="window").
Claimed windowstype="window" keeps the window's own controls, leaves the claimed content out and names the call that reaches it. A machine may name its viewer, the local application and window that show the machine. Unclaimed content stays with type="window".
window or screenwindow is for one application's window. screen is for the desktop, menu bar, system dialogs, drags across windows and windows that ignore background input. Both exist on purpose: refusing screen inside a window would leave such windows unreachable.
screen off by defaultOff until the owner turns on computer_use.whole_screen: until then local opens no screen, so type="screen" is neither listed nor callable, and a call gets UNKNOWN_TARGET: before any approval.
Why offAn ordinary task needs one application, and the owner decided the agent is not given the whole screen by default. Codex Computer Use has no whole-screen surface (every call names an app; keys go to that app), so off keeps the same reach and the route stays for tasks that need it.
Replacing the local driverAnother driver of this computer's own, such as cua_driver for window and screen, would be another opener offered for local. The calls, keys and locks stay the same; this computer never gets a second name.
Switching offA machine has an enabled switch. Nothing trims the list automatically.

What the model reads

The tool, fixed for the whole conversation:

computer_use(device?, type, app?, display?, title?, action?, args?, actions?, code?, timeout?)

Operate application windows, a whole screen or web pages, on this computer or on another device.

Where a call lands
- device: left out for this computer. Another device by its name in <devices>. …
- type="window": an application's windows, read as an element tree. app names the application (without app the call lists the running ones); title picks one of its windows.
- type="screen": a whole display, by pixels; it moves the user's pointer. display picks one, the main one without it.
- type="browser": web pages. Without app, OpenProgram's built-in browser; app="chrome" or app="edge" is the user's own browser with their sign-ins, … title picks a tab.
<devices> lists what can be operated now; anything else is refused.

The first <devices> note of a conversation:

<devices>
What computer_use can operate now, by device:
- this computer (device left out): the user's Mac, where OpenProgram runs; calls may send code.
  - type="window": application windows, read and operated in the background; app names the application.
  - type="browser": OpenProgram's built-in browser, this conversation's pages. Its http://localhost is this computer's.
  - type="browser", app="chrome": the user's own Google Chrome with their sign-ins; only when the user names it or the task needs their sign-in.
- devbox (device="devbox"): SSH host me@devbox; this conversation's shell and files are here.
- studio (device="studio"): another computer running its own OpenProgram.
  - device="studio", type="window": application windows of that computer (it lists its own with list_apps)
  - device="studio", type="screen": its whole screen, when that computer has Whole screen on
  - device="studio", type="browser": OpenProgram's browser there, or with app one of the user's browsers there
- lab (device="lab"): virtual machine, pixels only.
  - device="lab", type="screen": virtual machine, pixels only
A target not listed here is refused. A later message says what changes.
</devices>

A later turn, after the user installed the extension in Edge:

<devices>
Changed devices, as they are now:
- this computer (device left out): …
  - type="browser", app="edge": the user's own Microsoft Edge with their sign-ins; …
</devices>

  Cannot be reached right now (last check: ConnectError); calls to it will most likely fail. A later message says when it is back.
  - device="studio", type="window": …
</devices>

<devices>
Changed devices, as they are now:

PartRule
Parametersdevice, type, then what inside: app (the application of a window; chrome or edge for a browser), display (a screen), title (a window or a tab); then what to do: action and args, actions or code, and timeout. Only type is required. A step inside actions may still name its own tab.
Why device may be left outLeaving it out always means this computer, never the conversation's environment, so the default cannot move with the project: the loop, the App and the user are here, and that is what a user means by "my screen".
Why type and appThe same three types exist on every device, so a type and a device are two independent words and a new device adds no new names. The user's browser is app, as in "which application", because that is how the user names it ("in my Chrome"). The operating system is not a parameter: it belongs to the device, and the model reads it in <devices>.
The definition is fixedThe description and the JSON schema never mention what is set up; there is no enum of targets. A request is sent as tools, then system prompt, then messages, so a definition rewritten when a device connected or a permission changed broke the whole prompt cache.
<devices>A section of its own beside the user's message, never in the system prompt (devices in BESIDE_ONLY_SECTIONS, just before deferred_catalog). Grouped by device: this computer, then the others; a device with nothing to operate is listed only when the conversation's shell runs there. Each target line is how the call names it, then what it is, then what permission is missing ("Not usable yet: …").
Whole list, then changesThe whole list when no earlier note is in view: the conversation's first turn and the first turn after a summary. Afterwards only Added devices, Changed devices, as they are now and Removed devices, and nothing when nothing changed. The list each turn saw is kept on its user message, so the next turn compares against what is in view, the same mechanism as the deferred-tool catalog (catalog_shown, catalog_stored with the list's id).
ReachabilityAnother computer whose connection checks have failed for 45 s with no success between (status.OFFLINE_AFTER; two failed checks at least, that far apart) carries a line in its block: unreachable now, the last check's reason (at most 80 characters), calls will likely fail, a later message says when it is back. Its targets stay listed. The first successful check takes the line away, and the next note's Changed devices entry says "Reachable again" under its first line.
No probe for itThe line comes from what the checks Settings, the sidebar and calls already make (host/machines/status.py, unreachable); building the note never waits on the network. A failing device whose last check is older than STALE_AFTER is checked again behind the answer, one check at a time, so its return is noticed without anyone opening Settings; a device that answers costs nothing.
Why debounceOne failed check on a busy network or a laptop waking up would otherwise mark the device offline and back within a turn or two, each a Changed entry the model reads and acts on. The debounce lives in status.py, the one place that records checks; the icon beside a device still shows the latest check at once.
Turns with their own promptA check-in, a verification or an agent started for a task has no earlier note to compare with, so the whole list goes inside its system prompt's capabilities section (components._build_tool_sections, from the section computer_use registers).
A device connected mid-turnShows up beside the next user message. A call that names it before then is refused with the targets listed now, as any unknown target is.
GuidesA type guide (window, screen, browser) arrives with the first call that operates a target of that type. A target note of a few lines arrives the first time that target is: its machine, operating system, what it lacks, its shortcut keys.
Result headerA result from another device starts with how the call names it, [device="lab", type="screen"]. In a conversation whose environment is another machine, results from this computer get one too: [type="window", this computer].
Missing permissionThe target stays listed with a note; the call answers PERMISSION_MISSING: with where to grant it.
Codecu is the call's target and nothing else, within the subject the call names; it is approved exactly as an action call, and in Bypass each step still meets the owner's deny and ask rules as an action call would. A turn nobody attends, or one that works from text the owner did not write (a handoff, an automatic Goal turn), runs no page script from code.
Code on two targetsWork on two targets takes two calls, and the interpreter's variables carry over between them. Each step takes its own locks.
cuIts methods are the target's actions (await cu.click(element=3)); an attribute named after another target raises with the call to make, naming only targets listed now; one named after its own type raises too, since cu already is the target. A step that names another application, window, tab or display answers BAD_ARGUMENT:.
HiddenThe tool is not offered when no target exists.

Errors

CodeSays
UNKNOWN_TARGET:the targets listed now, as calls name them; checked before the permission decision, so in every mode it comes before any approval card, review or refusal for want of someone to approve
UNKNOWN_ACTION:the nearest action of this type, or the targets on the same device that have it
NOT_SUPPORTED:what this target lacks and the step that works instead
BAD_ARGUMENT:the action's signature, then the type's shared arguments; a title that matches several windows or tabs, with the candidates
PERMISSION_MISSING:which permission, and where to grant it
DEPENDENCY_MISSING:what the machine lacks and the line that installs it
MACHINE_UNREACHABLE:the reason; only when nothing was sent, as when the machine was switched off or removed after the call found it
OUTCOME_UNKNOWN:which steps are done and which was sent without an answer; read the state, do not repeat it
SCREEN_BUSY:another agent has held it for 60 s, counted over the whole call; nothing was sent
ELEMENT_GONE:the element is no longer there, or was printed by another target; the current state follows
TIMEOUT:the steps that took effect, or that nothing was sent; an action call stops after 300 s (registry.FINISH_SECONDS); a code step stopped while it waits for a lock (the deadline, a stop, a revoked grant) answers TIMEOUT: stopped while waiting for <target>: …; nothing was sent and is recorded as not applied

type and a browser's app are matched without regard to case (Google Chrome is chrome), and a call is never moved to another device or type. A batch result states how many steps are done.

An action of another type answers UNKNOWN_ACTION: with the targets that have it; one of the target's type that it lacks answers NOT_SUPPORTED: with the other targets of the same device that have it.

open and close never point to another target: each type reads them as an operation of its own, and where the target lacks them, UNKNOWN_ACTION: gives the nearest action and the target's own.

On a screen over OSWorld a batch is checked whole before its first step is sent: one bad argument answers BAD_ARGUMENT: step N (action): … and nothing is sent; a get_state step in it counts as done, since the screen is read after the steps.

Rules for actions

RuleDetail
GatingA core action needs the input capability the provider declares (pointer, hover, keyboard); find and set_value need tree. A missing one answers NOT_SUPPORTED: with the step that works.
Elementelement takes what the state printed: a number in a tree, a ref such as e12 or f1e3 on a page. An id is valid only on the target that printed it. Pages also accept role and name.
Typingtype_text inserts on every surface. clear empties the field first (set_value with "" where the field takes it, else select all and BackSpace) and submit presses Return after; when that key fails, the text counts as done and the result gives the error and the state. set_value replaces a field's value.
Waitingwait with text reads the state until the text shows, up to seconds or 10 s; text that never shows is not an error. On a window it also reads the text of the window's screenshot, for a window with little tree.
Keysxdotool spelling: Return, Escape, ctrl+shift+Tab. super is Command on macOS and the Windows key elsewhere. Other spellings are normalized, and a name that is no key answers BAD_ARGUMENT:; browser providers translate to their own names. Shortcuts are in the target note, never in a type guide.
Tabstab is a stable id on every browser target. list_tabs prints it and every result names the tab it acted on. A step with tab selects that tab first; a step without it acts on the tab this agent last used on that target, and once that tab is gone answers BAD_ARGUMENT: naming it, sending nothing. A number or an unknown id answers BAD_ARGUMENT: with the open tabs.
User browser tabsIn the user's Chrome and Edge the id is made here (t and a hash), follows its page when the extension connects again, and an agent that has chosen no tab, or closed its last one with close_tab, acts on the one the extension has selected. close_tab closes only a tab the step names. read_console_messages with pattern or limit and read_network_requests with only_errors or limit answer NOT_SUPPORTED:.
User browser tab goneWhen another agent closes this agent's tab, its next step without tab answers BAD_ARGUMENT: naming it. list_tabs marks as current the tab a step would act on; once the agent's tab is gone it says so, asks for tab on every step and marks none. An extension left with no attached tab while a tab is chosen or listed answers MACHINE_UNREACHABLE: with nothing sent, and OUTCOME_UNKNOWN: right after create_tab.
Mobile (not built)click is a tap. scroll keeps its meaning: show what lies further that way. swipe takes two points. press_button takes a name the provider declares; home, back and volume keys given to press_key go there.
Applicationsapp names an application on a window. Without it the call lists the running applications; get_state with it opens the application if it is closed. open, open_app and launch_app are carried-over names for that.
TypesA new kind joins a type and touches only its module. A new type, for a device with neither pointer nor touch, adds one table to actions/vocabulary.py, one guide and one value of type. An Android television would be mobile with pointer input narrowed off.
Displaysdisplay is the operating system's display id, as list_displays prints it; without it, the main display. A screenshot is at most 1568 pixels on its long side, and x,y are pixels of the last one of that display.
PathsA path in upload_file or open_file is on the target's machine.
Carried-over namesRewritten inside the target's type. A rewrite sets the argument it implies (double_click sets click_count=2) and never drops items: a list of keys becomes one chord. actions/vocabulary.py holds the whole table.
Carried-over argumentsRewritten too: click's text or key becomes modifiers when it is empty or names modifiers only, and any other text answers BAD_ARGUMENT: with click's signature; scroll_amount becomes pixels at 100 per wheel click; zoom's region=[x0,y0,x1,y1] of four finite numbers or numeric strings becomes x, y, width, height, and any other corner, a boolean, NaN or infinity included, answers BAD_ARGUMENT: region is [x0, y0, x1, y1] in screenshot pixels.

Pointer or foregroundDecided per platform before any step runs, by action: the driver picks foreground delivery while the step runs, so every action that has such a path holds the machine, an element step included. macOS: no step. X11: click, scroll, press_key, type_text, hover, drag. Windows: click, drag, press_key, type_text, paste, and focus, since UI Automation's SetFocus can bring the window to the front; scroll and hover are posted messages. Lists take no lock.
OrderFirst come, first served across processes: a waiting request, shared or exclusive, goes before every later one, also one queued behind another request of its own process. From its arrival each waiting request holds a ticket file q-* in the key's folder, and goes to the gate only when no earlier ticket of another process is still held. A call's waits share one 60 s deadline; after it the call answers SCREEN_BUSY:.
ReachLocks are files under the state directory, so they hold across the worker's processes. A call holds the locks of its target's machine, and of a local window it drives: a simulator operated through the Simulator window also takes that window's locks.
Window and screenThe locks follow the step: the only thing a window and a screen call on one machine contend for is the physical pointer.
Unknown systemUntil a machine's screen server has described its operating system, pointer and key steps on its windows take the machine exclusively.
CancellingA cancelled remote call keeps its lock until the machine answers or 10 s pass.

Another computer's OpenProgram

PartDecision
SendingThe call is not checked or run here. Its type, app, display, title, action, args, actions, code and timeout, never device, go with the pairing's Bearer token to POST /api/computer-use/call, each pairing address in turn, 6 s to connect to each. The answer is {text, images, is_error}, images in base64; this side puts [device="studio", type="window"] in front.
ReceivingRuns computer_use on that computer only: the device is forced to that computer and never hops on. Its own settings apply: the whole screen stays off unless turned on there, its operating-system permissions are its own, and its tools.permission_rules for computer_use are read there: a deny rule refuses, and an ask rule refuses too, since nobody there is asked.
The switchLet paired devices operate this computer (computer_use.paired_devices, off by default), in Settings → Devices → This computer on the receiving computer. While off, the endpoint answers 403 paired_devices_off and the sender gets PERMISSION_MISSING: naming where to turn it on.
Other answersA device whose checks have failed for 45 s (the same state that puts the line in <devices>) is answered at once, nothing sent, and checked again behind the answer unless a check is running or is under 10 s old (RECHECK_AFTER). A device that has only just failed is still tried, so a lost packet turns no call away. 401: this computer was revoked there; pair again. 404: the OpenProgram there is older; update it.
AskingThis side asks its user once per target, with a rule key naming the device (State, locks and approval).

The screen server

PartDecision
ProtocolMCP tools screen_describe, screen_list, screen_get_state, screen_act; notifications screen/report (the fields of native.action, native.window, native.control) and screen/frame. A server someone else wrote that speaks them plugs in with configuration only.
PolicySent with every list, state and act call; the server stores none. Element ids are kept per agent.
CodeAll of computer_use/desktop/ moves to host/desktop/. The drivers take a policy object (refused applications, password fields, permission mode, cancellation, recordings directory) and a reporter (action, control, window) in place of their runtime and Resources imports. The Linux and Windows drivers, which report nothing today, call it at the same points as macOS.
ShippingA zipapp of that code without the embedding part. Over a shell it is piped to the machine's cache directory on first use and started there; a new digest is sent again. For a server reached by address, machines add writes the zipapp, a token and the start command for the user to copy; an old one answers DEPENDENCY_MISSING:.
Finding the sessionOn Linux it uses the configured display, else the environment of the user's graphical session. No X session answers DEPENDENCY_MISSING:; a Wayland session answers NOT_SUPPORTED:; without an accessibility service its window type answers DEPENDENCY_MISSING: and its screen works by pixels.
ProcessOne per machine instance in each worker process, closed after five idle minutes, shared by the machine's window and screen; the file locks keep the processes apart. It installs nothing.
