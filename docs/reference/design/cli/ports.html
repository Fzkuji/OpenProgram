The worker is the only thing that chooses: claim_worker_port() in operations/worker/lifecycle.py settles the port right after the worker takes its lock, and resolve_worker_port() reads it. The App reads the same files (apps/desktop/main/worker/web-port.js), so the two always agree.

One port per account

Loopback ports belong to the whole computer. With one fixed port, a second account signed in on the same PC, or anyone with another program already on 18100, had no worker and an App that waited forever. Each account therefore owns its port:

  1. The first start of an account's worker takes the lowest port from 18100 up that it can bind, and writes it to web-port. The first writer wins, so a first App start and a first CLI start agree.
  2. Later starts use the recorded port, so the address stays the same.
  3. When something else holds the recorded port at start, the worker moves to the next free one and rewrites the record. The App sees the record change and opens again on the new port.
  4. A port the user set (ui.web_port, OPENPROGRAM_WEB_PORT) never moves. Its holder is named and the worker exits.

Jupyter works the same way: it takes the next free port and writes the address it serves to a runtime file the clients read.

Why 18100
  • Below 49152, so never in the OS ephemeral range handed to outbound sockets.
  • The 18xxx block is rarely used by dev tooling, unlike 3000, 5173, 8000, 8080. The development instance's 18200 is outside the 18100–18199 range accounts choose from.
  • Kept once chosen: a bookmarkable URL, and browser state (localStorage, service worker scope) that survives restarts.
