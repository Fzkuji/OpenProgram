只有 worker 选端口：operations/worker/lifecycle.py 的 claim_worker_port() 在 worker 拿到锁之后马上定下端口，resolve_worker_port() 读取它。App 读同样的文件（apps/desktop/main/worker/web-port.js），所以两边总是一致。

每个账户一个端口

回环端口属于整台电脑。端口固定时，同一台电脑上同时登录的第二个账户，或者 18100 已被别的程序占用的用户，都没有 worker，App 一直等。所以每个账户有自己的端口：

  1. 账户的 worker 第一次启动时，从 18100 往上取第一个能绑定的端口，写进 web-port。先写的为准，所以 App 和 CLI 同时首次启动也会选同一个。
  2. 之后的启动用记下的端口，地址不变。
  3. 启动时记下的端口被别的东西占着，worker 换到下一个空闲端口并改写记录。App 看到记录变了，就在新端口上重新打开。
  4. 用户自己设的端口（ui.web_port、OPENPROGRAM_WEB_PORT）不会换。说出占用者，worker 退出。

Jupyter 也是这样：取下一个空闲端口，把它提供服务的地址写进客户端读取的运行时文件。

被别的程序或账户占用，端口是用户设的说出占用者并退出；不算这个版本启动失败显示端口 N 已被占用，写明占用者和怎样换端口，端口空出来后自动打开聊天页拒绝，说出占用者
刚退出（TIME_WAIT）算空闲：POSIX 用 SO_REUSEADDR 探测；Windows 本来就能重新绑定这样的端口

绝不杀占用者；监听者不证明自己是本账户的 worker，就拿不到本账户的 token。

operations/worker/ports.py 的检查方式
存活：port_in_use(port)裸 TCP 连接
能否监听：port_bindable(port)试绑定一次。Windows 上用 SO_EXCLUSIVEADDRUSE：那里的 SO_REUSEADDR 会绑到正在监听的端口上，把被占的端口说成空闲
身份：backend_is_ours(port)需要本 profile 存活的 worker（持有锁）和它的 worker.port，再读 profile 下仅属主可读的 web/access.json；向 /api/auth/challenge 发随机 nonce，本地验证 token-HMAC 证明。绝不发送属主 token 或 Bearer 头，外部监听者拿不到凭据。可选的 expected_revision 把证明绑定到升级目标的版本。
归属：describe_port_owner(port)、port_owner_hint(port)lsof 或 netstat + /proc、ps、Windows CIM：PID 和命令行

本账户没有 worker、而所问的端口上有别的东西在监听时，openprogram web auth-url 以退出码 3 结束并说出占用者；App 据此显示占用者，而不是一直等。

为什么是 18100
  • 低于 49152，不在系统分配给出站 socket 的临时端口范围。
  • 18xxx 段少有开发工具使用，不像 3000、5173、8000、8080。开发版实例的 18200 不在账户选择的 18100–18199 范围内。
  • 选定后保留：地址可收藏，浏览器状态（localStorage、service worker 作用域）跨重启保留。
