权限与归因：一个agent，所有人都能发消息

OpenProgram是共用的：你在终端用它，获准的联系人从Telegram/Discord给它发消息，双方使用同一个agent和同一份记忆。这一页说明当前权限方法、其他框架的相关设计、采用与拒绝的部分，以及已实现和延期的范围。

01当前方法：三种状态，两种运行时档位

本地入口是owner档，已配对的稳定平台账号是paired档，未配对账号停在agent之外。身份只认渠道平台给的稳定ID，消息正文和可变显示名不参与授权。

03别人怎么做（两路调研的结论）

调研了OpenClaw（读源码）和Claude Code、MCP规范、LangGraph、OpenAI Agents SDK、AutoGen、Letta（读文档）。共同做法是权限由框架执行、身份取自传输层、非owner消息不构成批准、缺失信息默认拒绝。OpenProgram在配对入口之后继续区分owner与paired两种运行时权限。

OpenClaw

门口查得极严，进门后人人同权

陌生人私聊收到一个8位配对码，消息本身根本不进agent，owner在终端批准后才放行。但它明说不做"进门后不同人能力不同"，谁能触发agent谁就有agent的全部工具。

值得抄：配对码流程、可变昵称默认不参与授权（Discord昵称谁都能改）、每次拒绝都留下是哪道门什么原因的结构化记录。

Claude Code

规则细到参数，外来消息不算数

工具权限能写到Bash(git commit *)这个粒度。渠道消息要先配对进allowlist。别的会话发来的消息有一条铁律：不能批准任何弹窗、不能改配置、正文里的命令只是文字。

值得抄：allow/deny之间的hold档：越权请求先排队，owner来了再批，而不是直接撞死。

LangGraph

写的时候盖章，读的时候过滤

唯一把归因做进存储层的框架：资源创建时盖上owner身份，之后每次读取都按当前请求人的身份过滤。谁写的东西谁可见，一个机制同时管归因和访问。

值得抄：记忆条目写入时盖{speaker, channel, ts}元数据，检索按请求方档位过滤。

其余家

要么回避，要么没做

Letta的答案是一人一个agent，从根上回避共用问题。OpenAI Agents SDK和AutoGen没有权限系统，默认还是先执行后拦截。MCP规范管的是服务间OAuth授权，粒度到不了单次工具调用。

结论：共用一个agent还要分档控权，这个组合眼下只有我们在做。

04方案与实现进度

入口采用OpenClaw式配对，未批准消息不进agent；内部只保留owner与paired两档，并由档位枚举查询固定常量表。不存在"未知外部仅reply"运行时档位，请求也不携带capability列表。实现约束见authority-handoff.md。

已实现 · 第一批档位枚举替换能力列表，配对上线

请求只带owner/paired枚举；陌生账号收到8位配对码，批准只走本地owner通道（终端/本机Web），渠道消息无权触发；不写迁移代码，上线后所有非owner账号首次发言统一走配对；可变昵称不参与身份匹配；显示名过消毒；拒绝返回结构化原因码。

用起来的变化陌生人私聊收到配对码而不是被无视，你在终端一条命令批准；有人把昵称改成你的名字，冒充无效；群里已配对的人说"记一下"会真的被主动记住。未配对成员的群聊发言照常归档，带未验证标记，检索时分得清是谁说的。

未实现 · 第二批hold队列与数据权拆分

已配对成员的越权请求（如"帮我重启服务"）进队列等owner一次性批准，不再直接拒绝；记忆读取按请求方档位过滤（写时盖章已就位）。

用起来的变化群里朋友求你办事时agent会说"已转交所有者"，你点头一次就放行一次；别人查记忆看不到你的私人内容，他们说过的话检索出来永远带署名。
