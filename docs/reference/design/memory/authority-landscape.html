权限与归因：本地owner、已配对账号和未配对消息

OpenProgram允许本地界面与Telegram、Discord等渠道共用一个agent和一份记忆。这一页依次记录当前方法、参考框架、采用与拒绝的设计，以及实现进度。

01当前方法：两个权限档位，一个入口拒绝状态

运行时权限只有owner和paired。未配对不是第三个权限档位：消息不会进入agent。身份只使用渠道平台提供的稳定ID，正文不参与身份判断。

03别人怎么做（两路调研的结论）

调研了OpenClaw（源码）和Claude Code、MCP规范、LangGraph、OpenAI Agents SDK、AutoGen、Letta（文档）。采用的共同约束是：权限由Runtime执行，身份只信任传输层，非owner消息不构成审批，未知状态默认拒绝。OpenProgram把OpenClaw式配对、固定两档工具权限和带信任状态的来源归档组合在同一条执行链中。

OpenClaw

先按稳定ID配对，配对后不再区分权限

未批准账号私聊时收到8位配对码，消息不进入agent；owner在终端批准后，该账号才可触发agent。OpenClaw在批准后不再按发言人限制工具能力。

采用部分：配对码流程、可变昵称不参与授权、每次拒绝记录检查位置和结构化原因。

Claude Code

规则可约束参数，非owner消息不能批准操作

工具权限可细化到Bash(git commit *)。渠道消息先通过allowlist；其他会话传入的正文不能批准交互请求，也不能修改配置。

待采用部分：在allow/deny之间增加hold状态，由owner对越权请求做一次性审批。

LangGraph

写入归因元数据，读取时按身份过滤

资源创建时记录owner身份，之后每次读取都按当前请求者身份过滤，归因与访问控制使用同一组持久化元数据。

部分采用：记忆来源已记录{speaker, channel, ts}元数据；按请求方档位过滤检索仍延期。

Letta、OpenAI Agents SDK、AutoGen、MCP

没有覆盖同一组需求

Letta通常为每个用户分配独立agent。OpenAI Agents SDK和AutoGen没有等价的发言人权限系统。MCP规范处理服务间OAuth授权，不负责单次工具调用的发言人权限。

结论：本页调研范围内，没有框架同时提供共享agent、发言人配对、固定权限档位和带信任状态的记忆来源。

04定案、实现与延期（2026-08-10）

入口采用稳定ID配对；运行时只保留owner和paired；工具执行只查询固定常量表；未配对群聊来源以pending归档但不主动提炼。详细定案见authority-handoff.md。

第一批 · 已实现档位枚举、配对、来源信任和默认writer

请求只带owner/paired枚举；陌生账号收到8位配对码，批准只走本地owner通道（终端/本机Web），渠道消息无权触发；不写迁移代码，上线后所有非owner账号首次发言统一走配对；可变昵称不参与身份匹配；显示名过消毒；拒绝返回结构化原因码。

用起来的变化陌生人私聊收到配对码而不是被无视，你在终端一条命令批准；有人把昵称改成你的名字，冒充无效；群里已配对的人说"记一下"会真的被主动记住。未配对成员的群聊发言照常归档，带未验证标记，检索时分得清是谁说的。

第二批 · 延期hold队列与读取范围

已配对成员的越权请求（如"帮我重启服务"）进入队列，由owner做一次性批准；记忆读取按请求方档位过滤，写入侧归因元数据已经实现。

用起来的变化agent会把已配对成员的越权请求提交给owner；owner批准后仅执行该次请求。非owner查询不会返回owner私有内容，发言记录保留来源标识。
同一memory稳定化批次已经完成：后台writer沿用默认聊天agent的provider、模型和凭据，memory.writer.model允许实时覆盖；未分类异常默认不可重试；memory.backend=none停止提示注入、召回、自动写入、整理与记忆线程，CLI memory动词和全部/api/memory/*入口也会在访问工作区前拒绝。正式工作区的23个旧v1 source文件经精确兼容读取后全部通过frame校验，一次真实写入把2条待处理消息提交为3个Topic文件、5个block；重复扫描没有改动revision。152个未引用frame的backfill、状态可观测字段和组合端到端测试仍在后续批次。
