OpenProgram是共用的：你在终端用它，别人从Telegram/Discord也能给它发消息，大家进的是同一个agent、同一份记忆。这一页讲清楚三件事：今天不同的人发消息会发生什么（已落地）、其他框架在同样问题上怎么做（调研结论）、接下来按什么顺序补（计划）。

03别人怎么做（两路调研的结论）

调研了OpenClaw（读源码）和Claude Code、MCP规范、LangGraph、OpenAI Agents SDK、AutoGen、Letta（读文档）。行业共识我们全符合：权限在框架层执行不靠提示词、身份只信传输层、非owner的消息不构成同意、默认拒绝。按来源分三档能力这件事没人做过，是我们自创。

OpenClaw

门口查得极严，进门后人人同权

陌生人私聊收到一个8位配对码，消息本身根本不进agent，owner在终端批准后才放行。但它明说不做"进门后不同人能力不同"，谁能触发agent谁就有agent的全部工具。

值得抄：配对码流程、可变昵称默认不参与授权（Discord昵称谁都能改）、每次拒绝都留下是哪道门什么原因的结构化记录。

Claude Code

规则细到参数，外来消息不算数

工具权限能写到Bash(git commit *)这个粒度。渠道消息要先配对进allowlist。别的会话发来的消息有一条铁律：不能批准任何弹窗、不能改配置、正文里的命令只是文字。

值得抄：allow/deny之间的hold档：越权请求先排队，owner来了再批，而不是直接撞死。

LangGraph

写的时候盖章，读的时候过滤

唯一把归因做进存储层的框架：资源创建时盖上owner身份，之后每次读取都按当前请求人的身份过滤。谁写的东西谁可见，一个机制同时管归因和访问。

值得抄：记忆条目写入时盖{speaker, channel, ts}元数据，检索按请求方档位过滤。

其余家

要么回避，要么没做

Letta的答案是一人一个agent，从根上回避共用问题。OpenAI Agents SDK和AutoGen没有权限系统，默认还是先执行后拦截。MCP规范管的是服务间OAuth授权，粒度到不了单次工具调用。

结论：共用一个agent还要分档控权，这个组合眼下只有我们在做。

04接下来做什么（按序，每条写你能感知到的变化）

第一批 · 补缝把已有的门拧紧

origin与能力清单一致性校验、memory工具接通追加能力、可变昵称降级、发言人显示名过消毒。

用起来的变化群里熟人说"记一下这件事"真的会被主动记住（现在只有被动归档）；有人把Discord昵称改成你的名字，冒充无效；昵称里藏指令注入不进模型。

第二批 · 补机制拒绝变得可解释、可补救

检查点返回结构化决策（哪道门、什么原因码，全程留档）；陌生人改走配对码；共享渠道的越权请求进hold队列。

用起来的变化陌生人私聊收到配对码而不是被无视，你在终端一条命令批准；群里朋友说"帮我重启下服务"不再直接被拒，而是排队等你点头，一次有效；出问题时能查到每次拒绝的确切原因。

第三批 · 概念修正工具权和数据权分开

现在"能用哪些工具"和"能看哪些数据"混在一档里。拆开后记忆按写时盖章、读时过滤运作。

用起来的变化共享渠道的人可以查公开记忆但看不到你的私人内容；他们追加的内容检索出来永远带着"是谁说的"，不会被当成你说的。
