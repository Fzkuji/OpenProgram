发言人身份：记忆里谁说的

一个agent可以被好几个人共用，共用同一份记忆工作区。记忆现在把所有人的话都记成"用户说"， 谁说的在写入那一步丢掉了。这页分三层：我们现在怎么做、 references里八个框架各自怎么做、我们计划怎么做。 第三层是照着第二层重写过的，原方案七个文件，学完之后两个文件。 正文在docs/reference/design/memory/overview.md，整体机制在memory-architecture.html。

层一 我们现在怎么做

现状，不是设计。发信人的显示名逐条消息存到了消息节点上，稳定id止步于门禁， 记忆写入那一步两个都没读。下面两节说清楚这为什么是真问题，以及断在哪一行。

已经存在的

发信人的显示名逐条消息带到了消息节点上：user_display从渠道适配器一路存进 session store，get_branch读回来还在。

断点一

发信人的稳定id在base.py:176门禁那一步用完就丢，没进dispatch_inbound。 TurnRequest.peer_id装的是路由目标，群聊里是群id。

断点二

_records()只读role，已经送到眼前的peer_display被丢掉， 三个人的话进SourceRecord之后全是user。

01一个会话里有几个人

身份要不要逐条消息带，取决于一个session里会不会出现两个发言人。会。路由键 (openprogram/channels/_session_routing.py:33-52 session_key_for_agent) 有两种配置把多个人放进同一条会话，其中一种还是Telegram群聊的默认值。

结论：身份必须逐条消息带。左边两种形状里，一条会话上只能记住一个peer，而说话的是好几个人， 会话级的字段永远指向其中一个。右边两种一人一条会话，逐条带身份也照样对，所以逐条是唯一一个四种形状都成立的做法。
出处：_session_routing.py:33-52的分支（group / channel永远按peer_id隔离， scope == "main"把所有私聊折成一条）；Telegram的peer_id_for在 implementations/telegram.py:55-60，group_sessions默认shared（telegram.py:48）。

02身份走到哪里断了

一条群消息进来，经过八站到达主题文件。显示名活到了第七站，稳定id死在第二站， 两个都在第七站被扔掉。下面这张图每一站标出手上有哪些身份字段。

层二 references下八个框架怎么做

八个都看了实现，不看README。八个里只有三个接了聊天渠道，三个里只有两个碰到过多人同会话， 两个的做法几乎一样：把发言人名字拼进消息正文，别的什么都不加。 剩下五个是单人命令行，"多人同会话"这个概念在它们那里不存在，这本身也是一种设计选择。

03八个框架有没有这个功能

先分清"没做"和"不需要做"。有没有多人同会话，取决于这个框架接不接聊天渠道。

档三的唯一例外要说清楚：claude-code-leaked里确实有senderName （src/tools/SendMessageTool/SendMessageTool.ts:93,157、 src/tools/TaskUpdateTool/TaskUpdateTool.ts:278-294）， 但那是团队模式下agent之间互发消息的署名，不是人类发言人。codex-cli里的participants 命中全在codex-rs/rmcp-client/src/bin/test_stdio_server.rs的测试用barrier服务器，跟身份无关。 opencode、pi-ai、pi-mono三个仓库对发言人相关词的搜索零命中。

第五列是这次调研最重要的一格：两个真做了多人会话的框架， 长期记忆层都没有发言人字段。openclaw的memory-core、memory-lancedb、 active-memory三个插件对sender/speaker/participant的搜索全部零命中； hermes的tools/memory_tool.py同样零命中。 身份之所以能进记忆，只因为它已经在消息正文里，记忆层原样收下。

05它们之间的分歧

共识只有一条（名字进正文），剩下四处两边选得不一样。这四处正好是我们要自己拿主意的地方。

分歧点openclawhermes-agent代价差在哪

系统提示要不要说明 说明放在user角色的"不可信元数据"块里，并写明理由：发言人名字是外部输入，不能进被当作权威的系统提示；会变的id进系统提示还会打掉前缀缓存 多人会话时系统提示加一句，且刻意不写死人名，同样为了前缀缓存 两边理由相同，落点不同

我们的路由已经是openclaw那一派：_session_routing.py的docstring写明 session_scope枚举继承自openclaw的dmScope，group/channel永远按peer_id共享。 所以"群聊里一定会出现多个发言人"对我们是默认状态，不是可选项，这一条不用再选。
层三 我们计划怎么做

按hermes的形状做，标签内容取openclaw的名字 (id)。 原方案是把身份当结构化字段一路透传，动七个文件；照着改之后只动两个文件， 因为身份进了正文，下游全部自动继承。

06学来的做法：一处前缀

动手的地方是base.py:_dispatch_and_reply。那里同时握着 ch_msg.user_id和ch_msg.user_display，而且是dispatch_inbound 的唯一调用点（全仓只有base.py:204这一处），所有渠道都从这里过。

为什么下游真的一行都不用改：_records()取的是message["content"]， 前缀就在content里；render_conversation是f"[{ref}] {speaker}: {text}"， speaker继续放role，名字在text开头；归档行同理。 这跟hermes的形状完全一致：role还是user，人名在正文最前面。

07七个文件变两个文件

左边是学之前的方案，右边是学之后的。划掉的六处全是"把身份当结构化字段透传"才需要的中转站， 留下的两处一处换了改法、一处原样保留。

网页、命令行、TUI三条路径零改动：它们不经过channels/base.py， user_text不带前缀，写入agent看到的跟今天一模一样。 这不是靠默认值兜住的，是因为改动点根本不在它们那条路上。
测试怎么写：一条会话里放两个不同user_display的入站消息， 断言两条SourceRecord的content各自带着不同的名字前缀、写入prompt里两个名字都出现； 另一条断言显示名里的换行被压掉。全用假的写入agent，不调真模型。

08抄了什么，没抄什么

五条。抄=照参考实现改，保留=原方案本来就对，不抄=参考实现有但我们不要。

A.身份放正文，还是放结构化字段

原方案选了结构化字段，这是七个文件的来源。

抄放正文。hermes是f"[{user_name}] {text}"（run.py:7759-7765），openclaw是`${sender}: ${body}`（envelope.ts:214-219）。下游transcript、摘要、归档、长期记忆全部自动继承，这正是它们记忆层里没有发言人字段的原因。
否掉结构化字段一路透传。每多一个下游消费方就要多改一处；两个参考实现都没走这条路。

B.标签里带不带稳定id

显示名会改也会重名，id不变但读不出是谁。这一点两个参考实现选得不一样。

保留带，用openclaw的形状显示名 (id)（sender-label.ts:21-30，10行）。base.py那里两个字段本来就都在手上，多拼一个括号不要钱。
不抄hermes只带显示名。改名之后同一个人在记忆里变成两个人，重名的两个人合成一个。

C.显示名是外部输入，要不要处理

显示名由发信人在平台上自己设，会被直接拼进写入agent的prompt。

保留去掉换行、截断长度。一行一条是render_conversation和归档的格式前提，显示名里的换行会把一条记录劈成两条，让ref对不上内容。openclaw同样做（sanitizeEnvelopeHeaderPart）。
否掉整套转义。归档文件是给人读的Markdown，转义会让它难读，而id才是可信的那一半。

D.要不要把前缀从显示和历史里剥掉

openclaw为此写了strip-inbound-meta.ts，317行。

不抄不剥。那317行是为openclaw那块当轮JSON元数据付的，它的正文前缀同样不剥。hermes一行都没写。代价是webui和TUI里用户自己那条消息前面会多一个方括号名字，可接受。
不抄整块JSON元数据（inbound-meta.ts:436-541，106行）。它装的是回复链、转发来源、群成员、位置这些openclaw专有的渠道上下文，跟"谁说的"是两件事。

E.记忆要不要按人隔离

共用一份记忆是产品形态，不是缺陷。

保留不隔离。一份工作区，一套主题文件，所有人共用。身份是记录的一部分，不是访问控制。两个参考实现的记忆层也都不按人分区。
抄人物写成主题页。openclaw的memory-wiki里，人是一张带canonicalId+aliases+handles的markdown页（markdown.ts:42-56、compile.ts:424-445），由模型自己维护，不是管道里的字段。我们的topics/people/就是同一个东西，跨渠道同一人的合并也归它管。
否掉给记忆加scope或按人分目录。团队机器人的价值就在于一个人告诉它的东西别人也能用上。要独立记忆的人跑自己的实例（openprogram --profile <name>）。

09实现状态

这一页第三层描述的是设计，还没有落地。今天跑的是_records()只取role， 所有人的话在记忆里都是user。已核实为真的四件事：显示名逐条消息存到了节点上并能读回； 发信人稳定id止步于base.py的门禁；两个渲染出口的格式串不用改； dispatch_inbound全仓只有base.py:204一个调用点，所以一处前缀覆盖所有渠道。 文字方案在docs/reference/design/memory/overview.md的"谁说的"一节。
