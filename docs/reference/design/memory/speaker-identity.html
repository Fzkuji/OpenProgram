发言人身份：记忆里谁说的

一个agent可以被好几个人共用，共用同一份记忆工作区。记忆现在把所有人的话都记成"用户说"， 谁说的在写入那一步丢掉了。这页画清楚身份现在走到哪里断掉、断在哪一行、补上之后一条消息全程带着什么。 正文在docs/reference/design/memory/overview.md，整体机制在 memory-architecture.html。

已经存在的

发信人的显示名逐条消息带到了消息节点上：peer_display从渠道适配器一路存进 session store，get_branch读回来还在。

断点一

发信人的稳定id在base.py门禁那一步用完就丢，没进dispatch_inbound。 TurnRequest.peer_id装的是路由目标，群聊里是群id。

断点二

_records()只读role，已经送到眼前的peer_display被丢掉， 三个人的话进SourceRecord之后全是user。

01一个会话里有几个人

身份要不要逐条消息带，取决于一个session里会不会出现两个发言人。会。路由键 (openprogram/channels/_session_routing.py:30 session_key_for_agent) 有两种配置把多个人放进同一条会话，其中一种还是Telegram群聊的默认值。

结论：身份必须逐条消息带。左边两种形状里，一条会话上只能记住一个peer，而说话的是好几个人， 会话级的字段永远指向其中一个。右边两种一人一条会话，逐条消息带身份也照样对，所以逐条是唯一一个四种形状都成立的做法。
出处：_session_routing.py:30-50的分支；Telegram的 peer_id_for在implementations/telegram.py:55， Discord在implementations/discord.py:19，Slack在implementations/slack.py:22； group_sessions默认shared（telegram.py:48）。

一条群消息进来，经过八站到达主题文件。显示名活到了第七站，稳定id死在第二站， 两个都在第七站被扔掉。下面这张图每一站标出手上有哪些身份字段。

怎么读：上排是站点，下排是这一站手上有哪些身份字段。红框是身份在这一站掉了东西。 第五站到第六站之间那条虚线是落盘和读回，中间隔着重启、隔着分支。
已核实：第五站到第六站这一段是真的通的。用SessionDB写两条带不同 peer_display的user消息再get_branch读回来，两个字段都还在，值也对得上。 所以断点二确实只是"没读"。

03peer_id不是发言人id

名字容易让人以为TurnRequest.peer_id就是发信人。它是路由目标，也是降级回发时的 outbound target。群聊里它等于群id，群里所有人共用一个值。

peer_id有它自己的职责，不能改语义去装发言人。发言人的稳定id需要一个新字段。
两个都带。显示名让主题文件读得懂，id让"同一个人"这件事在改名之后仍然成立。
渠道peer_id_for返回一条会话里的发言人发信人稳定id在哪
Telegram群，shared（默认） chat_id 多个 ch_msg.user_id，只进门禁
Telegram群，per-user chat_id_user_id 一个 拼在peer_id里，需要拆
Telegram私聊 chat_id 一个 ch_msg.user_id，只进门禁
Discord / Slack chat_id_user_id 一个 拼在peer_id里，需要拆
WeChat私聊 chat_id 一个 ch_msg.user_id，只进门禁
网页/命令行/ TUI 无 一个 没有
最后一列说明为什么不能靠拆peer_id拿身份：五种形状里三种根本没把user_id拼进去， 另两种拼了但拼法各渠道自己定，拆的规则要跟着peer_id_for的每个实现走。 从ChannelMessage.user_id直接传一路更短也更稳，那里本来就是渠道适配器已经解析好的字段。

04补上之后一条消息带着什么

同一条链路，两个断点接上。多出来的只有一个字段sender_id， 和SourceRecord上的两个字段。

标签只有一处逻辑：SourceRecord上一个label属性，prompt和归档各自读它。 有身份就是显示名(id)，没有就退回role，assistant一律是assistant。 两个出口的格式串本来就是f"…{speaker}: {content}"，槽位不用改。

05六个设计决定

每条给出选定的做法和被否掉的做法。绿=选定，红=否掉。

A.身份取自哪一层

会话级只有一个peer字段，群聊里说话的是好几个人。

选定逐条消息。每条user消息自带发言人，四种会话形状全都成立。
否掉会话meta上取一次。Telegram群默认shared，一条会话上只能记住一个人；session_scope: main同理。

B. SourceRecord带什么

显示名会改也会重名，id不变但读不出是谁。

选定两个都带：speaker显示名+ speaker_id稳定id，都默认空字符串。
否掉只带id。主题文件写成"702说预算8万"，人名搜不到，读的人也认不出。
否掉只带显示名。改名之后同一个人变成两个人，重名的两个人合成一个。
否掉把role换成发言人。role还有别的用处（_records靠它过滤非对话行），加两个字段比改一个语义安全。

C.稳定id怎么从渠道走到dispatcher

peer_id已经被路由目标占了，不能挪用。

选定加一个sender_id，从ChannelMessage.user_id出发，经dispatch_inbound和TurnRequest到user_msg。存储层不用改，节点metadata是排除法白名单。
否掉拆peer_id。五种形状里三种压根没把user_id拼进去，拆的规则还得跟着每个peer_id_for实现走。
否掉改peer_id的含义。它同时是降级回发的outbound target，群聊里必须是群id。
否掉把peer_display改名成sender_display。语义确实是发信人显示名，但这个名字散在webui、session store、broadcast十几处，改名的收益不抵风险。

D. prompt里怎么呈现

目标是让写入agent写出"甲提的预算是5万"，而不是"用户说预算5万"。

选定换掉speaker槽位的值，格式不动。render_conversation现在就是[{ref}] {speaker}: {text}，把role换成label。WRITE_MEMORY加一句：一行前面的名字是说这句话的人，把事实归给他。
否掉另起一个发言人清单段落。模型要在清单和正文之间来回对，比每行自带名字更容易错。
否掉改成JSON或结构化块。整套prompt是纯文本行，为一个字段引入第二种格式不划算。

E.显示名是外部输入，要不要处理

显示名由发信人在平台上自己设，会被直接拼进写入agent的prompt。

选定去掉换行、截断长度。一行一条是render_conversation和归档的格式前提，显示名里的换行会把一条记录劈成两条，让ref对不上内容。
否掉不处理。注入风险本身不是新增的（消息正文一样是外部输入），但格式被劈开是实打实的损坏。
否掉整套转义。归档文件是给人读的Markdown，转义会让它难读，而id才是可信的那一半。

F.记忆要不要按人隔离

共用一份记忆是产品形态，不是缺陷。

选定不隔离。一份工作区，一套主题文件，所有人共用。身份是记录的一部分，不是访问控制。
否掉给记忆加scope或按人分目录。团队机器人的价值就在于一个人告诉它的东西别人也能用上。要独立记忆的人跑自己的实例（openprogram --profile <name>）。

06单人场景的默认值

没有渠道就没有peer身份。默认值要让这些路径的输出跟今天一模一样， 这样这次改动对单人用户是零影响。

08实现状态

这一页描述的是设计，还没有落地。今天跑的是_records()只取role， 所有人的话在记忆里都是user。已核实为真的三件事：显示名逐条消息存到了节点上并能读回； 发信人稳定id止步于base.py的门禁；两个渲染出口的speaker槽位现成可用。 文字方案在docs/reference/design/memory/overview.md的"谁说的"一节。
