03写什么第二层

原话，还是模型提炼过的事实。两者都留的四家（claude-code、codex、pi-mono、我们）走的是同一条路： 原话只追加不改，提炼可以随便重写，出了问题拿原话对账。

codex 是两遍提炼，不是一遍。第一遍按会话做，把一次完整对话压成结构化的原始记忆和一份会话摘要； 第二遍另派一个没有网络、不问审批的子 agent，拿着全部第一遍产物加一份工作区差异， 重写 MEMORY.md、摘要页和技能目录。写的和整理的分成两个岗位， 和我们"写入"加"夜间重整"是同一个拆法，只是它拆在流水线里，我们拆在时间上。

一句话把这一格说完：凡是用下标或者时间戳当游标的，都靠"一个游标作用域里只有一条线"这个前提活着， 而它们保住这个前提的办法是分叉的时候换一个作用域：codex换thread_id，openclaw换会话， claude-code换进程，hermes干脆在分叉那一行把下标手动推过去。 换作用域之所以可行，是因为它们的分叉都拷贝了一份，新那边的坐标从头开始。 我们的分叉不拷贝，两条线共用一张图和一个会话id，作用域没得换，坐标也没得翻译， 于是唯一剩下的办法就是别再用坐标：记id，不记第几条。 pi-mono证明了这不是唯一解，它同样是会话内的树，靠"只取到最近公共祖先"把前缀挡在视野外； 但那要求每一次取都知道要跟哪条比，而记忆要的是"这个会话还欠什么"，没有第二条线可比。

opencode 有个反直觉的：revert 本身不删东西，但下一次提问一开始就会把标记之后的消息硬删。 也就是"改一条旧消息重跑"在它那里是不可逆的，想留住旧那条只能先 fork。 我们的 DAG 是两条都留着，代价就是要有办法说清哪条写过了。

06检索第二层

存下来的东西怎么回到上下文里。四条路：全量塞进去、关键词搜、向量搜、让模型自己挑。 第四条是 claude-code 独有的，也是最便宜的一条。

最值得抄的一条。claude-code 的做法是：不建任何索引，只让每个记忆文件在抬头写一句自我描述， 检索时把这些描述列成清单，花一次便宜的小模型调用挑出五个文件名。 这条路我们现在没有，而它和我们的 topics/ 结构天生匹配。 它挑的判据也写得比"相关就选"细：拿不准就不选，宁可返回空。
codex 有个闭环值得记：模型用了哪条记忆，要在回答里埋一段隐藏标记说出来； 服务端把这段解析出来记一次使用计数，然后在正文里删掉再给用户看。 使用计数回过头喂给整理阶段的排序。用得多的留下来，没人用的自然沉底， 整个过程不需要任何人手工评分。我们的夜间重整目前只按内容合并，没有这种使用反馈。

给"常驻块写满怎么裁"的结论：七道闸里没有一道让模型自由判断该丢什么。 五道是确定性截断（claude-code 的 MEMORY.md、codex、openclaw 的两层，加 claude-code SessionMemory 的兜底那级）， 两道是确定性拒绝再把选择权交回模型（hermes、我们）。 唯一沾一点模型判断的是 claude-code 的 SessionMemory，做法是先让模型压、压不动再确定性兜底， 而且判据写死在提示词里点名保住哪两节，不是让它自由发挥。 四条可以直接用的经验：一，闸门要两道，行数管不住长行，claude-code 的字节闸就是被一份 200 行 197KB 的索引逼出来的； 二，裁的时候看归属比看时间重要，openclaw 只丢自己写的、人写的一律不动； 三，要裁就整份都要裁到，codex 给项目级 AGENTS.md 设了闸却漏了全局那份，claude-code 反过来给自己管的 MEMORY.md 设了硬闸、给人管的 CLAUDE.md 只警告不截； 四，裁完必须留痕，codex 是唯一只写日志的，模型和用户都不知道自己少看了东西。 我们的core.md现在在"确定性拒绝加留痕"这一格。 第一条和第二条我们不打算照抄：第二道闸仍然是闸，仍然在写入的路上，加了它还是会把稳定事实挡在外面； 归属区分之所以要紧，是因为openclaw的常驻文件是唯一一份、丢一行等于销毁一行， 而把core.md变成派生视图之后丢不再等于销毁，归属也就不用判了。 判决和理由在对标之后抄什么第 02 节。

08实现规模第二层

不含测试。彩条是长期记忆本身，灰条是压缩和转录存储。同一件事从 0 行到三万四千行都有人做， 差别几乎全在"要不要自己建索引"。

复杂度都花在检索上。openclaw 的三万四千行里，向量、嵌入缓存、索引重建、混合排序占了绝大部分； 去掉这一层，它剩下的部分和 claude-code 的四千九百行是同一个量级。 我们六千三百行里没有向量必需项（嵌入是可选的），多出来的部分是事务和主题格式的校验。 真正的分水岭不是"有没有记忆"，是"要不要自己维护一个索引"。

09我们的方案落在哪第三层

前八节给出了当前方案在各维度上的位置。多数维度复用已有框架的成熟做法； 节点marker由SessionDAG的分支语义决定，原因见第05节。
