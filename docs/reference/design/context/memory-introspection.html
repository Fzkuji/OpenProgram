记忆的自我认知：agent怎么知道自己记得什么

一次实测把问题摆了出来：让跑在OpenProgram里的agent讲一讲"当前的记忆系统是怎么设计的"， 它讲的是宿主机上Claude Code的配置文件和技能，推荐用一个上一代早已删掉的工具去沉淀知识， 而openprogram/memory/下真正跑着的那套一个字没提。 这页把上下文装配摊开，逐条核对模型每轮能拿到的记忆线索，对照八个参考实现，给出界碑怎么加、 自省工具放哪、记忆坏掉时模型该看到什么。

00四层怎么分第一层

四层各答一个问题：现在的上下文里记忆长什么样、别人怎么做、下一步动哪几行、不受实现约束该长成什么样。

01十五个组件的实际形态第一层

context/components.py注册十五个组件，各自声明层（L0/L1）、层内order、出现条件、构造函数。 组装器按["L0","L1"]收集、按order排、条件为假的丢掉、剩下的build出来用两个换行拼起来。 order从小到大就是"越稳定越靠前"，因为前缀越稳定，供应商的缓存命中越长。

边界形态三种。 绿色自带XML标签，模型能看出块的起止； 橙色只有一句散文开场白，靠语义分辨； 红色是裸文本，前后两个换行，跟邻居完全糊在一起。 十五个里绿五、橙三、红七：identity、inline_prompt、workspace_files、current_date都在红的那一列， memory_global是绿的，但它绿得只说了半句话，下一节讲。

02记忆那块长什么样第一层

记忆有两条进上下文的路，走的是同一个围栏函数。围栏本身是为召回设计的：防止模型把旧事实当成用户刚提的新要求。 常驻块借用了它，于是常驻块也只说得出"这是回忆"这一句。

常驻块已经有围栏，缺的不是围栏。LocalMemoryBackend.system_prompt() （local_backend.py:59）就是return fence_memory(text) if body else ""， 所以<memory-context>一直在。围栏那句话是给召回写的，它要挡的是"模型把旧事实当成用户刚提的新要求"， 这个职责它做到了。常驻块借用它，就等于用一句"这是回忆"去回答"你是谁"。
再包一层是错的做法，因为围栏不幂等。fence_memory进门先调sanitize_context， 而sanitize_context的第一条正则_FENCE_BLOCK_RE剥的是整个<memory-context>…</memory-context>块， 连内容一起。实测fence_memory(fence_memory("hello world"))得到的是一个内容为空的围栏： <memory-context>\n[System note…]\n\n\n</memory-context>。 所以界碑只能是"换一句开场白"，不能是"再套一层"。

03失败为什么是静默的第一层

从磁盘到wire，记忆要穿过四道except，每一道都把异常换成空串。空串在组装器里等于"这个组件当轮不出现"。 于是"记忆是空的"和"记忆炸了"在模型眼里是同一件事：什么都没有。

这三种情况模型该有三种反应。后端关掉是用户的决定，模型不该提；工作区空是正常的新装状态，模型该说"我这边还没有关于这件事的记录"； 记忆坏掉时模型绝对不该推断"用户从没跟我说过这个"，那是把系统故障读成了事实。现在的代码让它无从分辨。

04模型每轮拿到的记忆线索第一层

把"模型能不能知道X"逐条拆开，对着这一轮真实的wire核对。这就是那次实测里agent会答错的完整原因。

压垮那次回答的最后一根：默认工具表里唯一像知识系统的，是一个上一代的东西。 DEFAULT_TOOLS二十四个工具里有wiki_agent（functions/__init__.py:113）， 描述字面是Maintain a wiki vault — route to ingest, enrich, browse, lint, or search depending on the task. 六个memory_*一个都不在。模型每轮扫一遍自己的工具表，问"我拿什么沉淀知识"， 表上写着答案，而那个答案指向的是重构时已经删掉的目录。这不是模型幻觉，是工具表在指路。

06界碑：八家的字面文本第二层

把各家包记忆的那一层原样抄出来对齐看。分成三档：有标签有措辞、只有标签、什么都没有。

claude-code那一套值得整段抄。它把记忆内容放进message[0]一条合成的user消息， 外层是<system-reminder>，里层逐文件写Contents of {path} ({来源标注})， 五种来源五句标注：user's private global instructions for all projects、 project instructions, checked into the codebase、 user's private project instructions, not checked in、 user's auto-memory, persists across conversations、 shared team memory, synced across the organization。 模型不但知道这是记忆，还知道每一份是谁的、走多远。八家里只有这一家把"谁写的"答到这个精度。

07自省工具与空坏可见性第二层

自省工具 · 谁默认给

只有openclaw和hermes默认给

工具存在，和工具默认在场，是两件事

openclaw把memory_search + memory_get放进memory-core， 而memory-core是memory插件槽的默认实现，装上就有，不用挑。 工具描述本身就是指令：Mandatory recall step…，还写明If response has disabled=true, memory retrieval is unavailable and should be surfaced to the user.

hermes的memory在核心集里默认开，但只有add/replace/remove，没有list； 靠"每次写完回全量列表"顶替。

codex-cli有四个真自省工具（List / Read / Search / AddAdHocNote）， 但双重开关默认关：Feature::MemoryTool是default_enabled: false， 还要再开一个memories.dedicated_tools。 claude-code干脆不做专用工具，记忆就是文件，用通用Write/Read/Grep， 提示里直接教模型往那个目录写。

我们的位置跟codex一样：六个工具做完了，默认不给。差别是codex的开关是明写的功能位， 我们的是"不在DEFAULT_TOOLS里"这个没人会注意到的事实。

openclaw默认给2个hermes默认给1个codex有4个默认关我们有6个默认关
空 / 坏 · 谁让模型看得见

只有openclaw三态都说得清

空、坏、关掉，模型能不能分辨

空：模板BOOTSTRAP.md直接写给模型看： There is no memory yet. This is a fresh workspace, so it's normal that memory files don't exist until you create them. 这句话把"空"从可疑变成正常。claude-code的子agent那条路上有同类占位句： Your MEMORY.md is currently empty. When you save new memories, they will appear here.， 但主会话那条没有。

坏：openclaw的检索失败返回结构化的disabled:true + unavailable:true + warning + action: Check embedding provider configuration and retry，并要求模型告诉用户。八家里独一份。

变了：codex是唯一会说"旧的作废了"的一家： The previously provided AGENTS.md instructions no longer apply. 但那是给项目文档用的，记忆缺失时它一样静默。

其余五家（含我们）都是静默消失：块不出现，模型无从分辨"没记过"和"取不出来"。

openclaw三态齐claude-code子agent有占位codex会说作废其余五家 静默

09我们计划怎么改第三层

四处改动，按"能独立落地、各自能验证"切开。合计每轮85 token，其中65坐在L0缓存前缀里，第二轮起不再重复计费。

改动A · 最小的那个

工具目录本身就是界碑

functions/__init__.py:72-114 + :123-136

抄hermes那句话的意思：这些是跑你的框架的东西，不是你正在改的项目。 模型再去~/.claude找"我的记忆系统"就没有借口了。

三个设计问题的答案。 界碑怎么加：不加新围栏，换常驻块那一条的开场白，因为围栏不幂等，而且已有的那句话是给召回写的、职责不同。 模型怎么知道自己有记忆：两者都要，但顺序有先后：工具目录（20 token）比散文（65 token）更便宜也更硬， 因为模型对工具表的信任度高于对散文的；散文补的是工具名答不出的那三件事（在哪、是不是摘要、谁写的）。 坏了该不该让模型知道：该，而且要跟"空"分开说，否则模型会把系统故障读成"用户没说过"。

10代价与落点第三层

为什么六个全延迟而不是留两个常驻。延迟目录只发名字，而memory_search和memory_browse 这两个名字本身就说清了用途，schema里的参数说明属于"要调的时候才需要"。 tool_search永不延迟，是加载其余工具的唯一入口，模型看到名字就能一步接上。

11理想状态第四层

不受当前实现约束的目标形态。四条，各自标明差在哪、为什么这一轮先不做。

四条共一个方向：把"模型能知道什么"从散文常量变成系统自报。 现在每一句关于记忆的话都是上下文层替记忆系统说的，说的是设计时的样子； 理想状态是记忆系统自己报当下的样子，散文只留下不会变的那部分。 第三层的四处改动全部落在"散文常量"这一侧，是有意的：它们不改接口，所以可以单独上线、单独回退。

12怎么核实的第四层

第一层

装配跑真的

直接调components.assemble(agent, ["L0","L1"], tools=…)， 逐块数token，得到1638与记忆块的821。工具表调agent_tools(names=DEFAULT_TOOLS, only_available=True) 逐个打印，二十四个里零个memory_*、一个wiki_agent。

围栏不幂等是跑出来的：fence_memory(fence_memory("hello world"))返回内容为空的围栏。

第二层

八个仓库读源码

每一条都给文件路径加行号，字面文本原样抄。 references/pi-ai/是pi-mono传输层的只读快照，没有agent层，六问全部N/A，不是"没查到"。 references/openclaw-full/不存在，references/openclaw/就是全量源码。
