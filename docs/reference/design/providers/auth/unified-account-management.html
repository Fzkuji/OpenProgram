Provider keys and failover

ConceptMeaning
ListOne file per provider, ~/.openprogram/auth/<provider>/credentials.json: strategy and the ordered credentials. An API key's secret is in its company's file. Every change (AuthStore.mutate) holds the file's lock from the read to the write and applies to the file as it is then, so a key the CLI added or a token another process refreshed is never lost. Removing or replacing a key also drops the last good copy (.bak, .bad-*), so its secret leaves the disk (models/auth/store.py).

Choosing a credential

  1. Pinthe conversation's chosen credential, if usable
  2. Bindingthe credential the conversation last used
  3. Strategyin_order, evenly, least_used (fewest uses today)

The binding and the pin live in the session's metadata (credential_binding, credential_pin); a call reads the conversation in its context before the cache key a Runtime sends (op-…), and a child session follows its parent_session_id up to the conversation, so programs, agent methods, sub-agents and Goal turns spend the conversation's pinned or bound key.

One with_credential() (models/providers/streaming/credential_failover.py) wraps every adapter's stream; adapter SDKs do not retry on their own.

Other 403a 403 about a model (verification, organization) blocks that model; one about a region or policy leaves the key alonenext usable one, or the error

5xx, networkunchangedtwo backoff retries on the same credential
None usable—wait if one is back within 60 s, the one that just failed included (one key and a 429 waits out its cooldown); else the model fallback; else an error listing each credential's state

A switch adds a muted notice to the reply (EventRetry, reason credential). A stored error message has the key, Bearer tokens and ?key= values removed first. Once output has been shown, a failure is not retried on another credential.

Adding a sign-in reuses /api/providers/{p}/login/{start,poll,submit,cancel}. Changes to the list go through models/listing/manage.py, which the routes and the CLI share.

Carry-over

The first start on this layout carries the old per-account files over once (models/auth/carry_over.py):

  1. Read every old account file: an object with a credentials list and the old account fields. Any other file is left alone; an unreadable one is logged by path.
  2. Copy auth/ once to auth/.carry-over-backup, inside the folder the sandbox never lets a tool read.
  3. Flatten each provider's files into one list, in account order and then each account's credentials; a missing or repeated id gets a new one.
  4. Keep every stored key. An old environment row that stored its key becomes a stored key with a new id, whatever the starting process's environment holds. A key a variable also holds is listed once at read time (store.env_rows). An environment row with no stored value is left out and logged.
  5. Correct the rest: a key refused for a spent balance (HTTP 402, or OpenCode's 401 CreditsError) is out of quota for a day from when it was seen, ready when no time is recorded. A sign-in takes its email and plan from its id_token.
  6. Check every row arrived, and only then remove that provider's old files.

A provider that fails keeps its old files without holding up the others. Running again adds nothing twice and makes no second backup.

An older OpenProgram installed elsewhere on the machine still writes an old file from the environment variable it reads, so the carry-over can run on any start. A key the list already holds is not added again, and rows that repeat a stored key keep only the earliest, which has the key's history.

A list an earlier carry-over wrote gets steps 4 and 5 once, on the next start (carry_over.repair, marked .repaired in the backup). It never changes a secret, so every .bak stays, and it reads a spent balance from the .bak when a later check wrote over it.

It also tidies: a lock file goes only while the repair holds that lock, empty folders go, and folders become 0700. A folder it cannot change stays as it is, and the repair is still marked done.
