认证存储

AuthStore（models/auth/store.py）：~/.openprogram/auth/<provider_id>/credentials.json，每个 provider 一个有序列表，原子写入，跨进程锁从读一直持有到写（mutate），文件被外部改动时重新加载。API key 的密钥存在所属厂商的文件 auth/_keys/<company>.json 里，写入方式相同。

请求计数（使用次数、上次使用、今天用了几次、轮换游标）放在旁边的 usage.json，所以请求从不重写密钥文件。CredentialProvider 只提供磁盘上已有的内容，不重新发现；导入是显式步骤。

登录注册表

auth/login/login_method_registry.py 是唯一的 provider → [method] 表；第一项为默认，CLI、网页、TUI 都按它显示。处理器在 auth/methods/ 和 auth/login/。Anthropic 没有公开第三方 OAuth client。

每种方式带中英文的标题和一行说明，导入还写明它读取的文件；网页的接入对话框据此列出各种接入方式。

刷新

refresh token 会轮换：第一个用掉它的持有者拿到新的一对，之后再用旧的会被拒绝（invalid_grant），这个持有者就被登出。所以同一时间只有一个进程花掉 refresh token，每个进程拿到锁后先重读登录。

规则行为
发送前CredentialProvider.prepare 刷新 expires_at_ms 在 60 秒内的登录；请求带出去的 token 没有过期
跨进程锁refresh_lock.py：provider 列表文件旁 <file>.refresh.lock 上的建议锁，和写入锁分开。两个 worker，或 worker 和它的定时任务子进程，轮流刷新
锁内重读文件。别的进程刚刷新好的登录直接用；仍然过期的才刷新并保存
过期前被拒HTTP 401 让这个登录刷新一次，并立刻重发同一个请求，不算传输重试。刷新记一行 INFO

凭据层在工作线程里让选中的登录可用（prepare），不在事件循环上，因为它可能要等别的进程的刷新锁和一次刷新请求。

读不了不等于空

步骤行为
写入（state/private_files._atomic_write）被替换的文件是合法 JSON 时保留为 <file>.bak（state/last_good.keep_previous）
读到非法 JSON（last_good.load_json）把原字节复制一次到 <file>.bad-<UTC 时间>-<摘要>，返回合法的 .bak，否则返回空
使用方read_config、update_config、认证存储
删除或更换密钥它所在列表的 .bak 和 .bad- 副本也一起删除，旧密钥不留在磁盘上
备份（operations/backup.py）排除 .bak 和 .bad- 副本，脱敏不会被绕过

沿用 magpie 的 lastgood（yetone/magpie，MIT）。
