API key 解析

Provider凭据来源
有 key 或登录的 LLM provider~/.openprogram 下 AuthStore 里这个 provider 的列表，由设置页或 openprogram providers keys <provider> add 写入
Worker 环境里的 key 变量同一列表里的只读一行（env:<VAR>），每次使用时从环境读取；取消设置该变量即删除
Amazon BedrockAWS 凭据链；哨兵值 "<authenticated>"，没有 bearer key
Google VertexGCP ADC 加项目和区域；同一哨兵值
config.json从不为 LLM key 读取。api_keys 只服务网页搜索和 TTS。

只有一个列表，运行时、模型目录和状态页就不会说法不一，请求在已存 key 和环境 key 之间用同一种方式选择。

调用

函数回答
selection.with_credential(model, opts, attempt)每个模型请求：选择、准备、切换凭据（Provider 的 key 与故障切换）
resolve_provider_key(provider)key 形态的凭据（key、环境变量、辅助命令）或哨兵值，否则 None。不含登录 token，因为这些调用方发 x-api-key 或 Bearer，access token 会 401。
is_configured(provider_id)有 key，或云端凭据链已满足
resolve_api_key_with_auth_store(provider_id)模型列表和探测：请求此刻会用的任意类型 bearer，经 resolve_api_key_sync
env_vars_for(provider_id)provider 的 key 变量，首选在前，来自它的连接条目；没有就退到 models.dev
provider_id_for_env_var(env_var)反查，取列出的第一个归属；非 LLM key 为 None

这些名称只在一张表里：auth/login/login_method_registry.py，和每个 provider 的连接方式放在一起。openprogram/models/providers/settings/env_api_keys.py 从它作答，运行时和服务端导入它不会循环。

resolve_api_key_sync 内部顺序
  1. 请求此刻会选的凭据（selection.choose，不计一次使用），然后按顺序是其他可用的
  2. 每个先经 CredentialProvider.prepare 准备（快过期的登录会刷新），再由 resolve_connection 读出
  3. resolve_provider_key：云端哨兵值

None 让调用方提示登录，或对本地端点不带 key。AuthCredentialProcessError 总是向上抛：坏掉的辅助命令按名称显示，不被另一个 key 顶替。
