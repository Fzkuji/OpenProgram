Provider 的 key 与故障切换

概念含义
列表每个 provider 一个文件 ~/.openprogram/auth/<provider>/credentials.json：strategy 和有序的 credentials。每次修改（AuthStore.mutate）从读到写都持有文件锁，并作用在当时的文件上，所以 CLI 加的密钥、别的进程刷新的令牌都不会丢。删除或替换密钥时连同上一份好副本（.bak、.bad-*）一起去掉，密钥不留在磁盘上（models/auth/store.py）。
使用次数<provider>/usage.json：每个凭据的使用次数、今天的次数、最近使用，以及 evenly 轮到哪里。请求只写这个文件，从不写密钥文件。
凭据id、label、kind（api_key、oauth、device_code、import、token、credential_process）、source（web、cli、import、env）、identity、enabled、status、冷却、被封的模型、最近错误、最近使用
状态ready、cooling、quota、invalid_key、needs_login
环境变量 keyprovider 读取的变量（login_method_registry.env_vars）已设置时，是一行只读的 env:<VAR>，使用时从环境读取；保存它的位置和状态，不保存值
重新登录同一个 account_id 或邮箱就地更新原来那一行：id、名称、位置都不变

显示的名称：label，否则登录的邮箱（套餐另外显示），否则变量名，否则 Key ····1234。任何列表都不带密钥。

选哪个凭据

  1. 固定对话指定的凭据，可用时
  2. 绑定对话上次用的凭据
  3. 策略in_order、evenly、least_used（今天用得最少）

绑定和固定存在会话 metadata 里（credential_binding、credential_pin）；调用先认上下文里的对话，再认 Runtime 发出的缓存键（op-…），子会话顺着 parent_session_id 找到所属对话，所以程序、agent 方法、子 agent 和 Goal 轮次都用对话固定或绑定的密钥。

所有 adapter 的流都由同一个 with_credential()（models/auth/selection.py）包住；adapter 的 SDK 自己不重试。

出错时怎么办

错误凭据请求
429，Retry-After ≤ 5 秒不变同一个凭据再试一次
429cooling，时长按 Retry-After，否则 60 秒起每次翻倍，最多 15 分钟下一个可用的
额度或余额quota，到服务给的重置时间，否则 24 小时下一个可用的
401，或指明密钥的 403登录先刷新一次（只在这里，adapter 不再刷新）；之后 invalid_key 或 needs_login刷新后用同一个，否则下一个
其他 403关于模型的 403（验证、组织）封这个模型；关于地区或策略的不动密钥下一个可用的，或报错
模型被拒这个模型封 24 小时下一个可用的
5xx、网络不变同一个凭据退避重试两次
都不可用—60 秒内有恢复的就等，刚失败的那个也算（只有一个密钥遇到 429 会等它冷却完）；否则走模型回退；再否则报错，列出每个凭据的状态

切换时在回复里加一行淡色提示（EventRetry，reason 为 credential）。保存的错误信息先去掉密钥、Bearer 令牌和 ?key= 的值。已经输出内容后出错，不再换凭据重试。

接口

入口内容
REST/api/providers/{p}/credentials：列表、添加、PATCH 名称或开关、删除、check、replace、reorder、strategy。/api/sessions/{sid}/credentials：绑定和固定。
事件provider.credentials.changed {provider}、session.credentials.changed {session_id, binding, pin}
CLIopenprogram providers keys <provider> list|add|replace|rename|move|enable|disable|check|remove|strategy；providers login 等于 keys add
用量每条用量记录 credential_id；额度按凭据读取

粘贴的密钥用 POST /api/providers/{p}/credentials/check-key 检查，这一步不保存；点“添加密钥”或“更换密钥”时连同名称一次保存，并沿用刚才的检查结果。添加登录沿用 /api/providers/{p}/login/{start,poll,submit,cancel}。对列表的修改都经过 models/auth/manage.py，路由和 CLI 共用。

旧数据迁移

在新布局上第一次启动时，把旧的按账号分开的文件迁移一次（models/auth/carry_over.py）：

  1. 读每个旧账号文件：带 credentials 列表和旧账号字段的对象。别的文件不动；读不了的只按路径记日志。
  2. 把 auth/ 复制一次到 auth/.carry-over-backup，在沙箱不让工具读的目录里。
  3. 把每个 provider 的文件展平成一个列表，按账号顺序，再按每个账号内的凭据顺序；缺 id 或重复的 id 换新的。
  4. 保留每个已存的密钥。存过密钥的旧环境变量行变成换了新 id 的已存密钥；变量在不在取决于哪个进程先启动，所以这里不做判断。和某个变量值相同的已存密钥照样保存，读取时只列一次（store.env_rows）。只有没存值的环境变量行会去掉，日志里写服务商、行 id 和原因。
  5. 改正其余的：因余额用完被拒的密钥（HTTP 402，或 OpenCode 的 401 CreditsError）是额度用完，从发生时起停一天，没记时间就是可用。登录从自己的 id_token 取邮箱和套餐。
  6. 确认每一行都到了，才删除这个 provider 的旧文件。

某个 provider 失败只保留它自己的旧文件，不耽误别的。再运行一次不会重复添加，也不再备份。

机器上别处装的旧版 OpenProgram 还会按它读到的环境变量写出旧文件，所以任何一次启动都可能再迁移。列表里已有的密钥不会再加一遍；重复同一个已存密钥的行只留最早的那条，它带着这个密钥的使用记录。

以前的迁移写出的列表，下次启动时按第 4、5 步的改法修一次（carry_over.repair，在备份里留 .repaired 标记）。它不改任何密钥，所以每份 .bak 都留着；后来的检查盖掉了余额用完的错误时，它从 .bak 里读出来。

它还会整理：只在拿着锁时删锁文件，删掉空文件夹，把文件夹改成 0700。改不了的文件夹保持原样，修复照样记为完成。
