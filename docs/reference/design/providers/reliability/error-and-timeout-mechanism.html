Length of a reply

Chat replies have no limit on tool interactions or total time; a stream that keeps producing is never cut for running long. User cancellation always applies. Explicit runtime.exec deadlines, program call-round parameters and declared budgets of standalone GUI or browser tools are not overridden.

Idle bound

A reply that stops arriving while its connection stays open ends its attempt after 300 s without an event, as StreamIdleTimeout: a transport error, retried by the layer that owns the attempt and shown as a retry.

  • Keepalive pings and comment lines are not events.
  • The wait for response headers counts as silence.
  • The stalled stream is closed before the error is raised.
  • A stop ends the wait at once.

boto3 blocks, so Bedrock reads on a thread of its own:

  • Closing the stream shuts its socket. botocore's own 60 s read timeout also applies to each read.
  • The Bedrock SDK transport is disabled in the product until its network path is managed.

Re-sending a failed reply

A reply that stalls or whose connection drops before its final event says nothing about the request, so stream._delivered sends the same request again. It serves the conversation turn path, AgentSession and one-shot calls alike.

CaseWhat happens
Failure before any contentSent again after a retry event. Chat Completions does this in its own loop first; a failure it spent its attempts on arrives flagged and is not sent again
Failure after reasoning, text or a tool callThe whole request is sent again and the partial is void, as Codex CLI and Claude Code do. The retry event carries restart; the reply's row and the loop's partial message drop the failed response's text and reasoning, so a steer during the wait commits none of it. Codex instead keeps the partial (stop_reason="length") and the turn continues from it
ToolsNever run twice: tools run only after a response's final event, and a failed response has none
Reply going out to a channelParagraphs already sent cannot be recalled. The unsent text of the failed response is dropped, and the new response skips the opening it repeats word for word. A new response with other wording is sent whole after what went out
Not re-sentRate limit, overload, auth or a bad request (SDK retries and failover own those); a request under a Goal or job reservation; anything after a stop
Bound spentThe failure is flagged transport_exhausted, so neither AgentSession nor exec retries it again
UsageAn attempt that reached the provider and ended without a final message is recorded: with the tokens it reported, or as one request whose cost is unknown. Reaching it means streamed content, reported tokens, or silence for the idle bound; an adapter's start event does not count. A refusal or a connection that failed before any content is not recorded

The consumer sees one start for the request, however many attempts it took. The redaction and failover wrappers own their producer task, so a stop reaches the provider request under them.

Stopping a call

MechanismEffect
DeadlineEnd to end; overrun bounded by one connect attempt. SSE waits are clamped to what remains.
transport_exhaustedretry_stream marks a spent budget; exec does not restart it, and keeps reason and retryable honest
ExecInterrupt(BaseException)Passes every except Exception retry layer. Only the outermost owner raises it.
OPENPROGRAM_EXEC_TIMEOUT_SProcess default for exec; 0 is unbounded. Needs no signals, which Python delivers only to the main thread.
Stop while a reply streamsThe turn ends without waiting for the provider to close: the read in flight is cancelled and handed to the turn's loop (event_stream.leave_unwinding). A bounded close that runs out of time is handed over the same way, still running: cancelling it would cancel the provider a second time and cut its socket close short.
The turn's loop closingOn a thread of its own, in asyncio.run's order: the reads and closes a stop handed over get 2 s to end (a socket close is a round trip) and are cancelled after that, the provider clients close, the tasks the turn left are cancelled, async generators are shut down and the loop closes
Tasks that appear while it closesThe close of an abandoned stream generator, or a socket close a cancelled task left running, runs to its end. Async generators are shut down only once no task is left, repeated until nothing new appears. This has 1 s; what is still running then is cancelled and named in a warning.
Reply ended inside a blockIts final message holds the text and thinking as content blocks, not the adapter's working dict, at stream._extract_final. An unfinished tool call stays as the adapter left it.

A benchmark runner with a sample budget subclasses ExecInterrupt for its watchdog, stops on authentication errors and scores by LLMError.reason.

Not built: a hard limit on a synchronous _call

Python cannot kill a thread: the caller would return while _call runs on until its socket fails, possibly writing model-call nodes or store state. The deadline, the idle bound and the SSE budgets already bound stalls. Subprocess isolation for benchmark samples is also not built.

LLMError carries reason, retryable, http_status, retry_after_s, attempts, elapsed_s, had_image, provider, model, last_error_type, cause. A deadline hit is TIMEOUT, never retryable. A spent budget of a retryable error stays retryable: retry with a new budget, not at once.

An exception with no verdict may show as UNKNOWN, non-retryable; error_retryable_inferred marks that, and only such messages keep Runtime's bounded fallback. An explicit verdict, known reason or spent transport budget is authoritative.

error_kind names a finer, stable category beside the reason, found on the exception or anything it wraps: a stalled stream and a reset connection are both TRANSPORT, only the first is stream_idle. The others are memory_unavailable, model_unavailable and auth.

DNS at the policy boundary

A DNS_ERROR from socket.gaierror is raised as httpx.ConnectError, so bounded transport recovery applies before anything is committed. Every attempt still resolves, validates and pins. Empty or malformed answers and denied origins stay policy failures. No DNS fallback, private-address exception or unbounded retry.
