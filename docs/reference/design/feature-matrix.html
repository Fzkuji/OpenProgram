功能清单对标：十二家能做的事逐条摆出来

前面六轮子系统对标加一轮整框架对标，全部是按我们自己的设计维度去查的。这个查法只能查到"我们已经知道自己在做的事，别人怎么做"，查不到"别人有一整块功能而我们连想都没想过"。这一页换查法：不按设计维度，按功能清单。入口是各家的功能开关配置、命令清单、工具清单、出厂 agent 定义、帮助文本和运行时目录。160 项功能，13 列，一格一个判定。

三个问题先回答 1功能全表 160 项 覆盖度 2只有别人有的 97 项 这一轮多找出多少 3只有我们有的 6 项 4我们该补哪些 取证与状态
和 framework-comparison 的分工。那一份按设计维度和机制比：执行模型、状态存哪、上下文装配、权限审批这些我们自己关心的轴，每轴一句定性加一张图。这一份按功能清单比：用户能点到、能敲到、能看到的事，一条一格。两份的输入完全不同，所以结论也不重合：那一份找出 55 条缺口，这一份找出 97 条，重合只有 21 条。要看机制去那边，要看清单看这边。

00三个问题先回答结论

只有别人有，最要紧的三个

版本控制整类、删除拦截、被别人驱动的口子

一，版本控制那一整类是空的。十项里我们只占两项，是十三类里第二低。生成提交信息、一键提交推送开 PR、对当前 diff 做安全审查、从 PR 链接直接开 worktree，四项我们一项没有，buddy 四项全有。这是编码 agent 每天用得最多的几步，成本也最低。

二，删除操作没有底线。我们的权限规则全在工具层，bash 里的 rm -rf 直接穿过去。buddy 的做法是在三个运行时同时挂钩子把删除改道系统回收站：Python 走 sitecustomize，Node 走 NODE_OPTIONS=--require，shell 走 safe-bin/rm。这是清单里唯一一条"没有它就可能丢数据"的。

三，别的程序进不来。MCP 服务端、ACP、官方 SDK 三个口子我们一个都没有，"集成与被集成"这一类 13 项里我们只占 1.5 项，是十三类里最低。

buddy vendor/shim/{sitecustomize.py,genie-safe-delete.cjs} · product.json commands[] commit / commit-push-pr / security-review
只有我们有

六项，核心那条核实成立

上一轮认定的最强项是"会话是一张图且函数调用树写进同一张图"。按 160 项功能逐条扫完，这条成立：没有第二家把 @agentic_function 那样的每层调用写成会话图上的节点，也没有第二家把会话本体存成一个 git 仓库（别家是 JSONL 或 SQLite）。

另外四条上一轮没提：多条分支 N 路合并成一条、按剩余消息预算裁子 agent 的工具面、升级前在临时端口把新代码启起来探健康再切、无人值守时直接把提问工具摘掉（不是压掉提示，是策略层不给这个工具，所以结构上不可能卡住等人）。

六项集中在两处：会话数据结构，和"跑起来别出事"。功能面上我们没有任何一项是别人完全没有的。

contextgit/dag.py · store/session/git_session.py · agent/internals/_merge.py · agent/attended.py

97 条里 76 条是新的

前六轮加整框架那一轮，一共认定 55 条"别人有我们没有"。这一轮按功能清单扫出 97 条，两边重合 21 条，新增 76 条。

新增的分布说明问题：版本控制 8 条、界面形态 7 条、多 agent 6 条全部是新的，前六轮一条都没碰到。编辑器集成 8 条里新增 6 条，集成与被集成 11 条里新增 9 条，部署与运维 9 条里新增 7 条。

原因清楚：版本控制、界面形态、部署运维这几类从来不是我们的设计维度，所以按维度扫永远扫不到。换查法这件事本身是有效的，产出比前六轮加起来还多接近一倍。

左端是我们，右端是这一类里覆盖最高的那家。差距最大的三类是编辑器集成、集成与被集成、版本控制。

04我们该补哪些顺序

只排顺序，不写方案。65 条"值得做"里挑出成组的六批，每批是一次可以做完的事。

批次补什么建在什么已有的东西上为什么排这里
一 删除拦截进回收站，加不可绕过的硬底线，加凭据进钥匙串，加密钥用外部命令间接取。 已有 functions/permission_rule.py 的规则引擎和 _approval.py 的八分支优先级链，缺的是工具层以下那一层。 唯一一批"没有它可能丢数据"的。我们的 bash 现在能 rm -rf 穿过全部权限规则。
二 版本控制那一组：生成提交信息、一键提交推送开 PR、对当前 diff 做安全审查、从 PR 链接直接开 worktree、worktree 建好后同步未跟踪文件。 已有 worktree/manager.py 的完整状态机、shadow git、apply_patch。缺的只是把这些包成命令和提示词。 十三类里第二低，四家都有，成本最低，日常频率最高。
三 被别人驱动的三个口子：MCP 服务端、ACP、官方 SDK。附带入站 webhook。 已有 181 个 REST 端点和一条 /ws 动作总线，工具注册表也现成。缺的是把它们包成标准协议并加鉴权。 上一轮已认定，这一轮按功能扫又多出 ACP 和入站 webhook 两个具体形态。
四 确定性假模型加请求录制回放。 已有 31 个 provider 的统一消息类型，加一个假的进注册表即可。 给核心循环补测试的前置条件。上一份文档已把它排在第一位，这里排在四是因为前三批都在补会丢数据或每天都在用的东西。
五 会话与历史那一组：到阈值自动压缩、归档、临时旁支、运行中插话改方向、跨渠道接管。加上把 TUI 里 /compact /context /mcp /doctor 四个死桩接上。 压缩、上下文统计、rewind 的后端全是真的，只是 TUI 那一侧没接。 四个死桩是纯粹的接线工作，不接等于我们在自己的表里虚报。
六 界面细节那一组：主题、Vim 模式、快捷键全量重映射、无障碍、PWA。加 /init、使用洞察、可分享诊断包。 TUI 与网页都是自己的代码，改动面可控。 单项收益小，但这一类 12 项我们只占 4.5 项，是"看起来不像个成品"的主要来源。
没排进来的两批，和不排的理由。编辑器集成（行内补全、行内对话、CodeLens、状态栏动作）：这四项要求我们变成一个 IDE 插件产品，和常驻 worker 加三个自有界面的形态是两条路。真要接 IDE，走批次三的 ACP 就够，让 Zed 和 VS Code 来驱动我们，而不是我们去长成一个插件。企业那一组（合规管控与外部模型开关、每次编辑静默审计上报、信用点购买、企业策略强制配置）：三家内网版和 buddy 都有，但那是"把框架交给一个组织去管"才需要的东西，我们是单人本机，装上只有负担。
