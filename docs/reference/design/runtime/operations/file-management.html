一个模型，四种操作

四个词不能互换。操作名称直接表达修改代码还是对话、作用于一轮还是一段历史。点击左侧操作查看完整影响。

Operation
四种语义不是四个同级按钮。Turn card 只显示当前适用的 Undo 或 Revert；user checkpoint 进入 Restore sheet；assistant message footer 才提供 Branch。成功 Undo 后，严格预检可用时在 UI 显示 Redo；历史 Revert 的反向操作显示 Reapply。两者都执行新的 reapply transaction，不维护独立线性 redo 栈。

目标架构与信任边界

对话 DAG、精确 mutation journal 和 Git workspace view 是三个独立事实源。历史操作 planner 可以读取三者，但只有 journal 中的可恢复 receipt 能授权文件恢复。

普通 Bash 与 Workspace Review 的边界：Bash 可以在沙箱或 worktree 中运行，但本地共享工作区里的通用 shell 结果不自动归因给某个 turn。Git 能显示当前 workspace 变化，却不能证明它属于哪一轮，也不能赋予 turn Undo 权限。

文件浏览、搜索与 Review 查询合同

Project file explorer 与 Review 都使用 project/session 绑定的服务端快照。目录、搜索和 Review 过滤先确定完整的有序候选集，再返回一页；客户端不得以当前页数据推断项目或 scope 的完整结果。

查询事实源与范围排序、筛选与分页无效化
Directory listing由 project_id 解析的项目根目录；path 必须是规范化的根内相对目录。排除路径穿越、符号链接逃逸和服务端禁止浏览的目录。先按类型（目录、文件）和根内规范化路径稳定排序，再建立 snapshot。每页最多 100 项；cursor 是不透明 token，不是数组下标。目录版本、ignore 规则或请求中的 project/path/sort 不匹配时返回 STALE_SNAPSHOT，客户端从第一页重取。
Project search服务端遍历同一项目根，并应用与目录浏览相同的访问与忽略规则；不依赖树已展开的节点。结果只包含名称或根内相对路径匹配的项目文件与目录。先以 query、匹配模式和类型过滤，再按稳定 rank、根内路径排序并建立 snapshot；分页只作用于已过滤结果。搜索 query 或模式变化必须丢弃 cursor。项目切换、搜索 snapshot 到期或根目录版本变化后显示可刷新状态；不得把其他项目的旧结果保留在新项目中。
Review scopeThis turn / Current branch 读取 mutation journal；Workspace 读取 Git 的 HEAD、index 和 worktree。每一项继续携带 source、actor 和 change-set 归因。服务端先按 category、path query、operation、diff state 与排序过滤，随后对该过滤结果建立 snapshot 并分页。计数和 totals 针对完整过滤结果，不是当前页。scope、assistant message、filter、sort 或 snapshot 任一不匹配时拒绝 cursor；Workspace 还比较固定 candidate list 与每个候选的 index/worktree identity。选择的文件若不在新 snapshot 中，清空 selection 和 diff。
Review file diff只接受已由同一 Review snapshot 返回的 path；turn/branch 读取 journal blob，workspace 读取 snapshot 中记录的 HEAD/index/worktree blob pair。diff cursor 同样是不透明且绑定 file identity、blob pair、scope snapshot 与行预算的 token。每次最多 200 行或 256 KiB。snapshot、候选列表、index/worktree identity 或 blob pair 改变时返回 stale，不返回来自另一版本的后续 diff 页。

cursor 不变量

  • cursor 只在创建它的 snapshot、owner、query kind、过滤条件和排序完全一致时有效；服务端不接受客户端提供的 offset、路径锚点或跨项目 token。
  • snapshot 保存候选集的稳定顺序或足以重建该顺序的不可变 revision；后续页绝不重新扫描后混入新增、删除或重排的项。
  • snapshot 可受容量和 TTL 限制。逐出或内容版本改变时明确返回 stale，由客户端刷新首屏；不得悄悄改用最新列表继续旧 cursor。
  • 目录和搜索各自使用 cursor；Review 文件列表与单文件 diff 使用不同 cursor namespace，不能互换。

Workspace 不变量

  • 创建 snapshot 时一次性确定未提交 candidate list，按规范化相对 path 排序；它包含 staged、unstaged、untracked、rename/delete 的所有相关 path，且保留旧路径和新路径的对应关系。
  • 每个 candidate 固定 HEAD base、index blob 和 worktree content identity/blob pair。文本 diff 只能从该 pair 渲染，不能在后续请求中重新执行最新 git diff 代替。
  • 请求下一页或单文件 diff 前，服务端重新读取 status candidate vector、index tree identity 和目标 path 的 no-follow worktree identity；任一新增、删除、状态、mode、index blob、worktree digest 或路径映射变化均返回 STALE_SNAPSHOT。
  • snapshot 保存的 content blob 受同一 review storage quota 管理；blob 缺失、超限或过期也返回 stale/unavailable，绝不从当前 worktree 近似补齐旧 diff。

所有文件 WebSocket 请求

规则合同禁止
必填关联键所有文件浏览、读取、写入、创建、重命名、复制、删除、reveal、turn summary、turn diff、Review scope 与 Review diff 请求都带客户端生成的 UUID request_id；成功、stale、validation error 和 transport error 都原样回显。不接受缺失或非 UUID 的文件请求；不再以 response type、path 或到达顺序认领响应。
响应验证客户端以 request_id 作为唯一 pending key，并额外验证 action、project/session、snapshot 与目标 path；组件卸载、项目切换或新查询会取消并遗忘旧 pending key。不得用全局请求队列消除竞态；一个慢目录请求不能阻塞另一个文件 read 或 Review diff。
写入幂等与冲突有副作用的文件 action 还携带独立 idempotency_key 与现有的 optimistic-lock 条件。服务端以 action、owner、canonical payload 和 precondition fingerprint 建立 durable record。request_id 仅关联本次传输，不替代写入幂等键。不把重连后的新 request id 当作新写入；不以缓存 mtime 覆盖服务端冲突结果。
错误形状每个结果提供 request_id、action、owner、status 和稳定 error code；STALE_SNAPSHOT、NOT_FOUND、CONFLICT 与 INVALID_REQUEST 可被 UI 明确处理。不吞掉缺少 request id、错误 owner 或未知 response 的帧，也不将其更新到当前文件状态。

写操作 idempotency_key

{
  "record_key": {"owner": "profile + project", "action": "project_file_write", "idempotency_key": "uuid"},
  "fingerprint": "sha256(action + owner + canonical payload + precondition)",
  "state": "prepared | in_flight | completed",
  "operation_id": "fileop_...",
  "result": "canonical terminal result or null"
}

幂等不变量

  • owner 是经授权的 profile 与 project；canonical payload 使用规范化根内 path、标准化 operation 参数和内容 digest，排除 request_id 与 idempotency_key。precondition fingerprint 包含 expected mtime/digest、源与目标路径、overwrite 条件及影响目录的版本条件。
  • 服务端在与文件 mutation 同一 durable scope 中原子领取 (owner, action, idempotency_key)。同一 record key 的 fingerprint 不同，返回 IDEMPOTENCY_KEY_CONFLICT，零文件写入。
  • 同 fingerprint 的 in-flight 重试绑定既有 operation_id，等待既有操作到本次请求的响应期限；未完成时返回 IN_PROGRESS 和该 operation id，客户端只能重试同一个 key，不能另发写入。
  • 完成后 durable record 保存 canonical terminal result。相同 fingerprint 的任何重试只重放该结果，即使 request_id 不同，也不再次执行文件 mutation。进程重启先恢复或判定 in-flight record，再允许其结果被重放。
  • record retention 至少覆盖客户端重试窗口与 worker restart recovery；过期清理不得删除仍为 in-flight 的 record，且不会将已过期 key 解释为一个不同 fingerprint 的成功重放。

缓存与未保存草稿

存储键与容量淘汰与一致性数据保护
Read cache键为 project_id + canonical relative path + content revision；最多 64 项且最多 16 MiB，使用访问顺序 LRU。只缓存成功且完整的只读结果。写入、rename、delete、tree revision 变化和容量超限会失效或淘汰最旧的干净 read；缓存未命中只触发新的 request_id 请求。缓存不是编辑状态，也不保存 dirty text。
Dirty draft store浏览器原生 IndexedDB 的 openprogram-file-drafts 数据库，键为 project_id + canonical relative path；持久化 UTF-8 draft、baseline content revision、baseline mtime、保存状态与更新时间。容量上限为 32 个 draft 或 8 MiB。干净 draft 可删除；dirty draft 不参与 LRU 淘汰。所有 entry 与 aggregate byte/count index 在一个 readwrite transaction 中更新。页面刷新、tab unmount、切换项目和 read-cache 淘汰都不能删除 dirty draft。服务端文件变化后保留草稿并标记冲突，保存必须继续提交其原始 baseline 条件。
路径变更与清理成功 rename 在 IndexedDB transaction 中移动同项目 draft key；copy 不共享 source draft。删除文件、项目解绑或删除项目先列出 dirty draft，要求明确的保存、保留/导出或丢弃选择。任何文件操作失败时不变更 draft key。确认 discard/unlink 后，相关 draft 与 project aggregate index 在单个 IndexedDB transaction 中清理；清理失败保留原记录并报告失败。跨项目的同名 path 永不共享 cache、draft、selection 或 search snapshot；不因 tree 刷新、Review 切换或后台响应重置编辑器 buffer。

持久化与恢复不变量

  • 使用浏览器原生 IndexedDB，不增加依赖。配额计算使用 TextEncoder 的 UTF-8 byte length，计入 draft、baseline 与所存元数据；project_index 保存每项目的键集合、count 和总 bytes。启动时以 project_index 恢复该项目的 dirty drafts；索引缺失或不一致时扫描 drafts 重建索引，不删除记录。
  • 新建、更新、rename、discard 与 project cleanup 都在一个 IndexedDB readwrite transaction 内先计算新旧 bytes，再同时写 draft 与 aggregate index。超出 32 项或 8 MiB 时 transaction 不写入，现有 draft 保持不变。
  • 编辑器在接受会把持久化 draft 超出配额的输入前先检查预算；满额时阻止创建新 dirty draft，并显示可见的保存、还原、导出或显式丢弃提示。已有 dirty draft 不自动淘汰；更新已有 draft 遇到浏览器 QuotaExceededError 时保留最近成功持久化版本、显示持久化失败状态并暂停进一步会扩大该记录的编辑，直到用户处理空间或显式导出/丢弃。
  • 删除项目文件时，若对应 dirty draft 存在，服务端删除完成前 UI 必须要求保存、导出保留或明确 discard；成功 discard 才清理该 key。项目解绑或删除同样先展示该项目 draft 数量和 bytes，确认后清理所有该项目 keys 与 index；取消或失败不清理。
  • draft 内容仅保存在当前浏览器 origin 的 IndexedDB；不进入日志、遥测、模型上下文、WebSocket payload 或跨设备同步。显式 discard、确认的项目清理、浏览器站点数据清除和应用卸载会删除本地内容；恢复时不得自动上传或重新写回项目文件。
Review 的顺序固定：解析 scope 和 owner → 取得或创建事实源 snapshot → 服务端过滤与排序 → 对过滤结果分页 → 客户端渲染单页。分类按钮和搜索框不是前端对已加载一页的二次筛选。

不变量

  • 原始写入先持久化 prepared receipt，再写文件，确认 after state 后转 committed；prepared 持久化失败时 trusted mutator 必须在写盘前失败。
  • {kind:"absent"} 只表示已精确确认路径不存在；baseline 获取失败只能由 recoverability=unavailable 和 reason 表达，永远不能编码成 absent。
  • recoverability=unavailable 只用于 journal 已成功持久化、但因明确大小或文件类型策略不保存 recovery blob 的 mutation，不用于吞掉 journal 故障。
  • 每个 user prompt 定义 before_turn；assistant 完成后定义 after_turn。UI 必须写清恢复哪一个边界。
  • 同一 turn 多次修改同一 file lineage，摘要折叠为 first-before 到 last-after 的净变化；rename 后仍保持 lineage。
  • 所有共享 checkout 的 transaction 在 workspace lock 下领取全局单调 workspace_sequence；多轮投影按 sequence 和 lineage，不按 DAG seq/DFS。
  • before/after regular state 都保存 blob ref，才能稳定显示历史 diff、恢复和条件式 Reapply。
  • 路径在 capture/plan/apply 时都重新规范化；保存并复检父目录链 identity、leaf lstat、device/inode 和 hardlink count，使用已验证 directory handle 或等价 no-follow 原语。
  • Current branch 只折叠 active lineage 的 transaction，不混入 sibling branch。
  • Revert/Restore/Reapply 本身也写 mutation transaction，原记录保持不可变。

规划算法

阶段规则失败结果
Resolve lineage从当前 HEAD 沿 conversation predecessor 回到目标 user checkpoint；caller subtree 只按明确 ownership 纳入。目标不在 active lineage：拒绝，提示先切换分支。
Fold target state按 journal 投影 checkpoint 时每个路径的目标状态；同文件跨多轮只生成一个最终 restore action，不逐轮覆盖。journal 不连续或历史 receipt 不精确：代码模式 unavailable，对话模式仍可选。
Preflight从全局 current_workspace_revision 规划到 target checkpoint，只比较实际 plan actions 涉及的 file lineage；检查 blob、父目录/leaf identity、file type、root、空间和权限。任一失败进入 BLOCKED，列出每个路径，零文件改变。conversation/workspace mismatch 本身不是 source digest。
Prepare intent保存 plan id、expected branch/head version、workspace revision、before images、目标 images、writer epoch 和恢复模式；请求幂等。确认前状态变化返回 stale-plan，重新预览。
Apply files获取 workspace mutation lock；每个 action 持久化 pending/applied/verified/rolled_back 和本 transaction applied digest；逐文件原子替换，删除仅在 current digest 匹配时执行。回滚前再次确认 current digest 仍等于本 transaction applied digest；外部 actor 已改写时不覆盖，进入 RECOVERY_REQUIRED。
Create conversation branchconversation-only 或 code+conversation 先准备新的稳定 target branch id/ref，source branch HEAD 不变；首轮前目标统一为持久 synthetic ROOT，禁止 head_id=None fallback。创建/激活使用 expected source head_version CAS；失败则按 intent 恢复文件并保留 source/active branch。
Finalize追加 rewind transaction 和 navigation event；不把旧节点全局写成 rewound。提升 branch writer epoch，使旧异步任务无法回写当前 branch。重启时扫描未终态 intent，完成或回滚，不猜测成功。

性能、保留、安全与兼容

Turn finalize

复杂度只与 committed changed paths 有关；不遍历 workspace。摘要在 finalize 持久化并随 transcript 返回。

Review loading

服务端先筛选和稳定排序，文件列表每页 100；客户端只保留当前页和相邻页。选中文件后每批最多 200 行或 256 KiB，并支持继续加载。

Diff budget

计算超预算返回 timeout metadata；不阻塞 Agent 完成，也不回退到 before 与当前磁盘的跨轮近似 diff。

Snapshot pagination

目录、项目搜索和 Review 的分类、搜索、排序与 opaque cursor 都绑定同一 snapshot；workspace 或项目变化后旧页返回 stale 并整体刷新，不能混页。

Request identity

每个文件 WS 请求有 UUID request_id；切文件或切项目取消旧请求。迟到响应还必须匹配 owner、scope、snapshot revision、change set 与 blob pair。

Large restore plan

上千文件预检作为可观察后台任务，冲突结果分页；进入 APPLYING 后不可取消，只能完成或事务回滚。

Recovery blobs

使用独立内容寻址存储，按 digest 去重，权限限于本地用户；不进入 session Git。默认保留最近 100 个 checkpoint 和每个 file lineage 的首个 baseline。

GC visibility

Pinned、活动 task、未解决冲突、prepared/applying intent 和仍被 branch ref 引用的 checkpoint 不回收。其余 blob 到期后显示 Review available / Code restore unavailable。

Secrets

blob 不进入日志、遥测或模型上下文；session 删除一并清理无引用 blob。外部路径必须有当时和恢复时的明确授权。

Read cache and drafts

Read cache 受 64 项 / 16 MiB LRU 限制；dirty draft 独立持久化，受 32 项 / 8 MiB 配额保护且绝不自动淘汰。

Legacy sessions

旧 checkpoint 只用于只读 Review 或明确标记 unavailable；没有 digest/recovery contract 时不提供新 Undo/Rewind code 模式，也不保留无 request_id 的兼容入口。

TUI parity

/rewind 先展示同一 server plan，再选择模式并确认；不能继续直接调用旧 rewind_to。

App/Web parity

同一 plan/apply 协议和幂等 request id；UI 只渲染 server 返回的 canonical impact，不在客户端重算。
