OpenProgram · Runtime design

Self-Programming Agentic Workflow

Workflow 不是新的调用协议。它是一个独立 Git 仓库中的普通 Python 小项目，可以按任务直接组合 goal()、agent() 和 llm() 中的任意一种或多种调用。三层能力的依赖顺序固定：Goal 建立在 Agent loop 上，Agent loop 由反复的模型调用和工具执行组成，llm() 直接暴露其中的一次模型调用。入口使用现有 @agentic_function，项目之间通过正常的 Python import 和函数调用组合。

1. 设计问题

系统需要管理多个可复用 Workflow。一个 Workflow 可以调用另一个 Workflow，也可以调用普通 Function、单次模型请求、Agent loop 和 Goal loop。调用方不应学习另一套 API，生成代码也不应通过字符串名称交给额外 dispatcher。

公开代码只有一种语义：导入 Python 函数，然后调用。OpenProgram 的工作是准备可导入的代码、建立 Runtime context、记录 DAG 和隔离执行环境。

范围：Workflow 的项目结构、组合方式、Git 管理、加载、运行上下文、DAG、创建复用和管理入口。

不在范围：自定义 revision 数据库、单独 Workflow DSL、远程 Marketplace、自动 push、后台分布式调度和新的模型工具协议。

2. 当前实现与设计偏差

当前事实问题目标
@agentic_function 已支持 Python 直接调用、模型工具注册、Runtime继承和 DAG 节点。此前设计又增加 @workflow 和双调用适配层，重复现有能力。只保留 @agentic_function。
llm()、agent()、goal() 已共享 ambient Runtime。此前 Workflow 设计把“Workflow 可任选入口”和“能力之间的固定依赖”混成了一种关系。Workflow 可直接组合三层中的任意一层；层间依赖固定为 Goal → Agent loop → 单次模型调用。
当前 agentic_workflow 生成零参数单文件代码，并维护自定义 project/revision 目录。任务输入容易被写死，生成结果难以形成可维护项目；版本机制与 Git 重复。生成多文件 Python 项目，入口接收参数，每个项目是独立 Git 仓库。
不同生成 Workflow 之间没有正常 Python import 关系。已有能力无法被其他项目直接复用。Workflow仓库作为 Python package 被导入，调用仍是普通函数调用。
此前文档中的 @workflow、call_workflow()、invoke_workflow()、Function sidecar 和 shared resolver/executor 公开概念全部删除。内部仍可有加载和执行代码，但不能形成新的编程接口。

3. 抽象结构与具体例子

抽象结构

具体例子：论文调研 Workflow

from openprogram.agentic_programming import agentic_function, goal, llm

@agentic_function(as_tool=False)
def collect_evidence(topic: str) -> str:
    return goal(
        prompt=f"检索并核对与 {topic} 有关的论文",
        condition="候选论文已核对年份、出处和研究问题",
    )

@agentic_function(as_tool=False)
def screen_papers(evidence: str) -> str:
    return llm(f"筛选与任务直接相关且来源可核对的论文：\n{evidence}")

@agentic_function(as_tool=False)
def synthesize(selected: str) -> str:
    return llm(f"根据筛选结果整理研究脉络：\n{selected}")

@agentic_function
def literature_review(task: str) -> str:
    evidence = collect_evidence(task)
    selected = screen_papers(evidence)
    return synthesize(selected)

内部 Goal 函数可以使用 @agentic_function(as_tool=False)：它保持 Python 可调用和 DAG 记录，但不暴露成模型工具。确定性 helper 保持普通函数；需要显示在 DAG 时才使用现有 @traced。

4. llm、agent、goal 的职责

现有方法执行语义适用位置不负责
goal(prompt, condition, ...)以 agent() 作为每轮工作执行器，满足 condition 或达到上限后返回；当前代码使用 llm() 判断 condition。有明确完成条件、需要多轮修正的阶段性目标。判断器是内部实现细节；自身不是装饰器，也不单独创建函数节点。
agent(prompt, tools, ...)反复执行单次模型调用；模型可以请求工具，工具结果进入下一次模型调用，直到完成或达到迭代上限。Goal 的执行基础，以及检索、读写文件和代码修改。不自行定义成功条件。
llm(prompt, ...)直接执行一次模型调用，配置为 tools=[]、max_iterations=1。分类、提取、判断、改写和局部生成；也用于当前 Goal 的 condition judge。不执行工具循环。
@agentic_function包装普通 Python 函数，建立 ambient Runtime、模型工具入口和 DAG call node。公开 Workflow 入口，以及需要独立可见性的内部 Goal 函数。不改变 Python 的 import 和函数调用规则。
固定能力依赖是 Goal → Agent loop → 单次模型调用 → Model Runtime。Workflow 不属于这条依赖链中的一个强制步骤；它是上层 Python 组合，可以直接调用 goal()、agent() 或 llm()。实现上，agent() 和 llm() 都调用 Runtime.exec()，通过 tools、max_iterations 和 execution_kind 选择执行模式。

5. 一个 Workflow 是一个 Git 管理的 Python 小项目

文件职责
workflow.py公开 @agentic_function，接收本次任务输入，按需组合 goal()、agent()、llm() 和其他 Workflow。
goals/可选目录。只有存在明确、需要循环判断的阶段目标时才拆分 Goal 函数；直接 Agent loop 或单次模型调用不要求创建该目录。
helpers/确定性 Python 逻辑，不需要模型的解析、路径和格式处理。
__init__.py稳定导出公开入口，例如 from .workflow import literature_review。
pyproject.toml标准 Python 项目元数据和外部依赖；不复制一份 Workflow manifest。
README.md / tests/说明输入、输出、产物位置和验证方式。

入口参数必须表达每次调用的任务数据。研究主题、输入路径、输出目录和条件不能写死在首次生成的源码中。

6. Workflow 之间只使用 import 和函数调用

# workflows/research_pipeline/workflow.py
from openprogram.agentic_programming import agentic_function
from workflows.paper_search import paper_search
from workflows.paper_screening import paper_screening
from workflows.research_synthesis import research_synthesis

@agentic_function
def research_pipeline(task: str, output_dir: str) -> str:
    papers = paper_search(task, year_from=2025)
    selected = paper_screening(papers)
    return research_synthesis(task, selected, output_dir)
No dispatcher

没有字符串调用

不使用名称解析器、callee id 或公共 resolver API。

Normal Python

类型和异常保持正常

参数、返回值、异常和测试都遵循 Python 规则。

Existing wrapper

DAG 自动继承

被导入的对象仍是 @agentic_function，直接调用已有 wrapper。

跨 Workflow 依赖关系由静态 Python import 得出。项目内部仍可使用相对 import，外部 Python 依赖仍由 pyproject.toml 声明。生成代码中的跨 Workflow 调用只允许绝对、静态的 from workflows.<package> import <function>；首版不支持根据字符串动态导入另一个 Workflow。这使 Calls / Used by、循环依赖检查和执行快照都可以在运行前完成。

7. 加载与执行：准备 import 环境，不改变调用语义

临时执行目录保持同一 namespace 结构，例如 <run-root>/workflows/paper_search/。Worker只需把 <run-root> 放入普通 Python import path；不实现 sys.meta_path hook或自定义 importer。

边界合同
代码版本根项目和可达依赖在一次执行开始时固定到Git commit；工作树未提交内容不进入本次执行。
Import范围隔离worker的import path只包含本次可达Workflow快照、OpenProgram和获准依赖；不修改主App进程。
Runtime顶层 @agentic_function 建立ambient Runtime；嵌套 @agentic_function、llm()、agent() 和 goal() 继承它。
取消与权限沿现有Runtime调用树向下传播，不由Python import单独实现。
失败ImportError、函数异常、Goal未满足和Agent超限均按普通异常/返回值进入caller；不会自动修改代码。
循环静态import依赖环在启动前拒绝；同一 @agentic_function 的运行时自递归继续使用现有深度保护。

8. agentic_workflow 负责创建和复用项目

agentic_workflow(task) 本身仍是现有 @agentic_function。它不是所有 Workflow 的调用网关，而是一个能检查现有项目、编写代码、验证并提交 Git 仓库的 authoring agent。

每个项目的 __init__.py 导出公开 @agentic_function。OpenProgram按现有程序加载流程导入这些入口，装饰器把它们注册成普通 AgentTool。自然语言任务选择已有能力时，agent() 直接调用这些现有工具；生成一个需要长期复用的编排项目时，代码再通过静态 Python import组合它们。这两种入口最终都执行同一个 @agentic_function wrapper。

已有入口可完成导入已有项目的公开函数并正常调用。本次任务作为函数参数传入，不改代码。
已有项目可组合生成一个小型编排项目，只 import 现有 Workflow 并实现参数映射和执行顺序。
缺少独立能力创建新的多文件 Workflow Git 仓库，再由当前项目 import。
实现确实需要修改在临时 Git worktree 中让Agent修改、测试和提交；普通运行失败不触发自动 revision。

Author内部可以使用 agent() 写代码，也可以使用 goal() 反复执行“实现—测试—判断”直到满足明确条件。完成条件来自项目测试和入口调用，不来自额外planner枚举协议。

9. DAG 来自现有函数调用关系

research_pipeline(task)              # @agentic_function
├── paper_search(task)               # imported @agentic_function
│   └── collect_evidence(topic)       # @agentic_function(as_tool=False)
│       ├── agent(...)               # goal() work round
│       └── condition judge          # 当前实现使用 llm()
├── paper_screening(papers)          # imported @agentic_function
│   └── llm(...)
└── research_synthesis(...)          # imported @agentic_function
    ├── agent(...)
    └── llm(...)

@agentic_function 当前已经通过 ContextVar 维护Runtime和caller id。直接Python嵌套调用时，子函数自动继承父caller；llm()、agent() 和用户交互节点继续挂在当前函数下面。因此不需要通过一个额外调用函数重建DAG。

代码类型DAG显示
公开 @agentic_function显示可折叠Workflow / agentic function节点，并可被模型调用。
内部 @agentic_function(as_tool=False)显示为子Goal节点，但不注册为模型工具。
llm() / agent()显示在当前Goal或Workflow节点内部。
普通helper默认不显示；需要调试可使用现有 @traced。

11. 参考框架与取舍

参考采用不采用
Python import system / contextvars标准package/import语义，以及当前 @agentic_function 已使用的调用上下文继承。不实现自定义import hook，不增加字符串Workflow dispatcher。
Git commits / git worktree项目历史、回退、提交快照和隔离修改。不在Git上再实现revisions目录和active pointer。
GitHub reusable workflows独立可复用单元、明确输入和组合调用。不采用YAML Workflow DSL；OpenProgram继续使用Python。
现有 OpenProgram @agentic_functionPython直接调用、模型工具注册、DAG、Runtime、权限、取消和provider/model继承。不再新增 @workflow、call_workflow 或并行注册体系。

明确删除

  • 设计中的 @workflow、call_workflow() 和 invoke_workflow()。
  • Function calls_workflows sidecar和Workflow专用manifest。
  • workflow-projects/<id>/revisions/0001、project.json、active revision pointer和自定义revision分配器。
  • 零参数、禁止imports、单文件 workflow() 作为长期复用格式。

12. 公共入口验收

公共路径必须观察到的结果
直接调用一个 @agentic_function作为普通Python callable执行；模型工具调用与Python直接调用进入同一个现有wrapper。
Workflow A import Workflow BA使用正常import和函数调用获得B的返回值；没有 call_workflow 或字符串名称解析。
B的内部Goal函数调用 goal()内部 @agentic_function(as_tool=False) 节点位于B下面；每轮工作的执行主体是Agent，condition judge是内部步骤。
A → B → CDAG按Python嵌套调用显示父子关系；权限、取消、provider/model和working directory沿ambient Runtime继承。
同一Workflow接受两个任务使用同一代码入口和不同参数运行，首次任务文本没有写死在源码中。
agentic_workflow(task) 创建缺失能力生成独立Git仓库和多文件Python package，公开入口是现有 @agentic_function；内部可以选择 Goal、直接 Agent loop 或直接 llm()，并提供入口测试。
现有B/C可完成新任务只生成import B/C的编排项目；不复制B/C源码，也不创建新的调用协议。
仓库存在未提交修改本次执行使用固定commit快照；修改只在authoring worktree中验证后提交。
循环import或缺失包启动隔离worker前返回结构化错误，不开始模型或Agent调用。
父调用取消现有Runtime取消向所有嵌套 @agentic_function、agent() 和 goal() 传播。

13. 实现状态与迁移边界

能力状态说明
@agentic_function Python调用、工具注册、Runtime和DAG保留当前实现已经提供目标语义。
llm()、agent()、goal()保留agent() 支撑 Goal，Agent loop 依赖反复的单次模型调用；llm() 是该模型调用层的直接入口，并继续承担当前 condition judge 实现。
现有受限执行、checkpoint、权限、取消和Conclusion保留迁移不能改变这些公共行为。
自定义project catalog和revision目录移除由Git仓库和commits替代。
零参数单文件Workflow移除由接收参数的多文件Python package替代。
Workflow Git仓库扫描和commit快照待实现仅负责准备正常Python import环境。
跨Workflow静态import分析和隔离worker待实现用于依赖快照、循环检查和主进程隔离。
agentic_workflow 多文件author/reuse逻辑待实现使用现有 Goal、Agent 和单次模型调用能力创建、组合或修改项目。
迁移顺序必须保持概念边界：先让生成代码使用现有 @agentic_function、llm()、agent() 和 goal()；再建立Git项目与标准import；最后删除旧revision/catalog。整个过程不新增公开调用API。
