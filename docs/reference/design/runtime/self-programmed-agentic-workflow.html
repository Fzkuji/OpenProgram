Self-Programmed Agentic Workflow

agentic_workflow(task) 只有一个入口。每次调用都先检索已有 workflow project， 再由 planner 根据任务和候选项目决定直接复用、基于已有项目创建新修订，或创建新项目。 用户不选择“新建”或“继续”模式。workflow project 是可跨会话复用的多文件程序；workflow run 是一次执行及其固定代码快照、调用记录和终态。两者分别持久化。

1. 当前实现与已验证缺口

当前行为缺口目标
每次普通调用在 session 内创建 workflows/<run_id>/code.py。 代码属于运行，无法跨会话查找或维护。代码属于全局 workflow project；运行只保存项目修订的不可变快照。
以“continue / resume / 继续 / 接着”前缀猜测是否恢复最近一次运行。 任务文本承担控制协议，容易误选；相似新任务也无法复用已有程序。 所有新任务统一进入候选检索与 planner 决策；只有明确 run_id 恢复同一次中断运行。
planner 返回 SINGLE 或单个 Python code block。 复杂流程全部集中在一个文件，职责、测试和局部修订难以维护。 planner 返回一个有 manifest、README、入口文件和步骤文件的小项目。
运行失败后覆盖当前 code.py，旧文件按编号留档。 失败候选会先改变运行目录，项目没有稳定的可用修订。 候选先在 staging 校验并复制到 run snapshot；snapshot 执行成功后才发布项目 revision。

2. 参考框架比较

比较基于当前官方文档，不把这些框架的文件格式直接引入 OpenProgram。

参考采用调整不采用或缺失
LangGraph persistence 运行状态和可恢复 checkpoint 分开；已成功任务在恢复时不重复执行。 OpenProgram 保留现有调用边界 checkpoint，不引入 graph/super-step 数据模型。 其 checkpoint/store 解决执行状态，不负责搜索和版本化 agent 生成的多文件 workflow project。
GitHub reusable workflows 复用稳定定义，并让运行引用确定版本；可维护代码和运行记录分离。 OpenProgram 用本地目录和 revision，不用 YAML、仓库 ref 或远程分发。 GitHub Actions 不根据自然语言任务检索并修订 workflow，也不执行 LLM 生成的受限 Python。
OpenProgram @agentic_function / Runtime 继续使用现有函数注册表、DAG、调用 checkpoint、provider/model 和 Conclusion。 增加 project catalog 与多文件加载，不增加第二种运行时函数类型。 当前没有跨 session workflow catalog、稳定 revision 或项目级搜索。

文件稳定合同
project.json稳定 project_id、当前名称、任务摘要、tags、active revision。只含索引元数据，不含运行结果或秘密；这些搜索字段与 active revision 同一次发布。
revisions/*/README.md该 revision 的权威 README：适用任务、输入假设、产物与限制。project 根 README.md 只是 active README 的原子派生副本，搜索与修订读取不依赖该副本。
workflow.jsonschema version、项目文件加载顺序、入口文件与入口函数。路径必须是项目内相对路径。
entry.py只定义一个零参数 workflow() 入口；从共享 namespace 调用步骤函数和受管函数。
steps/*.py普通 helper function。按 manifest 顺序执行到同一个受限 namespace，首版不实现 Python import。
多文件不是任意 Python package。首版继续禁止 import，也不增加依赖管理和自定义 importer。 这保留现有受限执行边界，同时允许按职责拆文件。需要第三方包时由受管 function 提供能力，而不是由生成项目直接加载。

5. 搜索、选择和修订

候选检索

框架扫描合法 project.json，把任务和 name + summary + tags 规范化为 token， 按共有 token 数量排序并截取少量候选。检索不调用模型、不读运行结果、不执行项目。候选只缩小 planner 需要阅读的范围；零候选、低分候选和高分候选都交给同一 planner phase 1 决策。

planner 输出

phase 1 返回一个 JSON envelope：action 为 reuse、revise 或 create。reuse/revise 的 project_id 必须来自本次候选集合，revision 由框架读取该候选的 active pointer，模型不能指定；create 不接受模型指定的 id，框架根据名称 分配未占用 id，冲突时追加稳定短后缀，不能把 create 降级成 revise。reuse envelope 不含文件。

选择 revise 后，框架读取该 active revision 的 README、workflow manifest 和全部源码， 连同新任务交给 phase 2。选择 create 时 phase 2 没有基础源码。phase 2 和运行 repair 都必须返回 结构化对象 {project_metadata:{name,summary,tags}, readme, files}；files 是完整 Python 文件映射，不能只返回 diff。create 的搜索 metadata 由 phase 2 产生，project id 仍由框架分配；revise 可随 任务更新 metadata。README、metadata 与完整源码一起进入 run staging 和 snapshot。

修订发布

完整候选先写到 run 私有 staging，逐文件验证后复制到 run snapshot 并执行。执行成功后才在 catalog 锁内分配 revision，并在 catalog 根内建立临时 revision 目录；框架从 run snapshot 复制 README、manifest 与源码到该目录并再次校验，再在同一文件系统内原子 rename 到最终 revision。随后原子更新 project.json 的 metadata 与 active pointer，并原子刷新根 README 派生副本。run snapshot 始终保留且 字节不变。运行失败时 repair planner 必须接收失败 snapshot、结构化错误和 checkpoint 状态，修好的 完整候选重新校验并替换该 run 的 snapshot；旧 active revision 在整个过程中保持不变。失败、取消或 capped 都不发布 revision。reuse 始终不创建 revision。

6. 执行、恢复与兼容

  • 新任务总是创建新 run_id，即使复用同一 project；不同任务不会共享 checkpoint 结果。
  • run 开始执行前复制 project revision 到 snapshot/，随后只执行 snapshot。
  • 明确传入既有 run_id 时恢复该 run；不再根据自然语言前缀猜测恢复。
  • 恢复仍从 workflow() 第一行重跑，已完成且 key 一致的受管调用从 state.json 回放。
  • 旧 run 若只有 code.py，继续按单文件兼容路径恢复；它不自动发布到全局 project catalog。
  • SINGLE 作为旧 run 兼容格式保留；所有新任务即使只需一次 agent，也创建一个最小 project，避免不可复用分支。

7. 信任边界与失败处理

边界要求
路径project id、revision、manifest file 均拒绝绝对路径、..、重复文件和 symlink；只读取 catalog 根目录内文件。
代码每个 Python 文件先 AST 解析；禁止 import、class、async entry 与非白名单顶层语句；全项目只能有一个 workflow()。
信息catalog manifest 不记录 task 原文、调用参数、结果、错误正文或凭据；这些只保存在受现有策略约束的 run state。
取消KeyboardInterrupt / CancelledError 直接传播，不触发 planner 修订，也不发布候选 revision。
失败invalid plan 在 staging 内重写；执行异常生成新的 repair candidate 并替换 run snapshot；只有 candidate 执行成功后才发布 revision。达到真实调用上限后保持 capped，不再修订或发布。
并发catalog 根目录使用跨进程文件锁；revision 分配、目标不存在检查、catalog 临时 revision 目录 rename 与 active pointer 更新全部在锁内。run snapshot 不移动。进程内锁继续保护同一 run checkpoint，不同 run 的执行不持有 catalog 锁。

8. 明确不包含

  • 不增加向量数据库、embedding、远程 registry、Marketplace 或项目 UI 编辑器。
  • 不允许生成项目安装依赖、执行任意 import、访问 catalog 外路径。
  • 不把 workflow project 和用户聊天 Project、Skills、Programs 分类合并。
  • 不根据历史运行成功率自动决定复用；planner 必须看到候选元数据后明确给出 action。
  • 不改变 DAG、聊天折叠、Conclusion、provider/model 继承和 18100 单实例合同。

9. 公共入口验收

公共路径可观察结果
首次调用 agentic_workflow(task)创建 project revision 和独立 run snapshot；多文件 helper 被实际调用；发布后 run snapshot 字节不变并可恢复；结果带 project id/revision。
另一 session 调用语义相近任务planner prompt 收到已有候选；选择 reuse 时不生成新代码，仍创建新的 run 和 checkpoint。
相近但需要调整的任务phase 2 收到选中 active revision 的 README、manifest 与全部源码；发布同一 project 的新 revision，未要求修改的文件与旧 revision 一致，旧 run snapshot 字节不变且可恢复；搜索 metadata、revision README 与 active pointer 属于同一次发布。
无关任务同一入口创建新的 project，不依赖“新建”关键词。
非法 action / project 绑定reuse/revise 指向非候选 project或模型指定 revision时拒绝并重新规划；create 的名称产生已占用 id 时，框架在 catalog 锁内分配唯一短后缀，不覆盖已有 project，也不重新调用 planner。
项目校验或运行修复失败旧 active revision 仍可复用；非法路径、symlink、import 或无效入口都不改变 catalog。
取消或 capped不进入 repair planner，不发布候选 revision，不改变 active pointer。
两个进程并发修订同一 project得到不同 revision；两个目录完整，project.json 指向其中一个完整 revision且仍可读取。
resume_workflow(run_id) 或 Retry恢复指定 run snapshot，不重新搜索 project，也不切换到最新 revision。
旧单文件 run仍能恢复并完成；不会被错误加入新 catalog。
