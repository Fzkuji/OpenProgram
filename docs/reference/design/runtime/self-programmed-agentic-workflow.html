Self-Programmed Agentic Workflow

agent 自己把任务写成程序，再由自己执行：todo list 就是这个程序，list 是控制流， item 是有界子任务，每个 item 只带自己需要的上下文。目标是两件事：长任务的稳定性 （范围钉死、item 级重试、断点续跑）和 token 经济性（历史不随步数膨胀）。 入口是内置 agentic function run_task_list。

1. 全流程

2. item 级上下文用量

planner 给每个 item 标注上下文规格，落到现有的 render_range 机制上。 小 item 少看，大 item 多看，由 planner 在写 list 时决定，不在执行时猜。

3. 运行中修订 list

list 不是编译后冻结的静态 DAG。executor 回报"这个 item 需要拆分"或发现新工作时， planner 修订 list（拆分、插入、作废），修订记录在运行结果的 revisions 里（前后 item id 对照）， 之后的派发按新 list 走。

4. 与现有机制的归并

系统里已有两块同类机制，本设计不新建平行物，workflow 是它们之上的薄驱动层：

已有机制在 workflow 中的角色
todo planning board（functions/tools/todo/，session 级 todos.json， todo_create / todo_update / todo_list） 就是 list 本体。条目 schema 扩展三个可选字段：done_criteria（完成判据）、 context_spec（上下文规格）、result_summary（交接摘要）。存储读写全走现有 shared.py，旧条目兼容，现有 todo 展示界面直接可见 workflow 进度。
goal 判定（agent/goal/judge.py 的 evaluate_goal） 就是 item 的 judge。item 的 done_criteria 作为 goal payload 传入，不另写判定。 turn 级的 continuation loop（goal/loop.py）保持不动，item 级推进是独立的一层。
新增的只有薄驱动层：run_task_list 入口与规模判断、item 串行推进、修订逻辑 （走 todo_update）、交接摘要组装与长度上限、item 上下文规格到 render_range 的映射。

5. 边界与取舍

决定理由
默认串行执行共享可变的仓库状态下，并行是例外不是默认。第一版不做并行、不做自动依赖推断。
judge 复用现有 goal 判定单个压缩上下文 LLM 判定已定案，item 完成判据在规划时写好，判定时不重新发明标准。
小任务不拆planner 第一步做规模判断，单 agent 能一口气完成的直接执行。
交接摘要有长度上限摘要退化成转录就失去全部 token 收益；超限截断并要求 executor 给产物路径而不是内容。
重试预算：item 内 1 次，然后回 planner同样的失败重试第三次没有意义，回 planner 拆分或改判据才是修复路径。

部分落点
入口与规模判断run_task_list(task, session_id, resume, spawn_caller, agent_id)；planner 第一步答 split，false 时整个任务作为单个 item 直接执行
list 持久化就是会话的 todo 计划板（<session-repo>/todos.json），条目扩展 done_criteria、context_spec、result_summary 三个可选字段，读写全走 tools/todo/shared.py；没有第二份清单格式
断点续跑每次状态变化在动手之前写板；续跑按 owner + 任务文本认领自己的条目，任何 in_progress 都视为上次执行中断并重新获得完整两次尝试预算，completed 跳过
串行 loop_run_one_item 取下一个未完成条目 → executor（工具限定 EXECUTOR_TOOLS，输入=item+上游交接摘要）→ judge → 过则写 result_summary
judgejudge_item 调 openprogram.agent.goal.evaluate_goal（经包对象调用，符合 goal 包的 monkeypatch 约定），done_criteria 作为 goal 载荷；非 met 一律算未完成。turn 级的 goal/loop.py 是另一层，本模块不涉及
item 级上下文planner 写 context_spec.upstream，同一个数既决定交接摘要取几条，也经 render_range_for 映射为 {"callers": 0, "subcalls": upstream}
重试与修订item 内重试 1 次（把 judge 的理由回传给 executor），再不过回 planner 重写未跑部分；已完成条目的结果不动，每次修订记录前后 id
交接摘要上限HANDOFF_SUMMARY_MAX_CHARS=1200，超限截断并附一句"给产物路径不是内容"
修复合同：executor 的 render_range_for(item) 必须传入共享 run_agent_turn 边界，并由该 turn 内未显式声明范围的 agentic function 读取；使用 spawn subprocess 的 agentic tool 必须显式传递该范围，显式 decorator 范围仍优先。修订回复只有显式 JSON 数组 "items": [] 才表示放弃，缺字段或非数组均为无效回复，不得改写 board；驱动返回 error 并保留 in_progress checkpoint 供后续 resume。

未做：并行执行、自动依赖推断、token 收益量化对比——都等第一版跑通真实任务后再决定。 另外 MAX_ITEMS_EXECUTED=40 是运行上限，触到即以 capped 停止。
