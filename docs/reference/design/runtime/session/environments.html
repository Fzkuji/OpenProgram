Environments

The project decides which machine a conversation's shell and files are on: a project is a folder on one machine, and every conversation in it runs there.

This page covers what follows from that. Machines themselves, each with one connection method, are one registry, designed in Machines and targets. A channel (WeChat, Telegram, …) only decides where messages are mirrored. Product page: Run conversations on another machine.

The shell feature maps the connection methods commands run through in SHELLS (openprogram/host/backend/__init__.py): local, ssh and docker, each with its backend and, for Docker, instance_scope="conversation" and remove_instances. The device layer registers the methods ssh and docker (settings schema, check) in openprogram/host/machines/shells.py. backend_for(machine, session_id) builds the backend from the machine's method and names no method.

Targets of computer_use are a separate binding, chosen per call; being the environment never makes a machine the default target.

Turn binding

TurnBindings.bind sets the _current_environment ContextVar. current_environment() reads it first, then the current session's project's machine, then this computer when there is no session. get_active_backend(), beside it in openprogram.host.machines, builds the backend from that and the current session.

When the shell is not this computer's, the <environment> block names the machine by id, its name and what its method says of it, and that the chat and OpenProgram stay on this computer; with computer_use offered it adds that calls without device act on this computer.

  • A shell with remote_files (SSH): the worktree ContextVar is the project's folder on the host (remote_project_folder), so commands start there and the permission fence checks it too. The folder was made absolute on the host (cd then pwd -P) when the project was opened.
  • remote_workdir, the machine's remote folder setting, is only where browsing for a project folder starts. Relative tool paths join with posixpath and never touch this computer's filesystem.
SSH command options 
ssh -o BatchMode=yes -o StrictHostKeyChecking=accept-new
    -o ControlMaster=auto -o ControlPath=<state>/ssh/%C -o ControlPersist=300
    <target> 'cd <dir> && <cmd>'
  • Connection sharing keeps each tool call to one round trip after the first.
  • %C hashes host, port and user, keeping the socket under the macOS sun_path limit. ControlMaster is skipped on Windows.
  • A leading ~ reaches the remote shell unquoted so it expands there.
Docker container lifecycle
  • The conversation's instance: one long-lived container, container_name = openprogram-<machine>-<conversation> (characters outside [a-zA-Z0-9_.-] become -, at most 120), labelled openprogram.machine, openprogram.conversation and openprogram.home (a digest of the state directory, so two installations sharing one Docker tell their containers apart), started with docker run -d --init … tail -f /dev/null.
  • Working folder, project folder and additional working directories are bind-mounted at identical paths. The first mount is the starting folder.
  • A hash of image plus mounts is the openprogram.mounts label. Changed: remove and recreate. Matching: start a stopped container again. A per-process cache skips docker inspect after the first command; a spawned process does not trust it and checks the container each time.
  • When the daemon refuses a command because the container is gone ("No such container") or stopped ("is not running", after a Docker restart or docker stop), the cache entry is dropped, the container is started or created again and the command runs once more: nothing reached the old one. Only a refusal that starts Error response from daemon: counts.
  • A conversation's container is made only while its machine is configured and on. After the command is counted on the machine, and again before that retry, a machine switched off or removed since the backend was made refuses the command ("machine '<id>' was switched off" or "was removed"), and no container is created.
  • remove_instances finds this installation's containers by those labels, not by the machines configured now, and removes them in a background thread: by conversation when it is deleted, alone or by Clear all, whether or not it was opened since the worker started; by machine when the machine is removed, switched off or saved off.
  • For conversations it asks only the shells some configured machine's method uses, switched-off machines included, so nothing runs docker ps without a Docker machine. Clear all hands every deleted conversation to one thread, which takes them one after another.
  • Without a session ID the backend uses one-shot docker run --rm, as machines test does; it is not checked against the machine's state.
  • For a machine, remove_instances first lets running computer_use calls finish (up to registry.FINISH_SECONDS, 300 s), then waits for the commands counted on it (wait_idle, up to RELEASE_WAIT, 300 s); current_environment() refuses new ones meanwhile.
  • Counted are the run calls and spawned processes of its SSH and Docker backends, the supervisor of a background or supervised bash command for as long as it lives, and the check or creation of a container for a spawned process.
  • A machine configured and on again, checked before the release and after the wait, ends the removal, so its containers stay.
  • openprogram machines remove and disable remove a machine's containers before they return (wait=True). The CLI's process counts none of the worker's calls and commands, so they do not wait for them.

Remote file tools

read, write, edit, apply_patch, glob, grep and list call remote_target(). A machine whose shell kind has remote_files (SSH) gets a RemoteFS (host/machines/remote.py) and delegates to programs/tools/files/_remote.py, with the local tool's output format; results name the machine by id (devbox:/path).

Docker and local get None and stay local. A conversation whose machine cannot be used gets RefusedFS: every operation raises ConnectionError with the reason, so the tool reports it and never reads this computer's disk.

Implementation status

Implemented: the environment as a role over the machines registry, decided by the project; shells for the methods local, ssh and docker; openprogram machines, wizard step, Settings → Devices, WebSocket actions; remote file tools; per-conversation Docker containers removed by label.

Not implemented:

  • WSL and cloud environments
  • Password or interactive SSH sign-in
  • Checkpoint or undo for remote files; revert does not restore them
  • Moving a project to another machine
  • Waiting for supervised processes that outlived a worker restart before a removed or switched-off machine's instances go; after the restart they are not counted
