Worker memory

A Worker holds only what something is using. Everything below is read from files again when asked for, so letting it go loses nothing.

Held in memorySizeLet go

The Job runner's reconcile pass (_reconcile_loop) does the letting go; it runs at least once a minute (Change notification).

The restart pass

reconcile_interrupted_runs marks what a dead Worker left running. It reads a conversation whole, so it reads only the ones that can hold such work:

  • those with a log written since the last finished pass began: every node, run row and Goal state is a line of the session's logs;
  • those the last pass left with a run, a wait or an attached Job open, or could not lock;
  • those with an unfinished-run marker, or a row that says running.

A finished pass records its start and the open conversations in projects/.restart-reconciled.json. Without that file every conversation is read. Each one read leaves memory when its turn in the pass ends (passing_through).

The Worker log names each startup step that took 50 ms or more ([startup] … took N ms); requests wait for those steps.

An empty file logs/sample-threads asks for a thread sample: for half a minute the Worker notes the call each thread is in, and writes those calls and the processor time each thread used to logs/thread-sample.txt.

A thread listed at a call may be waiting there; its processor time says whether it worked. A request left before the Worker starts is taken as it starts.

Measurements behind this design
  • The restart pass read all 640 conversations and left them cached: 106 conversations held 260 MB after 45 seconds, and the Worker stayed near 950 MB. Reading them took it to 700 MB in its first seconds even when each was let go.
  • The catalogue took 26 MB as parsed; 10,021 models repeat a few hundred distinct values.
  • With 640 conversations and 15 open in the App, a Worker 45 seconds after start takes 130 MB, against 950 MB; its peak is 420 MB, against 1.8 GB. What remains is the open conversations: the App reads each one's resources, which reads the conversation and its run tables.
  • While the pass read every conversation, the first requests of a page took seconds (resources 3.9 s, enabled models 3.3 s); the same requests take 60–170 ms once it reads only changed ones.
  • Forcing a collection after each conversation did not lower the peak (351 MB against 366 MB over 106 conversations), so the pass reads fewer conversations instead.
