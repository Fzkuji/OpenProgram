Change notification

Nothing in the Worker or in a window looks again on a short timer to find out whether something changed. The code that makes a change says so once, and whoever waits on it wakes. A loop with a deadline sleeps until it. An idle Worker does almost nothing.

The hub

PartWhat it does
signal(topic, *keys)Called right after a change is written. Keys name what changed: a conversation, a job, a table. Costs nothing when nobody listens
listen, wait_forA loop waits for its topics, the next time it must act at (due), or a long resync. What was signalled while it was busy is kept
subscribeFor a loop that already waits on its own event: a callback on the signalling thread sets it
watchFiles written by another process (the CLI, a command's supervisor, the update controller, the user editing a skill). One thread takes the operating system's file events through watchfiles, which uvicorn[standard] already brings: 8 ms of processor time per 30 s idle, a change seen within about 0.7 s
process_exits.watch_process(pid, identity, topic, key)A command's supervisor or the update controller: its topic is signalled when it ends, through kqueue NOTE_EXIT on macOS, a pidfd in epoll on Linux, the process handle in WaitForMultipleObjects on Windows. One thread serves every process; a killed one is seen about 1 ms later on macOS. The process is held before its birth identity is compared, so a reused PID counts as ended at once. Without these, it is looked at every 10 s
publishForwards a topic to the windows as {"type": "changed", "topic", "keys"}, changes within 0.2 s in one frame

Threads and frames start only in the Worker (start_watching for file events and process exits, set_publisher). In the CLI and in tests a signal only wakes listeners, and a loop that relies on file events looks on its fallback interval (poll).

Some topics stay inside the Worker; they wake loops and are not sent to windows.

TopicSignalled when
turn_endedKeyed by session: a turn's cancellation token retires the first time, the server hands back a run slot, or the Worker begins shutting down (no key)
session.recordsA conversation's log makes a durable write; while a live run is watched, also a file event on the session's main.jsonl or agents/. Keyed by session
memory.checkpointA manual memory edit makes a history checkpoint pending
recordingsKeyed by recording id: a step is added, typing into a new element begins, or the recording stops. It drives the server-sent stream /api/recordings/{id}/events

subscribe_idle (run_control/idle.py) gathers what can end a conversation's busy state: turn_ended, runs, and run-table commits to executions or job_finalizations. Whatever holds something for a busy conversation waits on it.

Windows

useChanged(topics, refresh, keys) (apps/web/lib/net/ws/changes.ts) runs refresh when a frame for one of its topics and keys arrives.

  • A hidden window keeps the change and reads once when it shows.
  • After a reconnect every topic counts as changed: frames sent while the socket was down are lost.
  • A cached answer stays fresh until a topic says it changed: React Query answers never age (staleTime: Infinity), and QUERY_TOPICS invalidates them by topic.
  • Elapsed times, countdowns and "5 min ago" share one clock (below).

useNow(cadence, from) (apps/web/lib/clock/use-now.ts) is the one clock. The whole App keeps a single setTimeout, set for the earliest moment any shown text reads differently. It stops with no subscribers, pauses while the document is hidden and catches up when it shows.

Some views follow a source other than a topic:

  • A terminal view reads from its cursor when the desktop app pushes output (terminal:data) or the resource changes.
  • A web resource's thumbnail is taken after each Agent operation on its tab, not re-captured on a timer.
  • System-access recovery checks when the window shows or gets focus back; a grant made elsewhere closes the wait on the server (system_access.waits).
  • The recording bar reads a server-sent stream; provider sign-in asks with a request held up to 25 s until the sign-in changes.
  • The command page reads on its own op:execution-update; the sidebar project list and working-folder chips ask again when the socket opens.

Decisions

DecisionWhy
Announce changes; do not look for themOpenCode works this way: one bus inside the server, file events from the operating system, and a stream of events the client reads instead of polling. Looking every few seconds cost an idle Worker 2.5 s of processor time per 30 s and found nothing
Keep a long resyncA lost announcement must not leave work undone. Kubernetes controllers work from events and still list everything again on a long period; here 30 to 60 s for loops that hold a turn or a Job, 300 s elsewhere
Wait until a due timeDeadlines (a Job's budget, a durable wait expiring, a scheduled agent, a pending checkpoint, a credential's expiry, the recheck_in that channels and routing return) are known in advance; a loop or window sleeps until the earliest one instead of checking whether it has come
Operating system file events through watchfilesIt is already installed with the server, has wheels for macOS, Linux and Windows, and falls back to polling by itself where events cannot be had (WSL, some network drives)
A loop is not woken by its own writesA pass that writes would otherwise wake itself for ever
Folder metadata is not a changeThe self-update store chmods its folder on every write lock; counting that would wake the watchdog and the reconciler for nothing. A file made or changed inside a watched folder still counts
Liveness comes from the operating system, not from heartbeatsA heartbeat costs a write for a process's whole life and still leaves its death unseen until a staleness deadline passes (15 s for a supervisor, 30 s for the controller). The operating system knows the moment a process ends, as waitpid does for a parent; kqueue, pidfd and process handles give that to any process. A process says once who it is (pid and birth identity, in its record, controller.json or the .migrating marker) and writes nothing more
An exit, not a hangNone of the replaced heartbeats detected a hang: each was written by a timer thread of its own, which goes on beating while the work is stuck. A stuck controller or migration is bounded by its phase limits (MIGRATION_LIMIT_SECONDS, VERIFY_LIMIT_SECONDS), a stuck command by its own Stop
Busy waits wait on what ends themA notice, a queued message or a Goal's next turn held for a busy conversation wakes through subscribe_idle, not on an interval
A running command and its waiter ring each otherThe supervisor and the tool call waiting on it are separate processes, and a quick command must return in milliseconds, so file events (about 0.7 s, and only in the Worker) are too slow. Each supervisor listens on a loopback TCP port with a token in its record: the one local channel Python has on macOS, Linux and Windows alike. processes.db stays the record; a ring only says "look now", and its connection closing says the supervisor ended (command sessions)
Bursts are coalescedOutput streaming into a command's records or nodes written by a live run would wake a loop many times a second; the exit-notice loop looks at most every 2 s and the run tree pushes at most once a second. In windows, a gap only merges a burst of change frames into one read: READ_GAP_MS (execution debugger), GAP_MS (agent roster), CHANGE_SETTLE_MS (provider status)
Opening is the eventLocal model services announce nothing; the picker or providers page opening is when their state matters, so that is when they are probed, never in the background
Probe what announces nothing, only while it mattersThe operating system announces no permission grant, so the reconciler checks every 5 s only while a system-access wait is open

A program's own process writes session-resources.changed beside the database, and the Worker watches that file rather than the database, which it writes all the time itself. The Worker writes processes.db only when it delivers a notice or a supervisor ends, so that file is watched directly.

Timers that stay

TimerWhy
A launched controller's start windowAfter the watchdog launches a controller, it waits up to 30 s for controller.json before launching again; nothing announces a launch that produced no process
The fallback process lookEvery 10 s, only for a process the operating system cannot follow here
A stop's graceA stopped command's group has 5 s after SIGTERM before SIGKILL; nothing announces that a process ignores SIGTERM
A command group without exit eventsWhere neither kqueue nor pidfds exist (a Linux kernel before 5.3), group_guard lists its group every 0.1 s while a background child runs
Loop-stall watchIt asks the event loop to answer four times a second to notice a loop that stopped answering: a hang, which no exit announces. Idle, it costs 8.8 ms of processor time per 20 s. Timing only the loop's work, by wrapping its selector, would cost nothing idle but misses a loop woken yet waiting for the interpreter another thread holds, the case busy_threads names; the ping sees it
