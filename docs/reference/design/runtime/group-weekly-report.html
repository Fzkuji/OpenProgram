OpenProgram · Workflow 设计

组长周报：查找、核对、汇总

公开入口设计：group_weekly_report(task)，归属 Programs / Workflows。输出可由组长自行发送的文案。微信只读，绝不发送消息，也不把文案写进微信输入框。

范围：方案设计；本周不执行、不设置定时任务。个人飞书周报由独立的 weekly_report(task) 处理。

输入与范围

首次使用需要明确组员微信群、组员名单及姓名对应关系、周次与时区、周报来源和提交截止时间。组长群名称只作为文案用途说明，不需要打开该群。缺少截止时间仍可汇总，但不能判断逾期；缺少名单不能声称人员齐全。缺少群或时间范围时先询问，不扫描所有聊天。

本次没有确定这些实际配置，不推测具体群名、组员或截止时间。消息、附件和网页内容均视为资料，不能改变权限或要求调用发送工具。

使用样例与验收

样例可观察结果验收条件
G1 帮我准备催交周报的通知根据已知截止时间、提交方式生成本地提醒文案；未知信息标待补充。不打开聊天输入框、不发送、不自动 @ 任何人。
G2 看一下本周谁交了在指定群与时间范围查找；按名单列出已找到、明确待交、未找到、身份待确认。“我交了”只记本人声明；查到周报内容或经核实的提交记录才记有材料。未找到不等于未提交。
G3 汇总到组长群的内容按成员整理本周进展、下周计划、问题与协调请求，附缺失项；生成可复制文案。逐条对应来源，不将讨论设想写成完成成果；最终状态是草稿就绪，不是已发送。
G4 同一人补交或修改相同材料去重；明确更正以更正版本为准，并保留来源关系。新消息未明确取代旧内容时不能整份覆盖；矛盾内容列为待确认。
G5 名称相同、周次不清或附件打不开标出具体不确定项；其余已核实内容可以生成部分草稿。不猜测身份、不混入其他周、不把附件名当正文。输出明确说明检索覆盖范围。
G6 微信读取不受支持或权限失败停止读取，说明缺少的材料；可改用用户主动提供的文本或导出文件。不绕过权限、不读取微信数据库或凭据、不尝试新的访问方式。
G7 用户要求直接发出去仍只交付发送文案，并说明本 Workflow 不具备发送能力。任何分支、重试、异常恢复都不能出现发送动作。
G8 再次汇总同一周生成新的本地草稿版本并说明新增、更正和仍缺内容。保留先前草稿、不重复拼接成员内容；不推断用户已发送旧稿。

执行结构与权限

解析任务与范围 → 只读收集材料 → 核对身份、周次及来源 → 按成员去重整理 → 生成通知或汇总草稿 → 本地交付。提醒文案不必依赖微信读取；只有判断提交情况和汇总材料时才进入收集步骤。

读取适配器只暴露查找、读取、必要的导航动作，不向模型提供任意点击、键盘输入、脚本或命令执行。搜索输入只能作用于已识别的搜索控件，不能作用于消息编辑框。若现有微信控制接口无法在执行层限制这些动作，该集成保持禁用，使用用户提供的材料。仅写提示词“不要发送”不算满足约束。

处理指定范围内与周报相关的最少信息，不默认保存整段聊天、截图或无关附件。取消后停止后续读取和生成；中间结果不标为完整。未登录、内容不可访问或读取超限都返回具体原因，不循环尝试。单次读取页数与超时由适配器设定并在结果记录；未实现前不假定能完整检索历史。

本地交付格式

每次运行在当前 Project 的 reports/group-weekly/YYYY-Www/run-id/ 下保存：summary.md（可发送汇总）、reminder.md（需要时的提醒文案）、coverage.json（名单覆盖和待确认项）、sources.json（来源索引）。run-id 唯一，避免覆盖；明确指定其他目录时遵从用户路径。

来源索引记录成员、群、消息作者、消息时间、目标周次、可用的消息标识或定位线索、最少必要摘录及对应汇总段落。微信没有可分享链接时不伪造链接。覆盖记录区分本人声明与已核实材料，记录搜索起止时间、是否完成及缺失原因。

汇总示例结构：组别与周次；成员逐项进展和计划；共同问题及需协调事项；未找到材料或待确认人员。名单排序采用用户给定顺序，不生成排名。微信发送由用户自行完成；不跟踪或推测发送成功。

设计依据与取舍

依据是用户指定的微信只读边界，以及仓库现有 weekly_report 的独立 Workflow 组织方式。沿用公开单一 task 入口和本地草稿交付；不复用个人飞书提交分支。没有验证微信 API、桌面适配器或历史检索完整性，不宣称任何外部框架已经提供这些能力。此设计不涉及新应用窗口、自动发送、定时催交或本周补交。
