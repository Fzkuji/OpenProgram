Task list workflow

把任务的 todo list 直接构建为可执行的 agentic workflow：list 是控制流，item 是有界子任务， 每个 item 只带自己需要的上下文。目标是两件事：长任务的稳定性（范围钉死、item 级重试、断点续跑） 和 token 经济性（历史不随步数膨胀）。

1. 运行循环

入口是一个内置 agentic function run_task_list(task)，prompt 写在 docstring 里。 planner 第一步先做规模判断：预估单个 agent 能一口气做完的任务不拆，直接单 agent 执行—— 拆小任务的规划与交接开销会超过一次做完。

2. item 级上下文用量

planner 给每个 item 标注上下文规格，落到现有的 expose / render_range 机制上。 小 item 少看，大 item 多看，由 planner 在写 list 时决定，不在执行时猜。

3. 运行中修订 list

list 不是编译后冻结的静态 DAG。executor 回报"这个 item 需要拆分"或发现新工作时， planner 修订 list（拆分、插入、作废），修订本身作为 DAG 节点记录，之后的派发按新 list 走。

4. 边界与取舍

决定理由
默认串行执行共享可变的仓库状态下，并行是例外不是默认。第一版不做并行、不做自动依赖推断。
judge 复用现有 goal 判定单个压缩上下文 LLM 判定已定案，item 完成判据在规划时写好，判定时不重新发明标准。
小任务不拆planner 第一步做规模判断，单 agent 能一口气完成的直接执行。
交接摘要有长度上限摘要退化成转录就失去全部 token 收益；超限截断并要求 executor 给产物路径而不是内容。
重试预算：item 内 1 次，然后回 planner同样的失败重试第三次没有意义，回 planner 拆分或改判据才是修复路径。

实现状态

设计完成，第一版实现进行中：run_task_list 入口、list 持久化与断点续跑、串行 loop、 item 级上下文规格、judge 接线。并行执行、自动依赖推断、token 收益量化对比留待第一版跑通真实任务后决定。
