Conversation activity and execution control

Activity does not show an error during initial loading, reconnecting, or cursor resynchronization. A failure notice requires a confirmed request failure owned by the current conversation; changing conversations cannot display the previous conversation’s error. Actual failed reads retain saved records and automatic retries.

What is counted, what needs your attention, and what happens when you pause or stop a task.

Activity counts conversation branches. Sending another message on the same branch does not add another History item.

Branch details use a short branch heading and an execution count. The request appears only in its execution row. Declined waits are labelled Declined, and open waits are labelled Waiting for your response. Declining does not execute the pending operation. The durable checkpoint preserves the previously displayed text, reasoning blocks, and tool calls; the terminal projection publishes a session reload after saving the outcome.

Opening an existing execution store does not renumber historical events. Sequence backfill belongs to the migration that adds the sequence column; function subprocess startup must not hold a history-wide write transaction. Standalone function progress frames address the existing code node when there is no assistant caller, so the transcript receives internal steps before completion. Function completion releases foreground occupancy before optional model-generated session naming.

Recovery considers a resolved wait only while its checkpoint is still the execution’s current checkpoint. Outcomes from earlier questions cannot resume, fail or cancel a newer wait. Repeated recovery is idempotent. Regression coverage includes an answered first wait followed by an open or answered second wait. Implementation status: specification and quality reviews pass; controlled recovery tests cover sequential waits and repeated startup recovery.

Resuming the same turn

A resumed Agent run restores the same session, turn, reply, runtime and tool bindings as the initial entry, and releases them on completion, suspension or error. Browser page capabilities remain bound to the original owner; resuming never accepts another owner’s token. A browser rejection is an explicit tool error with its original reason preserved. Exhausting the configured iteration limit ends the run as unsuccessful, not Completed, while retaining its text and operation history.

Pending approval is shown near its owning assistant message only when the authoritative execution update identifies that message in the same session. The composer remains the decision surface. Missing ownership evidence never attaches another run’s decision to a message.

Acceptance covers a suspended and resumed public Agent entry, fresh browser discovery followed by observation with the returned token, binding cleanup on error, foreign-owner rejection, iteration exhaustion, and approval isolation between messages and sessions. Implementation status: specification and quality reviews pass. Controlled regression coverage verifies resumed browser capability ownership, explicit browser errors, binding release, iteration exhaustion as Failed, and message-scoped approval display. Default-App acceptance remains a separate release check.

History counts ended branches. The other sections list branches that still need attention or contain active work.

Ordinary branch status comes from its newest execution. Real waits, active descendants and owned processes are also checked. Missing records are never used to guess a new branch.

4. What each control does

ControlResultBoundary
PauseRequest a stop at the next safe point.The current action may finish first. It does not freeze an arbitrary line of code.
ContinueResume the same execution from saved progress.Available only when its saved state and capability permit it.
StepRun one declared step, then pause again.A step is a tool action or another declared boundary, not a source-code line.
SteerAdd instructions for work that has not run yet.Already completed work stays unchanged.
CancelEnd the selected execution and its execution descendants.Cannot undo external actions already completed. A managed process also has its own control.
Fork / RetryCreate an independent child execution from an allowed saved point.The original history stays. Agent chat children start paused and need Continue; other execution types follow their scheduler.

The UI offers only controls supported by that execution. A visible “accepted” response means the request was saved; “applied” means it took effect.

5. What survives a restart?

RecordPlain meaningWhy it matters
CheckpointSaved progress at a declared stopping point.Continue starts here; it does not restore a frozen thread.

Attempt ownershipWhich worker may currently update this execution.An old worker cannot overwrite a replacement worker’s state.
Engineering reference: identifiers and safety rules
IdentifierPurpose
session_idConversation scope and authorization; never a control target.
run_idGroups related original, fork and retry executions.
execution_idExact control target. Pause/Continue keep it; a fork or retry creates another.
attempt_idOne activation of a worker; resuming can create a new attempt.
revision_idAn immutable version of the program and its contract.
command_id + expected_versionPrevent duplicate actions and reject stale commands.
  • All transports use one command service. It saves the command before the owner applies it. UI state does not authorize an operation.
  • Cancellation takes precedence over pause, step/continue and steering. Only the current owner can publish progress or a final state.
  • Known model errors and aborts get response records. Unknown tool outcomes remain unresolved; the History label does not clear them.
  • Forks validate the saved point, immutable revision and permission. Changes to program, model or tool contracts retain independent review requirements.
  • Agent and background Job work share the same execution owner. For Jobs, job_id equals execution_id. Resource allocation stays separate from execution state.
  • Branch membership comes from the existing conversation graph and message IDs. Compaction retains earlier associations. The current stored project location is read before loading a session.
  • Reads and controls are restricted to the authorized conversation. Reconnect uses saved versions and event positions; it does not create a duplicate task.
  • Managed processes retain identity, ownership and bounded output. Restart recovery checks the supervisor; a saved PID alone is not permission to send a signal.

Limits: no arbitrary thread-stack restoration, automatic undo, or reconstruction of process records that were never saved. Runtime calls that ask questions inside an ordinary function still need a declared interaction boundary.
