Conversation activity and execution control

Activity does not show an error during initial loading, reconnecting, or cursor resynchronization. A failure notice requires a confirmed request failure owned by the current conversation; changing conversations cannot display the previous conversation’s error. Actual failed reads retain saved records and automatic retries.

What is counted, what needs your attention, and what happens when you pause or stop a task.

Activity counts conversation branches. Sending another message on the same branch does not add another History item.

Branch details use a short branch heading and an execution count. The request appears only in its execution row. Declined waits are labelled Declined, and open waits are labelled Waiting for your response. Declining does not execute the pending operation. The durable checkpoint preserves the previously displayed text, reasoning blocks, and tool calls; the terminal projection publishes a session reload after saving the outcome.

Opening an existing execution store does not renumber historical events. Sequence backfill belongs to the migration that adds the sequence column; function subprocess startup must not hold a history-wide write transaction. Standalone function progress frames address the existing code node when there is no assistant caller, so the transcript receives internal steps before completion. Function completion releases foreground occupancy before optional model-generated session naming.

Recovery considers a resolved wait only while its checkpoint is still the execution’s current checkpoint. Outcomes from earlier questions cannot resume, fail or cancel a newer wait. Repeated recovery is idempotent. Regression coverage includes an answered first wait followed by an open or answered second wait. Implementation status: specification and quality reviews pass; controlled recovery tests cover sequential waits and repeated startup recovery.

Resuming the same turn

A resumed Agent run restores the same session, turn, reply, runtime and tool bindings as the initial entry, and releases them on completion, suspension or error. Browser page capabilities remain bound to the original owner; resuming never accepts another owner’s token. A browser rejection is an explicit tool error with its original reason preserved. Exhausting the configured iteration limit ends the run as unsuccessful, not Completed, while retaining its text and operation history.

Pending approval is shown near its owning assistant message only when the authoritative execution update identifies that message in the same session. The composer remains the decision surface. Reconnecting or restoring pending questions requests the existing canonical execution replay; message ownership comes from the snapshot display metadata, with compatibility for older input envelopes. Missing ownership evidence never attaches another run’s decision to a message.

Acceptance covers a suspended and resumed public Agent entry, fresh browser discovery followed by observation with the returned token, binding cleanup on error, foreign-owner rejection, iteration exhaustion, and approval isolation between messages and sessions. Implementation status: specification and quality reviews pass. Controlled regression coverage verifies resumed browser capability ownership, explicit browser errors, binding release, iteration exhaustion as Failed, and message-scoped approval display. Default-App acceptance remains a separate release check.

Automatic continuation after interruption

Closing a conversation tab or disconnecting its view leaves worker-owned execution running. When the worker actually stops, its restart window defaults to 7200 seconds. The execution setting allows a different nonnegative duration; zero disables automatic restart. The interval is measured from the orderly shutdown intent or the abandoned attempt's last durable activity, not from the next startup. Restarting again does not extend an existing intent.

Agent provider decisions and completed tool actions publish their existing canonical checkpoint and effect receipt atomically during ordinary execution. Owner recovery can retain a compatible, current checkpoint as Paused. An orderly stop requests cooperative pause before process teardown. The original execution ID, immutable inputs, permissions, budgets and original continuation commands remain authoritative; queued Jobs use the existing resource queue.

Only a pause owned by restart recovery can resume automatically. User pause, cancellation, unanswered approval, unresolved external effects, stale checkpoints and incompatible runtime contracts remain explicit recovery states. A shutdown during an unconfirmed external operation cannot safely replay that operation. Expiry keeps the checkpoint for manual continuation and never deletes conversation data. Self-update maintenance still controls admission and verification.

Restart intents are canonical execution events, stored with the execution transition. Fixed command identities make repeated startup idempotent. No second execution database, scheduler, process owner or permission path is introduced. Acceptance covers ordinary checkpoint publication, restart within and beyond two hours, repeated startup, real foreground and queued Job continuation, explicit user pause/cancel, maintenance and uncertain effects.

Resume ownership records the exact inherited checkpoint; a second interruption before a new effect retains that checkpoint. Shutdown retries a racing checkpoint version at most three times within the same attempt and original deadline. Shutdown disables dispatch and restart reconciliation in the exiting runner before pause requests. New Jobs own stable user and assistant message IDs at admission, so resumed checkpoints validate against the same turn. Pause completion releases resources using the completed attempt and resource lease identities retained by the Job waiter.

Startup classifies abandoned ownership before the initialized runner applies the same bounded restart policy. Provider-only or never-activated chat admissions can continue from their immutable input within the original activity deadline. Unknown external tool results retain reconciliation-required state; recovery never fabricates a not-committed tool receipt. Legacy paused records without a restart intent require explicit continuation.

Self-update task continuation uses the same configured duration, measured from the completed update’s last persisted activity. Its fixed deadline and expiry are saved in the existing update directory. Resume, contract-repair planning and original-session follow-up all honor it. This does not stop an update that remains actively running for longer than the continuation window.

Function versions and durable continuation

Execution policy first selects keep_original or use_latest, with a global default and a persisted per-execution override. The default is keep_original. Relevant function and dependency identity, rather than an unrelated repository edit, determines whether code changed. A policy change is a version-fenced execution command and does not create a new call implicitly.

Manual function calls and functions invoked by an Agent share the function continuation mechanism. A manual call updates its original result record. An Agent-owned call returns its result to the original tool-call position before the Agent proceeds. The surrounding chat and the function retain distinct code and continuation identities. Delivering an already committed function result does not execute the function again.

A durable function records immutable source identity, dependency identity, input, completed step identities and results, the next safe position, serializable state, and outstanding effects. Original code must remain loadable; the implementation cannot label current code as an old revision. Switching to new code preserves completed results with their original provenance and validates the remaining continuation. State conversion and step correspondence must be explicit; ambiguous edits remain paused with specific differences. A missing source, unavailable dependency, nonserializable state or unsupported execution boundary cannot silently degrade to fresh execution.

Completed effects are reused. An in-flight step without a confirmed result remains unresolved unless its own protocol proves safe recovery. Cooperative pause stops at a persisted safe boundary; crash recovery uses the last durable boundary and fences the former owner. Nested calls retain parent identity, parallel branches retain separate progress, and a stored result awaiting handoff is delivered without re-execution. Repeated resume and a second crash cannot duplicate accepted effects.

The existing restart deadline applies to automatic continuation. Explicit cancellation, manual pause, unanswered approvals, permissions and resource admission retain authority. An incompatible use_latest selection does not fall back to keep_original or retry from the beginning. Retry remains a separate explicit new execution.

The implementation uses explicit synchronous step, nested workflow and named parallel boundaries. Pure orchestration reconstructs local JSON state from committed results. Existing execution events, blobs, checkpoints and the effect ledger own all durable data. A version-fenced Continue payload chooses policy. A compatible candidate becomes the retained active version before new work; later keep_original selections retain that adopted version. Imported dependency identity changes pause recovery if the retained dependency is unavailable. Native frames, asynchronous orchestration and live handles are outside this contract.

5. What survives a restart?

Automatic continuation of running conversations

Conversation execution records are persisted during normal operation. Each completed provider decision and tool result records the next action in the existing checkpoint and receipt transaction, without a pause command. Restart does not require a special save step or a graceful exit.

Startup claims abandoned running Agent executions once and activates the original execution, revision, turn and assistant reply from their durable input and latest continuation record. Manually paused, cancelling, cancelled and completed executions are not automatically continued. An interrupted model request can be regenerated from committed context; completed tools are skipped. An unresolved external operation is not blindly repeated and remains subject to result reconciliation. A missing first model response can restart from the existing admission input.

Closing or reconnecting the interface preserves the transcript. Worker interruption is not an assistant failure, does not append an error reply and does not introduce restart or recovery loading messages. Real provider and tool failures retain their existing presentation.

Acceptance uses isolated stores and controlled production entry points: resume with the same identities after owner loss, repeat startup without duplicate dispatch, recover before the first response, skip committed tools, preserve uncertain tool operations and user stop intent, and retain transcript content on reconnect. No live restart reproduction is required. Implementation status: implemented. Specification and quality reviews pass. Controlled verification covers repeated startup, original reply identity, complete provider context, committed tool coverage, and independent conversation controls. The full non-browser, non-live Python suite and Web, Desktop, documentation, and static checks pass.

  • All transports use one command service. It saves the command before the owner applies it. UI state does not authorize an operation.
  • Cancellation takes precedence over pause, step/continue and steering. Only the current owner can publish progress or a final state.
  • Known model errors and aborts get response records. Unknown tool outcomes remain unresolved; the History label does not clear them.
  • Forks validate the saved point, immutable revision and permission. Changes to program, model or tool contracts retain independent review requirements.
  • Agent and background Job work share the same execution owner. For Jobs, job_id equals execution_id. Resource allocation stays separate from execution state.
  • Branch membership comes from the existing conversation graph and message IDs. Compaction retains earlier associations. The current stored project location is read before loading a session.
  • Reads and controls are restricted to the authorized conversation. Reconnect uses saved versions and event positions; it does not create a duplicate task.
  • Managed processes retain identity, ownership and bounded output. Restart recovery checks the supervisor; a saved PID alone is not permission to send a signal.
