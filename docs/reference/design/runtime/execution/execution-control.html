1. 固定设计结论

所有运行控制都是对一个持久 Execution 提交命令。用户可以暂停、继续、执行一个安全步骤、调整未执行部分、取消，或从检查点创建新 revision。Runtime 先持久化命令，再由当前 attempt 的 owner 执行；界面只读取 canonical Execution Record 和事件，不推断运行状态。

同一控制对象

run_id → execution_id → attempt_id

会话负责归属，run 负责逻辑链，execution 绑定不可变 revision，attempt 表示一次物理激活。控制命令只接受精确 execution_id。

同一持久协议

command → event → materialized state

所有 transport 调用同一个命令服务。命令幂等，状态有版本，迟到响应不能覆盖新状态。

同一恢复模型

safe point + checkpoint + effect receipt

暂停和恢复只发生在声明过的安全边界。已确认副作用不重放，结果不确定的副作用必须先核对。

暂停不是冻结 Python 线程。Runtime 不保存任意指令地址、调用栈、锁状态或不可序列化对象。暂停请求在下一个 durable safe point 生效；继续从已发布的 checkpoint 恢复。这个边界同时支持跨进程恢复、server restart 和后续 revision 修改。

3. 能力与边界

正式能力

  • pause：目标执行子树到达安全点并发布 checkpoint。
  • continue：从当前 checkpoint 继续同一 execution。
  • step：只推进到下一个声明的安全点，然后再次 paused。
  • steer：调整未执行逻辑，不修改已提交历史。
  • cancel：终止目标执行子树，Runtime 必要时自动升级终止。
  • fork：从 checkpoint 与不可变 revision 创建 execution 分支。
  • retry：从失败或中断执行的合法 checkpoint 创建新 execution。

明确不提供

  • 通用 Python 源码行级暂停与恢复。
  • 保存线程栈、锁、socket、生成器或 provider stream 的内存快照。
  • 通用事务回滚或未知外部系统的自动撤销。
  • 客户端提交 PID、timeout、force、checkpoint 内容或 finalizer。
  • 按 session 猜测目标，或关闭页面时自动取消。
  • 对运行中的历史 revision 原地修改代码。
  • 由 UI 组合低层命令模拟正式能力。

6. Canonical Record 与命令记录

Runtime Store 保存 append-only events，并维护可按版本 compare-and-set 的 materialized record。DAG node、Job row、Workflow state、消息状态和 UI indicator 都只读取或投影该记录。

ExecutionRecord {
  execution_id, run_id, session_id,
  parent_execution_id, revision_id,
  status, status_version, reason_code,
  current_attempt_id, owner_lease,
  checkpoint_head_id, safe_point,
  active_child_ids, pending_command_ids,
  capabilities, effect_summary,
  created_at, updated_at, terminal_at
}

ControlCommand {
  command_id, execution_id, expected_version,
  kind, payload, actor, submitted_at,
  status: accepted | applying | applied | rejected,
  result_version, rejection_code
}
  • 每个状态变化产生 event；materialized record 可从 events 重建。
  • expected_version 防止旧页面覆盖新状态；重复 command_id 不重新执行。
  • terminal transition 只发生一次；late owner 只能附加审计事件，不能改终态。
  • Runtime Store 是唯一事实源；owner registry 只保存短期运行句柄。

7. 两层状态机

逻辑 Execution 与物理 Attempt 分开建模。用户看到 Execution 状态；worker lease、进程退出和恢复使用 Attempt 状态。

running：存在有效 attempt lease，owner 可以派发新 managed action；Runtime 在每个 safe point 检查待处理命令。

Attempt 状态

leased → active → checkpointing → ended。pause 可以在 checkpoint 发布后结束 attempt，也可以短暂保留 lease；这是调度策略，不改变 Execution 的 paused 语义。失去 lease 的 owner 无权写 checkpoint 或终态。

命令优先级固定：cancel > pause > step/continue > steer。已经持久化 cancel 后，continue、step 和 fork 拒绝；cancel 会解除 pause、question、approval 和 resource wait。

REST、WebSocket、CLI、TUI、ACP、MCP 和内部 Python 调用只是 transport adapter，共同调用 submit_execution_command(command)；任何 transport 都不得直接设置 token、event、DAG status 或 process signal。第 22 节 Job brief 只能复用这个 envelope，不得定义 Job 专属 wire shape。

所有 public command 的固定 envelope

所有 public command 均使用同一顶层 envelope、同一 authorization、同一 status lifecycle 和同一 snapshot/cursor 返回。payload 由 kind 的严格 schema 决定：pause/cancel 只允许固定 reason code；continue/step 为空；steer 是有上限的 SteerInputV1；fork 是已发布 RevisionManifestV1 的 ref、source checkpoint 和 prefix proof；retry 只允许 source checkpoint selection；wait answer/decline 只允许 wait ref、generation 与 answer ref。服务端拒绝多余字段、客户端 actor/project/session/attempt/generation/lease/capability/checkpoint content，以及未发布 revision 的内嵌内容。

ExecutionCommandRequestV1 {
  type: "execution.command", action: CommandKind,
  command_id, execution_id, expected_version, payload
}
ExecutionCommandUpdateV1 {
  command: {command_id, execution_id, kind,
            status: accepted | applying | applied | rejected,
            result_version, rejection_code, result_ref},
  execution: ExecutionSnapshot, event_cursor: EventCursor
}

accepted 只表示 intent、actor 和 validation decision 已持久化；applying 表示 command 已被一个 fenced owner、wait claim 或 revision transaction 领取；只有 safe-point transaction、activation transaction、wait outcome transaction 或 fork transaction 完成后才为 applied。每个 rejection 返回稳定 code 和当前授权可见 snapshot。重复 command id 必须逐字段匹配 execution、kind、payload hash 和 actor binding，才返回原结果；否则为 idempotency_collision。cancel 高于 pause，高于 continue/step/wait outcome，高于 steer；cancel 后所有较低优先级的未应用 command 以明确 superseded code 结束。steer/fork/retry 与 pause/continue/step/cancel 不存在第二种 wire shape 或旧 action alias。

9. 安全点与单步单位

safe point 表示此前工作已提交、此后工作尚未派发。每个 Execution Driver 声明边界与能力；没有 checkpoint 能力的 owner 可以 cancel，但不能声称支持 pause/continue。

类型合法 safe point一个 step
Chat / agent loopprovider 请求前；完整响应提交后；tool dispatch 前；tool result 持久化后。一次 provider decision 或一次 tool action。
Workflow稳定 step_id 前后；branch join；显式 checkpoint。一个确定 step 或控制流节点。
后台 Job领取任务前；durable item 完成后；batch 边界。一个 item 或声明 batch。
Tool / subprocessdispatch 前；带 receipt 的完成后。一个完整 invocation。
Question / approval请求已持久化且尚未 resolved。接收并提交一个 answer/decision。
Child executionadmission 前；child terminal 或 paused 后。创建并等待 child 到下一个 durable boundary。
  1. pause intent 持久化后立即关闭目标子树 admission gate。
  2. 已 dispatch 的 provider/tool/child action 继续到结果、超时或 cancel；Runtime 不伪造中间结果。
  3. owner 到达边界时提交 checkpoint fragment 和 effect receipts。
  4. 所有活动后代确认后，根状态从 pausing 进入 paused。
  5. step 只发一个 permit；涉及 child 时覆盖到 child 的下一个 durable boundary。

10. Checkpoint Manifest

Checkpoint 是不可变内容对象。Runtime 先写 payload 与 blobs，验证 hash 和 schema，最后 compare-and-set 更新 checkpoint_head_id；未发布对象由 GC 清理，不能用于恢复。

CheckpointManifest {
  checkpoint_id, execution_id, revision_id,
  parent_checkpoint_id, status_version,
  frontier: [{step_id, phase, branch_id}],
  completed_frontier: [{step_id, contract_hash}],
  program_state_ref, conversation_state_ref,
  completed_actions: [{action_id, input_hash, result_ref}],
  effect_receipts: [{effect_id, classification, receipt_ref, outcome}],
  child_frontier, pending_commands,
  schema_version, created_by_attempt_id, content_hash
}

必须包含

revision、稳定 frontier、可序列化 Program state、已完成 action receipt、子执行关系、待处理 durable command、schema 和 content hash。

不包含

线程栈、mutex、PID、socket、provider stream object、任意闭包、未提交局部变量或原进程对象地址。

现有 mutation journal、Workflow checkpoint 和 DAG history 作为 manifest fragment 或 projection 接入，不再分别定义“resume 已完成了什么”。

12. 调整后续逻辑与从检查点分支

Steer：同 revision 的输入调整

补充约束、改变下一步优先级或提供新上下文。命令在 safe point 应用；如果会改变已完成 step contract，owner 拒绝并要求 fork。

Fork：新 revision 的结构调整

修改 workflow graph、后续代码、工具集合、model policy 或输出 schema。先暂停，选择 checkpoint，创建不可变 revision，再创建同一 run_id 下的新 child execution。

Fork 校验

  1. 源 checkpoint 已发布且没有 unresolved effect。
  2. 新 revision 声明 compatible_prefix：完成的 step_id、输入/输出 schema、effect contract 和依赖 hash。
  3. 一致的完成前缀可复用；受影响 step 从更早 checkpoint 重新执行。
  4. 新 execution 记录 parent、forked checkpoint 与新 revision；原 execution 保持 paused 或原 terminal。
  5. UI 同时显示两个分支，不把新结果写回原 execution。
未来可以增加源代码断点、条件断点、step in/out 和变量修改，但它们只能作为特定 Driver capability。基础协议的 identity、command、safe point、checkpoint 和 revision 边界不改变。

12.1 RevisionDraft、验证、审批与 fork transaction

“修改后续逻辑”不是向运行 owner 发送源码或任意 JSON。它先创建不可执行的 RevisionDraftV1，再验证、审批、发布不可变 RevisionManifestV1，最后由 execution.fork 从精确 checkpoint 创建 child execution。draft 从不改变 source execution、working directory、当前 revision 或已发布 checkpoint。

RevisionDraftV1 {
  draft_id, project_id, source_execution_id,
  base_revision_id, base_revision_hash, source_checkpoint_id,
  project_binding: {project_id, worktree_id, root_identity, source_commit},
  changes: [{kind: workflow | prompt | tool_contract | model_policy |
                    output_schema | program_artifact,
             target, before_hash, after_ref, rationale}],
  frontier_mapping: [{old_step_id, new_step_id | null,
                      relation: preserved | replaced | split | merged | removed,
                      old_contract_hash, new_contract_hash | null}],
  requested_by, created_at, draft_version
}
RevisionManifestV1 {
  revision_id, parent_revision_id, content_hash,
  program_artifact_ref, resolved_runtime_contract_ref,
  project_binding, frontier_mapping, compatible_prefix_proof,
  validation_report_ref, approval_ref, created_by, published_at
}

每个 after_ref 是内容寻址、大小受限、schema-versioned 的受控 blob 或已解析的 project artifact；revision 固定其 hash、project binding、源码提交/工作区 identity、完整 model/system/tool contract、permission rules 和 output schema。继续或 fork 时只读取这些 immutable refs，不重新从可变 session、当前磁盘、provider 默认值或 UI draft 推断逻辑。

稳定 frontier 与 prefix proof

frontier_mapping 是有向、按 execution frontier 顺序编号的映射，不是按 step_id 字典序排序的集合。验证器从 source checkpoint 的实际 branch/frontier、join 和 completed action trace 构造 compatible_prefix_proof；proof 必须逐项包含 branch path、old/new step id、contract hash、input/output schema hash、dependency hash、effect contract hash 和 reuse decision。只要一个已完成 action 的 contract、依赖、effect classification、输入 schema 或 branch path 改变，该 action 及其所有依赖后继都不可复用；fork 选择该影响范围之前最近的合法 checkpoint。没有 proof、proof 与 source frontier 不一致、存在 unresolved effect、或新 runtime contract 不可解析时 fork rejected，不能以“看起来未改动”复用结果。

验证、审批与原子提交

  1. 验证器以 draft 的 base revision/hash 和 source checkpoint 为输入，执行 schema、frontier mapping、contract compatibility、policy、artifact availability、effect boundary 和 project binding 检查，写 immutable validation report；验证不能执行新业务 action。
  2. 审批以精确 draft version、validation report hash、project binding 和 policy version 为对象。需要审批的工具权限、model/provider 变化、output schema 变化或 program artifact 变化，不允许由 draft 作者隐式批准。
  3. execution.fork 在一个 canonical transaction 中重新验证 authorization、source status/version、checkpoint、proof、manifest、approval 和 effect ledger，写 revision、child execution、immutable child input/runtime contract、branch/audit event 和 projection outbox。任一项失败不创建 child。
  4. fork 后 source execution 保持 paused 或原 terminal；child 使用新 revision/new immutable input，并仅从 proof 指定的 checkpoint frontier 恢复。它不能写回 source 的 checkpoint、messages、effects、Job row 或 DAG lifecycle。

draft 可被修改或废弃，但已发布 manifest、validation report、approval 和 fork receipt 不可修改。UI 可以显示 diff 和验证结果；它不能直接提交 program artifact、兼容前缀或审批结果。

13. Runtime Control Service 与 Execution Driver

protocol ExecutionDriver:
    capabilities() -> CapabilitySet
    activate(attempt, activation) -> DriverHandle
    request_pause(handle, command_id) -> Ack
    request_cancel(handle, command_id) -> Ack
    inspect(handle) -> RuntimeSnapshot

runtime.arrive_safe_point(attempt_id, manifest_fragment, effect_receipts)

activation 是独立的 ActivationInput，包含原始、不可变且可验证的 CheckpointManifest，以及按 submitted_at, command_id 排序的 durable pending steer inputs。Driver 不得把 steer 临时写入 checkpoint 或修改 checkpoint 的 content_hash；后续 safe point 负责发布包含实际输入的下一份 checkpoint 和 applied receipt。

  • Control Service 唯一负责授权、状态 CAS、命令优先级、父子传播、fencing、recovery 和 terminal finalization。
  • Driver 负责执行类型特有的协作信号、checkpoint fragment、inspect 数据和受控 terminate。
  • canonical CapabilitySet 只序列化 pause、step、steer、fork、retry、safe_point_kinds 和 state_schema_version；continue 由 pause capability 加上 paused checkpoint/initial-handoff 状态推导，cancel 普遍可用且不在 set 中。
  • Driver 不直接写 canonical status；projection failure 进入可重试 outbox。

公开 Agent 入口切换

ACP、Channels、MCP prompt service、scheduler prompt、Web chat/query（包括 /spawn 与 /merge）、REST fn-form 和 WS retry_function 都是同一公开 Agent admission 边界。入口先验证 strict version-1 bounded payload，在 ExecutionStore 的一个 transaction 中创建 revision、immutable input、queued execution 和 projection outbox；ResourceGovernor 的 reservation 位于另一 SQLite authority，二者通过 durable saga/outbox 对账，不能声称跨库原子。用户/DAG 内容与 chat_ack 只在 admission saga 达到可发布阶段后写入或发送。ack、running task、question 和取消都携带该精确 execution_id；msg_id 只保留为消息与传输关联，不能生成 ownership，也不能以 msg_id_reply 代替 execution identity。

阶段公开可见结果失败处理
Admissionqueued execution、immutable TurnRequest payload 和 input message IDs 已提交。不发送 ack，不创建运行中任务；输入或 revision 无效时返回明确 admission 错误。

14. Cancel 算法

01 · COMMIT

持久化 intent

授权 exact execution，按版本写 cancelling，关闭目标子树 admission gate，记录 reason。任何信号都不能早于此步。

Gate: durable command + canonical cancelling
02 · PROPAGATE

固定后代集合并传播

对非终态后代写 cancel intent；竞态创建的 child 因祖先 gate 关闭而拒绝 admission。

Gate: no child escapes the subtree
03 · COOPERATE

请求 owner 协作结束

中止 provider stream、取消 async task、解除 question/approval/resource wait，并通知所有 Driver。

Gate: every live owner receives one exact request
04 · ESCALATE

宽限后自动终止

对仍持有相同 fenced lease 的 owner 执行 terminate。用户不提交第二个命令，不传 force 或 timeout。

Gate: ownership rechecked immediately before terminate
05 · FINALIZE

控制面写唯一终态

完成 usage、resource、question、checkpoint 和 projection finalization。已 terminal child 保持原状态；因父级终止的 child 记录 parent_cancelled。

Gate: no active owner; terminal compare-and-set
cancel 不等于 rollback。已提交消息、文件 mutation、tool result、usage、checkpoint 和外部 receipt 保留。Program 可提交显式 compensation，但 cancel 本身不撤销历史。

15. Restart 与 owner 丢失恢复

  1. 启动时扫描所有非终态 Execution Record、未完成 ControlCommand 和 finish repair intent。
  2. 使旧 owner lease 过期并增加 fencing generation；旧进程迟到写入拒绝。
  3. queued 或 paused 若遗留尚未 activate 的 leased attempt，结束并 fencing 旧 attempt、清除 owner，同时保持逻辑状态，使新 owner 可以重新 lease。
  4. 带 immutable Agent input 但没有 attempt 的 admission 是启动前崩溃窗口，恢复时以 owner_lost_before_activation 明确转为 failed，不永久保留 queued。
  5. Agent admission 在同一 execution DB transaction 中预留 bounded finish-repair slot；slot 是容量预留，不表示 execution 需要 reconciliation。slot 在 terminal finish、stale/terminal GC 和未激活 admission recovery 时释放。finish repair 按稳定的 created_at, execution_id, attempt_id, generation keyset 分页反复读取，并按当前 execution/attempt fence replay；成功、terminal 或 stale 项删除 repair row，避免遗漏或无界积累。只有实际 finish repair row、slot 的 repair 状态或容量迁移溢出项进入 repair reconciliation；actionable repair 始终先持久化，高水位只拒绝新的 canonical Agent admission，不删除已有 intent。
  6. 标记为 finish_repair_stalled 的项目不会被普通 owner-loss 改写；持久化的 retry_count 与 next_attempt_at 由 startup 和单一低频 reconciler 按到期时间继续领取，成功后清理 repair row。
  7. cancelling 继续 cancel finalization，不恢复业务逻辑。
  8. 任何状态存在 dispatched 或 uncertain effect 时先进入 reconciliation_required；checkpoint 不能覆盖该判断。
  9. pausing 在 effect 已解决且存在已发布 checkpoint 时转 paused；没有合法 checkpoint 时转 interrupted。
  10. paused 保持 paused，不自动创建 attempt。
  11. running 只有 Driver 可恢复、checkpoint 合法且无 uncertain effect 时创建新 attempt，否则 interrupted 或 reconciliation_required。
  12. 唯一 startup entrypoint 先完成 canonical recovery，再 reclaim outbox leases，最后由已有 consumer replay；没有 consumer 的项目保持 pending。
  13. projection outbox 重放到 DAG、Job、Workflow 和 UI；projection 不能反向覆盖 canonical record。
Question 和 approval 的 durable resource 与 execution checkpoint 一起恢复。未解决 wait 不由 restart 自动回答；它保持 execution 的可见等待状态，直到 authorized answer、decline、timeout 或 cancel 写入唯一 outcome。

Durable Question / Approval Wait

Question 和 approval 是 execution-owned durable resource，不是 session inbox、WebSocket future 或进程内 callback。WaitRecordV1 固定 wait_id, execution_id, attempt_id, generation, checkpoint_id, kind, request_ref, request_hash, policy_snapshot_ref, status, claim_generation, answer_ref, created_at, expires_at；唯一的可恢复 opening API 在一个 transaction 内发布 checkpoint、请求和 paused frontier，并结束原 attempt。合法状态为 open → claimed → resolved | declined | expired | cancelled。一个 wait 的 outcome 只能由一个 claim generation 提交，重复 answer command 返回同一 outcome，旧 owner、旧连接和过期 claim 不能覆盖它。

answer/decline 也是 execution.command 的严格 kind：携带 wait id、expected wait generation 和有上限 answer ref；服务端从 execution/project/session authorization 取得 actor，按 policy snapshot 验证，再写唯一 outcome。on_answer、on_decline 和 on_timeout 只能选择 continue、fail 或 cancel；continue 创建确定的内部 continuation command，重新领取资源和 attempt，并只读取 wait 记录的 checkpoint。cancel 优先将 open/claimed waits 收敛为 cancelled。

可恢复的 Runtime interaction 必须由工具在 dispatch 前提供 version-1 interaction manifest。manifest 固定 kind、展示请求、request metadata、timeout 与三种 outcome policy；Agent loop 在 agent.wait.before_tool 将其交给 safe-point transaction。恢复的 tool 调用只可读取同一 wait 的已 resolved answer，并逐字段验证 kind 与展示请求。任意 Python 函数在已开始运行后第一次调用 runtime.ask、ask_many、confirm 或 form 而没有该 manifest 时，执行以 runtime_interaction_requires_safe_point 失败；系统不保存栈、不重新执行已开始的 tool，也不创建普通 wait。

restart 先 fencing attempt，再 reclaim 已过期 wait claim；open wait 保持 open 并重新投影给 authorized surfaces，不依赖原订阅。claimed 但无有效 owner 的 wait 退回 open；已经提交 outcome 的 recovery 扫描只处理 paused execution，因此重复扫描不会创建第二个 attempt 或重放已完成 effect。execution paused 后的 Job resource release 通过 ResourceSaga 持久化；继续前必须重新 claim。等待不占 active runtime 计时；wall deadline 仍由 wait expiry 与 policy snapshot 约束，超时生成 durable expired outcome，不由 UI 本地 timer 决定。

Revision 与 command 的恢复

draft、validation、approval、published manifest 和 fork transaction 都有 durable status 与 recovery owner。未发布 draft 在重启后保持 draft；validation/approval claim 丢失后以其 generation fencing 并可重取；已发布但未 fork 的 manifest 不自动执行；fork transaction 在启动时按 command id 重放或完成为 rejected，绝不创建第二个 child。accepted steer 在 owner 丢失后保持原 command 和 payload ref；新 attempt 依 submitted_at, command_id 读取，只有在新的 safe point 写入 applied/rejected receipt。manifest、approval、project binding、checkpoint blob 或 runtime contract 任一不可解析时，execution 进入 reconciliation_required 或 command rejected with stable code，不能回退到当前磁盘或默认配置。

17. 权限、审计与资源

  • 服务端从 Execution Record 解析 session、owner、revision 和 process handle；客户端字段不能替代记录。
  • 未授权或跨租户 execution 返回统一 not found，避免泄露存在性、状态和输出。
  • command event 记录 actor、surface、reason、expected version、结果和 receipts，但不记录秘密、完整 prompt 或环境变量。
  • paused execution 默认释放 worker slot、GPU/CPU admission 和并发配额；只保留声明过的 durable storage 与外部 lease。
  • pause 期间 timeout、预算和外部租约是否继续由资源类型声明；UI 显示 policy，Runtime 不隐式补时。
  • 强制终止只针对 registry 解析的 fenced process group；不接受客户端 PID 或路径。

Session policy 与 Execution command 分离

attended 是 session 级 capability policy，不是 execution lifecycle。所有 surface 通过同一 session.policy.update 写持久 session metadata；新 execution 在 admission 时得到 policy snapshot。attended=false 表示工具目录不提供 ask/clarify 能力，但不能暂停、取消或改变已经运行的 execution。需要改变活动 execution 时，仍提交精确的 execution command。

三端同步使用同一规则：连接先读取 session、active execution 和 pending command 快照，再从 event cursor 继续；任何 surface 都不保存独立的 attended、running、paused 或 steering truth。

Public Agent entry contract

Every public Agent turn enters through the transport-neutral canonical adapter. The real public WebSocket chat entry is apps/server/openprogram_server/_webui/ws_actions/chat.py::handle_chat; it constructs a bounded TurnRequest, calls CanonicalAgentAdapter.admit, and sends chat_ack only after admission returns the random execution_id. ACP, Channels, MCP prompt service, scheduler prompts, web query, /spawn, /merge, fn-form, and retry use the same boundary. Each first constructs a strict version-1 bounded payload with kind=chat or kind=forced_tool, admits it, and only then persists user/DAG content or acknowledges the request. Message and DAG identifiers are provenance only.

The adapter leases and activates the exact attempt generation. The Agent driver reconstructs TurnRequest or ForcedToolActivation, and the driver alone records completion, failure, or cancellation through Control Service. Startup failures after admission are terminalized for that same execution. Forced-tool dispatch receives the exact execution, attempt, generation, and cancellation binding. No public entry derives ownership from msg_id, claims a run_control token, or falls back to a legacy finalizer. Global pause/resume and session stop routes are removed; WS/TUI steer requests return unsupported_capability. The P0 Agent driver will expose pause, continue (derived from pause plus checkpoint/initial handoff), and step for ordinary chat after the two durable safe points are available; the serialized CapabilitySet has only pause/step/steer/fork/retry/safe-point/state-schema fields, while cancellation is universal and outside the set. Durable question/approval wait persistence and restart subscription are a later independent slice and do not block those P0 capabilities. Forced-tool, spawn, and merge remain cancel-only.

21. Agent durable safe point / checkpoint implementation brief

下一独立切片只为 Agent driver 接入 durable safe point。它沿用已经集成的 canonical Agent admission 与 exact cancel；不修改 public WS chat 入口的 identity 合同，不给 Job 打开 pause，也不新增第二套 dispatcher、checkpoint 或 control API。P0 只支持两类可验证边界：agent.provider.decision.after 和 agent.tool.action.after。

Safe-point 单位

safe point kind进入与离开条件step 消费单位

Agent 不保存任意 Python 指令地址、调用栈、线程、锁、生成器、async task、provider stream、闭包、PID、socket 或对象地址。暂停只在上述边界生效；continue/step 由 checkpoint frontier 重新激活新的 attempt，不能依赖原进程的内存状态。phase 只有 after_provider 与 after_tool；frontier 只在对应 terminal receipt 与 state blob 同一事务提交后推进。

Admission capability 分流

Capability 由 admitted payload 与 interaction 决定，不由 transport 或 message id 推断。普通 kind=chat 且没有 spawn/merge interaction 的 Agent turn 获得 pause、step 和上述两类 safe point；kind=forced_tool、spawn 和 merge 只获得 cancel，避免在没有完整 Agent loop checkpoint 时被 pause 卡住。所有类型仍获得 exact cancel；WS ack、running task 和 command 均继续使用 admission 返回的随机 execution_id。

同库 content-addressed blobs

使用同一 execution SQLite 的 execution_state_blobs 表保存 canonical UTF-8 JSON 或受允许的二进制 payload。ref 格式固定为 execstate://sha256/<64 lowercase hex>；hash 覆盖 canonical bytes，写入时校验 byte length、media type 和 schema version。blob 由 execution_id 拥有；跨 execution 复用必须在 fork transaction 中复制 ownership。

固定上限与拒绝

MAX_AGENT_CHECKPOINT_BYTES=262144、MAX_AGENT_STATE_BLOB_BYTES=1048576、MAX_AGENT_STATE_REFS=32、MAX_AGENT_PENDING_MESSAGES=64、MAX_AGENT_TERMINAL_EFFECT_RECEIPTS=64、MAX_AGENT_DELTA_BYTES=65536、MAX_AGENT_REPEAT_FAILURES=16。拒绝码为 checkpoint_too_large、state_blob_too_large、state_ref_limit、state_ref_invalid、checkpoint_schema_invalid；pause 遇到上限失败时 fail closed 为 interrupted，不截断继续。

execution_state_blobs 的 owner、manifest/effect/message 引用和 terminal GC 在同一 execution SQLite transaction 中维护：未发布对象只能由创建 attempt 清理；已发布 checkpoint、terminal effect receipt 和 pending message 引用的 blob 不得清理；execution terminal 且无任何引用后才可 GC。GC 不跨 execution 删除，也不依据内存 registry 判断 ownership。

action/step id 必须由内容稳定生成：provider action 为 sha256(revision_id + parent_checkpoint_id + normalized_context_hash + resolved_model_hash)；tool action 为 sha256(revision_id + provider_action_id + tool_call_id + normalized_args_hash)。step_id 包含 action kind 与该 digest，重启、重复事件和相同输入得到相同 id；frontier 从 after_provider 推进到 after_tool 时只接受对应 action 的 terminal commit。

turn 是 durable conversation branch anchor：user_message_id、assistant_message_id 和 base_history_head_id 必须能在同一 execution store 解析；current_decision 必须能解析为当前 provider action、assistant message ref 和有序 tool call IDs。resume carrier 是新的 ActivationInput，携带 immutable input、已发布 checkpoint manifest ref 和 pending command refs；safe-pause sentinel 使 Agent loop 直接从 checkpoint frontier 进入对应 after-provider/after-tool continuation，绕过 normal prepare、placeholder 和 finalize 路径。resume 不重写 user/placeholder/finalize message，不重新发送已 receipt 的 provider request，也不重复已经完成的 node。

resolved_model_system_tool_snapshot_ref 指向版本化 immutable runtime contract：model 必须包含完整 id、api、provider、base_url/endpoint 和影响请求语义的配置；每个 tool 必须包含完整名称与 JSON Schema、permission/approval 规则以及稳定的 runtime implementation descriptor；contract 同时固定 system prompt、structured-output 配置、toolset 和 request semantics。continue/step 在新 owner 绑定前从当前 durable revision 精确解析并逐字段比较；无法解析或任一字段变化均以 continuation_contract_mismatch 拒绝，保留原 paused checkpoint，且不得派发 provider 或 tool。

22. Job durable control：最终设计与实施 brief

Background Agent Job 是一种 Agent execution。一个 Job 只有一个 canonical execution，且 job_id == execution_id。ResourceGovernor 只负责 admission、queue、resource reservation 和 lease claim/release；claim 成功后由 AgentProductionDriver 在同一个 execution、attempt 和 generation 上运行。不存在 outer JobDriver lifecycle owner，也不存在 Job 路径内部生成的第二个随机 exec_* identity。

本节是 Job 控制实现的最终 brief。它复用本页已定义的 Execution command、AgentCheckpointV1、provider/tool safe point、effect receipt、activator、fence、immutable input/runtime contract 和 projection 规则。Job 不建立第二套 pause、resume、step、cancel、checkpoint 或资源协议。

22.5 Job 状态、pause/continue/step 与资源 lease

用户观察的是 canonical Execution status；resource ledger 的 queued/queued_resume/paused_waiting_claim/live/stopping/released 是 admission 状态，不能代替 execution status。Governor 提供幂等的 queue_resume、claim_next/claim_execution、reclaim_paused 和 fenced release API；queued_resume 与 paused_waiting_claim 保留 command_id、admission_id 和最后的 resource_lease_generation。Job 使用 queued → running → pausing → paused 与既有 terminal/reconciliation 状态。一个 Job 同时最多一个 active attempt 和一个 live resource lease。

queued initial STEP 是唯一的 queued-step 例外：state-machine 与 command handler 必须同时检查 kind=job_agent、strict JobAgentInputV1 可恢复、canonical CapabilitySet.step=true 和现有 admission fence。它从 immutable turn_request 与 job_context 开始，把一次 provider decision 作为一个 managed action，执行到第一个合法 safe point；没有 checkpoint 不是拒绝理由。其他 execution kind 或不满足 capability/input/fence 的 queued STEP 一律返回 invalid_state 或 unsupported_capability，不得借用该例外。

22.7 Safe point、AgentCheckpointV1 与 effect

Job 不定义 JobCheckpoint。background Agent Job 声明与 ordinary Agent 相同的两个 safe point：agent.provider.decision.after 和 agent.tool.action.after。checkpoint 使用第 21 节的 AgentCheckpointV1，外层 manifest 固定 execution_id、revision_id、parent、attempt、generation、content hash 和 schema；Job input 不可变，resume 只能从已发布 manifest 恢复。

  • provider request 前注册 effect intent，并在完整 AssistantMessage delta、usage、request id、current decision、next tool index 和 resolved model/system/tool contract 可验证后提交 provider safe point。
  • tool dispatch 前注册 action/effect，并在完整 ToolResult delta 与 terminal receipt 可验证后提交 tool safe point。部分 stream、async task、Python stack、provider object 和 socket 不能进入 checkpoint。
  • dispatched/uncertain effect 禁止 checkpoint、continue、step 和 retry；必须进入 reconciliation_required，直到外部查询或明确 reconciliation 写入 terminal receipt。
  • state blob 使用同一 execution SQLite 的 content-addressed store；沿用 MAX_AGENT_CHECKPOINT_BYTES=262144、MAX_AGENT_STATE_BLOB_BYTES=1048576、MAX_AGENT_STATE_REFS=32、MAX_AGENT_PENDING_MESSAGES=64、MAX_AGENT_TERMINAL_EFFECT_RECEIPTS=64、MAX_AGENT_DELTA_BYTES=65536、MAX_AGENT_REPEAT_FAILURES=16。超限返回稳定错误码，不截断并继续。
  • 未发布 blob 只能由创建 attempt 清理；已被 manifest、effect receipt、pending message 或 terminal record 引用的 blob 不得清理。Job terminal 且 execution-local 引用为零后才 GC，GC 不跨 execution，也不依据 process-local registry。

continue/step 激活前逐字段验证 immutable runtime contract（model id/API/provider/endpoint/config、system prompt、tool JSON Schema、permission/approval、structured output 和 implementation descriptor）。解析失败或任一字段变化返回 continuation_contract_mismatch，保留 paused checkpoint，不派发 provider/tool。

Job 控制面只返回稳定的 machine-readable codes：not_found、stale_version、unsupported_capability、activation_unavailable、continuation_contract_mismatch、checkpoint_schema_invalid、checkpoint_too_large、state_blob_too_large、state_ref_limit、state_ref_invalid、quota.queue_full、quota.jobs_exhausted、quota.token_exhausted、quota.cost_exhausted、quota.accounting_unavailable、error.worker_lost、error.dispatch_failed、error.canonical_unavailable 和 reconciliation_required。客户端根据 code 和 canonical snapshot 更新显示，不解析异常文本。

22.9 Projection、reconnect、auth 与 owner crash

  • 读取先按 authorized (project_id, session_id, execution_id) 获取 canonical snapshot，再以 event_cursor.next_sequence 订阅事件。cursor gap、连接重建或发现新 terminal version 时重新取 snapshot；不依赖本地 event buffer 补齐事实。
  • Job/DAG/UI projection 按 (execution_id, event_sequence) 幂等消费；重复 event 不重复写，迟到非终态 event 不能覆盖 terminal snapshot。Job card 与 Running 读取同一 Job resource DTO + execution snapshot envelope。
  • owner 在 safe point 前崩溃：旧 attempt fencing，保留最近合法 checkpoint，若无 unresolved effect 则可重新 claim/activate。provider/tool dispatch 后 receipt 前崩溃：写 reconciliation_required，禁止自动重放。
  • queued pause 没有 attempt/checkpoint 时保持 paused；continue 的 initial handoff 从 admitted immutable Job input 激活首次 AgentProductionDriver，不创建 synthetic checkpoint。paused execution 不由 startup 自动运行。
  • cancel intent 已持久化时，startup/reconciler 只继续 exact cancel delivery/finalization；不重新激活 Agent 业务。旧 owner 的写入均以 execution/attempt/generation/status_version 校验并记录 stale-owner event。
  • ResourceGovernor 启动恢复未完成 claim：释放或重置同一 admission fence；只在确认 owner 已结束后释放 live lease。terminal projection 重试不重复 release 新 generation 的 lease。

22.10 一次迁移与删除清单

迁移只执行一次，采用最终 schema 和最终命令名，没有长期 compat、双读、双写或 alias。旧 Job row 能映射到 canonical execution 的，按 job_id == execution_id 生成 projection；缺少 canonical identity、immutable input 或 admission fence 的 row 进入 error.canonical_unavailable terminal projection，并释放已验证的 resource reservation。迁移不会把旧 Job 状态提升为 canonical lifecycle。

删除

outer JobDriver lifecycle owner、JobDriverHandle、Job 专属 driver registry、Job 路径内部随机 exec_* identity、cancel_job 与 spawn_sub_agent aliases、session/token fallback、直接 JobStore control、按 message/session 猜 owner 的代码。

保留为 resource API

spawn、list、read/get_job 可以保留名称作为资源读写入口，但只能创建 admission 或读取 canonical DTO。它们不得写 lifecycle、cancel、checkpoint、lease 或 terminal fields；返回值必须包含 canonical execution_id 与 capability/resource/snapshot cursor。

迁移后新增 Job 只由 canonical admission 分配一次 id；Job continuation、pause/continue/step、terminal retry 和 projection recovery 均不重新 mint execution id。其他 execution kind 可以保留自身 admission identity，但不得在 Job 适配路径中生成或映射第二个 exec_*。

Foreground execution ownership and reconnect

Session hydration derives foreground activity from the reservation and runtime owner. A registered thread that has started and finished is stale and is removed under the runtime registry lock. Stale task removal checks the observed task identity and rechecks runtime liveness under the task lock, preserving any replacement owner. An unstarted thread remains occupied during reservation handoff; a live thread and an opaque non-thread runtime remain occupied until their normal cleanup.

Durable foreground chat executions retain occupancy across approval waits and continuation attempts independently of the initial transport thread. A shared foreground task snapshot selects active interactive Agent inputs, excludes jobs and paused or terminal records, and supplies the same execution identity and version to hydration and live UI projections. The complete public execution snapshot also carries this task, so cursor-gap replay and command responses restore the same controls without weakening event-order checks. The client restores controls only from an accepted execution update, removes the matching controls when the execution pauses again, and preserves a different current owner or an optimistic cancellation.

Every Web cancel entry emits a typed execution.command envelope with action=execution.cancel, command identity and expected execution version. Acceptance submits the JSON generated by the real composer to the server command handler and requires an applied command and a cancelled canonical record; clearing the local UI alone is insufficient.

Local shell execution observes the current execution cancellation signal while collecting output. The backend collector uses the shared ProcessTreeOwner: a creation-time POSIX process group or a Windows Job Object with suspended creation, assignment and resume. Normal completion releases ownership without terminating deliberately detached children. Cancellation and timeout terminate the owned tree and use bounded output draining; a cancellation failure receipt is returned only after confirmed termination, while uncertain cleanup remains an unresolved effect. UTF-8 replacement decoding, no-window creation and shell/sandbox environment selection remain platform-owned. Continuation cancellation closes the event stream and finalizes the original assistant message. Interrupt handling checks the execution-bound cancellation signal as well as its asynchronous projection, so a blocked event loop cannot skip finalization after the owner has already confirmed cancellation. Acceptance covers a real child through a resumed Agent and the public cancellation command, delayed-write absence, idle hydration, and the shared process-tree platform contracts.

Atomic profile-state writes create a private POSIX temporary file before writing any content and retain atomic replacement, directory flush, Windows long-path normalization and bounded sharing-violation retries. Publishing a broader file mode would make valid self-update records unreadable through their authenticated read-only interfaces.

Host adapters interpret paths using the selected target platform. POSIX backup recovery retains descriptor-relative traversal when the host exposes the rename-at capability; Windows retains its validated path fallback. These compatibility boundaries do not relax execution authority or private-state ownership.

A quiet live execution is not expired by session hydration. The run guard owns reservation expiry and stale task cleanup. Replayed running_task frames preserve both execution_id and status_version, so Stop after reconnect sends the same versioned execution.cancel command as Stop before reconnect.

Acceptance: reloading a session with an orphaned completed thread reports run_active=false; loading a quiet live task retains its owner and exact cancellation identity; cancelling the replayed execution remains idempotent and reload does not restore a terminal execution as active. The regression contract is exercised by tests/component/webui/test_execution_cancellation.py. Installed App acceptance and the full release gate are recorded separately from these component checks.
