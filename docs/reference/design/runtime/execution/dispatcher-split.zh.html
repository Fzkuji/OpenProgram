聊天轮次运行时

openprogram/runtime/conversation/turn_runtime/ 是聊天轮次的执行路径。Agent.run_turn 和 Agent.resume_turn 负责公开契约；process_user_turn 和 process_agent_continuation 是经由 ChatAgent 的入口。

头指针不变量

模块写头指针
turn_writer.py在持久化用户消息和记录失败时写头指针，并提供 head_for_finalize，由 finalize.py 写入。执行 advance_head，同会话派生的轮次无法移动头指针。

error_path.py 决定失败后的头指针，写入交给 TurnWriter.record_failure。其他模块不产生 head_id。

回复的文字

一条回复是一串块：文字、推理、工具调用、steer 消息。聊天界面画的是块。存下来的 content、TurnResult.final_text、--print、渠道消息、搜索结果、标题和复制出来的消息读的是一个字符串，只由 state/reply_text.py 里的 reply_text 生成。

两个文字块之间文字里
什么都没有逐字节接上。模型供应商会为了引用把一段连续的文字切成几块，超出输出上限后续写的响应也是从句子中间接着写。
工具调用、steer 消息或带文字的推理一个空行，中间隔了多少块都只有一个。边界任一侧已经有空白时不加。
只有签名的推理不加。它不会被画出来，也没有流帧提到它。
读的一方文字从哪来
结果帧、存下来的行、final_textloop_runner 把每次响应的块、送达的 steer 和停止时保留的文字依次交给同一个 ReplyText。
流式中的行stream_tap 读自己的块。分隔符算在追加的 output_tail 里，所以日志只往文字后面加，冷读折叠出来的和运行中的行一样。
自己累加增量的客户端开启一段文字的那个文字帧带 separator；stream_text 把它放在增量前面。页面、渠道、OpenAI 兼容接口的流、--print 的分段消息和 ACP 都用它。
暂停后继续的回复还是同一行。loop_runner 用暂停前显示过的整段轨迹给 ReplyText 打底，所以文字是这条回复的每一段，暂停后的第一段前面只有一个空行。
对话记录的行没有 content 的行和失败的行，读各块的 reply_text。
下一次模型请求按响应逐个发块（context/render.py）。分隔符不在任何块里，所以发回去的就是模型写的原文。
为什么是空行
框架中间有工具调用的回复，文字怎么拼
openclaw这次运行里每段助手文字，用空行接起来
opencoderun 把每个写完的文字部分去掉首尾空白，各自成行打印
pi-mono打印模式输出最后一条消息的文字块，每块后面一个换行
codex-cliexec 只保留最后一条助手消息

OpenProgram 采用 openclaw 的做法：空行在 Markdown 和聊天应用里都是分段，单个换行不是。每一段都保留，因为工具调用前的那句话常常是回复里唯一交代做了什么的地方。

连续的文字块原样不动。这条规则四家都用不上，因为它们都不会把一段连续文字存成几块。

测试接缝

测试在包对象上替换 _resolve_model、_load_agent_profile、_run_loop_blocking 和 process_user_turn。

  • __init__.py 以模块全局名调用它们，因此替换在调用时生效。
  • 兄弟模块不用模块级导入固定它们。loop_runner.py 在函数内导入包，并调用 _dispatcher._load_agent_profile(...)。
  • 接缝之外的模块（如 finalize.py）以参数接收解析好的 profile 和模型。

公开接口

_wrap_agentic_runtime_block, dispatch_forced_tool_call, execute_continuation, execute_turn, process_agent_continuation, process_user_turn, trigger_compaction

约定
  • 较重的 provider 和上下文导入留在函数体内。
  • 拆分不改变轮次生命周期、错误分类、持久化结构和事件载荷，也不给阻塞路径引入 async。
  • 完成轮次的提交摘要取提示第一个非空行（去空白），最多 60 字符；为空时用 turn。成功、错误和影子文件提交共用此规则。失败的会话提交保持未确认。
