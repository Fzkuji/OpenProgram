OpenProgram Runtime · normative architecture

运行取消：从用户意图到确定终态

本页是 OpenProgram 运行取消功能的唯一权威设计。它定义统一名称、精确目标、状态机、公共协议、协作取消、强制终止、父子传播、持久化、恢复和各界面行为。目标不是增加一个“Stop 函数”，而是让一次取消请求在 App、Web、TUI、CLI、Agent、Workflow 和后台 Job 中具有相同语义。

1. 设计结论

正式能力名称是 Execution Cancellation（运行取消）。用户发出一次 cancel_execution(execution_id) 请求；Runtime 先协作取消，宽限期结束后自动终止仍存活的执行。用户不选择“graceful”或“force”，也不需要再次点击。

目标必须精确

execution_id

session_id 只表示会话容器，不能确定要取消哪一次运行。所有控制、状态和事件都以不可复用的 execution_id 为主键。

状态必须持久

running → cancelling → cancelled

先持久化取消意图，再发送信号。进程被强制终止后，由父进程按同一执行记录完成终态写入。

策略不进入用户协议

cooperative → forced

协作和强制是 Runtime 的终止策略，不是两个用户动作，不是两个终态，也不是公开 mode 参数。

取消不等于回滚。取消保留已写入的消息、DAG 节点、checkpoint、usage 和部分产物。外部工具、文件、网络请求造成的副作用不能由通用 Runtime 自动撤销。需要回滚的 Program 必须提供自己的补偿操作。

2. 当前实现与设计缺口

当前代码已经具备协作信号、宽限期、子进程终止和部分状态修复，但名称、标识和状态来源没有形成一个公共合同。以下内容是现状，不是目标接口。

当前名称或行为已确认语义问题目标处理
handle_stop / WS "stop"按会话处理停止请求；第一次协作停止，第二次或 mode="force" 强制终止。“stop”没有说明目标是哪个 execution；重复点击被解释成不同命令。迁移为 execution.cancel，请求只含 execution_id。
mark_cancelled(session_id, execution_id=None)触发当前或指定执行的 token。名称像直接写终态，实际上只发出信号；可选 ID 允许退回会话级歧义。公共入口统一为 cancel_execution(execution_id)。
request_graceful_stop(session_id)向 agentic function 子进程的 stop queue 发消息。仍按会话索引；只覆盖特定执行容器。由 Execution Cancellation Service 通过 owner adapter 发协作取消。
kill_active_subprocess(session_id)宽限期后终止活动子进程。同一会话的新执行可能与迟到请求竞争；函数名没有记录终态职责。按 execution_id 解析受控 process group，并由父进程统一 finalization。
stopping / stopped / cancelled分别出现在 WS 状态、响应 envelope、DAG 和前端状态中。同一个生命周期有三套词汇，reload 时容易产生分歧。只使用 cancelling 和 cancelled。
_on_forced_kill特定 AgentTool 在父进程强制终止后补写组件状态。终态正确性依赖具体工具注册 marker，新增 Program 容易遗漏。所有执行 owner 在统一 registry 注册强制终止和终态适配器。
当前协议的根本风险不是按钮文字，而是控制目标主要由 session_id 推断。会话可以先后产生多个 execution；迟到的停止请求、reload、旧线程退出和新运行开始会发生竞争。目标设计禁止会话级取消函数直接修改运行状态。

3. 目标、约束与非目标

必须满足

  • App、Web、TUI、CLI 和内部调用使用同一个执行取消合同。
  • 请求只影响指定 execution 及其仍在运行的后代。
  • 取消意图、进度和终态在 reload 与 server restart 后可恢复。
  • 协作取消无效时自动升级；用户不需要理解进程策略。
  • 任何终态只能写入一次，取消不得覆盖已完成或已失败。
  • 部分输出、checkpoint、usage 和审计记录必须保留。

本设计不做

  • 不把取消实现为通用事务回滚。
  • 不新增第二套 DAG、Job 或 Workflow 状态数据库。
  • 不把 Debug Pause、权限等待或用户输入等待合并成取消。
  • 不允许客户端提交 PID、文件路径或组件 finalizer。
  • 不提供公开 force、graceful 或任意超时参数。
  • 不因关闭一个视图自动取消后台运行。

4. 官方框架对照

参考只用于确定语义边界。OpenProgram 同时运行 provider stream、同步工具、Agent、Workflow 和独立子进程，不能直接复制只面向单一 agent loop 的接口。

官方实现已确认合同采用修改或拒绝
OpenAI Agents SDKRunResultStreaming.cancel() 支持 immediate 与 after_turn；后者完成当前 turn、待处理工具、session state 和 usage 后再停。调用后仍需消费 stream events 才能完成取消。区分协作完成和立即中断；取消期间仍需 drain 与 finalization。OpenProgram 对用户只提供一个动作，Runtime 自动从协作阶段升级，不暴露策略参数。
LangGraph Agent Server按 thread ID 与 run ID 取消 pending/running run；默认 interrupt 保留 run、输出、历史和 checkpoints；wait 可等待终态。使用稳定 execution ID；保留部分状态；终态完成前保持可观察的中间状态。OpenProgram 将用户主动取消记为 cancelled；interrupted 只表示非用户意图的基础设施中断。拒绝通用 rollback。
Python asyncio取消在下一次协作机会抛出 CancelledError；清理使用 try/finally；捕获后通常继续传播；异常继承 BaseException。token 在 provider、agent loop、工具和 Program 边界检查；清理后传播取消。同步阻塞和独立进程没有协作机会，因此必须保留受控强制终止。
Kubernetes Pod termination先发送终止信号并等待宽限期，仍存活的进程随后接收 SIGKILL，最后进入终态。采用宽限期后自动升级的基础设施策略，并由控制进程负责终态。不把进程信号、PID 或 --force 公开为 OpenProgram 的用户协议。
CrewAI Flows官方 Flow 文档定义 @persist、UUID resume 与 fork；该页面没有给出一套与持久 Flow 对应的公开取消合同。持久状态与执行 identity 必须可恢复。不能把“有 persistence”推断成“已有 cancellation semantics”；OpenProgram 必须独立定义取消终态和恢复。

6. 执行标识与所有权

execution_id 是一次可控制运行的不可复用 ID。会话、turn、Agent、Workflow run 和后台 Job 都可以产生 execution；它们在创建时获得 ID，并在 DAG 中通过 caller 形成父子关系。

字段要求用途
execution_id全局唯一，不复用，不由客户端选择。控制命令、状态、事件、token、owner 和终态的唯一主键。
session_id必填，但只是归属与授权范围。权限校验、会话查询和 UI 分组；不能单独确定取消目标。
parent_execution_id根 execution 为 null；子 execution 指向直接调用者。它是现有 DAG caller 边在 Execution DTO 中的投影，不新增第二个存储字段。父级取消传播、DAG 展示和后代 admission gate。
execution_kind使用现有 kind vocabulary，不由取消服务重新定义。选择 owner adapter；不改变取消语义。
owner_id仅服务端生成或解析。定位 async task、thread、process group 或 provider request；不返回可操作 PID。
同一规则覆盖直接运行和嵌套运行。后台 Job 可令 execution_id == job_id；Workflow 可令 execution_id == run_id；它们不需要再创建一个同义 cancellation ID。

7. 状态机

  • cancelling 是持久状态，不是前端临时 spinner。它表示取消请求已经接受，但至少一个 owner 或后代尚未完成终态确认。
  • cancelled 只在指定 execution 及取消范围内的所有 owner 已停止、组件状态已写入、资源 lease 已释放后写入。
  • interrupted 只用于没有取消意图的异常失联。重启发现持久化的取消意图时，应继续完成 cancelled，不能改写成 interrupted。
  • cancelling 由 reconciler 持续驱动收敛，不依赖单次请求线程存活：owner 终止或 finalize 失败时按周期重试并记录诊断，直到写入 cancelled。cancelling 没有用户可见的超时，UI 显示已持续时间；Runtime 绝不因为终止失败而伪造终态。

8. 目标架构

Execution Registry 只保存控制所需的运行时句柄

不新增持久数据库。DAG/session execution record 是状态来源；registry 是进程内索引，按 execution_id 保存当前 owner。每个 owner adapter 必须实现四项职责：

职责语义禁止行为
request_cancel设置同一 execution 的 token、provider abort、task cancel 或 stop queue。按 session 猜测目标。
is_alive确认 owner 或受控后代是否仍在执行。只根据 UI task 或历史 status 判断。
terminate宽限期后终止服务端拥有的 task/thread/process group。使用客户端 PID；终止整个 session 的无关进程。
finalize_cancelled以 compare-and-set 写入组件投影，释放 lease，保留部分产物。覆盖已有 terminal state；依赖具体函数名 marker。

Token retirement 与 owner generation

registry 中每个 execution_id 的 owner 条目带一个单调递增的 generation。execution 进入任一终态时，其 token 和 owner 条目立即 retire：retired token 的 request_cancel、terminate 都变为 no-op，只能读取终态。同一 session 的下一次运行创建新的 execution 条目和新 generation，因此迟到的取消请求、迟到的宽限期回调和迟到的 provider event 在 registry 层就被拒绝，不需要各 surface 自己判断“这是不是旧运行”。第 12 节的竞态规则以这一机制为准。

9. 公共函数与传输协议

Python 服务合同

def cancel_execution(execution_id: str) -> Execution:
    """Request cancellation of one execution and its active descendants.

    Returns the canonical Execution record after the request is applied.
    The returned status is usually `cancelling`; `cancelled` means finalization
    already completed. Repeating the request for an already-cancelled execution
    returns the same terminal record.
    """

这是唯一公共参数。取消来源由调用上下文确定并写入 reason_code，用户不能伪造；宽限期、信号和进程策略是服务端策略，不是函数参数。

返回与错误语义

目标状态结果原因
queued / running接受，原子转为 cancelling。合法取消范围。
cancelling / cancelled幂等返回当前记录。重试和重复点击不产生第二个动作。
completed / failed / interruptedExecutionNotCancellable，返回现有终态信息。取消不能覆盖已决定的结果。
不存在或无权访问ExecutionNotFound。避免跨会话泄露 execution 是否存在。

10. 取消算法

01 · RESOLVE

解析并授权精确 execution

由 execution_id 读取 canonical record；验证当前主体拥有该 session 的控制权限。客户端的 session、PID、路径和 execution kind 都不能替代服务端记录。

Gate: identity exists, authority matches, status is cancellable or idempotent
02 · INTENT

先持久化取消意图

对根 execution 与当前已知的非终态后代执行 compare-and-set：queued|running → cancelling，写入 reason_code 和请求时间。任一祖先进入 cancelling 后，禁止创建新的后代。

Gate: no signal before durable cancelling state
03 · COOPERATE

并行请求所有 owner 协作取消

设置 execution-scoped CancellationToken，中止 provider stream，取消 asyncio task，解除权限/用户输入等待，并通知 Agent、Workflow 与 Job owner。工具在安全检查点清理后重新传播取消异常。

Gate: every active owner has one registered cancellation path
04 · GRACE

等待已有宽限策略

初始迁移保留当前 4 秒宽限期，避免在命名重构中同时修改运行行为。该值是服务端常量，不进入用户配置；后续改变必须有实际取消延迟和产物完整性数据。

Gate: observe liveness by execution owner, not by UI running flag
05 · TERMINATE

自动终止仍存活的 owner

Runtime 只终止该 execution 注册的 task、thread 边界或 process group。强制阶段不改变 reason code，不产生 killed 状态，也不需要第二个用户请求。

Gate: target is still alive and still belongs to the same execution_id
06 · FINALIZE

父进程完成所有持久终态

以幂等 finalizer 更新 DAG execution record、消息投影、Workflow state.json、Job 状态、usage/lease 和 pending question。先前已经 terminal 的组件不改写。

Gate: every owned projection is terminal or confirmed absent
07 · PUBLISH

发布唯一终态并从持久状态重载

写入根 execution 的 cancelled 后发布 execution.updated。前端收到终态后重新使用 canonical DTO；丢失事件时，session reload 得到相同结果。

Gate: no stopped envelope and no local-only terminal truth

11. 父子传播、部分产物与组件终态

请求目标取消范围不受影响
根 chat execution该 turn 下仍非终态的 Agent、Program、Workflow、Job 和工具 owner。同一 session 的历史 execution；取消完成后新建的 execution。
某个 Agent/Workflow execution该节点与它的非终态后代。父 execution 的其他分支；父执行可根据 cancelled 子结果自行决定后续。
queued Job从队列移除并直接 finalization，不启动 worker。同 session 的其他 queued/running Job。
session 关闭或 owner 请求 session cancellation服务端枚举该 session 当前所有非终态根 execution，逐个调用同一服务，reason 为 cancel.session。其他 session。

父级原因使用现有稳定词汇：用户直接请求为 cancel.user，祖先传播为 cancel.parent，会话生命周期请求为 cancel.session。资源预算使用自己的 budget reason code，不伪装成用户操作。

保留内容

  • 已经提交的用户消息、assistant streaming 片段、工具调用记录和 DAG 节点。
  • 已经成功落盘的 checkpoint、Workflow snapshot、usage 与审计信息。
  • 已经生成且可安全读取的部分产物，并明确标记 execution 未完成。

停止后禁止内容

  • 不得继续发布 Workflow revision、提交新的 Agent/Job 或发送新的 provider 请求。
  • 迟到的 stream event 不得把 cancelled 节点改回 running/completed。
  • 取消 finalizer 不得删除历史、checkpoint 或外部副作用。

12. 幂等、竞态与重启恢复

竞争场景确定规则验证方法
完成与取消同时发生对同一 canonical record 做 compare-and-set；第一个终态获胜，另一方读取并返回已有终态。barrier 控制两个 writer，断言只有一个 terminal transition。
旧取消请求晚于下一次运行请求携带旧 execution_id；retired token 和 owner generation 拒绝影响新 execution。同 session 连续两次运行，延迟发送第一执行的取消。
取消期间产生新后代admission 检查所有祖先；任一祖先为 cancelling/cancelled 时拒绝创建并返回 cancel.parent。在父状态 CAS 后阻塞 signal，尝试 spawn。
两个 surface 同时取消第二个请求幂等读取同一 cancelling/cancelled record，不重置宽限期，不重复 finalizer。App 与 CLI 并发请求同一 execution。
终态事件丢失后 reloadUI 从持久 Execution DTO 恢复；本地 optimistic 状态不能覆盖 server record。丢弃 terminal frame，再执行 session load。
server 在 cancelling 时重启startup reconciler 读取持久取消意图；owner 不存在则完成 cancelled，owner 仍存在则重新建立控制并继续取消。在 intent、signal、terminate、finalize 四个边界分别模拟重启。
进程强制终止，child finally 未运行父进程 owner adapter 执行 idempotent finalizer；终态不依赖 child callback。child 在不可协作阻塞中被 terminate，核对所有组件投影。
owner 无法被终止（不可杀进程、内核态阻塞）execution 保持 cancelling；reconciler 周期重试 terminate 与 finalize 并记录诊断，不伪造 cancelled，不回退 running。模拟不可杀 child，断言状态保持 cancelling 且重试与诊断可观察。
权限外 execution ID统一返回 not found，不设置 token、不读取输出、不广播。两个 session/owner 的交叉请求。

13. 与 Debug、Pause、权限和用户输入的边界

动作是否继续同一 execution状态语义与取消的关系
Pause / Resume是临时停止调度，保留可恢复控制状态。Pause 不是终态；暂停时仍可取消，取消优先并解除等待。
Debugger Stop否终止当前 debug execution。直接调用 cancel_execution(execution_id)；不建立第二套 Debug Stop Runtime。
Step / Continue是Debugger 的执行推进。只在未 cancelling 时允许。
Permission request是execution 等待授权。取消关闭 request，结果为 cancelled，不解释为拒绝权限后继续。
User input request是execution 等待用户输入。取消关闭 request 并终止 execution；迟到回答无效。
Retry / Resume from checkpoint否基于旧记录创建新的 execution ID。旧 execution 保持 cancelled；新 execution 不复用旧 token。

因此，代码运行、Workflow、Agent 和未来 Debugger 都对应同一“取消运行”能力；它们可以有不同的 owner adapter，但不得有不同的用户终态。

14. App、Web、TUI、CLI 与 Agent 行为

Surface入口取消中终态
App / Web Composer按钮文本或 tooltip 为“取消运行”，发送当前 active execution 的 ID。按钮禁用并显示“正在取消”；reload 后仍由 server record 恢复该状态。消息和 DAG 节点显示“已取消”，保留部分输出。
Execution strip / DAG节点菜单取消该节点 execution。节点及后代显示 cancelling；父级其他分支不变。节点 subtree 进入 cancelled；根执行按自己的控制流处理子结果。
Programs直接运行表单保存返回的 execution ID，使用同一命令。页面切换或打开 Effort 等窗口不得改变取消状态或产生第二个控制层。Function、Agent、Workflow 共用同一状态文案。
TUI / CLIexecution cancel <execution_id> 映射到同一服务。查询 canonical execution；不轮询 session cancel flag。输出统一 status/reason，不显示内部 PID 或 signal。
Parent Agent / Runtime父级取消后代时直接调用服务，reason 由上下文确定为 cancel.parent。不能选择 force；不能扩大到同 session 的其他 root。读取结构化 cancelled 子结果，而不是解析字符串。
关闭一个 tab、切换页面或网络暂时断开默认不取消 execution。客户端断开策略若以后需要支持，必须作为 session/run API 的独立明确政策设计，不能由组件卸载隐式触发。

15. 权限、信任边界与审计

  • 客户端只能提交 execution_id；服务端从 canonical record 解析 session、parent、owner、process group 和所有状态路径。
  • 只有 execution 所属 session 的 owner、被授权的协作者或拥有内部 parent authority 的 Runtime 可以取消。
  • 不存在与无权访问使用同一外部错误；日志可记录内部区分，但不能泄露其他 session 的执行存在性。
  • 审计记录至少包含 execution ID、session ID、reason code、请求主体、请求时间、最终状态和是否发生内部强制终止；不记录 prompt、credential 或工具 secret。
  • 强制终止只能作用于 registry 中由 OpenProgram 创建并仍归属该 execution generation 的 process group。

16. Canonical Execution DTO 的取消字段

{
  "execution_id": "exec_...",
  "session_id": "session_...",
  "parent_execution_id": null,
  "execution_kind": "agentic_function",
  "status": "cancelling",
  "reason_code": "cancel.user",
  "cancellation_requested_at": "...",
  "finished_at": null,
  "partial_output_available": true
}

这些字段进入现有 Execution/DAG DTO，不另建 StopResult 或 CancellationReceipt schema。内部强制终止方式可以写入受限诊断字段，但不是公共 status。时间格式沿用现有 DTO 规范，本设计不另定义。
