Execution authority, permission, and sandbox

This is the canonical engineering contract for request identity, tool approvals, live permission changes, and local process isolation. It covers Web, CLI, ACP, channels, nested Agents, scheduled tasks, and continuation. Permission changes do not redesign host isolation or add speculative capability tiers.

Authority: the authenticated principal and fixed capability ceiling.
Permission: allow, ask, classify, or deny one operation.
Sandbox: the resources an approved process can access.

Authenticated authority

Authenticated local entries attach the complete owner authority to TurnRequest before durable admission. The audit actor and the execution request are separate values; providing only an admission actor does not authorize tools. Paired channels retain the paired tier; browser MCP grants may use mcp_browser. Nested requests inherit and cannot expand authority. Missing or unknown authority fails closed with a stable reason code. Recovery never reconstructs owner authority from a source label or from model text.

One operation decision

The approval manifest and execution wrapper use the same policy decision. Order: hard constraints, authority, plan restrictions, explicit deny, explicit ask or mandatory approval, exact Web Use grant, bypass, explicit allow, scheduled Memory exception, safe reads, acceptEdits, Auto classification, ordinary approval. Non-interactive requests that require approval return a denial.

Bypass skips ordinary approval and Auto classification. It does not override explicit ask/deny, mandatory approvals for plan exit or self-update, plugin tool gates, or Sandbox. Invalid mode values are rejected by configuration commands. Denials identify their reason and capability without exposing secrets.

Session settings take precedence over project defaults, then ask. The effective resolved mode is used for actual admission and UI acknowledgements.

Versioned live permission lifecycle

The existing SessionStore owns a versioned permission_state dictionary. Atomic compare-and-set prevents stale clients from overwriting a newer selection. State includes mode and owner principal. The WebSocket settings command authenticates the owner, validates session scope, and returns the authoritative mode and version. No parallel approval database or generic policy engine is introduced.

Interactive local requests read their principal-bound permission state at each tool approval check. One call retains that decision through dispatch; already authorized calls are not interrupted. Immutable admission input and continuation contracts remain unchanged. Non-interactive tasks, paired channels, and other sessions cannot adopt these live overrides.

On a mode change, open ordinary permission approvals are re-evaluated using the shared decision. An operation now allowed is resolved through the existing canonical wait-answer command and resumed from its checkpoint. Explicit ask, mandatory approval, Sandbox escalation, and user questions remain waiting. A wait published concurrently with a settings change performs the same recheck after the old runtime releases its cancellation token. Startup recovery also re-evaluates persisted mode changes. Expired, cancelled, or completed work is never resurrected.

The UI distinguishes a requested selection from an acknowledged mode. Updates carry a version; older acknowledgements and hydration snapshots cannot replace newer state. Transport errors remain visible. An unsent draft stores its selection locally without creating an empty session; initial submission supplies it. Existing sessions use confirmed server state.

Plan restrictions are enforced at the tool boundary so switching into plan blocks writes already proposed by the model. Keeping the tool catalog stable permits switching out of plan during a running turn without invalidating continuation. Model-entered plan state still requires its approved exit operation.

Tool and host boundaries

File tools apply in-process guards. Local subprocesses use Seatbelt on macOS or bubblewrap on Linux. Browser/Web Use uses an exact surface grant. Docker and SSH use their own execution boundary; configured MCP processes are owner-configured trust and are not described as local sandbox isolation.

workspace-write allows working roots, masks protected reads, filters credential environment variables, and disables network by default. danger-full-access uses host user permissions. Missing sandbox backends refuse by default; explicit warn is an acknowledged fallback. Auto-imported agentic application paths retain hard write restrictions.

Sandbox is a session override resolved into an immutable turn snapshot. Changing its switch affects subsequent turns, not current processes, other sessions, scheduled tasks, or inherited child policy. Ordinary approval never disables Sandbox. Bypass does not offer automatic sandbox escalation.

Sandbox escalation

A structured sandbox denial can request an exact retry only from an interactive local owner with approval.request. Approved escalation lifts configurable restrictions while retaining protected application paths and credential filtering. always_path adds only the specific permissible read path. An approval is bound to its session, execution, tool, and tool call. A normal tool approval cannot authorize a sandbox escalation. The current execution protocol has no post-tool escalation wait; such denials require an explicit settings change and a new call, and cannot silently reuse the ordinary approval. A second failure is returned without another retry. Paired channels, MCP clients, cron, and subagents cannot escalate.

Failures and compatibility

Missing authority, stale settings versions, invalid modes, denied capability, explicit rules, classifier failure, and sandbox refusal remain distinguishable. No failure silently becomes owner or bypass. Existing stored permission_mode is readable when no versioned state exists. New authenticated submissions attach fresh authority; legacy admitted requests without authority must be resubmitted through an authenticated entry rather than elevated during recovery.

Host process visibility may prevent ps, top, or lsof; Docker sockets are not exposed automatically. Linux wildcard masking has limitations. Domain/port network allowlists require a managed proxy and redirect checks and remain unimplemented. Browser and remote networking have separate controls.

Implementation status

The permission lifecycle implementation passes independent specification and quality review. Regression checks exercise authenticated chat admission, versioned updates and inheritance, operation snapshots, approval restoration, and approval-card dismissal through the production driver. Full repository verification and default installed-App acceptance are recorded separately from these scoped checks in the release evidence.

Existing host isolation is retained. Domain allowlists, resource quotas, Windows sandbox support, per-tool sandbox overrides, and a full background Auto-classifier product remain outside this implementation.
