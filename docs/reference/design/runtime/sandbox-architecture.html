LAYER 1

我们现在怎么做

实现是openprogram/sandbox/__init__.py，两个消费者：backend/local.py::_invocation（bash和process工具）和 memory/scriptorium/management/workspace.py::shell（memory写入器的MCP shell）。 下面四节全部实测：四个方向的边界、两个平台各自的机制、开关为什么现在传得到、以及25个执行点里哪些真的被包住。

01一张边界图

四个方向不对称：读除凭证清单外敞开，写被收在工作目录，执行不设限并靠子进程继承沙箱兜底，网络两个平台都断。 凭证曾经全在敞开的读通道上，现在那一条通道装上了出厂就填好的屏蔽清单。

闸门读法：双箭头=不设限，单箭头加挡板=部分放行，叉=封死。 连线颜色跟闸门一致，虚线表示这个方向的请求到不了对面。

02两个平台

同一个wrap_command在两个平台走完全不同的机制，各自额外放行了一些东西，也各自有一处只在实跑里才会暴露的细节。

MACOS

Seatbelt

/usr/bin/sandbox-exec -p <profile> /bin/bash -c <命令>
机制
profile内联生成，(deny default)兜底，逐条往上加放行。嵌套再开一层沙箱会被拒，放宽不了。
额外放行
/dev/null等五个字符设备用require-all加vnode-type CHARACTER-DEVICE放行读写，所以2>/dev/null正常。sysctl-read和mach-lookup仍是无名字过滤的全开，剪贴板可读、Apple Events通道开着。写范围里还整树带着/private/var/folders。
屏蔽写法
每条deny glob编译成锚定正则，deny file-read*和deny file-write-unlink成对发，被禁读的路径不能用删除反推存在性。工作目录拼进profile前先转义。
方言的坑
Seatbelt的正则引擎不认(?:…)，非捕获分组会让一条deny规则变成无声空转，实测过；引擎匹配的是解析软链后的真实路径，所以每条glob在静态前缀指向别处时要发两遍。
LINUX

bubblewrap

bwrap --new-session --die-with-parent --unshare-pid --unshare-ipc --unshare-uts --cap-drop ALL --ro-bind / / --proc /proc --dev /dev --unshare-net --tmpfs /tmp --bind <cwd> <cwd>
机制
挂载视图重建：根只读，工作目录单独bind成可写，net / pid / ipc / uts四个命名空间隔离，capability全丢。
屏蔽写法
目录用--perms 0000 --tmpfs盖掉，文件用--ro-bind /dev/null顶掉。--cap-drop ALL拿走了DAC_OVERRIDE，所以容器里子进程是root时权限位依然生效，实测报Permission denied。
进程隔离
--unshare-pid之后实测：沙箱内只看得到4个PID，读宿主进程的/proc/<pid>/environ报文件不存在，kill -9报进程不存在，宿主进程照常活着。没有它的话，洗干净子进程环境也没用。
顺序的坑
--tmpfs /tmp必须发在cwd bind之前，否则工作目录落在/tmp下会被tmpfs盖掉、静默消失。屏蔽挂载还必须跳过宿主上不存在的路径：根是只读绑定的，bubblewrap没地方创建挂载点，硬来会让整条调用失败。两条都是实跑撞出来的。

03开关：载体从ContextVar换成配置

开关原来是一个ContextVar：设它的地方和真正执行命令的地方不在同一个上下文里，值就丢了，三条路径里两条在丢，其中一条是用户最常用的Web。 下图是改之前的传递，留在这里是因为它说明了为什么载体必须换。

三个边界的共同点：每一个都在起一份新的执行环境。逐个补copy_context()并不等价： spawn出来的子agent确实能靠它把开关带进worker线程，但在followup线程上照样掉回默认值，这是实测的；嵌套CLI根本不是线程，补不了。 一个要跨进程存活的用户级设置，本来就不该挂在上下文变量上。

现在的载体是文件：策略在包装命令的那一刻从~/.openprogram/config.json的sandbox.*读出来。 文件不属于任何上下文，所以三个边界都跨得过去。

路径改之前改之后（实测）
Web：asyncio任务里设，裸线程里执行读回false，命令裸跑线程内写工作目录之外被拒，$OPENAI_API_KEY长度为0
CLI：REPL同线程有效有效，且跨会话保持
spawn：@agentic_function的子解释器读回false，全部裸跑子进程内写工作目录之外被拒，$OPENAI_API_KEY长度为0
审批bypass：permission_mode="bypass"短路到工具自己的execute照样被包住：策略在权限层之下解析，实测写越界和读SSH私钥都失败
平台工具缺失静默落回普通执行默认refuse，命令失败并给出两条出路；warn可选
七个配置键：sandbox.mode、writable_roots、deny_read、deny_write、network、pass_env、on_unavailable， 都在config_schema.py的SETTINGS里，所以openprogram config、setup向导、TUI设置页和Web设置页一起有。 默认mode=off：默认打开是第04步，要单独拍板。

04覆盖面

全仓库约25处会把内容变成运行中的进程，走沙箱的有2处：bash工具那条，和memory写入器的MCP shell那条。

从模型输出到宿主进程内任意代码，最短的一条路径不经过bash，也就不可能被wrap_command包住。

还有两处会拆掉闸门：spawn出来的子agent把轮次的permission_mode设成bypass， 而_gated_execute在bypass那一步就短路，位置排在会拦住bash / execute_code / process的risky工具检查之前（规则层的deny和ask更靠前，仍然生效）。 沙箱不在这条被绕过的清单里，它在权限层之下解析，被bypass的bash照样被包住，实测过；要补的是权限层自己那条底线，见第05步。另外， webui/_runtime_management.py往create_runtime()传的sandbox="read-only"看着像在防护， 而provider那边把这个kwarg明确记为接受即忽略。

别人怎么做

05八家的隔离立场

按隔离强度分四档。左边是主动移除隔离的，右边是把执行推到另一个内核视图或另一台机器的。 同一个框架出现两次，表示它跨档：左边是默认路径，右边是可选配置。

09缺口对应到谁解决了

左列取自层一的实测结果，中列是层二里已有的做法，右列是它落在修复路线的哪一步。

10修复路线

五步按依赖排，每一步都是下一步能产生价值的前提。前三步已完成，剩下两步改的是产品默认行为，要单独拍板。每张卡底下标出这一步抄的是哪一家。

STEP 01 · 已完成

可用性

macOS放行五个字符设备的读写；exec白名单换成不限制，靠子进程继承profile兜底；Linux把--tmpfs /tmp发在cwd bind之前。
实测结果：git、python3、make、clang、conda python、/usr/sbin、2>/dev/null全部正常；工作目录落在/tmp下也在。仍然跑不了的只有ps和top，setuid，平台限制。
抄：codex-cli的字符设备规则；两个系统调用级实现都放开exec
STEP 02 · 已完成

凭证屏蔽

两个平台的deny-read清单出厂装弹，macOS上deny读和deny删除成对发。子进程环境变量走白名单而不是从注册表推导的黑名单：白名单会自己丢掉没见过的名字，新加provider不用更新任何东西，兜底名字正则留作pass_env的底线。Linux加--unshare-pid。函数watcher的agentics目录禁写且删不掉。
实测结果：SSH私钥、~/.openprogram/auth/**、keychain、.env全部读不到，删也删不掉；164字符的OPENAI_API_KEY在子进程里是空串；Linux上宿主进程的/proc/<pid>/environ读不到、也杀不掉。git hook和git config保持opt-in，因为禁掉会让git init和git clone直接失败。
抄：hermes-agent的注册表思路（改成白名单）；openclaw的兜底名字正则；claude-code的写保护理由
STEP 03 · 已完成

开关语义

砍掉ContextVar。策略在包装命令的那一刻从配置里的sandbox.*解析，bash()函数体内不带参数就能取到，不依赖执行时所在的线程或调用链。SETTINGS加了七个键。不可用时默认拒绝执行，文案说清缺什么、给两条出路。
实测结果：Web那条形状里裸线程被包住、spawn子进程被包住、审批bypass也照样被包住。wrap_command接收显式策略，但目前还没有按工具或按调用点给出不同策略的地方。
抄：codex-cli的per-command策略；openclaw的硬拒绝文案与doctor预警
STEP 04

默认开

默认workspace-write语义。前提是01到03都做完，否则默认开等于默认坏。
不做：一个默认关又没有配置项的机制在真实使用中不会运行，前三步全都无从检验。
抄：codex-cli的默认立场，八家里唯一默认就开的
STEP 05

审批联动

正向：将在沙箱内执行且策略未放宽的bash跳过审批卡。反向：沙箱内被拒的命令带原因发起审批，批准后不带沙箱重跑。向下：一条bypass掀不动的底线，加上cron和子agent的按上下文默认值；任何命令pattern规则之前先归一化并解包argv。
不做：沙箱纯粹是额外负担，审批一次不少、能跑的命令变少，没人会打开它；而且几条bypass路径会继续绕过沙箱做的一切。
抄：claude-code的沙箱内免审批；codex-cli的失败升级；hermes-agent的hardline底线与按上下文默认值；openclaw的argv解包
配套的profile修补清单：已完成的部分是工作目录拼进profile前先转义、放开exec之前补上限定在同沙箱内的signal和process-info*、 Linux加--new-session --die-with-parent --unshare-pid --unshare-ipc --unshare-uts --cap-drop ALL、functions/agentics/禁写、两条沙箱路径统一用/bin/bash。 仍然敞着：sysctl-read和mach-lookup收成具名白名单，/private/var/folders收窄到本进程的TMPDIR。 --unshare-user不在清单里：非setuid的bubblewrap构建自己就会建用户命名空间，setuid的构建不接受这个参数。
接memory写入器的边界：它有两个执行面。MCP的shell工具在OpenProgram进程内跑，已经接上，用暂存目录作为工作目录、解析同一份策略； Claude Code CLI子进程里的Read/Write/Edit/Grep/Glob在CLI进程内部执行，wrap_command够不着， 而这个CLI进程也不该被包进沙箱，因为它要调Anthropic API而沙箱没有网络。 上一轮到此为止，结论是只能靠allowed_tools。本轮修正：openclaw对嵌套的Codex app-server做的是坐在协议上分类每个方法、拦掉 command/和fs/、再注入绕回自己沙箱的替代工具。Claude Agent SDK有对等的缝，can_use_tool回调加几个MCP提供的替代工具能把文件操作放回我们的策略下面。 所以准确的说法是这些内置工具按现在的接法在沙箱之外，不是原理上够不着。第01到03步是硬前置，都已完成。 这条挡住的威胁是具体的：只要挂了消息渠道，入站消息正文里就带着发信人自己设的显示名，那段文本会一路流进写入器的prompt； 从那里被执行的命令本可以读~/.openprogram/auth/*/default.json写进topic文件，而记忆库内容会回到之后会话的上下文里，全程不碰网络。
一句话收尾：原来的问题不是策略不够严，是三件事同时成立：开关在真实调用路径上多半是关的、开了之后macOS上正常工作干不了、最该防的凭证是敞开的。 这三条都已经修掉：开关换成配置驱动、可用性补齐、凭证清单出厂装弹。剩下的两步是默认打开和审批联动，它们改的是产品默认行为， 也是决定这套机制会不会被真正打开的那两步。
