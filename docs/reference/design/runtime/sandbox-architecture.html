Architecture · Canonical Design

谁能做、这次准不准做、获准后能访问什么

OpenProgram 把 Agent 执行控制拆成三个独立合同：Authority 给出请求的能力上限，Permission 对一次具体操作作出允许、询问或拒绝，Sandbox 在操作获准后实施宿主资源边界。三者按固定顺序组合，不能互相替代。

现状：核心执行边界已有实现目标差异：Claude Code 风格 Auto 待实现平台：macOS Seatbelt / Linux bubblewrap / Windows WSL2 委托范围：Agent 工具与模型驱动执行面

1. 结论与边界

本文是 Agent 执行安全的唯一设计正文。它不讨论 provider 登录凭证管理；openprogram/auth/ 解决“如何获得模型服务凭证”，本文解决“一个已经进入 Runtime 的请求如何被约束”。Authority、Permission、Sandbox 保持独立数据结构和独立判定点，任何一个机制都不承担另外两个机制的职责。

固定顺序：越靠前的约束越不能被后续放宽。tool_gate、hard constraints 和 tier capability 在规则、审批、bypass 与执行之前完成；缺失身份或未知能力一律拒绝。

bypass 的目标合同：只跳过 Permission 的普通审批与 Auto 后台判断，不改变 Sandbox。Authority、hard constraints 和显式 deny 仍然有效；显式 ask 不在 bypass 中产生确认。只有用户单独关闭 Sandbox，本地命令才使用宿主权限直接执行。

不在本文范围：Windows 原生 AppContainer 沙箱、CPU/内存/进程数配额、OS Keychain/keyring/Credential Manager、把第三方 plugin 宣称为进程隔离、把远端 SSH/Docker 说成宿主原生沙箱。Windows 已实现的 WSL2 委托属于本文定义的本地命令边界。

2. 三个独立问题

合同输入回答的问题输出
Authority入口构造的 principal、tier、interaction这个请求最多具备哪些 capability？继续，或带 reason code 拒绝
Permissiontool、args、规则、会话模式、审批能力这次具体操作是否获准？allow、ask 或 deny
Execution boundary获准操作及其执行面该执行面实际能访问哪些资源？结果，或该边界的结构化拒绝
“用户批准”不等于“取消沙箱”。普通批准只满足 Permission；进程仍按 SandboxPolicy 执行。只有单独的 sandbox escalation 才会使用放宽后的策略重试，而且仍保留不可取消的 hard floor 与凭证过滤。

4. Authority：能力上限

入口只携带一个固定 tier 枚举，capability 集合只存在于进程内常量表。模型正文、speaker display、工具参数和项目设置都不能创建或扩展 capability。

Tier允许能力明确禁止交互
ownerreply、memory、schedule、fs、process、network、approval、runtime、browser仍受 hard constraints、规则和 sandbox 约束本地认证入口为 interactive
pairedreply、memory.read、memory.source.append文件、进程、网络、cron、审批升级、runtime controlnon-interactive
mcp_browserbrowser.control其余全部限定 first-class Web Use 路径
恢复也不使用环境兜底：continuation、subagent、inbox 和 cron 必须显式携带或从签名记录恢复 authority。字段缺失或 tier 未知时拒绝，不把旧状态自动提升为 owner。

5. Permission：一次操作的决策

模式默认行为不能绕过
ask安全只读自动执行；修改性操作询问hard constraints、tier capability、显式 deny/ask 规则
acceptEdits安全工作目录内的读写编辑自动执行；命令仍询问
plan隐藏写工具；这是工具可见性控制，不是独立安全边界
auto默认不询问；独立安全分类器在后台阻止明显危险、不可逆、越出用户任务或面向未知外部基础设施的操作
bypass不询问并跳过 Auto 安全分类器；不改变 Sandbox 开关

规则作用域与优先级

deny  > ask > allow

global config
  < project .openprogram/settings.json
  < session override

“总是允许”持久化到项目规则，并保存规范化后的精确 operation；复杂 shell 只允许单次批准，不能把一次 bash 批准扩大成永久允许所有 bash。

Auto 安全判断

默认直接执行默认阻止阻止后的用户体验
工作目录内的普通文件操作、测试、构建、当前分支的常规 Git 操作、只读网络请求下载后直接执行未知代码、敏感数据外发、生产部署、数据库迁移、共享基础设施或权限变更、大量或不可逆删除、force push 或直接推送主分支先让 Agent 改用安全替代方案；记录拒绝原因并允许用户手动重试。重复阻止后退出 Auto，回到 ask

Auto 分类器不可用、无法给出可靠判断或当前模型不受支持时，Auto 不得退化成 bypass；界面将模式标为不可用，正在运行的会话回到 ask。对话中“不要 push”“部署前等我确认”等限制参与后台判断，但需要强保证时仍使用正式 deny rule。

Web 档位传递合同

权限徽章显示会话的有效模式。未显式选择时继承项目默认值；项目也没有默认值时使用 ask。后端必须回传本次 turn 实际采用的模式，不能由前端自行推断。

阶段必须携带或产生的值失败处理
Composer 选择inherit | ask | acceptEdits | plan | auto | bypass未知值不进入发送路径
普通发送、Goal 回答发送当前会话的显式 override；没有 override 时发送 inherit发送失败保留草稿和会话选择
运行中排队、拒绝后重排队真正开始执行时读取该会话的最新模式用户从 bypass 切回 ask 后，未开始的消息不得继续使用旧 bypass
后端接收计算 session override → project default → system ask，并回传 effective mode字段缺失或非法时 fail-safe 到 ask，不得默认 bypass

6. Sandbox：获准执行后的宿主边界

“获准执行”之后没有一个覆盖所有工具的通用沙箱。OpenProgram 按执行面选择边界：进程内文件工具执行路径约束，本地命令进入宿主原生沙箱，Docker/SSH 使用自己的外部边界，Browser 与 MCP 使用各自的受管接口。

Permission 与 Sandbox 的组合结果

PermissionSandbox用户看到的效果
ask开启需要确认；批准后在 Sandbox 内执行
auto开启默认不询问；通过后台安全判断后在 Sandbox 内执行，危险操作被阻止
bypass开启不询问、不经过 Auto 安全判断，直接在 Sandbox 内执行
bypass关闭不询问、不经过 Auto 安全判断，直接使用宿主权限执行

固定原则：Permission 只决定是否询问以及是否运行 Auto 安全判断；Sandbox 只决定本地命令的资源边界。开启 Sandbox 不增加审批，选择 bypass 不关闭 Sandbox。

状态可观测性合同

界面不能用一个“Sandbox ON/OFF”值描述整个 Agent。必须分开显示配置状态、turn 的有效权限和具体工具实际采用的执行边界。

状态层数据来源界面表达不得表达成
Configured process policy后端读取 sandbox.mode、backend availability 和 networkPlus 菜单显示开关和可用性；高级设置页显示具体策略所有工具均已隔离
Effective turn permission后端解析 session/project default 后的 effective_permission聊天 turn 状态显示实际采用的权限模式仅回显前端本地选择
Effective tool boundary工具分派和执行结果：in-process guard、Seatbelt/bwrap/WSL2 delegation、external、surface、configured trust执行详情按工具显示边界类型；本地进程额外显示 sandboxed / bypassed / unavailable统一的全局 Sandbox 徽章

本文不定义 strict/balanced/open 组合预设，也不提供“沙盒内自动批准/沙盒内仍然询问”的第二套模式。Permission 已经负责审批策略；Sandbox 只有开启或关闭。高级配置只处理路径、网络、环境变量和后端不可用策略。

作用域与并发

层级含义生效时机
系统默认新会话没有项目或会话设置时采用的 SandboxPolicy创建或恢复会话时解析
项目默认该项目新会话的默认策略；不覆盖已有会话的显式选择会话没有 override 时解析
会话 overridePlus 菜单开关及高级例外，只影响该 session下一个尚未开始的 turn
turn snapshotturn 开始时冻结的有效策略整个 turn 及其子进程保持不变；中途切换不改写正在运行的任务

并行会话分别持有自己的有效策略。一个会话关闭 Sandbox，不能让另一个会话、cron 或 subagent 改成宿主直执行；cron 使用创建时签名冻结的 SandboxPolicy，subagent 继承父 turn snapshot 且不能放宽。

菜单不增加常驻 Sandbox logo，不增加齿轮，也不在开关后引入额外审批。合法操作被 Sandbox 拒绝时，拒绝提示提供“仅本次放开”或“打开高级设置”；高级设置位于 Settings，不进入 Plus 菜单。

兼容性例外

默认 Sandbox 不开放宿主进程信息，因此 ps、top 和 lsof 可能失败；Docker socket 也不自动暴露。这些限制不能通过模型重复尝试解决。

场景目标行为不采用
ps/top/lsof返回结构化 host_process_info_denied，同一 turn 不重复尝试；高级设置可为当前会话显式开启宿主进程可见性默认向所有沙盒命令暴露宿主进程列表
Docker socket提示改用显式 Docker backend，或由 owner 为当前会话配置精确例外自动把 /var/run/docker.sock 暴露给本地 Sandbox
bypass + Sandbox不弹升级确认；显示拒绝原因和手动修改入口自动关闭 Sandbox、自动重试宿主命令

域名级网络控制

目标网络策略不再使用单一布尔值，而是 off | allowlist | unrestricted。默认 off；普通用户无需预先配置，命令需要联网时再按域名添加一次性或会话级例外。

模式行为界面
off阻止本地命令的全部网络访问Sandbox 高级设置显示“Network off”
allowlist只允许配置的域名和端口；重定向逐跳重新校验；直接 IP、未授权 DNS 路径、UDP 和 Unix socket 默认拒绝拒绝时显示目标域名，并提供仅本次或当前会话允许
unrestricted允许本地命令使用宿主网络，界面持续显示风险状态只在高级设置中开启

实现要求本地命令的出站连接只能到宿主侧受管代理，由代理执行域名、端口、解析结果和重定向校验；沙盒进程不能直接连接外网 IP。代理不做 TLS 内容检查，因此允许宽泛域名仍可能产生数据外发风险。Browser/Web Use、内置 HTTP 客户端和远程 backend 继续使用各自的网络边界，不继承这份 Bash 域名表。

7. 审批与 Sandbox escalation

普通审批只改变 Permission 结果。Sandbox 执行返回结构化 denial 后，系统才进入独立升级流程。

条件行为
本地 interactive owner，且有 approval.request可批准一次精确重试；策略放开可配置限制，但保留 applications hard floor 和凭证环境过滤
paired、MCP 普通客户端、cron、subagent不能发起或回答升级审批，直接拒绝
选择“总是允许此路径”只把具体路径写入 sandbox.allow_read；不能重开 hard-floor 路径
Permission 为 bypass不弹 Sandbox 升级确认；返回 denial 并显示手动关闭 Sandbox 或修改设置的入口
已经升级重试不再弹第二次升级卡；返回原始 denial，避免重复执行同一策略
