LAYER 1

我们现在怎么做

实现是openprogram/sandbox/__init__.py，65行，唯一消费者是backend/local.py::_invocation。 下面四节全部实测：四个方向的边界、两个平台各自的硬伤、开关在哪条路径上丢掉、以及25个执行点里哪一个真的被包住。

01一张边界图

四个方向不对称：读整盘敞开，写被收在工作目录，执行只在macOS受限，网络两个平台都断。 最该防的东西全在敞开的那一条通道上。

闸门读法：双箭头=不设限，单箭头加挡板=部分放行，叉=封死。 连线颜色跟闸门一致，虚线表示这个方向的请求到不了对面。

02两个平台

同一个wrap_command在两个平台走完全不同的机制，各自额外放行了一些东西，也各自有一处会真正咬到人的硬伤。

MACOS

Seatbelt

/usr/bin/sandbox-exec -p <profile> /bin/bash -c <命令>
机制
profile内联生成，(deny default)兜底，逐条往上加放行。嵌套再开一层沙箱会被拒，放宽不了。
额外放行
sysctl-read和mach-lookup都是无名字过滤的全开，结果是剪贴板可读、Apple Events通道开着、security能触达securityd。写范围里还整树带上了/private/var/folders。
硬伤
开了就干不了活。/dev不在写白名单，2>/dev/null直接报错；/usr/bin/git和/usr/bin/python3是跳板，真身在CLT目录、不在exec白名单，所以git和python全废。conda python、nvm node、ps、/sbin、/usr/sbin同样被拒。
潜伏
工作目录用f-string直接拼进(subpath "{cwd}")，未转义。配平括号的路径能放宽写范围，不配平的会让解析失败、命令不执行。目前没有模型可控的路径到得了这里。
LINUX

bubblewrap

bwrap --ro-bind / / --bind <cwd> <cwd> --tmpfs /tmp --proc /proc --dev /dev --unshare-net
机制
挂载视图重建：根只读，工作目录单独bind成可写，网络命名空间单独隔离。只隔离了net一个命名空间。
额外放行
/dev/null可写，exec完全不限制，环境变量全量继承（没有--clearenv），没有seccomp过滤。
硬伤一
看得见也杀得掉沙箱外的进程。没有--unshare-pid，/proc挂出来的是宿主PID视图。实测在沙箱里读到了沙箱外进程的/proc/<pid>/environ和内存映射，然后kill -9把它杀掉了。这意味着即使把子进程环境洗干净，agent主进程的key照样能从/proc读走。
硬伤二
工作目录落在/tmp下会被抹掉。bwrap按参数顺序挂载，--bind cwd在前、--tmpfs /tmp在后，后者盖住前者。实测ls、cat、写全部报文件不存在，宿主侧文件还在。memory写入器的暂存目录正是tempfile建的，这是接入的硬阻塞。

03开关为什么失效

开关是一个ContextVar。设它的地方和真正执行命令的地方不在同一个上下文里，值就丢了。 三条路径里两条在丢，其中一条是用户最常用的Web。

为什么说是漏改不是设计：functions/_runtime.py和agent/task/runner.py把活交给别的线程时都正确做了copy_context()， 只有webui/下一次都没有。
另外两件事：开关没有配置项，config_schema.py的SETTINGS里找不到sandbox， 只能靠两个手动toggle，默认关；平台工具缺失时_invocation直接落到普通执行分支，不报错也不提示， 已经是ON的状态下工具消失就是无声降级。

04覆盖面

全仓库约25处会把内容变成运行中的进程，走沙箱的只有1处，而且还要求开关真的传到了执行点。

从模型输出到宿主进程内任意代码，最短的一条路径不经过bash，也就不可能被wrap_command包住。

还有两处会拆掉闸门：spawn出来的子agent把轮次的permission_mode设成bypass， 而_gated_execute在bypass那一步就短路，位置排在会拦住bash / execute_code / process的risky工具检查之前（规则层的deny和ask更靠前，仍然生效）； webui/_runtime_management.py往create_runtime()传的sandbox="read-only"看着像在防护， 而provider那边把这个kwarg明确记为接受即忽略。

别人怎么做

references/下八个框架逐一：claude-code、codex-cli、openclaw、opencode、 hermes-agent、pi-mono、pi-ai、weclaw。 其中四个完全不做系统级沙箱，这本身是一种设计立场，下面写清它们各自靠什么替代。 计数上有两点：pi-ai是pi-mono同上游的只读子集、没有执行面； claude-code和pi-mono的扩展调的是同一个外部包，所以这一组里独立的系统调用级实现只有两份。

05八家的隔离立场

按隔离强度分四档。左边是主动移除隔离的，右边是把执行推到另一个内核视图或另一台机器的。 同一个框架出现两次，表示它跨档：左边是默认路径，右边是可选配置。

09缺口对应到谁解决了

左列取自层一的实测结果，中列是层二里已有的做法，右列是它落在修复路线的哪一步。

10修复路线

五步按依赖排，每一步都是下一步能产生价值的前提。每张卡底下标出这一步抄的是哪一家。

STEP 01

可用性

macOS补/dev/null等字符设备的读写；exec白名单换成不限制，靠子进程继承沙箱兜底；Linux按路径判断挂载顺序，cwd在/tmp下时先挂tmpfs再bind。
不做：一开沙箱，macOS上git、python3、node和2>/dev/null全部失败，Linux上/tmp里的工作区静默消失。用户第一件事就是关掉它，也就是现在这个状态。
抄：codex-cli 的字符设备规则；两个系统调用级实现都放开exec
STEP 02

凭证屏蔽

两个平台加deny-read glob并且出厂就装弹：ssh、aws、~/.openprogram/auth/**、~/.claude.json、**/.env、keychain。macOS上deny读要和deny删除成对发。子进程环境变量按白名单传，名单从provider注册表推导。Linux同时加--unshare-pid。
不做：沙箱防不住这里唯一值得防的东西。接上memory写入器就补齐了那条不需要网络的凭证外传链路。
抄：hermes-agent 的注册表推导；openclaw 的兜底名字正则；claude-code 的配置文件写保护
STEP 03

开关语义

砍掉ContextVar，改成显式参数sandbox: SandboxPolicy | None由调用方传；工具定义带默认值，会话设置提供默认来源。SETTINGS加一组sandbox.*键。不可用时默认拒绝执行，文案说清缺什么、给两条出路。
不做：开关在三个边界上丢，两处已实测。Web路径和每个agentic function里沙箱都是关的，界面显示什么都不影响。
抄：codex-cli 的per-command策略；openclaw 的硬拒绝文案与doctor预警
STEP 04

默认开

默认workspace-write语义。前提是01到03都做完，否则默认开等于默认坏。
不做：一个默认关又没有配置项的机制在真实使用中不会运行，前三步全都无从检验。
抄：codex-cli 的默认立场，八家里唯一默认就开的
STEP 05

审批联动

正向：将在沙箱内执行且策略未放宽的bash跳过审批卡。反向：沙箱内被拒的命令带原因发起审批，批准后不带沙箱重跑。向下：一条bypass掀不动的底线，加上cron和子agent的按上下文默认值；任何命令pattern规则之前先归一化并解包argv。
不做：沙箱纯粹是额外负担，审批一次不少、能跑的命令变少，没人会打开它；而且几条bypass路径会继续绕过沙箱做的一切。
抄：claude-code 的沙箱内免审批；codex-cli 的失败升级；hermes-agent 的hardline底线与按上下文默认值；openclaw 的argv解包
配套的profile修补清单（不构成独立步骤，跟着01和02一起做）： sysctl-read和mach-lookup收成具名白名单，/private/var/folders收窄到本进程的TMPDIR， 工作目录拼进profile前先转义，放开exec之前补上限定在同沙箱内的signal和process-info*， Linux加--new-session --die-with-parent --unshare-user --cap-drop ALL， 把.git和functions/agentics/加进禁写，两条路径统一用/bin/bash。
接memory写入器的边界：它有两个执行面。MCP的shell工具在OpenProgram进程内跑，形状和_invocation一致，包起来是几行； Claude Code CLI子进程里的Read/Write/Edit/Grep/Glob在CLI进程内部执行，wrap_command够不着， 而这个CLI进程也不该被包进沙箱，因为它要调Anthropic API而沙箱没有网络。 上一轮到此为止，结论是只能靠allowed_tools。本轮修正：openclaw对嵌套的Codex app-server做的是坐在协议上分类每个方法、拦掉 command/和fs/、再注入绕回自己沙箱的替代工具。Claude Agent SDK有对等的缝，can_use_tool回调加几个MCP提供的替代工具能把文件操作放回我们的策略下面。 所以准确的说法是这些内置工具按现在的接法在沙箱之外，不是原理上够不着。第01、02步仍是硬前置，第03步是因为写入器跑在后台线程和子进程里、ContextVar到不了。
一句话收尾：现在的问题不是策略不够严，是三件事同时成立：开关在真实调用路径上多半是关的、 开了之后macOS上正常工作干不了、最该防的凭证是敞开的。三条各自都能让这套机制归零，所以顺序是 可用性 → 凭证屏蔽 → 开关语义 → 默认开 → 审批联动。八家对标改变的不是这个顺序，是每一步的具体做法有了可以直接照抄的先例。
