Agent Goal 功能：实现方式对比

本文比较 Goal 在运行时中的真实职责：目标数据放在哪里、谁触发下一轮、谁判定完成、如何限制资源、如何处理等待与人工介入、进程重启后能否恢复。重点不是功能名称，而是控制流和状态所有权。

1. 范围与比较口径

一个系统只有在保存目标状态，并能在普通 agent turn 结束后根据该状态决定是否自动开始下一轮时，本文才把它记为“原生 Goal”。Todo、Plan、Task、Cron 可以参与 Goal，但单独存在时不等于 Goal。

比较对象

OpenProgram、Codex、Claude Code、Hermes Agent；OpenCode 与 OpenClaw 作为相邻实现；OpenAI Agents SDK、LangGraph、AutoGen、CrewAI 作为通用框架基线。

固定观察维度

入口、状态结构、循环触发、完成判定、预算、等待、人工介入、持久化、恢复、并发控制、事件与 UI。

证据优先级

公开源码与本仓库源码优先；官方运行文档用于闭源实现；产品表象只用于说明接口，不用于推断内部数据结构。

Claude Code 的实现源码不公开。本文对它只记录官方文档明确给出的控制合同：/goal 是 session-scoped prompt Stop hook、判定器输入、三种 verdict、恢复和后台任务等待规则；不推断它的数据库表或内部类名。

Goal 总控制流程

四个原生实现都包含“工作完成后决定是否再开一轮”，差别集中在状态由谁保存、完成由谁判断，以及等待是否会暂停执行。

一个 Goal 从输入到终止的最小闭环实线是当前工作路径；虚线表示未完成或外部条件变化后的再次执行。

任务无法完成时，控制器如何停止

原生 Goal 会在普通 agent turn 结束后自动决定是否继续，因此必须同时处理“暂时没有完成”“缺少外部条件”“目标不可实现”和“持续没有有效进展”。只有轮数上限不能识别这些原因，只能限制最坏情况下的执行长度。

困难任务的状态机绿色是成功；黄色状态必须停止自动工作并等待明确事件；红色状态需要修改目标、预算或运行环境后才能继续。

为什么“调用了工具”不是进展

工具调用只能证明 agent 执行了动作，不能证明验收条件更接近满足。停滞检测应比较连续轮次新增的 evidence refs、通过的 deterministic gates、未完成 checklist 项和外部状态变化。相同证据反复出现时，应进入 stalled，而不是重置停滞计数。

等待不能占用工作轮次

问题先进入持久化异步队列；只要还有不依赖答案的安全工作，controller 就继续执行。仅当全部剩余工作依赖答案时才进入 waiting_user。CI、后台进程、时间或外部事件进入 waiting_external；当前需要显式 resume。

结论：这些实现都不能仅凭语义 evaluator 保证收敛。可靠的控制器需要硬预算、基于证据的停滞检测、明确的 blocked/impossible/waiting 分类，以及只有外部事件才能解除的等待状态。

数据与判定

  • 入口只有一段 prompt；同一文本交给工作 agent，并由 refinement 生成完成规格与 checklist。
  • schema v3 快照包含 goal/run ID、revision/version、typed status、预算/用量、checkpoint、问题队列和待消费答案。
  • session 入口把 refinement 与 judge 作为不推进主线的独立 agent turn；无 session 的 programs run goal 也在当前 runtime 中执行带只读工具约束的独立 refinement/judge turn。
  • judge 不只阅读工作 agent 的声明，还能检查文件、命令输出和清单项；严格 JSON 解析失败会重试一次，连续 3 轮判定失败进入 failed。

停机与恢复

  • 默认 150 个工作轮次，并支持 token、active-time 与 cost 总预算；清单停滞和连续无工具轮次会进入 stalled。
  • /goal clear 写 cancelled，取消旧 execution；CAS version 防止旧 controller 覆盖新操作。
  • needs_user + can_continue 把问题加入队列并继续独立工作；没有独立工作时才进入真正的 waiting_user。
  • worker 重启时执行中 Goal 进入 paused_recoverable；目标、checklist、用量、问题和 checkpoint 保留，resume 创建新 run。
实现判断：OpenProgram 已具备独立 tool-capable judge、typed states、版本化持久快照、异步问题、硬预算和重启后显式恢复。仍未实现通用 deterministic gate executor、外部事件自动唤醒与独立 evidence repository；同机 multi-worker 由 OS 文件锁提供独占 ownership。

数据与权限分离

  • ThreadGoal 是 typed record：thread_id、goal_id、objective、status、token budget、tokens used、time used、created/updated。
  • status 为 active、paused、blocked、usage_limited、budget_limited、complete。
  • 模型工具只允许创建、读取以及把状态改为 complete/blocked；pause、resume、budget/usage limited 由用户或系统控制。
  • 外部 app-server 提供 thread/goal/set|get|clear 与 updated/cleared 通知。

并发与完成语义

  • Goal mutation 与 idle continuation 共用 semaphore，写入使用 expected_goal_id 避免旧 turn 更新新 Goal。
  • resume 读取持久 Goal；只有 active 才重新登记 idle continuation。
  • completion audit 写在 continuation prompt 中，由同一个工作 agent 基于实际证据决定是否调用 update_goal，没有独立模型复核。
  • blocked 要求同一阻塞连续出现至少 3 个 Goal turn；token budget 耗尽由系统转为 budget_limited。
实现判断：Codex 的优势是 first-class state、权限边界、CAS 式更新、资源核算和 resume；风险是完成判断与执行者相同，主要依赖 prompt 约束和工具调用纪律。它累计 elapsed time，但当前结构没有 time budget，也没有等待外部进程的专门状态。

复用 Hook 协议

  • 普通 Stop hook 可返回 decision:"block" 和 reason；reason 进入 Claude 的下一轮上下文。
  • prompt hook 可由模型返回 ok、reason、impossible。/goal 在这一通用机制上增加 condition、状态显示和恢复。
  • stop_hook_active 防止扩展脚本无条件递归；通用 Stop hook 连续阻止 8 次后由运行时强制结束。
  • Goal evaluator 只看对话中已经出现的证据，不读取文件或运行测试。

等待、错误与预算

  • 后台 shell/subagent 运行时不判定；完成结果会触发新 turn。长时间等待使用退避 check-in，交互会话每次用户输入之间最多自动发起 3 次 idle check-in。
  • 连续多轮无工具进展时停止自动循环，但保留 Goal，等待下一次用户 prompt 后继续评估。
  • 不可恢复的 auth、余额、无法压缩的 context overflow、模型不可用会清除 Goal；瞬时错误保留 Goal。
  • Goal 没有独立 typed budget；可把 turn/time 终止条件写进 condition。外层 print mode 另有 --max-turns 和 --max-budget-usd。
实现判断：Claude Code 证明了 Goal 可以作为通用“停止拦截器”的特化，而不需要独立执行器。它对 background work 的 defer/check-in 处理完整，但 evaluator 无工具，可靠性依赖工作 agent 把验证证据写入 transcript。

完成合同与 gate

  • GoalContract 把 outcome、verification、constraints、boundaries、stop_when 分开保存，并同时注入工作 prompt 与 judge prompt。
  • GoalGate 在 LLM judge 之前执行；失败时跳过 judge，限制输出尾部并把失败证据作为 continuation。
  • gate 记录 attempts、exit code、output tail 和 workspace fingerprint；工作区未变化时复用失败结果，避免重复运行同一检查。
  • subgoal 是用户追加的验收条件，不重启主 Goal，也不重置原始目标。

状态、等待和适配层

  • GoalState 保存 status、turn budget、judge failure counters、subgoals、wait barrier、contract 与 gates。
  • judge 输出 done、blocked、continue 或 wait；wait 可指定 PID、process session 或秒数。
  • CLI 与 gateway 共用 GoalManager，但各自负责把 continuation 排进现有消息队列；不修改 system prompt 和 toolset。
  • Goal 状态随 session resume 恢复；context compression 造成 session id 轮换时迁移 Goal 并清理旧记录。
实现判断：Hermes 当前方案把“可验证完成”和“外部工作尚未结束”分开：确定性 gate 对验证结果负责，judge 对开放式语义负责，wait barrier 对异步依赖负责。默认仍是单 session 单 Goal 与 turn budget；总 token/cost budget 不属于已确认的 GoalState 合同。

实现方式

  • SessionPrompt.run 循环读取最新消息；assistant 有非 tool-call finish reason 且不存在未处理 tool call 时退出。

OpenClaw

把持久工作拆成 scheduler、background task、heartbeat、standing instruction 与 commitment，而不是提供通用 Goal evaluator。

调度与状态

  • Automation job 保存 id、name、enabled、schedule、session target、wake mode、typed payload、delivery、failure alert 和 run state。
  • payload 分为 system event、agent turn、command、script；session target 可为 main、current、isolated 或命名 session。
  • 运行结果区分 execution 与 delivery；持久化 job、运行状态和历史，gateway restart 后继续调度。
  • 脚本与 command 可以用 exit code 提供确定性成功，但这只判定一次 run，不判定开放式目标。

Heartbeat 与 commitment

  • Heartbeat 是系统拥有的 monitor automation；读取 scratch 或 HEARTBEAT.md，无到期任务时跳过模型调用。
  • 结构化 heartbeat task 只有 name、interval、prompt，按各自周期进入下一次 monitor turn。
  • Commitment 记录 agent promise 或从用户上下文推断的后续联系，包含 due window、confidence、status、attempts 与 delivery scope。
  • 这些机制擅长“何时再次执行/通知”，但没有 met/unmet evaluator，也不会把多个 run 约束为同一个完成条件。
实现判断：OpenClaw 最适合作为 Goal 的外部等待和调度参考。把它直接称为 Goal 会丢失完成判定语义；更合适的组合是 Goal controller 在需要未来时间或外部事件时创建/绑定 automation，收到事件后再恢复 Goal。

OpenProgram 当前合同与剩余扩展

Goal 不新增第二套 agent loop。当前 controller 位于现有 session/dispatcher 之上，工作仍通过公开 agent() 执行；图中 implemented 是当前代码，target 是尚未实现的扩展。

  1. Spec 与 run 保存在一个版本化快照中。goal_id 跨 resume 保持稳定，run_id 标识一次 execution；编辑生成新 revision，并重新完善 spec/checklist。refinement 只转述用户要求与必要正确性检查，保留“约”等近似约束，不自行增加格式比例、基准名、数量门槛或参考作品比较；重要歧义作为待确认问题保留。
  2. Stop policy 在阶段边界检查累计预算。rounds、tokens、active elapsed time 和 cost 在 resume 后累计；等待和暂停不消耗 active-time 预算。工作轮次默认限时 300 秒，provider 静默流受整个调用的截止时间约束；累计预算不是对当前阶段的精确抢占上限。
  3. Controller 是状态转移提交者。每个阶段保存 checkpoint；pause/edit/answer/cancel 与旧 controller 使用 CAS version 竞争，旧执行不能覆盖新状态。
  4. Evaluator 是独立 inspection agent。它输出 met、unmet、blocked、impossible、waiting_external、needs_user 和 can_continue。本地检查之外提供 web_fetch、web_search，沿用现有 URL 与网络权限检查；网页工具的失败通过结构化 is_error 回执传递。一次判定含失败的工具检查回执时，controller 不接受 met，先重新判定；持续失败报告 judge failure。该规则保守地要求一次无检查错误的验收，不证明成功回执本身足以满足全部语义要求；通用确定性 gate executor 尚未实现。
  5. 异步问题队列不阻塞无关工作。问题可以累积并逐项回答；active execution 在下一个边界消费答案，只有所有剩余工作都依赖答案时才进入 waiting_user。问题只占用 Goal 详情面板，不替换或禁用普通 composer。
  6. 重启恢复采用显式新 execution。启动 reconciliation 把遗留执行状态改成 paused_recoverable；恢复沿用快照而不尝试复活旧调用栈。
  7. 外部 scheduler 是目标扩展。waiting_external 已有状态，但 job/timer/event 的自动 wake handle 尚未实现。同机共享 session store 的 Goal controller 使用独立 OS 文件锁，启动恢复持相同锁，避免改写 live sibling 的状态。

实现与验收合同

独立规格审查要求保证两项合同：真实人类依赖转入等待，不能被普通无进展计数覆盖；Web 操作成功后的 HTTP 快照立即更新可见状态与共享缓存，旧版本事件不能回退新状态。修复限定在 Goal 状态转换及前端投影，不改其他工作流。验收分别使用公开 Goal → 回答命令的回归测试，以及无 WebSocket 广播的操作响应与重新挂载测试；修复后需要原审查者复核，再做独立质量审查。

真实人类依赖不会被无进展计数错误覆盖，预算判断仍独立执行。前端通过共用 updateSessionGoal 按 session version 应用 HTTP、WebSocket 与 hydration 快照；无广播暂停、重新挂载、乱序消息、后台会话及迟到加载由 4 项组件测试覆盖。Web 测试合计 229 项通过，TypeScript、静态检查和 32 页生产构建通过；等待状态与前端修复的独立规格复核均通过。构建仍有既有 Next SWC lockfile 修复警告，未改依赖锁文件。

控制器保存使用 CAS；发生同运行并发更新时，以最近确认快照、本轮状态和磁盘最新状态合并，并在 session 写锁内提交，不执行无界重试。合并仅允许相同 goal_id/run_id 且最新状态仍在执行的情况；预算和新答案保留，本轮进度与已消费答案也保留。暂停、取消、替换运行仍拒绝旧控制器写入。终止保存共用此路径；新答案使旧终止判定失效，保存为 paused_recoverable / answer_received，用户可继续处理，不能误报 achieved。分批消费的答案共同进入后续工作提示；再次恢复时从当前 revision 的持久问题记录重建已确认决定，并恢复有长度上限的 evidence window。编辑目标隔离旧 revision 的决定和证据。

并发修复的独立质量复核为 PASS，覆盖原有“修改预算导致控制器退出但仍显示运行中”的复现。审查者独立执行 9 项针对性回归通过：预算/答案在 evaluating/terminal 的竞争、暂停/取消/替换运行、消费期间收到新答案及旧 CAS 拒绝。集成后的 Goal、存储和 Web API 相关测试通过，完整统计见下方全量验证。该结论限于已审修复，不能代替修复后全量验证、尚未实现的设计能力或默认 App 可视验收。

实现状态与证据边界

当前代码已经具备

  • 单 prompt Goal、Working Agent 与独立 inspection judge。
  • schema v3 版本化 session 快照、goal/run ID、checkpoint、CAS 写入和旧数据规范化。
  • typed stop states、round/token/active-time/cost 预算、checklist stall 与 idle-spin 检测。
  • 异步问题队列、逐项回答、边界消费、有人/无人值守判定策略。
  • Web Goal dialog、TUI 操作、页面重载 hydration 与 worker 重启后的可恢复暂停。
  • 五张 Archify typed source 生成并以内联 SVG 写入本文档。

仍未实现或尚未验收

  • deterministic gate executor、外部事件自动 wake handle 和 append-only evidence repository。
  • 跨主机分布式 lease；同机共享目录的 Goal ownership 已实现。
  • 默认 App 的已验收范围见上文；异步回答的完整界面操作、无障碍树与暂停执行取消仍未全部验收。
  • Goal 主体与恢复启动修复已合入主分支并包含在默认 App；执行树摘要缺陷尚未修复。
