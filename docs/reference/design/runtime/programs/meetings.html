Meetings

Built from what exists: voice-input speech engines, the long-running session shape of workflow recording, the owner turn of reminders and check-ins, the browser microphone API and computer use's ScreenCaptureKit stream. No new infrastructure.

Parts

Meetings is an application package (openprogram/programs/applications/meeting/): a manifest, a Python backend and a built window. It runs like any installed application; what only the host can do it asks for through capabilities, so the package carries no import of the host's code and can later be exported with a trimmed runtime.

  • An operation still runs in a process of its own. A host call is a host event on the runner's stdout; the application service answers it in the worker (programs/_host/ui/host_calls.py) on the runner's stdin. The core never imports the speech interface: it reaches it through speech_link.
  • A recording outlives one operation and the window, so the host owns it: one per instance, at most 4 hours. Each chunk is written to recordings/<key>/<track>/<seq>.<ext> and handed to ingest one at a time, in order; when the recording stops and every chunk is in, finish runs with its final status. Disabling the application cancels without finish.
  • Every save of the state document signals application-state, every recording change application-audio; the App forwards both to the window as state and audio events, so it reads again instead of polling.
  • The window draws in the App's theme: the host posts its data-* attributes, colour scheme, language and custom properties (appearance), and the SDK applies them to the page before its first frame. Fonts ship with the package, as the sandbox loads them only from its own origin.

The computer's sound, on the server
  • audio.start with the system track starts capture in Recording.begin. ScreenCaptureSource reads the shareable content and builds SCContentFilter.initWithDisplay_excludingWindows_(display, []) for the first display, no window excluded.
  • screen_capture_audio.open_audio opens the stream: capturesAudio, 16 kHz, one channel, excludesCurrentProcessAudio, a 2×2 frame once a second, no screen output attached. Computer use's per-application recording (desktop/common/audio.py) shares this module and differs only in its filter.
  • macOS asks for Screen & System Audio Recording the first time. The worker runs inside the App's runtime bundle (screen_recording capability in openprogram/host/system_access), so the prompt and the System Settings row name the App. ScreenCaptureKit audio needs no other declaration.
  • SystemAudio is independent of ScreenCaptureKit. A source pushes float32 buffers; it cuts 30-second chunks by sample count. A chunk's t_ms is the meeting clock at its first sample: the arrival of the buffer that starts it, less that buffer's remaining length.
  • Its own thread converts each chunk to 16-bit WAV and calls Recording.take("system", seq, t_ms, wav, "wav"), the intake the microphone's uploads feed.
  • Recording.stop stops the stream and flushes the last partial chunk while still recording. Cancelling (the application disabled) drops it.
system_audio_reasonWhen
unsupportedNot macOS, or PyObjC's ScreenCaptureKit does not import
permissionScreenCaptureKit refusal (error -3801 "declined TCCs") or CGPreflightScreenCaptureAccess reporting no grant
errorAnything else; text in system_audio_message

If the source cannot start, the recording is microphone only and its status, then the meeting's entry, say system_audio: "unavailable". A working capture reports recording.

The microphone, on the App's page
  • The sandboxed window has no microphone. On audio.start the App's page asks for it, then starts the host's recording, and counts chunk offsets from the elapsed_ms in the start response, so both tracks share one clock.
  • MediaRecorder is stopped and restarted every 30 seconds. A timeslice recorder emits later chunks without a WebM header; restarting makes each a complete file, at a cost of a few milliseconds' gap per chunk.
  • A chunk carries track, sequence number and offset (t_ms), so out-of-order uploads land in place. One stopped under 100 ms after it started has only a header and is not uploaded.
  • Uploads go to /api/application-instances/<instance>/audio/<recording>/chunks, serialized and tried three times on network or 5xx errors. A 4xx means the recording ended elsewhere (Stop in another window, the time limit): the microphone stops.
  • The recorder lives in a module-level store keyed by instance: closing the window or switching tabs does not stop it, only Stop does.
  • A refused microphone arrives as NotAllowedError; the window names the System Settings pane.
  • The recording card says whether the computer's sound is recorded. If not, it says microphone only and, for permission, names Privacy & Security → Screen & System Audio Recording and asks to reopen the App.

The meeting's id is the recording's key. ingest transcribes one chunk, writes its JSON beside it and updates the entry; a request key per chunk makes a repeated hand-over run once. A chunk that fails is recorded and counted; the meeting goes on. Saves retry when another operation changed the document first.

LanguageThe meeting's, never Settings → Voice's: a forced voice-input language makes Whisper invent text. The start operation takes an optional ISO language, stored in the entry. The window sends the choice beside the meeting name, none for "Detect automatically". Empty means detection: whisper.cpp -l auto, no language field for OpenAI and Groq.
Timing by enginewhisper.cpp prints [from --> to] lines (no -nt). Groq and OpenAI Whisper models answer verbose_json. gpt-4o-*-transcribe answers text only: one segment spanning the chunk.
Merge, transcript.pySegments move onto the meeting clock and sort by start. A microphone segment at least 75% similar to a system segment starting within 4 s is echo (no headphones) and is dropped. Consecutive segments of one speaker less than 1.5 s apart join into one turn, up to 600 characters.
Linespeaker (me, others, others:<n>), which the window localizes, and English label ("Me", "Others", "Speaker n"). The window reads the lines with transcript after each chunk, so it shows them growing.

Access

  • The window reaches nothing but its bridge; the recording, chunk and show routes under /api/application-instances/ need the owner's sign-in and the capability in the manifest.
  • The microphone is recorded where the App's page runs; the computer's sound is always the worker's computer's.
  • Meetings stay in the state directory. With a cloud speech engine each chunk goes to that provider. An update's trial copy leaves applications' files out.

Speaker diarization

Once per meeting, over the whole system track, so clustering sees every voice at once and no embeddings are matched across chunks. About 4 s per minute of audio on four threads.

StepWhat
AudioSystem chunks in order, converted one at a time and concatenated. concatenate records (concat_ms, t_ms, duration_ms) per chunk; to_track_clock maps turns back and splits one crossing a boundary. Lives in interfaces/speech/diarize.py, reached through context.diarize.
Diarize, runsherpa-onnx OfflineSpeakerDiarization; pyannote segmentation-3.0; 3D-Speaker's bilingual CAM++ (3dspeaker_speech_campplus_sv_zh_en_16k-common_advanced.onnx); up to four ONNX threads; min_duration_on 0.3 s, min_duration_off 0.5 s; FastClusteringConfig(num_clusters=-1, threshold=0.75), as the speaker count is unknown.
Label, backend/speakers.pyEach system segment takes the speaker whose turns overlap it longest (ties: lower sherpa number). Renumbered others:1, others:2… by first appearance. Written back to the chunk JSON and merged again, so transcript.json, summary.md and the prompt carry "Speaker n".
Stays "Others"A segment no turn overlaps, or whose only voice was heard under MIN_SPEAKER_MS (3 s) in the whole meeting. Clustering leaves one- or two-second strays that would become "Speaker 5" to "Speaker 7".

Why this model and threshold

Tried on four recordings with known speakers: pyannote's AMI excerpt (two people talking over each other, scored against its labels), sherpa-onnx's four-speaker test, a two-voice recording and four synthesized voices.

SettingResult
CAM++, 0.6–0.75Right speakers on all four; 91% of AMI speech labelled right
CAM++, 0.8Merges two of the four Chinese speakers
Top of the range, 0.75On a four-person AMI meeting through a conference call and plain playback, splits one person into two numbers least often: five numbered voices, against seven at 0.65
ERes2Net zh-cn (sherpa-onnx's example)Needed a different threshold per recording; merged the AMI pair at every value that kept the four-speaker recording at four
Dependency and model download
  • sherpa-onnx is the optional meetings extra (with numpy), also in all so the packaged App carries it. Imported only inside run.
  • Models download on first use from sherpa-onnx's GitHub releases into <state>/models/diarization/: speaker-segmentation-models/sherpa-onnx-pyannote-segmentation-3-0.tar.bz2 (only model.onnx extracted) and speaker-recongition-models/…_16k.onnx.
  • Each goes through a temporary file and an atomic rename under one lock, as voice input downloads Whisper models.

Implementation status

Everything above is built. Open: exporting the package as a standalone App with a trimmed runtime that answers the same host calls; a check of the Screen & System Audio Recording prompt and permission classification in a freshly installed App.

How it is verified
  • Tests with a faked sample source, ffmpeg, speech, diarizer and summary turn; the backend's tests run it against a stand-in context and check that it imports nothing of the host.
  • The stable App recorded recordings played through the computer's sound output: sherpa-onnx's four-speaker test, an AMI two-speaker excerpt (both found), an AMI four-speaker excerpt (all four found, every line's number consistent with the reference).
  • A real call: two participants in a Jitsi Meet room, the second speaking the AMI four-person excerpt, the first playing it on this computer. Exactly four numbered speakers, every line consistent. Call audio reaches the recorder through the same path as Zoom or any other application.
  • Microphone track, from the Meetings window in a browser whose microphone was the AMI excerpt: seven chunks uploaded, six lines labelled "Me", summary written. The header-only last chunk was the one failure; the page now skips it.
