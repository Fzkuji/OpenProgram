Agent collaboration

A saved AgentSpec is reusable configuration (Agent configuration). A runtime branch is conversation state and can run many Jobs; creating one creates no AgentSpec. To isolate code edits: worktree tools. How the 21 reference harnesses do this: comparison.

Each choice follows one of the 21 reference harnesses (comparison).

Saved Agent settings

SettingRule
delegationon: listed in the agent description and startable by other agents. Empty: on for an Agent with tools, off for one without (tools.mode="none"). Editing the list announces a prefix-cache break (agent_roster).
isolationworktree or none when started by another agent. Empty: a background helper whose tools can write gets its own worktree in a git repository, otherwise shares the folder. A call's isolation wins. The worktree cannot be merged or discarded while its helper runs (owner_running).
permissionsWhat it may do when another agent starts it: mode, allow, deny, ask (rules), additional_directories, sandbox. Each key only narrows its caller (Permissions). Empty: it runs as its caller. Its tool policy narrows the same way.
ExplorerBuilt-in, read-only (read, search, web, read_conversation). Without a model of its own it runs on the utility tier: the Lightweight helper's model when that has one, else the usual fallback (builtin_agents.UTILITY_TIER).
Markdown agent files.claude/agents/*.md and .agents/agents/*.md in the project folder (up to its git root) and the home folder, nearest first, at most 50. Frontmatter name and description are required; tools maps Claude Code names (Read, Bash, …) and drops the rest, none meaning every tool; model counts only as provider/model; isolation as above; the body is the system prompt.
A Markdown agent hereId md:<file stem>, delegation on, memory off. A saved Agent wins a name. Writes do not see them (update, delete and set-default report not found); duplicate one to edit it here. Not on the Agents page.

The Agents page edits both: General has the switch "Other agents can use it" (delegation; an Agent that never set it shows its default), Advanced has "When delegated" (isolation: Automatic, Same folder, Own worktree). Both settings are stored on agent.json and travel through PATCH /api/agents/{id} and AgentConfigDTO. Empty means the default, so no stored Agent is rewritten.

Permissions

For every helper and delivered message, the caller's mode, rules, extra folders and Sandbox are frozen into the Job when it is admitted (spawn_permission_snapshot), a Sandbox left to the caller's project resolved against the caller's conversation; the Agent's permissions block then narrows them.

SettingThe helper gets
ModeThe stricter of the two, in the order Plan, Ask, Accept edits, Auto, Bypass
Deny and ask rulesThe caller's plus the Agent's
Allow rulesThe caller's; when the Agent lists allow rules, only those it also lists. An Agent's allow rule alone allows nothing.
Extra foldersThe caller's; when the Agent lists folders, only those it also lists
SandboxOn when either turns it on
A call that needs approval, inResult
A foreground helper (fresh or fork) of a person's turnThe existing approval card in the caller's conversation. Its title row names the helper in a badge (asked_by on the question frame) on the command, screen and terminal cards; the CLI prompt and a channel message put the name after their heading. The answer resumes the helper; the caller's tool call keeps waiting through it. "Always allow" saves the rule for the conversation as usual.
A foreground helper forked into another conversation (start_from="SID:MSG")The same card, shown in the caller's conversation where the person waits: the question carries asked_in_session, so the live frame and a reload's list (waits.list_open) put it there.
A background helper, a delivered message, or a caller no person answers forRefused at once (HELPER_CANNOT_ASK): the tool result says to go on without it and name what was needed in the final reply. Nothing waits.

The route is frozen on the helper's stored input (asks_through) at admission, only when its caller is the live owner turn whose policy it inherited. This moves where an existing question is shown; it adds none.

Closing and archiving

close_agent(execution_id) checks the Job belongs to this conversation, stops it with its descendants (cancel.parent, so no stop notice comes back about the caller's own act), archives its branch and drops its pending notice. Archiving writes archived: true to the branch; history is kept and there is no unarchive.

On an archived branchResult
Normal list_agentsHidden; scope="archived" shows it

Running executionContinues, unless closed with close_agent

PartRule
statuscompleted, failed, stopped or stalled; a limit adds reason (user, spend cap, timeout, idle limit)
ReplyThe final reply, cut at 20,000 characters with a read_conversation pointer; a background spawn's reply travels in the notice (an older unmarked card carries it instead); a stopped helper, waited on or in the background, has no final reply and reads (no reply) Its work so far: read_conversation("<id>"), with its branch tip set to the reply row it was writing, as Claude Code tells the caller only that the task was stopped
FilesWhen the helper had its own worktree: changed files and line counts
UsageDuration and tool calls on its branch; tokens and cost from the usage ledger for the helper and every helper under it (agent_result.subtree_job_ids); a cost with an unknown price is left out, not guessed
StageBehaviour
QueueEvery terminal path goes through JobRunner._update_attach_card: patches the card with status, usage and, for a helper with its own worktree, the files it changed (attach.files: count, branch, uncommitted), applies archive_when_done, queues an entry in the caller's notices.json. Background Jobs that completed, errored, or were stopped by the person or a limit; a stall is queued once as its own entry.
Deliverrun_job_notices sweeps every 2 s; a session is busy while a foreground execution runs. All pending entries become one automated notice turn (source="job_followup"). A notice has no timeout, so a reply is never dropped while the caller is busy.
FailureReported the same way; the notice says to retry narrower with send_message or tell the user. Nothing is resubmitted automatically.

Stored hand-offs

The removed handoff tool kept its turns in <state>/always_on/handoffs.json. When the Worker starts, every entry moves (always_on/handoff_migration.py) and the file is left empty; the hand-off's own replay is gone:

EntryBecomes
Waiting messageA delivery from its sender to its target, keeping its hop count and who waits above it; the reply comes back as a notice
Waiting replyA delivery from the conversation that answered (named in the reply) to the one that asked
Running or paused turnA watch: its sender gets the conversation's latest reply once it is idle (notices.watch)
Earlier conversations it also owes (owed_after)A relay each, nearest first: each gets the answer of the one below it once that one has answered (notices.hold_reply)
Finished, or a reply naming no conversationKept in the record only

The file is copied once to handoffs.before-migration.json first. Every entry is kept as it was in handoffs.migrated.json with its delivery state and execution_id. Each delivery's Job id and each watch's id are fixed by its entry, so a Worker that stops midway delivers each one once.

A delivery send_message refuses stays pending under a new Job id and is tried again at the next Worker start; one whose conversation is gone is marked failed. migrate() without apply only reports. The transcripts' 📨 and ↩️ rows are unchanged.

The chat reads a stored row's header and draws it as the one-line row other agent traffic gets, when the conversation it names exists.

The recipient answers in its final reply; a send_message back would deliver it twice, and the receipt says so. A message from another conversation is marked as another agent's input, not the recipient's user.

Attach pointers and cross-session spawns

A spawn writes an attach pointer with predecessor = caller_msg_id; the sub-branch never merges into the caller. send_message writes none, so its reply stays inline in the notice.

Caller node A in S with start_from="T:M" runs in T. The Job records parent_session_id=T, parent_msg_id=M, caller_session_id=S, caller_msg_id=A. The card in S is looked up by extra.attach.session_id and head_id; neither creating nor finishing it moves the selected HEAD of S or T (DAG attach rendering).

Cancellation

  • Follows parent_job_id: prevents unstarted descendants, requests cancellation of active ones, stays stopping until exit is acknowledged.
  • A stop by the caller itself (close_agent, cancel.parent) sends it no notice.
  • A terminal Job stays queryable; cancellation is idempotent.
