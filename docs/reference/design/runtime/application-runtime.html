建议：把 Application 定义为可重复使用的程序

OpenProgram 的应用包含自己的界面、业务逻辑、数据和依赖；框架负责应用注册、打开、运行上下文与公共能力。创建完成并验证的应用，以名称和图标出现在新标签页。用户点一下就打开应用，不需要重新描述需求，也不需要回到生成它的对话。

默认界面采用标准 Web 技术：HTML、CSS、JavaScript，以及编译后的 React、Vue 等。应用可以自行设计页面、编辑器、图表和交互，不必由 OpenProgram 的几个固定组件拼装。Python 后端处理业务和模型任务。HTML 是界面的实现技术，不能据此判断程序是否完整；后端、状态、运行合同和部署依赖才决定软件能力。

应用默认在 OpenProgram 中运行。架构允许同一应用以后用最小 runtime 单独部署，不要求打开整个桌面客户端；这仍属于依赖 OpenProgram runtime 的软件。完全去掉 OpenProgram 依赖，需要应用提供替代模型、存储和运行实现，不能承诺自动导出任何应用为独立程序。

这项设计的具体价值是：应用按钮与 Agent 使用同一业务操作，模型调用归入已有执行记录，业务数据不依赖聊天窗口，升级不会改变正在运行的任务代码。它是产品合同的组合，不能声称上述单项机制市场独有。Hermes 的 UI 扩展、MCP Apps 的可移植界面和 AgentOS 的运行服务都已有直接参考。[8] Hermes Desktop Plugin SDK [40] MCP Apps [29] Agno / AgentOS

已保存的内容

上方仅演示“从新标签页打开已存在应用”，不调用模型、不安装软件。四个内置项目作为背景展示；两个应用按钮和返回按钮可以操作。

同一应用在同一项目默认复用已打开标签页；不同项目可以分别打开，数据范围明确分开。新标签页没有活动项目时，先使用应用已绑定的项目；应用要求项目而尚未绑定时，首次打开才选择。应用不能跟随任意另一个聊天标签页的 cwd 静默改变数据目录。

“一句话创建”的入口仍是已有对话：Agent 编写应用包和依赖说明，完成构建与行为验证，然后在该创建任务授权范围内注册应用。注册成功才出现菜单按钮。创建失败保留源码和错误供修复，不把尚不能打开的半成品显示为可用应用；后续修改生成候选版本，验证后再替换。

第一次打开可能显示准备依赖或启动中；失败时留在同一个应用页显示失败原因和重试入口。普通页面关闭仅关闭视图。用户已发起的后台任务继续运行；重新打开读取同一任务状态。服务进程退出与业务任务中断分开报告。

调研范围与判断方法

本报告覆盖下表列出的主要公开 Agent harness、编码工具、嵌入式框架、应用平台及界面协议。分类按本问题中的作用划分，不是市场份额排名。协议不是 harness；纳入它们是为了回答界面如何集成，而不是把不同层次混称为同类产品。

DSH 发行包、worktable 和 OpenProgram 进行了相关代码路径核查；其他项目以当前官方文档、公开示例或仓库说明为证据。未安装并端到端验证所有产品。表中的“未核实”表示来源不足，不等于产品绝对不支持。Cursor、Windsurf 的内部实现未知。AutoGen、Semantic Kernel 在 Microsoft Agent Framework 的沿革中讨论，未伪装成三套已经逐项核查的当前实现。

“所有市面框架”没有封闭名录。未穷尽商业产品、社区分支及私有 harness；例如 Qwen Code、Strands 的相关页面本次未成功获取，Trae、Kimi CLI、各类云端软件生成服务也不在已核查矩阵内。这些缺口限制了市场唯一性结论，不影响下方已经明确的应用运行需求。

对每个项目分别问：扩展交付什么？谁加载和执行？谁渲染 UI？业务状态存在哪里？能否离开宿主？“会写软件”“能执行代码”“有 UI”“支持安装应用”分别判断，不互相替代。

哪些机制直接影响我们的选择

DSH：宿主插件和生成页面是两条不同路径

安装的 worktable 插件通过宿主服务和 UI 插槽工作，自己的分屏布局由 React 实现；它不是一个可以直接双击运行的独立软件。其“生成窗口”则根据产物清单读取 HTML、URL 或文件，把内容放入窗口。页面如果只使用自身资源，可以单独托管；一旦依赖 DSH 路由、会话或插件服务，离开 DSH 就缺少这些实现。[2] dsh-worktable

另一个机制是 DSH 动态 Cordis 插件：已读发行包中，host 部分注册处理函数，client 部分由宿主提供运行环境并调用后端。它可以有真实逻辑，不只是静态展示；但受支持 API、加载生命周期及动态代码格式约束，不是“任意代码都能在任意窗口运行”。其 Node vm 使用也不能当作操作系统级安全隔离。[1] DeepSeek Harness

Hermes 与 Pi：宿主扩展可以提供复杂交互，但依赖明确

Hermes Desktop SDK 有 pane、page、sidebar、status bar、palette 等贡献点；本地插件直接在宿主环境加载，与隔离 HTML 预览是不同执行路径。Dashboard 也支持页面与 slot。可采用其明确的贡献点和生命周期概念，但不应让普通生成应用拿到宿主全部内部对象。Pi 的自定义 UI 是终端组件，说明“插件界面都是 HTML”本身也不成立。[8] Hermes Desktop Plugin SDK [9] Hermes Dashboard extensions [3] Pi

OpenClaw：展示面板与交互应用不可混为一谈

当前 macOS widget panel 文档明确说明该面板只负责渲染；宿主集成操作在 Control UI 和 session dashboard 使用，A2UI 也属于 dashboard。不能只看同一个 canvas 名称，就把旧文档或其他界面的能力迁移到面板上。[11] OpenClaw Widget panel

MCP Apps、AG-UI、A2UI 分别解决不同问题

MCP Apps 提供可移植的 Web 资源与宿主通信合同；AG-UI 描述 Agent 和用户界面之间的事件；A2UI 让宿主根据组件目录渲染声明式数据。完整自由布局的应用适合 Web UI，常见表单适合可选声明式渲染，流式任务需要事件协议。三者均不自动提供应用安装、数据迁移和后台服务生命周期。[40] MCP Apps [41] AG-UI [42] A2UI

运行框架：独立部署不等于不依赖框架

LangGraph 的状态持久化、AgentOS 的运行 API、OpenHands 的 SDK/Agent Server 都支持将 Agent 能力用于自己的产品。应用可以独立部署，同时依赖某个运行库或服务。OpenProgram 应沿用这一依赖表达，不把“离开桌面客户端”与“删除全部 OpenProgram 依赖”混为一谈。[25] LangGraph [29] Agno / AgentOS [14] OpenHands

因此这不是单纯补一个按钮，也不需要重新实现整个 Agent harness。可复用来源管理、Program 注册、模型与 Agent 原语、执行记录和现有标签页基础；缺少的是应用定义、前后端边界、运行实例及持久状态之间的明确连接。

目标架构与责任划分

新标签页 / 应用标签页
名称、图标、打开、关闭视图
Application 定义
来源、版本、UI、操作、数据范围
应用 Web UI
自己的组件和业务交互
能力接口 / 运行适配器
校验身份、操作、授权和任务
已有 Tool / Workflow / Runtime
普通代码、llm()、agent()
应用状态 / 任务记录
业务数据、事件、结果与恢复

Application 是一种 Program 包，扩展已有来源注册。Plugin 是扩展宿主行为的安装单元；它可以贡献 Application 定义，也可以只提供工具或主题。不是每个插件都出现在新标签页，也不是每个 Application 都要改动宿主 UI。一个包只保留一份应用定义；插件适配和 Program 来源都引用这份定义。

普通应用只能在自己的标签页内渲染。全局工具栏、聊天编辑器、主题和系统级服务属于另一类受信宿主扩展，沿用插件权限。对应用暴露少量稳定的 API，不公开 React store、全局 session manager 或框架内部模块。应用可选用外观组件包，但标准 HTML 和独立前端构建同样有效。

第一阶段支持静态 Web 应用和带 Python 业务操作的 Web 应用。浏览器可执行的 JavaScript、Canvas、WebGL、WASM 可以用于页面；系统 GUI、GPU 驱动、任意二进制、任意语言服务不是浏览器天然能力。后续如需 Node/其他语言后端，增加明确的 runtime adapter 和依赖合同，不宣称首版支持任何程序。

包保留自己的依赖文件、测试和发布边界。发布 UI 使用构建产物，不在每次点击时运行开发服务器、安装 latest 依赖或让 Agent 再生成代码。应用没有后台操作时完全不启动 Python 进程；有操作时按需启动对应 runner。runner 是应用执行容器的逻辑角色，进程隔离与安全沙箱必须分别实现、分别标注。

最小应用合同

首版以应用清单引用 Python entrypoint 和已构建静态目录；以下为拟定字段，不是现在可以使用的 CLI 或 SDK。操作名只在 UI/进程通信边界寻址，Python 内部仍用普通函数 import 和调用，不新增第二套 Workflow 字符串调度系统。

{
  "id": "local.paper-reader",
  "title": "论文阅读器",
  "version": "1.0.0",
  "ui": { "root": "web/dist", "entry": "index.html" },
  "backend": { "kind": "python", "entry": "paper_reader.app:operations" },
  "scope": "project",
  "capabilities": ["model.invoke", "storage.app", "files.project.read"],
  "dataSchema": 1,
  "operations": { "summarize": { "agent": true, "input": { "type": "object" }, "output": { "type": "string" } } }
}

静态应用省略 backend，capabilities 可为空。id 是包内稳定身份，不使用标题、绝对路径或生成它的 chat ID。安装记录关联 owner、来源、内容摘要和已选版本；应用实例由 app ID、owner 和显式 project scope 标识。应用展示偏好如隐藏与排序属于用户偏好，不写入发行包。

对象责任与最少字段
ApplicationDefinitionapp ID、来源引用、版本/UI 资源、运行类型、操作 schema、能力需求、数据 schema。
Installation引用已有来源记录；选中版本、启用状态、验证结果和权限决策。不是复制源码目录就算安装完成。
AppInstanceowner + app ID + project scope；业务数据位置及活动运行。一个窗口不是一个数据库。
Viewtab ID、instance ID、UI route、正在显示的运行；可以销毁并重建。
OperationRunrun ID、instance ID、操作版本、输入、身份、幂等键、状态、事件序号、结果引用。与已有执行记录关联，不复制完整 DAG。

跨进程操作提供输入/输出 schema。客户端不能自行指定任意 import path、源码路径或 owner；服务器根据安装记录解析。后端可信身份来自已认证连接，不相信 JSON 中的 appId 就是权限凭证。运行事件包含递增序号，客户端断线后按游标补读；结果与错误都写入持久记录。

业务状态采用按应用实例划分的 SQLite 数据库与附件目录，置于当前 profile 状态目录下，由宿主使用内部生成的实例键定位。默认 profile 对应 ~/.openprogram；不在源码版本目录保存用户数据。项目路径变化只更新项目绑定，不改变实例身份。已有 Runtime 数据库保存执行事实，应用状态仅引用 run ID；不另建平行的 Agent 会话数据库。localStorage 只缓存可丢弃的视图偏好。

Python runner 使用固定版本的应用依赖环境；应用依赖不得直接安装进主 worker 环境。宿主通过已选安装记录启动允许的入口，不接受来自浏览器的任意启动命令。后台服务无任务且无视图时允许闲置退出；下一次打开重新启动，业务数据不受影响。具体闲置时间属于配置，不能决定任务是否被取消。

模型与业务操作如何结合

例如论文阅读器有“导入 PDF”“生成摘要”“保存批注”三个操作。导入和保存由确定性代码完成；摘要操作进入 OpenProgram Runtime，再调用已有 llm() 或公开 Workflow。模型只承担需要推理的步骤，不要求每次按钮点击都先经过一次聊天。

用户按“生成摘要”和 Agent 调用该应用的 summarize 操作，都经过同一输入校验、权限和实现。是否向 Agent 暴露某项操作由应用明确声明，不能把所有内部数据库方法自动注册为工具。Agent 调用也必须绑定应用实例，不能因聊天切换而改用另一个项目的数据。

Runtime 由宿主创建并注入模型配置、工具范围、取消信号和执行归属。默认上下文只包含该操作输入与明确提供的应用状态。用户选择“使用当前对话”时才绑定具体 session；之后不会跟随全局活动标签变化。应用的模型偏好在操作开始时确定，运行中升级应用或切换聊天模型不更改已启动运行。

前端得到模型选择名称、任务进度和结果，不得到 provider 密钥。费用、失败、重试和审批由已有运行系统统一记录。需要用户确认时返回 waiting_input 事件，用户回答绑定 run ID 与 request ID；不能把某次确认广播给另一个应用或另一次执行。

数据修改应先由普通代码校验模型输出，再事务性提交。模型返回的自然语言“已保存”不是保存成功证据。对于不可幂等的外部副作用，重试必须查询已有操作记录或交给用户处理，不能因为网络超时就自动再执行一遍。

打开、后台执行、恢复与升级

打开路径

新标签页读取已验证 Application 定义 → 用户选择应用 → 解析应用实例与绑定项目 → 复用或创建应用标签 → 加载固定版本资源 → 建立能力连接 → 获取业务状态与活动运行。注册/列出应用只读 manifest，不导入应用业务代码，不发起模型请求。

任务路径

提交操作时先记录 accepted 和幂等键，再进入 running；需要输入时 waiting_input，完成时 succeeded / failed / cancelled。closing view 不产生 cancelled。停止任务显式传递取消信号，迟到的结果不能把 cancelled 覆盖为 succeeded。并发修改同一业务对象使用数据库事务或版本检查，不能以前端按钮禁用代替后端并发控制。

重启路径

重新打开页面恢复视图和状态；worker 重启后，未完成运行先标记 interrupted，再检查是否存在合法恢复点。首版至少保留输入、已完成步骤和结果，并清楚显示中断。只有实现了持久 checkpoint、幂等副作用和版本匹配的操作才支持继续执行；普通 Python 函数不能任意从上次某一行恢复。

升级路径

构建候选版本 → 静态/schema 校验 → 依赖准备 → 启动与行为验证 → 数据兼容检查 → 原子切换安装记录。正在运行的操作固定旧版本，新启动操作使用新版本。旧视图和新后端必须版本一致；不允许更新静态文件时悄悄切换已加载页面的操作合同。

数据迁移先备份并验证，再激活版本。代码回滚不等于数据回滚；不可逆迁移失败时保留旧版本不可用原因与恢复流程，不承诺一键还原一切。卸载默认移除注册和代码引用、停止相关运行，业务数据保留；删除业务数据是单独的用户操作。

隔离与可移植性

浏览器隔离是应用自由编写界面的前提。首版普通应用使用 sandbox iframe 与受限 CSP；不能复用当前无 sandbox 的同源插件页作为隔离保证。选择 opaque origin 时通过经校验的 MessageChannel/窗口握手通信；若后续使用独立 origin，也必须隔离宿主 cookie、storage 与管理 API。CORS 本身不是鉴权，iframe 本身也不是默认安全。

应用资源按安装内容摘要提供，只允许访问已发布静态目录。宿主监听消息时核对窗口来源、连接 nonce、实例和操作授权；不得接受任意页面发送的 app ID。前端默认不能直接访问全部 /api/*。需要联网、项目文件或设备权限时声明具体能力，服务端在每次操作重新检查，停用或卸载后撤销连接。

Python 独立进程可以隔离依赖和崩溃，但不能阻止代码直接读取宿主文件或联网。首版后端应用只支持明确获准的本地代码，不把 manifest 的能力列表宣传为恶意 Python 的安全沙箱。接纳不受信远程代码之前，必须实现平台级文件/网络限制或容器沙箱，并验证子进程、包安装脚本和继承环境。高信任宿主插件继续单独标识。

运行方式依赖设计承诺
纯静态应用标准浏览器和自身资源。无宿主 API 时可独立托管；数据迁移仍由应用负责。
OpenProgram 内应用UI + 应用后端 + OpenProgram Runtime。首版目标；菜单入口、模型操作、数据和任务归属一致。
独立部署，同一 runtime应用包 + 最小 runtime + 配置/存储。架构保留边界；在实施适配与验收前不宣称可用。
MCP Apps 跨宿主MCP server + 兼容宿主及其能力。共享 UI/工具合同；OpenProgram 特定后台运行 API 不自动可移植。
完全无 OpenProgram 依赖应用自己提供模型、任务、存储等替代实现。不自动保证；必须单独构建和测试。

采用、调整与暂不采用

选择依据具体处理
采用：标准 Web 应用界面[40] MCP Apps [39] OpenAI Plugins（原 Apps SDK 路径）自由前端构建；主题组件可选。用稳定接口连接宿主。
采用：明确贡献与生命周期[8] Hermes Desktop Plugin SDK [1] DeepSeek Harness应用贡献限制在自己的页面；宿主全局 UI 插槽留给受信插件。
采用：状态与页面分开[25] LangGraph [29] Agno / AgentOS业务状态和运行记录持久化；不以 localStorage 或聊天历史作唯一数据库。
调整：MCP Apps 集成[40] MCP Apps保留标准 bridge 适配，先实现本地应用合同；标准工具调用不足的持久任务以明确宿主扩展暴露，不能谎称标准保证。
调整：UI 事件流[41] AG-UI复用既有事件语义，需要跨框架接入时做 AG-UI adapter，避免重建内部任务系统。
可选：声明式 UI[42] A2UI适合确认单和普通表单；不规定所有应用只能使用内置组件。
暂不采用：任意动态代码直接进入宿主宿主稳定性与普通应用隔离要求。代码先成为可审查、可构建的应用版本，再注册运行；不把 eval 作为默认发布机制。
暂不采用：完整市场、任意语言 runner、原生 GUI 嵌入不影响已经明确的首版使用路径。先证明安装—打开—操作—恢复的合同；不把发布平台做成首版依赖。

实施分解与验收

此节是已批准的实施范围。阶段 1–4 正在实现，阶段 5 保持未实现。每一步必须从公开入口验证，不能仅凭注册器单测宣称用户可以使用应用。现有 Programs 与插件兼容测试应随相关改动一起运行。

阶段 / 主要位置交付行为必要验收
1. 应用定义与来源
programs/_programs.py、plugins manifest/loader、应用目录 API		一份定义、一份来源身份、验证与启用状态；元数据发现不执行代码。重复 ID、无效入口、缺失来源、停用后残留；未安装应用不出现在菜单。
2. 菜单与页面
new-tab-page.tsx、center-tabs state、app-shell.tsx、应用页面组件		点击固定入口打开静态应用，复用标签并绑定实例；隔离页面资源。从四入口页面增加两个应用；键盘打开、刷新恢复、两个项目互不串数据；iframe 无法访问宿主状态。
3. 业务操作与 Runtime
server 应用路由、Program 执行适配与事件		Python 操作进入已有模型/Workflow 运行合同；取消、提问、结果持久化。UI 与 Agent 调用相同操作；模型配置生效、凭据不出前端、重复提交不重复写入。
4. 完整生命周期
来源版本、应用状态存储与 runner 管理		依赖准备、后台任务、重启中断处理、版本固定、数据迁移与卸载。关闭页后任务继续；worker 中断可解释；升级期间旧任务不换代码；迁移失败不损坏旧数据。
5. 兼容与独立部署
独立 adapter，按需求增加		MCP Apps、最小 runtime 服务部署；之后再考虑非 Python runner。相同 UI/操作在明确支持的第二种宿主或部署目标实际运行；不以截图代替。

阶段 1–4 合起来才是可称为“完整应用支持”的第一版。阶段 2 单独完成只能称为静态应用入口。第一版使用三种验收应用：不调用模型的本地计算器、保存批注并生成摘要的论文阅读器、可显示进度并处理重启中断的批量文件分析。验收数据必须包括再次打开、重启、重复点击和模型失败。

性能目标以可测条件规定：列出新标签页不启动任何应用业务进程；已有应用重复点击不产生第二个同 scope 实例；打开应用不触发生成代码或模型请求；大产物按引用读取而非塞入每条事件。具体延迟和资源预算在首个完整样例中测量，当前没有基准数据，不给出未经测量的毫秒或周数承诺。

实现状态与证据限制

阶段 1–4 的实现候选包含应用注册与固定版本、新标签页入口、独立 UI 与能力 bridge、Python 操作、实例数据和执行记录。当前状态为 review-pending：独立规范审查、质量审查、完整测试和默认 App 验收尚未全部完成，不标记为已交付。独立部署与 MCP Apps 适配保持未实现。

操作状态使用现有 ExecutionStore；模型记录使用既有 SessionNodeWriter，保存到应用运行目录。UI 通过 MessagePort 使用实例限定的接口；opaque-origin 页面以单版本资源凭据加载相对模块，凭据只允许读取 UI 资源。Python 每个内容版本使用独立环境，依赖宿主框架；首版用 context.ask() 表达应用提问，worker 停止后报告 interrupted，不恢复 Python 调用栈。JSON 状态上限为 4 MiB，事件上限为 1 MiB；附件管理、自动 schema 迁移、对话上下文选择与菜单手动排序仍未实现。产品接口见 应用文档。

DSH 细节基于已安装的 0.1.5-rc.1 发行包，worktable 源码版本为 0.3.3。二者未做完整兼容性验收；GitHub 当前默认分支也可能继续变化。其动态插件加载机制与 worktable 的产物页面机制分别引用，不用一个版本的演示代表另一个版本的能力。
