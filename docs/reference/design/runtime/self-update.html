对话内自主更新

用户在 OpenProgram 中要求 Agent 修改 OpenProgram。Agent 在隔离 worktree 中完成修改、测试和提交；独立于 worker 的控制进程构建并安装完整 App；新 worker 启动后自动创建一次验收任务，依据原始目标检查结果。系统检查或目标验收失败时恢复旧 App。

核心约束：正在被替换的 worker 不能负责完成替换，也不能把重启后的执行描述为原 turn 的继续。重启前先持久化交接，重启后创建带来源标记的新验收任务。

03

目标架构

控制进程与 candidate runtime 分离。当前 worker 只负责准备和交接；supervisor 决定激活与恢复；新 worker 只负责运行固定系统检查和新的验收 Agent。

1 · 准备
Agent 在隔离 worktree 修改、测试、复核并形成 candidate commit。
2 · 交接
owner 批准；update record 记录 session、turn、candidate 和验收条件；supervisor 由 launchd 托管。
3 · 构建
旧 worker 仍运行时构建完整 App，并完成 packaged smoke 与 cold probe。
4 · 激活
当前回复已持久化且其他任务结束后，停止 App/worker，保留 previous.app，激活候选。
5 · 验收
新 worker 校验 revision/doctor，再创建新的 self_update_verify Agent turn 检查原始目标。
6 · 终态
通过后删除 previous.app；失败或超时则恢复旧 App，并把证据写回原会话。

候选构建允许执行 candidate code，但必须在 sandbox 中拒绝写入默认状态目录、安装目录和 update record。激活与恢复只由当前已安装版本生成的 supervisor 执行。

不使用普通 Scheduler task

Scheduler 的时间触发和用户任务 authority 不适合作为更新控制协议。新 worker 在 JobRunner、session store 和 owner-auth 可用后执行 recover_pending_updates()。

Exactly once

稳定 Job ID + 原子 claim

Job ID 使用 self-update:{update_id}:verify:{attempt}。claim 保存 owner、lease、attempt 和 job_id；重复启动发现已有 Job 或终态时不再提交。

Prompt contract

阶段上下文与工具隔离

实现 Agent 没有安装权限；验收 Agent 没有源码写工具；诊断 Agent 只读失败证据。每阶段记录 model、profile、prompt schema 和 tool policy。

启动顺序

  • 加载并迁移 self-update state schema，损坏时 fail closed。
  • 完成 Job orphan reconciliation。
  • 启动 JobRunner，确认 admission/resource governance 可用。
  • 完成 revision、owner-auth、Web/WS 和 doctor 系统 gate。
  • CAS 认领 attempt，提交一次验证 Job，然后启动普通 Scheduler。

普通 Scheduler 启动失败不阻止自主更新验收；JobRunner 或系统 gate 失败则请求 supervisor 回退。

受控迭代策略

  • 默认 approve_each_activation：失败后回退并诊断；新 candidate 激活前重新授权。
  • 可选 bounded_auto：owner 明确授权最多 3 次、总时限、允许路径和测试集合。
  • 新增依赖、修改权限/审批、安装器/supervisor、扩大路径或改变目标时立即暂停并重新授权。
  • 每轮使用新 SHA、attempt 和 Job ID，不覆盖上一轮证据。
  • 连续相同失败、rollback 失败、环境型 inconclusive 或预算耗尽后停止。
04a

失败后的执行流程

恢复服务、诊断原因、修改源码和批准激活是不同阶段。诊断结果不直接授权安装。

阶段
执行与持久化
限制与后续动作
恢复完成后自动诊断
新请求在 owner 授权时同时冻结诊断模型、profile、只读工具和输出格式。可信控制器确认 ROLLED_BACK 及旧版本系统检查通过后，在解除维护前发布本 attempt 的诊断请求。worker 使用稳定 Job ID self-update:{update_id}:diagnose:{attempt} 创建新任务。
复用 JobRunner，不创建 Scheduler task；不延续原 turn，不移动原会话 head。仅允许 read、glob、grep、list，不允许源码写入、shell、MCP、安装或再次发起更新。
固定期限与恢复
诊断请求绑定原 update、candidate、attempt、失败证据和回退系统证据；期限最多为回退终态后的五分钟，有 bounded_auto 总期限时取更早值。重复 startup 复用原请求与 Job ID，已有终态或 orphan Job 不重跑。
worker 内的有界等待负责收集结果和取消超时任务，不依赖普通 Scheduler。新更新取代待诊断更新、owner 取消、模型缺失、期限届满或证据变化均停止诊断；不改变原 ROLLED_BACK 结论，也不重新限制已恢复的服务。
结构化诊断
记录实现、测试、环境、目标不清或证据不足的分类、原因、原证据引用及修正建议。结果附加到原会话的独立 Job，并保存为本 attempt 的诊断记录。
模型的分类和建议是待验证内容，不是测试证据或新的 owner 授权。环境问题、目标不清及证据不足不得自动修改或激活。
生成并应用源码修正
仅当新请求冻结修正配置、诊断属于 implementation 或 test、旧版本已恢复且预算有效时，创建稳定 ID 的独立 repair Job。模型使用原模型、profile 和只读工具，返回结构化文件修改；控制器在新建的隔离 worktree 校验原文本并应用修改，不让模型执行 shell 或 Git。
默认限制到原 changed_paths；bounded_auto 使用原 allowed_paths。权限、审批、更新控制器、安装脚本、依赖声明及 Git 配置等保护文件均不自动修改。路径越界、符号链接、重复替换或源文本不匹配均停止；不修改用户原 worktree。
新 candidate 与测试证据
控制器创建本地新 commit，记录与原 base 的完整 diff，再在无网络、无 App 写权限的沙箱执行冻结的 required_tests；记录命令、candidate SHA、退出码和有界日志。测试后再次检查 HEAD、Git 绑定及 tracked 文件；测试修改源码则证据无效。
修正 Job 和测试共享回退后的十分钟期限，原总期限更早时取更早值。新更新、owner 取消或超时终止该阶段及其测试进程组。终态、失败和部分写入保留证据与隔离 worktree；重启不重复编辑、提交或测试，不延长期限。
再次授权与激活
候选记录绑定原请求、诊断、修正 Job、完整 diff 和测试结果；控制器调用迭代策略重新核对次数、期限、路径、依赖和连续失败。approve_each_activation 等待 owner 对新 SHA 授权；bounded_auto 仅在原 envelope 内自动提交下一次更新。
候选记录不是安装授权。缺少必需测试或测试失败不得激活；环境、目标或 inconclusive 诊断不自动修正。下一 candidate 仍经过完整构建、系统 gate、新验收 Job 和失败回退。源码修正与测试阶段的完成不代表后续激活流程已实现。

未包含冻结诊断配置的旧更新保持原有恢复行为，不从当前可变 profile 补造配置。诊断请求、claim 和结果位于原更新目录，唯一待处理指针位于 self-updates 根目录；新更新在同一存储锁下撤销旧待处理指针。执行入口再次核对持久化 Job、当前 worker claim、冻结输入与未过期期限，拒绝伪造 source 或恢复旧队列时的输入漂移。owner 通过现有 Job 取消入口停止诊断，不使用只对激活前更新有效的 self_update_cancel。诊断记录不得覆盖原 verifier verdict、签名验收结果或回退结论。

修正阶段同样要求原请求中的独立冻结配置；旧请求不自动获得源码写入能力。默认首次授权说明包括“回退后在隔离 worktree 修正和执行所列测试”，不包括再次安装；只有显式选择 bounded_auto 且批准下述完整迭代授权的新请求，才允许范围内再次安装。修正输出最多 32 处文本编辑、总计 1 MiB；每处 old_text 必须在目标普通 UTF-8 文件中唯一匹配，null old_text 仅用于创建不存在的文件。new_text 为 null 时要求 old_text 等于整个文件才允许删除。修正 Job 使用 wait=true、不产生普通后续 Agent、不移动原会话 head。模型 Job 完成后，owner 在原会话调用 self_update_repair_cancel(update_id)，取消仍在执行的候选测试。新 SHA、完整 diff、全部已配置测试和测试后检查通过才记录 candidate_ready；未配置 required_tests 时记录 awaiting_tests。任何已配置测试缺失、失败或测试后检查失败均记录 failed；主动取消与期限届满分别记录 cancelled、expired。这些状态均不代表已安装。

每次更新保留独立请求和证据；同一迭代序列共用原始目标、授权范围、次数和总期限。

约定

原始授权与兼容
首次请求冻结 root update、owner、session、goal、assertions、原 base、model/profile、模式、路径、测试、max_attempts 和可选总 deadline。bounded_auto 必须有完整的总期限、路径和非空测试集合，审批说明明确包含限次再次安装；授权记录的摘要写入不可变请求。

候选来自本 attempt 的已完成修正 Job；请求、诊断、Job 输出、生成 intent、candidate manifest 和测试日志摘要一致。重新读取真实 Git：专用 worktree 仍归原 session，HEAD 等于待批准 SHA，工作区干净，SHA 是上一 candidate 的新后继，与原 base 的完整 diff 满足范围及保护路径检查。审批展示前和批准返回后、预留 child 之前均检查；supervisor 构建及激活前继续执行已有漂移检查。
必须存在非空 required_tests，且每项命令、SHA、退出码和日志匹配；不接受模型声明或只检查 manifest 的成功字段。缺失、漂移、失败或超出范围时停止提交并保留原因，不以重新批准绕过。此前未配置测试的 awaiting_tests 候选须由 owner 发起带明确测试的新请求。
两种批准方式
默认通过原会话中的 self_update_retry(update_id, candidate_sha) 对这一精确 SHA 强制单次审批，显示完整变化、测试和剩余预算；不能保存为长期 allow 规则。bounded_auto 由控制器按原授权和真实证据自动提交，无需模型再次调用工具。
owner 拒绝或审批超时不创建后继请求。两种方式都核对当前 owner、原 goal/assertions、回退成功、剩余次数及总期限。只有实现或测试类失败可以继续；环境、目标不清、inconclusive、回退未证实或连续相同失败均停止。失败指纹取可信失败类别和失败 assertion/check 标识，不取模型解释、时间戳、SHA 或随机 ID。
次数与不可变后继
第一次更新计为 attempt=1；后继使用新的 update_id、SHA、attempt 和各阶段 Job ID，并记录 root/parent 关系。原 goal、assertions、base、owner、model/profile、policy 不变；只重新绑定本次身份及输出 schema。最多 3 次包含首次更新。
在同一个存储锁下预留唯一后继和下一 attempt；一次预留消耗一次预算，提交失败、取消、重启均不退还或重置次数。同一 parent 不产生第二个后继。每次构建/验收保留原单次超时，且不得超过原总 deadline；达到期限后只允许必要的安全回退及恢复，不再修正或安装。
中断、并发与完整更新
candidate 结果之后、移除修正 pending 指针之前，持久化下一阶段请求。startup 从同一请求恢复等待审批或提交；先保存固定 child ID/预算预留，再发布 child 请求和 active 归属，再调用既有外部 supervisor。重复恢复只能完成这一提交，不能重新编辑、测试或扩大授权。
其他 active update 或 maintenance 阻止新的提交；新 owner 更新撤销旧序列待处理项。默认审批请求在批准 turn 持久化后 release；自动提交以已落盘授权、结果和提交记录作为 release 条件，不伪造聊天 turn。后继仍执行完整打包、cold probe、系统 gate、新 verifier、commit 或回退；提交失败保留可查记录，不跳过阶段。
取消与可见状态
self_update_iteration_cancel(update_id) 在原 owner 会话持久化停止标记，停止整个序列尚未提交的审批或自动提交，并取消该序列仍运行的诊断、修正 Job 和候选测试。已创建但尚未激活的 child 使用现有取消路径；不影响其他序列或普通任务。状态显示 root、parent、当前 child、attempt/max_attempts、总期限及停止原因。
已进入激活/验收的事务不能通过删除请求强行中断；禁止后续 attempt，并由现有事务流程完成验证或安全回退。待提交阶段区分 awaiting_approval、submitting、submitted、stopped；submitted 只表示请求已交给 supervisor，不能显示为安装成功。成功仍以 child 的 SUCCEEDED 和验收证据为准。

该阶段复用 SelfUpdateStore 的进程锁、JobRunner、现有强制审批、可信 supervisor 和事务安装器，不创建第二套 Scheduler 或通用 workflow 执行器。self_update/iteration.py 保持无副作用策略判断；新的提交协调模块负责证据核验、预算预留、状态持久化和恢复。源码中的职责划分不能代替实际的重启、失败回退及多次尝试验收。

05

设计结论

首版只增加完成目标所必需的边界，不引入第二套 Job 系统、插件系统或更新依赖。

Controller

更新控制必须在 worker 外

使用 macOS launchctl submit 启动 one-shot supervisor。它不属于 worker 进程树，worker/App 停止后仍可完成激活、验证超时和恢复。

Candidate

只部署不可变 commit

candidate 必须来自专用 worktree、状态干净、base 明确。构建期间再次读取 HEAD；变化则废弃 artifact，不尝试部署工作目录快照。

Artifact

首版始终构建完整 App

复用完整 runtime、Electron builder 和 packaged smoke。暂不根据 changed paths 选择 wheel、asar 或完整 App，以免维护多套完成语义。

Handoff

工具调用不直接停止 worker

self_update_prepare 只持久化请求并启动 supervisor。dispatcher 在当前 assistant final、session commit 和变更归因完成后写入 turn_released。

Continuation

startup recovery 创建新验收 Job

新 worker 原子认领 update，再复用 JobRunner 创建 source=self_update_verify 的后台任务。普通 Scheduler 不创建、不轮询也不重试这个 Job。

Rollback

目标失败也恢复旧 App

previous.app 保留到系统检查和目标验收均通过。系统错误、Agent verdict=fail/inconclusive 或超时都会恢复旧 App；candidate worktree 和证据保留。

每次确认生成独立、持久化的恢复请求，绑定原更新与事务身份，限时十分钟；重试和进程重启不延长这次期限。只复用已保存的 controller/runtime/installer，通过包含恢复请求 id 的 one-shot launchd label 启动；不从待修复 App 重新复制控制代码。恢复进程使用原安装事务校验规范 App 后重启默认 worker，再验证新进程，使启动检查和普通 Scheduler 按正常启动顺序恢复。中断时允许在同一期限内重复幂等恢复及 worker 重启，但不能创建 verifier Job 或第二次更新。

原终态、原验收结论与旧期限保持不变；人工恢复写入独立 resolution receipt，区分“旧版本恢复”“已接受版本恢复”和“未激活更新恢复”。只有该 receipt 与新系统证据匹配，才原子解除本次维护归属。失败、过期或未确认时继续禁止普通任务；后续再次尝试必须重新确认。此入口不是任意 shell、文件修复或强制清除 maintenance 的接口。

权限与信任边界

“允许改代码”和“允许替换当前运行产品”是两个授权。第二个授权只授予一个 candidate SHA，或一个显式有界的多轮 envelope。

Trusted controller

控制逻辑来自当前已安装版本

supervisor 和安装器在 candidate 激活前从当前 runtime 复制并 hash 固定。candidate 不提供 supervisor、App path、state path、命令或恢复策略。

  • one-shot launchd label 包含 update id
  • 0700 controller，0600 状态
  • 固定默认 profile、18100 和规范 App path
Candidate code

构建可执行，权限受限

candidate 的构建和 smoke 会执行源码，因此在 sandbox 内运行，并使用最小环境。拒绝访问 provider 凭据、默认 session state、安装目录和 update record。

  • 只写 candidate worktree 与 staging temp
  • 不继承 token/API key
  • 网络默认关闭；依赖必须来自 lockfile/cache
User authority

激活必须处于 owner 批准范围

self_update_prepare 加入不可由 bypass 跳过的强制审批集合。默认绑定 candidate；有界自动迭代绑定 goal、允许路径、最大次数、时限和禁止变化项。

  • cron/scheduler/sub-agent/MCP 不能发起
  • 审批不持久化为通用 allow rule
  • scope、依赖或权限变化后失效
Verification

验收 Agent 权限单独收窄

自动验收不能修改源码或再次更新。它只能读取证据、运行受限检查和操作本地 UI；需要额外副作用时返回 inconclusive。

  • 固定 agent/profile/model snapshot
  • 每个 assertion 必须有 evidence
  • verdict 通过 supervisor 的一次性 token 提交

首版复用 Running 的有界轮询，不新增事件总线。每个视图至多一个在途读取；会话切换取消旧请求，并用请求代次拒绝迟到响应。state revision 只排序状态变更，关联结果使用完整投影摘要判断变化。断线保留带“上次同步”时间的旧卡，明确显示离线；重连重新读取，不能因 WebSocket 断开、Job 消失或 App 打开就推断失败或成功。

Chat and Running

一个更新，一份状态

聊天以 root update 聚合各 attempt，显示当前阶段、目标/已验证版本、预算和证据。Running 使用同一投影显示非终态事务或仍待执行的迭代工作；所有 attempt 终止后从 Running 移除，原会话历史仍保留。按钮调用已有强制审批/取消入口，UI 可见性不代替后端权限。

Durable result delivery

结果不依赖窗口在线

controller 先持久化终态，worker 通过已有 Job completion/follow-up 投递机制把有限结果写回原会话。以 update、attempt 和结果类型形成稳定投递键；重复启动或 ACK 丢失不产生重复消息。终态早于 verifier 创建、原会话未打开时也必须投递；会话删除则保留未投递状态，不改投其他会话或创建新的用户任务。

No false completion

分别显示执行与安装结论

自动验收任务完成、目标通过、安装提交、回退完成和后续修正分别显示。通知由确定性代码生成，不另起 LLM 来编写状态，也不因此触发再次安装。DAG 保留 origin caller 与验证 Job 的关系，不改写用户主分支 HEAD。

Desktop 重启定位原会话

复用 apps/desktop/worker-start-url.js 的 owner-auth 启动机制与现有 /s/{session_id} 路由。supervisor 在停止 App 前保存本次更新的受信任 reopen 意图，绑定 update、attempt、origin session、owner、期限和启动动作。Desktop 只接收不透明 update ID；由已认证服务解析经过核验的会话，再构造同源路由。候选、模型、CLI 参数和 renderer 不能指定任意 URL、文件路径或认证 fragment。

只在这次更新触发的重新打开中消费该意图，不改变普通启动、用户当前窗口、中心标签和稳定 Release updater。完成认证并确认原会话加载后才 ACK；ACK 前崩溃可重试定位，不能重新激活更新或重建 verifier Job。多窗口只由指定主窗口消费；重复消费是幂等定位，不重复建标签。用户主动离开原会话后不再强制跳回，保留可点击的结果提示。

owner 改变、session 不存在、意图过期、身份不匹配或恢复接口不可用时，保持普通启动并显示明确原因；不跳到其他会话，不自动创建会话，也不把定位失败判为安装成功。App 原本未打开时遵守保存的启动状态；若验收必须操作可见 App，应在 prepare 时显示并获得打开窗口的授权。更新与回退双方均须支持所需的最小读取/恢复协议，协议不兼容在激活前拒绝。

产品级完成条件

以下条件全部成立后，才能把“对话内自主更新”标记为 implemented。

真实聊天入口

owner 在默认 App 中提出修改；Agent 完成 worktree 修改、测试、提交并调用专用工具，不依赖开发者手工执行脚本。

不可变 candidate

request、artifact 和 live revision 绑定同一 SHA；dirty worktree、HEAD drift、version drift 均在停止旧实例前失败。

进程边界

旧 worker/App 停止后 supervisor 仍运行；当前 turn 已完成持久化，不产生永久 running node。

无并发损失

存在其他运行任务时只等待或中止更新，不隐式取消；maintenance gate 不丢失已提交用户输入。

完整 artifact

App bundle、embedded Python、Web/docs、Programs、Browser assets 和 capability manifest 都来自 candidate，并通过 packaged smoke。

live identity

重启后默认 18100 的 owner-auth challenge 证明 candidate revision；单独的匿名 health 结果不能满足该条件。

自动验收

新 worker 正好创建一个 self_update_verify Job；每条 required assertion 均有结果和证据，缺失即 inconclusive。

调度隔离

普通 Scheduler 停止、延迟或重复 tick 不影响验收触发；worker 重启、lease 接管和 orphan reconciliation 后，每个 attempt 仍至多一个验证 Job。

受控迭代

默认每次重新授权；bounded_auto 严格执行最大次数、总时限、路径和禁止变化项，任何越界都暂停。

自动恢复

系统 gate、目标验收和超时失败均恢复 previous.app，恢复后的 worker revision 可验证，并在原会话显示结果。

崩溃恢复

在 READY、ACTIVATING、VERIFYING 各阶段模拟进程/机器重启后，recovery 得到确定终态，不重复激活或重复发 Agent turn。

仓库与可见状态一致

设计、测试、review、candidate commit、App source marker、运行 worker identity 和 UI verdict 指向同一实现状态。
