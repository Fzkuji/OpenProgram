System access

System access is checked on the execution host, independently of operation approval and account credentials. Checks never request permission. Optional desktop access does not block installation, ordinary chat, or upgrade.

Shared contract

CLI doctor, TUI doctor, authenticated HTTP and System settings consume one live report containing host, executable, capability, status, reason and recovery instruction. Unknown is distinct from denied. A successful probe is not persisted as a permanent grant. Explicit setup actions recheck before requesting and cannot run from model tool calls or remote clients.

PlatformChecks and recovery
macOSCheck screen recording and Accessibility separately in the executing Python process. Explicit user setup requests the missing capability. Keep granted capabilities untouched. System Settings remains authoritative.
LinuxDetect headless, X11 and Wayland. Never report a DISPLAY variable as permission granted. Wayland requires a supported portal backend; unsupported capture must not be described as a missing macOS permission.
WindowsReport desktop authorization as unknown until verified against the target. Do not infer input authority from administrator status or elevate the whole application. Secure desktop and higher-integrity targets may remain inaccessible.

Lifecycle

Install dependencies and stable application identity → user enables a capability → explicit system authorization if missing → recheck actual executor → use capability. Recheck on settings focus and before operation. Revocation produces actionable status. A denied operation never retries automatically. Pending task recovery must revalidate original authorization and file state.

Reference and boundaries

Electron systemPreferences distinguishes query from explicit request. Apple screen recording settings are controlled by the user. Native permission state is not an application configuration boolean. Current macOS builds lack production signing; stable signed identity and upgrade acceptance remain release requirements. Linux portal persistence depends on the compositor; Windows secure desktop cannot be made generally accessible by a normal app.

HTTP setup requires owner authentication, loopback peer and URL, loopback Origin and no forwarding headers. An SSH tunnel can preserve loopback identities; HTTP alone cannot prove physical presence. The system authorization dialog is still controlled by the execution host user.

Named macOS runtime

The managed macOS runtime packages a small native Python embedding executable in an embedded application named OpenProgram with bundle identifier ai.openprogram.runtime and the product icon. The helper sets Python home to the existing relocated runtime; it does not copy or fork the Python environment. Workers and multiprocessing children keep the named executable. A runtime manifest worker_python entry selects it; a missing declared helper fails rather than silently reverting to anonymous Python. Query and request execute under the same application identity. The helper uses a relative library path and fixed ABI bundle version; ordinary Python package updates do not change the helper executable. Development signing is ad hoc, and production certificate-based signing remains a separate release requirement.

Application identity is verified through NSBundle and actual System Settings registration. Native requests still require user consent. Neither an application label nor an installed helper is evidence of an OS grant.

Task recovery

Local desktop GUI operations suspend at the canonical tool boundary before planning or desktop effects when macOS access is missing. The existing execution checkpoint and durable wait store own a system_access wait with no expiry. The record retains the original tool call, execution, current checkpoint and required capabilities. The running model attempt releases its resources. Browser and VM operations do not request desktop access.

The worker reconciler checks the actual executor independently of browser visibility. Read-only checks never prompt. Only a report in which every required capability is granted resolves the current wait and schedules the same execution through the existing continuation queue. Unknown and failed checks retain the wait. Startup performs the same reconciliation. Existing generation, checkpoint and cancellation guards prevent duplicate resumes and prevent resolved old waits from reviving cancelled or newer executions. The resumed boundary checks both current operation authorization and system access again. Completed effects are not replayed.

System access waits cannot be answered by the ordinary question or approval API. A client cannot grant system access by sending an answer. The Web interface combines active waits in the current conversation into one short waiting status without an approval form or a Continue action; each task retains its independent durable wait. For a newly requested local task it invokes the existing owner-only native setup endpoint once per missing capability. Native setup rechecks before requesting; if the native request cannot complete authorization, it opens the capability-specific System Settings page. Returning focus requests a fresh status check; it never retries the function. Historical records never open settings merely because they are viewed. A manual Open System Settings text action remains available. Remote clients cannot trigger local setup.

Closing a page does not cancel the task or stop reconciliation. An explicit task cancellation closes its wait and prevents later resumption. If macOS requires an application restart, the wait persists and startup checks it again. The application does not claim a successful settings toggle is an effective grant. A persistent check failure is reported separately from missing authorization. No model is retained solely to poll permission status.

Local bundle integrity

Local development refresh refuses to overwrite an outer distribution signature before mutating the installed application. After resource replacement, it repairs only invalid ad hoc Framework and App bundles inside Contents/Frameworks, deepest first, preserves their signing metadata, and signs the outer application. The separately signed named runtime helper retains its identity. Refresh requires strict verification of the helper and deep strict verification of the complete application before restarting. This local integrity check does not provide Developer ID signing, notarization or permission persistence across upgrades.

Verified gaps

The previous Web-owned polling path ends the GUI function and submits retry_function after authorization. It does not satisfy durable same-execution continuation and is replaced by the worker-owned wait. The installed named helper reports OpenProgram, and the full application passes deep strict signature verification. The actual launchd worker still reports screen recording as not granted despite an enabled application entry in System Settings. A probe launched by another authorized application gives a different result and cannot establish the worker grant. Fresh authorization and same-execution continuation remain unverified.

Acceptance

Public report distinguishes individual denials, unavailable dependencies, unsupported backends and failed checks. Repeated status reads cause zero prompts. Granted capabilities cause zero requests. Setup rejects remote and non-owner callers. Optional capability failures leave doctor installation health unchanged. Settings automatically rechecks on focus and gives failure feedback. Actual macOS worker, Linux and Windows acceptance are recorded separately.

Implementation status

Shared live diagnostics, explicit local-owner setup, System settings, CLI/TUI advisory reporting and GUI capability integration pass specification and quality review. Focused Python, Web/CLI type checks, repository contracts and documentation link checks cover the foundation. Native host acceptance, signed upgrade persistence, portal capture, durable pending-task recovery and first-run onboarding remain unverified. The worker-owned wait implementation has passed independent specification and quality review plus the backend and Web suites. That candidate passes the full automated verification manifest and is installed in the default App. Actual acceptance exposes session replay as a generic question, duplicate wait status and a running timer for a paused execution. The repair distinguishes live wait events from passive replay, retains live intent until the visible session mounts, and projects the canonical paused status. This repair requires independent reviews, integrated verification and installation. Native authorization acceptance remains pending.
