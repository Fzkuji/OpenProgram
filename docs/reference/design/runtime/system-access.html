System access

System access is checked on the execution host, independently of operation approval and account credentials. Checks never request permission. Optional desktop access does not block installation, ordinary chat, or upgrade.

Shared contract

CLI doctor, TUI doctor, authenticated HTTP and System settings consume one live report containing host, executable, capability, status, reason and recovery instruction. Unknown is distinct from denied. A successful probe is not persisted as a permanent grant. Explicit setup actions recheck before requesting and cannot run from model tool calls or remote clients.

PlatformChecks and recovery
macOSCheck screen recording and Accessibility separately in the executing Python process. Explicit user setup requests the missing capability. Keep granted capabilities untouched. System Settings remains authoritative.
LinuxDetect headless, X11 and Wayland. Never report a DISPLAY variable as permission granted. Wayland requires a supported portal backend; unsupported capture must not be described as a missing macOS permission.
WindowsReport desktop authorization as unknown until verified against the target. Do not infer input authority from administrator status or elevate the whole application. Secure desktop and higher-integrity targets may remain inaccessible.

Lifecycle

Install dependencies and stable application identity → user enables a capability → explicit system authorization if missing → recheck actual executor → use capability. Recheck on settings focus and before operation. Revocation produces actionable status. A denied operation never retries automatically. Pending task recovery must revalidate original authorization and file state.

Reference and boundaries

Electron systemPreferences distinguishes query from explicit request. Apple screen recording settings are controlled by the user. Native permission state is not an application configuration boolean. Current macOS builds lack production signing; stable signed identity and upgrade acceptance remain release requirements. Linux portal persistence depends on the compositor; Windows secure desktop cannot be made generally accessible by a normal app.

HTTP setup requires owner authentication, loopback peer and URL, loopback Origin and no forwarding headers. An SSH tunnel can preserve loopback identities; HTTP alone cannot prove physical presence. The system authorization dialog is still controlled by the execution host user.

Named macOS runtime

The managed macOS runtime packages a small native Python embedding executable in OpenProgram.app with bundle identifier ai.openprogram.runtime and the product icon. The helper sets Python home to the existing relocated runtime; it does not copy or fork the Python environment. Workers and multiprocessing children keep the named executable. A runtime manifest worker_python entry selects it; a missing declared helper fails rather than silently reverting to anonymous Python. Query and request execute under the same application identity. The helper uses a relative library path and fixed ABI bundle version; ordinary Python package updates do not change the helper executable. Development signing is ad hoc, and production certificate-based signing remains a separate release requirement.

Application identity is verified through NSBundle and actual System Settings registration. Native requests still require user consent. Neither an application label nor an installed helper is evidence of an OS grant.

Acceptance

Public report distinguishes individual denials, unavailable dependencies, unsupported backends and failed checks. Repeated status reads cause zero prompts. Granted capabilities cause zero requests. Setup rejects remote and non-owner callers. Optional capability failures leave doctor installation health unchanged. Settings automatically rechecks on focus and gives failure feedback. Actual macOS worker, Linux and Windows acceptance are recorded separately.

Implementation status

Shared live diagnostics, explicit local-owner setup, System settings, CLI/TUI advisory reporting and GUI capability integration pass specification and quality review. Focused Python, Web/CLI type checks, repository contracts and documentation link checks cover the foundation. Native host acceptance, signed upgrade persistence, portal capture, automatic pending-task recovery and first-run onboarding remain unverified.
