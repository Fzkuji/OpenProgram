System access

System access is checked on the execution host, independently of operation approval and account credentials. Checks never request permission. Optional desktop access does not block installation, ordinary chat, or upgrade.

Shared contract

CLI doctor, TUI doctor, authenticated HTTP and System settings consume one live report containing host, executable, capability, status, reason and recovery instruction. Unknown is distinct from denied. A successful probe is not persisted as a permanent grant. Explicit setup actions recheck before requesting and cannot run from model tool calls or remote clients.

PlatformChecks and recovery
macOSCheck screen recording and Accessibility separately in a fresh process of the executable used for desktop tasks. Explicit user setup requests the missing capability. Keep granted capabilities untouched. System Settings remains authoritative.
LinuxDetect headless, X11 and Wayland. Never report a DISPLAY variable as permission granted. Wayland requires a supported portal backend; unsupported capture must not be described as a missing macOS permission.
WindowsReport desktop authorization as unknown until verified against the target. Do not infer input authority from administrator status or elevate the whole application. Secure desktop and higher-integrity targets may remain inaccessible.

Lifecycle

Install dependencies and stable application identity → user enables a capability → explicit system authorization if missing → recheck actual executor → use capability. Recheck on settings focus and before operation. Revocation produces actionable status. A denied operation never retries automatically. Pending task recovery must revalidate original authorization and file state.

Reference and boundaries

Electron systemPreferences distinguishes query from explicit request. Apple screen recording settings are controlled by the user. Native permission state is not an application configuration boolean. Current macOS builds lack production signing; stable signed identity and upgrade acceptance remain release requirements. Linux portal persistence depends on the compositor; Windows secure desktop cannot be made generally accessible by a normal app.

HTTP setup requires owner authentication, loopback peer and URL, loopback Origin and no forwarding headers. An SSH tunnel can preserve loopback identities; HTTP alone cannot prove physical presence. The system authorization dialog is still controlled by the execution host user.

Named macOS runtime

The managed macOS runtime packages a small native Python embedding executable in an embedded application named OpenProgram with bundle identifier ai.openprogram.runtime and the product icon. The helper sets Python home to the existing relocated runtime; it does not copy or fork the Python environment. Workers and multiprocessing children keep the named executable. A runtime manifest worker_python entry selects it; a missing declared helper fails rather than silently reverting to anonymous Python. Query and request execute under the same application identity. The helper uses a relative library path and fixed ABI bundle version; ordinary Python package updates do not change the helper executable. Development signing is ad hoc, and production certificate-based signing remains a separate release requirement.

Application identity is verified through NSBundle and actual System Settings registration. Native requests still require user consent. Neither an application label nor an installed helper is evidence of an OS grant.

Task recovery

Local desktop GUI operations suspend at the canonical tool boundary before planning or desktop effects when macOS access is missing. The existing execution checkpoint and durable wait store own a system_access wait with no expiry. The record retains the original tool call, execution, current checkpoint and required capabilities. The running model attempt releases its resources. Browser and VM operations do not request desktop access.

The worker reconciler checks the actual executor independently of browser visibility. Read-only checks never prompt. Only a report in which every required capability is granted resolves the current wait and schedules the same execution through the existing continuation queue. Unknown and failed checks retain the wait. Startup performs the same reconciliation. Existing generation, checkpoint and cancellation guards prevent duplicate resumes and prevent resolved old waits from reviving cancelled or newer executions. The resumed boundary checks both current operation authorization and system access again. Completed effects are not replayed.

System access waits cannot be answered by the ordinary question or approval API. A client cannot grant system access by sending an answer. The Web interface combines active waits in the current conversation into one short waiting status without an approval form or a Continue action; each task retains its independent durable wait. A persisted runtime card for an active system-access wait remains paused, suppresses a null result, and does not offer Retry or Edit; genuine failed and cancelled executions retain their own terminal labels. For a newly requested local task it invokes the existing owner-only native setup endpoint once per missing capability. Native setup rechecks before requesting; if the native request cannot complete authorization, it opens the capability-specific System Settings page. Returning focus requests a fresh status check; it never retries the function. Historical records never open settings merely because they are viewed. A manual Open System Settings text action remains available. Remote clients cannot trigger local setup.

Closing a page does not cancel the task or stop reconciliation. An explicit task cancellation closes its wait and prevents later resumption. If macOS requires an application restart, the wait persists and startup checks it again. The application does not claim a successful settings toggle is an effective grant. A persistent check failure is reported separately from missing authorization. No model is retained solely to poll permission status.

Fresh native permission checks

macOS can retain a permission result inside a long-lived process after System Settings changes. The desktop GUI executor is a separate named runtime process. A permission check therefore uses a fresh, bounded invocation of that same executable on the execution host, with the existing isolated Python import mode. It queries Core Graphics preflight and Accessibility trust only; it never enumerates screen content or requests authorization. Results from an unrelated authorized application are not accepted as executor evidence. A failed, malformed or timed-out probe reports unknown and keeps the task waiting.

The worker performs one fresh report per reconciliation pass and shares it across open system waits. It retains the existing checkpoint, cancellation and continuation guards. Explicit native setup remains owner-only and uses the same named executable; checks do not implicitly become requests. The candidate contains this repair; combined verification and native acceptance remain pending.

Restart and continuation projection

The canonical execution owns task status throughout permission recovery, including the interval after a wait is resolved and before the continuation opens another wait or starts its tool. Startup reconciliation does not infer abandonment solely from the absence of an open wait. It preserves recoverable canonical executions and their session anchors. Session hydration and continuation repair only obsolete restart markers that conflict with the current authoritative execution; real interruption, cancellation and tool output remain intact. An active permission wait displays a paused task without a stale interruption result or Retry controls. This repair requires public restart and session-load verification plus native acceptance.

Startup availability

Restoring the session registry does not enumerate existing history directories to decide whether old sessions are empty. An existing history directory is conservatively retained, even if it may be empty. This avoids blocking the worker and permission recovery on a directory enumeration before the HTTP service starts. Sessions with absent history remain subject to the existing empty-shell policy; archive retention is unchanged. Legacy history reconciliation runs in a daemon background thread after canonical execution recovery has finished. Waiting for a project history directory or its per-session lock never delays HTTP readiness or blocks the Web event loop. Canonical cancellation and owner recovery still complete before requests are served; per-session ownership checks remain in legacy reconciliation. Rewind and history-intent recovery is enforced when a session is first loaded into a SessionStore cache, under the existing per-session lock, after its cache is initialized and before it is returned to a reader or writer. A recovery failure withdraws that unpublished cache entry so a later read cannot bypass recovery. Explicit rewind entry points also recover before planning or applying. Cached reads do not repeatedly scan journals while checkpoint callbacks hold an active intent lock. A private store-and-session-scoped reentrancy guard allows recovery to use the existing head and compare-and-set operations without recursively recovering itself. Existing intent and workspace locks and terminal-intent rules remain authoritative across processes. Web startup does not await a scan of every session journal. Public session hydration retains its current canonical projection repair; unavailable project history affects that session rather than HTTP startup or unrelated sessions. During one continuous backend outage, the desktop recovery coordinator may issue at most one forced worker restart. Failure of that command does not renew its restart allowance; health checks continue, and verified backend availability resets the allowance for a later outage. This prevents a pending system permission or slow startup from repeatedly killing the same task. This startup repair requires public SessionStore construction, application lifespan responsiveness and repeated recovery-command failure coverage, plus installed-worker acceptance.

Execution owner registration

Registering a task owner uses the session identity already supplied by the active execution. It checks cancellation state only in that session and its matching Job record; absence there does not trigger a search of unrelated histories while holding the shared cancellation lock. Callers without a session identity retain the legacy discovery path. Owner generations, late cancellation and exact-owner fencing remain unchanged. This prevents a blocked old project from delaying a new task before its system-access checkpoint.

Local bundle integrity

Local development refresh refuses to overwrite an outer distribution signature before mutating the installed application. After resource replacement, it repairs only invalid ad hoc Framework and App bundles inside Contents/Frameworks, deepest first, preserves their signing metadata, and signs the outer application. The separately signed named runtime helper retains its identity. Refresh requires strict verification of the helper and deep strict verification of the complete application before restarting. This local integrity check does not provide Developer ID signing, notarization or permission persistence across upgrades.

Verified gaps

The previous Web-owned polling path ends the GUI function and submits retry_function after authorization. It does not satisfy durable same-execution continuation and is replaced by the worker-owned wait. The installed named helper reports OpenProgram, and the full application passes deep strict signature verification. Local ad hoc application updates can invalidate an existing system grant because macOS attributes the named helper to the containing application. Removing that application entry through supported system controls and adding the current application establishes a valid grant for a fresh named executor. A long-lived worker can still retain the previous denied preflight result. Fresh executor checks address that stale result; actual capture and same-execution continuation remain required acceptance.

Updated local application recovery

The managed macOS worker records the containing application's verified ad hoc code hash only after its own fresh screen-recording check succeeds. A later denied check with a different verified hash is reported as an application-update reauthorization, not a completed grant. Ordinary checks never reset or request access. At the existing explicit local-owner setup boundary, a matching stale-grant record allows a bounded reset of ScreenCapture for ai.openprogram.desktop only, followed by the standard native permission request. A durable per-hash attempt marker prevents repeated resets after refusal, reconnect, or process restart. Granted capabilities, unchanged identities, unsigned or unverified code, missing receipts, unknown checks, Accessibility, and other applications are never reset. The receipt is local recovery evidence, never authorization to run a tool. A failed reset leaves the task waiting with an explicit recovery error. Pending tasks remain under the existing durable wait and cancellation rules.

The receipt is written only by the managed worker, not by a shell-launched diagnostic which may inherit a different system authorization. Native grants remain controlled by macOS. Developer-signed updates retain the existing platform flow; ad hoc recovery is limited to the installed canonical application and its own identity.

Acceptance

Public report distinguishes individual denials, unavailable dependencies, unsupported backends and failed checks. Repeated status reads cause zero prompts. Granted capabilities cause zero requests. Setup rejects remote and non-owner callers. Optional capability failures leave doctor installation health unchanged. Settings automatically rechecks on focus and gives failure feedback. Actual macOS worker, Linux and Windows acceptance are recorded separately.

Cancelled wait projection

When a canonical execution is terminal, hydration updates a stale pending, running or paused conversation node to its canonical status without removing recorded output. Real terminal results remain unchanged. This covers cancellation while a system-access wait has released its owner. Verification is pending.

Repeated native setup

A handled system-access wait does not automatically request native setup again after duplicate live events or conversation remounts. The shared browser wait store retains handled IDs until authoritative removal. Explicit setup remains available. App restart replay restores presentation without automatic setup. The duplicate-live remount regression passes; final review and native acceptance remain pending.

Implementation status

Shared live diagnostics, explicit local-owner setup, System settings, CLI/TUI advisory reporting and GUI capability integration pass specification and quality review. Focused Python, Web/CLI type checks, repository contracts and documentation link checks cover the foundation. Native host acceptance, signed upgrade persistence, portal capture, durable pending-task recovery and first-run onboarding remain unverified. The worker-owned wait implementation has passed independent specification and quality review plus the backend and Web suites. That candidate passes the full automated verification manifest and is installed in the default App. Actual acceptance exposes session replay as a generic question, duplicate wait status and a running timer for a paused execution. The repair distinguishes live wait events from passive replay, retains live intent until the visible session mounts, and projects the canonical paused status. The replay and waiting-display repair passes independent specification and quality review. Combined verification, installation, native capture and same-execution recovery remain pending.
