Code design review

This review covers every tracked source file and the configuration, examples and assets that determine product behavior. Repository organization acceptance is one input; it does not establish complete design coverage. Uncommitted owner work is inventoried separately and preserved.

Design contracts

  • Core, transport, presentation and release modules have explicit owners and dependencies. Public behavior and persisted data remain compatible unless a concrete defect requires a documented correction.
  • Every mutable store, cache, lock and execution identity has one authority. Context binding, cancellation, failure and shutdown release all resources they own, including partially completed initialization.
  • Inputs are validated at trust boundaries. Authorization, path identity, secret handling and asynchronous request ownership remain explicit across processes and user interfaces.
  • Files and abstractions have cohesive responsibilities. Duplication, unnecessary indirection and oversized mixed-purpose implementations are assessed through their callers and observable behavior. Generated and third-party code receives a recorded maintenance decision instead of an automatic exemption.
  • Tests demonstrate the contract rather than reproducing implementation details. Discovery, isolation, fixtures and package acceptance remain part of the review.

Review coverage

A file inventory records its exact content hash, subsystem, inspected symbols, callers, invariants, findings and acceptance evidence. A directory count, static scan, passing suite or earlier extraction review cannot mark an unread file reviewed. A changed hash invalidates the affected review. Each file receives an explicit keep, simplify, repair, replace or remove decision; changes require independent specification and quality review.

The review includes Agent and execution services, storage and history, providers and authentication, Programs and integrations, security and process management, Server transports, Web state and components, Desktop, CLI, tests, build scripts and distribution. Documentation code examples and executable configuration are checked against their owning public entry points.

Failure and compatibility verification

Each repair starts from a reproducible public or shared-boundary failure, then verifies the affected layer and repository contracts. Concurrency and shared-fixture changes require the documented repeated fixed-worker manifest. Import compatibility, transaction boundaries, cancellation delivery, resource cleanup, file identity and delayed UI responses are checked on the actual affected path.

Turn context lifecycle

TurnBindings owns only the tokens it installs. Entry rolls back successful bindings on any escaping exception, including cancellation, while preserving the entry error. Deferred-tool installation retains its reset token so nested turns restore the outer set. Cleanup validates the surface token before releasing browser resources, attempts each remaining token reset independently, and reports operational cleanup errors after restoration. Foreign tokens do not authorize resource destruction and do not prevent valid local tokens from being restored.

Both ordinary and resumed dispatch protect setup immediately after binding. Failures in attachment initialization, placeholder persistence or stream-event setup release the turn. Existing outer session and execution ownership, provider-independent GraphStore binding, continuation project baselines and inherited sandbox policy remain unchanged. Acceptance exercises these shared boundaries with controlled failures and checks the enclosing context after both success and failure.

Dispatcher attribution lifetime

Ordinary turns and resumed turns enter the same lexical usage and plan-mode scope before dispatcher setup and leave it after finalization or any return or exception. Plan tools use the active request session. Usage attribution retains an explicitly supplied outer call kind, label, parent session, session and agent; missing identifiers are filled from the request and an unknown call kind defaults to chat. Exiting the turn restores the exact enclosing context, including failed admission, initialization failure and cancellation. The existing usage_scope primitive owns metering reset; the dispatcher owns its plan token.

This perimeter is separate from TurnBindings because it spans admission and finalization, while tool runtime bindings cover the execution stage. Public signatures and stop-hook dispatch remain unchanged. Controlled public-entry acceptance covers rejected successive turns, exceptions within enclosing scopes, resumed plan-tool identity and terminal finalization attribution. Storage transactions, provider behavior and continuation admission semantics are outside this repair.

Blank-text turn commits

A completed turn with no text still produces its session Git commit. Commit descriptions use the first nonempty leading text after trimming, limited to 60 characters; an empty or whitespace-only prompt uses turn. Successful, failed and shadow-cache commits share this formatting rule while retaining their existing prefixes and commit destinations. Commit acknowledgement remains false on a real commit failure. Attachment-only prompts therefore retain the same durable completion contract as text prompts. This correction does not change session data, project commit ownership or metadata transaction semantics.

Node metadata write ownership

SessionStore owns updates to existing node fields and shallow metadata patches. A writer takes its session lock and the stable session-id file lock, revalidates placement and deletion, refreshes a stale index, and reads each target's current history record while the write lock is held. Requested fields apply to a detached node; the cache and edge indexes are updated only after its atomic history replacement succeeds. Independent top-level metadata keys survive interleaved writers; same-key patches retain last-writer behavior. Batch updates share one open and write scope, with per-node persistence rather than a cross-file atomic transaction.

Turn file summaries, shadow Git stamps and project commit stamps use the same metadata merge API. They do not format or rewrite history files independently. Existing history filename identity stays fixed; an update cannot repoint it. Edge identifiers must remain strings or null and are checked before persistence. Missing nodes are not recreated. Metadata merging does not change session HEAD or session-level metadata; output spilling and edge reindexing keep their existing semantics. File relocation and failures must leave public reads consistent with durable history. Append and session-level metadata transactions require their own review and are not certified by this repair.

Acceptance uses independent stores over temporary storage, a deterministic intervening committed patch at the write-lock boundary, fresh-store reads, forced atomic-write errors, placement changes and actual finalization entry points. Merely moving a cached mutation under a lock is insufficient: the merge input must be read after lock acquisition.

Session export redaction

Shareable Markdown and HTML exports apply the existing provider redaction policy to every exported free-form label, including session title, session identifier, turn role and tool name. Tool arguments retain their dictionary or list structure until secret-field redaction completes; JSON-encoded arguments use the same rule. Redaction precedes clipping and rendering, so serialization cannot conceal a password field from the redactor. Content and tool output keep the same policy. If argument nesting prevents parsing or recursive redaction, the export replaces those arguments with an explicit omission notice and continues rendering the remaining session. It never uses unredacted input as that fallback. This does not introduce new secret detection patterns or change stored session data.

Both formats retain branch selection, call inclusion, normal labels, HTML escaping and existing size limits. Acceptance invokes export_session over temporary real SessionStore data and verifies synthetic secret removal in titles, tool names, nested arguments and JSON argument strings, while harmless values remain visible.

Session search placement and literal queries

Session-scoped message search resolves the current readable session directory through SessionStore, including project nesting and relocation. Missing, deleted or invalid scoped identifiers return no results and do not create storage. An omitted scope continues to search across sessions. Both optional ripgrep and the Python fallback interpret the query as case-insensitive literal text; punctuation and leading option-like text are not regular expressions or command options. Nonpositive result limits return an empty list.

The repair retains result enrichment, agent filtering, existing history matching and the WebSocket response contract. Integration acceptance uses temporary real sessions, real ripgrep when available, the Python fallback, canonical relocation, invalid or absent sessions, literal punctuation and result limits. Broader ranking, pagination and concurrent search snapshots are outside this bounded repair.

Session field and branch metadata updates

Session field patches, versioned dictionary updates, branch names, branch lifecycle fields and branch turn increments use one durable metadata transformation owner. The existing session write scope refreshes placement and stale history after stable-id locking. Each transformation reads current meta.json, preserves fields it does not own, writes the result, and only then publishes metadata and HEAD to the cache. Creation and later field updates serialize through this same scope; no uncommitted creation metadata is installed in the cache. Durable metadata remains authoritative. A rejected dictionary callback or failed write leaves committed state unchanged. Returned dictionary update values are detached from the published cache. Counter increments and branch field merges therefore compose across independent stores.

Session field updates keep their existing non-null patch and registry behavior. Branch label changes do not change session activity time. Existing node updates reuse the generalized write scope. This task does not certify legacy whole-index metadata writers, node append multi-file recovery, branch deletion or explicit HEAD movement; these remain separate pending write-ownership work. Acceptance covers independent intervening commits, failed persistence, callback rejection and retained fresh history through public store entries.

Message identity projection

Every message returned from a stored node takes its id from the node and its session_id from the requested session. Metadata cannot override either identifier, including metadata persisted through legacy extra fields. The shared projection enforces this rule for message lists, branch reads and descendant reads without rewriting history. Other extension fields and the legacy system role remain compatible. Acceptance writes real temporary sessions through both message and node APIs and checks cached and reopened reads.

Durable node append

Both message and node append entries use one session writer. After placement validation and stable-id locking, it refreshes committed history, validates edges and assigns an unused sequence to a detached node. A repeated durable id preserves its existing payload. Caller-less message inserts advance HEAD only from the current tip; node inserts retain the advance_head option. Failed history writes do not publish cache-only nodes.

A private append intent under the session Git administrative directory records the node and resulting session metadata before history replacement. Once history exists, recovery completes metadata before exposing the session or admitting another locked writer. Recovery retains the intent until both files are durable; a history failure with no durable node cancels the intent. A completed intent is removed before later writes, so replay cannot reverse a later explicit HEAD change. Cached nodes publish only after both files succeed. The registry remains a derived activity view. The protocol provides restart recovery for interrupted appends, not a cross-session transaction or a general snapshot-read guarantee. Existing rewind recovery remains separately owned.

Acceptance covers both entries, independent intervening appends, duplicate-id metadata preservation, history and metadata failures, reopen recovery, later HEAD changes, caller-owned branches and advance_head=False. Existing-session metadata and unrelated history must survive. Remaining legacy whole-index metadata writers require separate repair; this append contract does not certify them.

Turn commit ownership

Session turn commits record already-persisted session files while holding the stable session-id lock. They do not copy cached metadata back to disk. Session mutation APIs own persistence, and the append recovery owner completes any interrupted history/metadata pair before the commit proceeds. A title, HEAD or other field committed by another writer before lock acquisition therefore remains present in both the working tree and the resulting Git commit.

The commit entry retains its commit identifier or no-change return value, missing-session behavior, error propagation and existing Git staging scope. Git errors do not discard the durable files, so a later commit can record them. This correction does not certify legacy mutation APIs that still write whole cached metadata. Acceptance uses real temporary session repositories and inspects metadata from the resulting Git object, including an interrupted append followed by turn commit.

Session identifier path boundary

A session identifier is a nonempty string naming one visible directory component. Parent/current-directory references, drive-qualified paths, separators, null bytes, hidden names and reserved session-root entries are rejected, including case variants of reserved names. Invalid identifiers are not rewritten into different identifiers. Unicode and ordinary embedded dots remain supported. Read entries retain their missing-result behavior for invalid identifiers; creation, append and session deletion raise ValueError before creating locks, resolving projects or changing files.

Placement, delete-intent and migration staging/hold paths share the same validator. Migration validates before taking its registry lock. Recorded legacy placement remains supported for valid identifiers; this rule does not redefine project identifiers or certify arbitrary recorded paths. Acceptance creates isolated sentinel directories, attempts relative/absolute traversal and reserved-name operations through public store entries, and checks that all fixture data survives with no storage changes. Valid session creation, append and deletion remain compatible.

Resource view connection lifetime

Shared-budget resource views keep the usage ledger read scope open while querying each ancestor scope. The connection never escapes its protected read lifetime. A concurrent ledger close may proceed after the read scope ends, and the view then returns already-computed values. This retains budget calculations and shutdown ownership while preventing a worker query from using a connection closed by teardown. Acceptance closes the real ledger immediately after each read scope and verifies the public resource view still reports the expected shared budget.

Session index sequence ordering

Session node reads retain ascending sequence order even when a caller supplies an unused sequence lower than an existing node. The in-memory sequence index and predecessor/caller child indexes use the same sequence order as a reopened session. Automatic appends keep the constant-time ordered-append case, while out-of-order insertion uses binary search and list insertion. Explicit sequences remain unchanged and automatic numbering continues above the greatest assigned sequence. This correction does not change graph edges, HEAD policy, duplicate rejection or durable append recovery.

Acceptance appends nodes through SessionNodeWriter with explicit nonmonotonic sequences and compares cached and reopened public node, latest-user, equal-depth leaf and caller-descendant reads. Edge reparenting, graph cycle policy and legacy whole-metadata mutation are separate audit scopes.

Session node deletion ownership

Single-node removal and branch-tail deletion share one durable deletion owner. The owner acquires the stable session write scope before selecting nodes and metadata. Node identifiers are literal identities; history paths come from validated sequence, role and identifier fields without glob patterns. Tail removal follows both predecessor and caller edges once per node, and single-node removal selects only its requested node.

A deletion intent records selected node identities and resulting metadata before any history file is removed. Once persisted, the intent commits to completing that deletion. Recovery under the same session lock removes the selected files idempotently, synchronizes the history directory, writes metadata, and removes and synchronizes the intent. Public opens and later writes recover an interrupted deletion before returning session state. Errors and cancellation propagate, retain unfinished recovery and invalidate the old cache; the cache is rebuilt only from the completed durable state. An intent-write failure leaves existing records unchanged.

Unrelated concurrent metadata is retained. Names for removed nodes are discarded; an active HEAD among removed nodes falls back to the selected root's predecessor. A legacy last_node_id alias naming a removed node is cleared in the same intent, so reopening an empty session cannot restore the deleted HEAD. Single-node callers remain responsible for choosing nodes whose children need no deletion. Missing sessions and nodes keep their false or zero result and create no session. Activity timestamps and Git commit ownership remain unchanged. Acceptance covers literal metacharacter IDs, interleaved writers, unlink and metadata failures, cancellation and process interruption followed by a fresh public read. Project placement trust and other legacy metadata mutators remain separate audit scopes.

Session cache synchronization ownership

Writing a GitSession file invalidates its cache fingerprint before any file mutation. A successful file replacement does not prove that SessionMemoryIndex has been updated. Only an index rebuild or a completed shared session write scope records synchronization. The shared scope invalidates before invoking the mutation and on every exception, then records the fingerprint after the owning operation has published its index updates. Append and deletion use this common publication boundary instead of marking independently.

Public reads after an OSError or cancellation following a durable write reload that write instead of returning the pre-write cache. This includes session metadata, HEAD compare-and-set and in-place node payload updates whose directory timestamp need not change. Direct GitSession writes likewise leave the index stale until rebuilt. Normal successful operations preserve existing return values and cache efficiency. A completed metadata batch reuses its already-updated writer index; an external reader still rebuilds once to observe the batch. Reads concurrent with external writers outside the stable lock and project placement arbitration remain separate audit scopes.

Remaining session metadata mutations

Unconditional HEAD assignment, branch-name removal and merged-head accumulation transform current durable metadata inside the shared session write scope. The transformation reads the refreshed index when validating a HEAD and publishes metadata only after its write succeeds. Concurrent titles, branch entries and other unrelated fields are retained; write failures leave the cached state consistent with the durable state. Merged heads retain first-seen order, whitespace normalization and idempotence. A missing branch-name removal or unchanged merged-head list does not write metadata.

HEAD assignment preserves its ability to initialize a missing session and rejects a compaction summary using the index refreshed after lock acquisition. An explicit HEAD assignment clears the legacy last_node_id alias so clearing HEAD remains effective after reopening. Branch-name removal and merged-head accumulation remain no-ops for missing or invalid session identifiers and never create a session. Existing session field and dictionary transformations retain their public callback signatures. Creation uses the same durable transformation, as described below.

HEAD compare-and-set ownership

HEAD compare-and-set uses the same durable metadata transformation as other session mutations. It validates the target against the index refreshed after acquiring the stable write lock and compares the expected HEAD with the durable canonical or legacy HEAD. A successful update writes the explicit target, clears last_node_id and increments the HEAD version. A mismatch returns false without writing metadata; a missing session is not created.

The operation owns head_id, last_node_id, head_version, writer_epoch, branch_refs and active_branch_id. Supplemental meta_update fields cannot replace those controls; matching operations reject such input before writing. Branch changes use branch_update, retaining source references, target preservation and rollback status behavior. The resulting metadata is normalized through its JSON representation before publication so caller mutation cannot alter cached state and cached values match reopened values. Existing workspace alignment metadata remains supported. Error and cancellation recovery use the shared cache publication scope, and no operation-level duplicate lock or cache publisher is introduced.

Packaging and publication

Publication follows the existing distribution workflow and immutable release tags. After complete coverage and all repair reviews, verify the combined source head, build supported artifacts, check installed entry points and checksums, and publish the exact reviewed source and artifacts. Completion requires observing the resulting remote refs, release assets and workflow results. Updating the local App alone does not complete publication.

Reference contracts: repository organization, test system, and distribution. These subsystem documents remain the authoritative owners of their detailed designs.

The affected DAG acceptance also requires automatic append sequence allocation to skip occupied sequence numbers when the cached counter lags. When the counter points to an occupied sequence, allocation chooses one greater than the largest occupied sequence without mutating the index before persistence; explicitly supplied duplicate sequences remain errors. The existing public append regression reproduces on the task base.

Session creation metadata admission

Creation decides whether metadata already exists inside the shared durable write scope. It constructs initial fields without publishing them to the index, preserves pre-existing history and HEAD, and publishes the normalized metadata only after a successful write. A repeated creator preserves the first durable creator's fields. A failed initial write leaves creation retryable; a write that reached disk before cancellation remains authoritative on retry.

The old cached whole-metadata persistence helper and pending in-memory creation exceptions are removed. Concurrent metadata updates serialize after creation and preserve its initial fields. Existing project resolution, location selection and registry publication remain in place; cross-project placement arbitration is a separate remaining scope. Tests exercise temporary stores, deterministic writer interleaving, failure and cancellation, existing history and caller-owned nested metadata.

Implementation status

Whole-repository design coverage and a new public release are pending. The existing module-organization and file-safety acceptance remains valid for its documented scope. The review ledger records additional verified work without reclassifying uninspected files as complete.
