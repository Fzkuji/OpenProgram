# Commitments and Heartbeat

> The agent remembers what was promised and speaks up at the right moment,
> instead of waiting to be asked. Two mechanisms, one loop: commitments are
> the state, the heartbeat is the clock. Visual companion:
> [`commitments-and-heartbeat.html`](commitments-and-heartbeat.html).
> Related code (planned): `openprogram/memory/runtime/`,
> `openprogram/functions/tools/cron/`, `openprogram/proactive/`.

## What a commitment is

A commitment is a dated obligation extracted from conversation: "submit the
rebuttal by Wednesday", "rotate the server password next week", "reply to the
reviewer after the experiments finish". It has an owner-visible shape:

| Field | Meaning |
|---|---|
| `text` | The obligation, one sentence, imperative |
| `due` | Absolute date or `null` (undated commitments still surface, less urgently) |
| `speaker_id` | Who took it on — the owner or a paired speaker, from authority |
| `source` | Source v2 citation, same anchor contract as Topic blocks |
| `status` | `open` / `done` / `dismissed` |

## Extraction rides the writer

No new pipeline. The memory writer already reads each session batch to
distill Topics; the same pass now also emits commitment records. Extraction
follows the same trust rule as distillation: only `trusted` sources produce
commitments — an unpaired stranger cannot put an obligation on the owner's
plate. Relative dates are resolved to absolute dates at extraction time using
the session's timestamp, because "next Wednesday" is meaningless a month
later.

Storage is a derived view, `commitments.jsonl`, next to
`recent_events.jsonl` — same rebuild discipline: derived from cited sources,
regenerated by the writer, never hand-authoritative. Marking one `done` or
`dismissed` is a state transition recorded in the view, made either by the
writer when a later conversation says so ("rebuttal 已经交了" closes it on the
next distillation) or explicitly through `memory_update`.

## The heartbeat

A scheduled turn — the existing cron machinery, one built-in job — whose
prompt is fixed and narrow: read open commitments, compare against today,
decide whether anything deserves the owner's attention, and say so through
the channel the owner already uses. It is a normal turn in every enforcement
sense: it carries `runtime_authority` derived from the owner (non-interactive,
so it can never approve anything), its outbound message rides the existing
channel reply path, and its sandbox policy is the frozen cron policy.

What keeps it from becoming a nag:

- **It speaks only when there is something to say.** Due or overdue
  commitments, or nothing — a silent heartbeat sends no message at all.
  "Nothing to report" reports are noise and are not sent.
- **Once per commitment per escalation step.** A commitment notifies when it
  first comes due and again if it goes a configured interval overdue, not on
  every beat. The notification state lives in the commitment record.
- **Quiet hours.** `proactive.quiet_hours` (default 23:00–08:00 local)
  suppresses sending; suppressed items carry over to the next allowed beat.
- **One knob for cadence.** `proactive.heartbeat` — `daily` (default),
  `hourly`, or `off`. Off means the whole loop is inert; commitments are
  still extracted and visible in `memory status`, just never pushed.

## What this is not

Not a task manager: no subtasks, no priorities, no projects — a flat dated
list with citations, because everything richer already failed as a product
(the graveyard of todo apps) and the agent's edge is that the list writes
itself. Not an autonomous actor: the heartbeat reminds, it does not execute.
"You said you'd rotate the password" is in scope; rotating it unprompted is
not. Acting on a commitment stays a normal owner-initiated turn.
