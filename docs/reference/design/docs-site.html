Documentation HTML rendering and authoring

For contributors maintaining product and implementation documentation. Every published page is HTML, with shared navigation, search and theme controls. The source format is chosen for the document: native HTML for visual implementation/design documents, Markdown for short usage and reference text.

Rendering paths#

Source Published result Author responsibility
Markdown HTML article in the site layout Headings, prose, commands and relative document links.
HTML fragment HTML article in the same layout Semantic sections, diagrams and optional native interactions; use the site theme variables.
Standalone HTML Site page containing an iframe, plus a .raw.html payload Own responsive layout, theme and internal navigation. The outer site controls remain available.

Prefer HTML fragments for implementation documents that should share the site layout. A standalone document is appropriate when its visualization needs an independent viewport. The iframe separates layout; it is not a security sandbox for untrusted scripts.

Reading and visual design#

Start with the document's question, audience, scope and implementation boundary. Explain the public entry and data/state flow before implementation details. Use a source map for ownership, a diagram for control or data flow, and a final implementation-status section for remaining work and evidence gaps.

Use the existing --bg, --bg-code, --tx, --tx-soft, --acc and --bd theme variables in fragments. The site uses the Web application's warm neutral palette and orange accent. Do not repeat a fixed light-only palette inside an article.

Use semantic headings with stable id values so HTML sections appear in the page navigation. Tables need a locally scrollable container when their columns cannot fit a narrow screen. Diagrams need an accessible title and description. Native disclosure controls can separate detailed evidence from the main explanation. Keyboard focus, reduced motion and mobile reading are part of document acceptance.

The site theme preference is stored as op-docs-theme; documentThemeChange is dispatched on the site window when the toggle changes. An iframe has its own document and does not automatically receive that event. Keep a standalone page's theme behavior explicit or use a fragment to inherit the shared theme.

Navigation and bilingual sources#

The nine tabs are start, install, capabilities, interfaces, models, integrations, server, reference and virtual design. Design sources stay under docs/reference/design/; there is no docs/design/ source directory.

TAB_SECTIONS declares product reading order; PAGE_ORDER controls explicit page ordering. Remaining pages are grouped by directory. Directory headings use configured labels or README titles. Do not assume that the sidebar is a literal filesystem tree or that all pages are ordered by filename.

English is the default. topic.zh.md pairs with topic.md, and topic.zh.html pairs with topic.html. The Chinese source is attached to the English page and reached through the language control, rather than appearing as a second sidebar entry. Update both members when changing a bilingual topic.

The builder supports existing same-name Markdown/HTML companions by assigning the HTML companion a .viz.html output. A relative topic.md link targets the text output; a relative topic.html link targets the HTML companion at topic.viz.html, preserving its section anchor. The Chinese HTML companion uses topic.zh.viz.html, while the Chinese Markdown output keeps topic.zh.html; language controls use these distinct outputs. This compatibility behavior does not justify maintaining two copies of the same explanation. Compare content before consolidating: retain distinct diagrams and evidence and update their incoming links.

Generated output and static-only folders are excluded from page discovery. docs/superpowers/ is explicitly excluded. A leading underscore alone is not an exclusion rule: the proactive research archive currently remains discoverable.

Build and serving#

python -m scripts.docs_site.build
python -m scripts.docs_site.checklinks
python -m scripts.docs_site.checklang
python -m scripts.docs_site.check_landing

Run these commands from the repository root with the documentation dependencies available. The contributor guide lists the uv run environment. The link checker reads built HTML, so rebuild before checking.

checklang currently checks default product Markdown only; it excludes the design directory and does not scan HTML sources. A pass does not establish bilingual compliance for all design pages. Review the language and counterpart of revised HTML separately.

The build regenerates code-derived CLI/config/provider reference pages, writes docs/_site.tmp/, and replaces docs/_site/ after successful rendering. docs/_site/ is ignored by Git. Files under docs/_static_root/ are published at the site root without entering navigation or search.

A source checkout serves its docs/_site/. An installed runtime can serve bundled documentation under the Server's _frontend/docs/; rebuilding a different checkout does not update that bundle. Compare the served page with the expected output before claiming local acceptance. Default local verification uses http://localhost:18100/docs/. Completed application updates use scripts/refresh-local-app.sh under the repository's local-App rules.

The source worker checks for a rebuild when registering documentation routes; ordinary HTTP reads do not scan or rebuild the source tree. There is no continuous watch mode.

Design alternatives#

The existing design chooses the in-repository Python renderer to preserve native HTML/SVG/script content and integrate with the single-port worker. The alternative comparison concerns this project's requirements, not a current capability survey of external products.

Consideration Current Python renderer VitePress alternative MkDocs alternative
Existing native visual documents Preserve as fragments or independent pages Requires evaluating integration with the component/layout system Requires evaluating raw-HTML and theme integration
Shared navigation and search Maintained in this repository Evaluate built-in navigation and search against project needs Evaluate built-in navigation and search against project needs
Toolchain Python rendering and static browser assets Additional Node-based documentation build Python-based documentation build and theme configuration
Maintenance ownership The project owns layout, navigation and accessibility Framework configuration and upgrade maintenance Framework/theme configuration and upgrade maintenance

The renderer uses markdown-it-py, mdit-py-plugins and Pygments. It produces static assets without a client framework or an editor/CMS. A framework migration is outside this documentation update.
