GUI Agent execution design

One public invocation, one explicit runner, one terminal status. Desktop control and exact-Page browser control share the result contract but retain separate trust boundaries.

Public entry and routing

OpenProgram exposes one tool named gui_agent. Program discovery imports GUI-Agent-Harness, then the OpenProgram bridge registers the public wrapper. The wrapper must call the harness's raw Python implementation, not its already-decorated wrapper, so the execution tree contains exactly one gui_agent node.

The runner owns the loop and terminal status. A step returns either an executable action result or one terminal status. The latest eight action results form bounded cross-step state. A fourth identical failed action terminates with repeated_action. The conclusion model writes user-facing text only; it never decides whether the run succeeded.

Result contract

Both desktop and browser modes return status, deterministic success, reason_code, summary, and handoff_instruction. Desktop compatibility keeps infeasible_declared, step counts, timing, and history. Browser compatibility keeps backend and WebSession metadata.

User-visible status

The Function card presents the GUI task outcome, not the internal worker lifecycle. A persisted node may use completed to mean that its worker returned a structured result, but that transport state is not shown as the task result. success remains a compatibility field derived from status; it is never an independent decision or a second visible status.

Trust and lifecycle boundaries

  • Desktop mode records the frontmost app, must validate the current target window before a coordinate action, and must not learn components from another app. A window outside the observed macOS Space receives one bounded Window-menu recovery; continued invisibility terminates as infeasible with a handoff instruction.
  • Browser mode keeps exact Page identity, backend selection, owner isolation, stale-observation checks, screenshot revocation, and session cleanup inside Web Use.
  • allow_general remains false for the OpenProgram public entry unless explicitly enabled by a trusted caller.
  • Cancellation and unrecoverable exceptions terminate the runner; an unlimited step budget must not convert a repeated infrastructure error into an infinite retry.

Compatibility and exclusions

The standalone CLI, direct Python gui_agent(), benchmark execute_task() wrapper, current function name, and existing result details remain compatible. Desktop and Web Use are not merged into one execution engine. Benchmark-only grounding pipelines remain internal and are not part of the public runner refactor.

Acceptance criteria

  1. The OpenProgram DAG shows one gui_agent node followed by gui_step; it never shows nested duplicate gui_agent nodes.
  2. Done, infeasible, step exhaustion, invalid planner output, cancellation, and exceptions produce deterministic terminal statuses.
  3. The exact fail blocker reaches the user-facing handoff text.
  4. Desktop and built-in-browser invocations expose the same core result fields.
  5. A terminal GUI Function card displays Succeeded, Failed, or Needs takeover from the structured GUI result. It never labels a failed GUI result Completed merely because the worker returned normally.
  6. Long desktop and browser tasks retain bounded state, avoid repeated actions, and complete only after verification.
  7. Real acceptance uses the default OpenProgram App and includes one multi-step desktop task and one multi-step built-in-browser task.
