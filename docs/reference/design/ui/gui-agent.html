One task entry, two mode executors, explicit control primitives.

gui_agent is the ordinary user entry. It selects exactly one surface and calls an unregistered executor: run_computer_task for foreground desktop control or run_browser_task for one exact built-in Browser Page. Browser primitives belong to browser_control. No layer calls another decorated task function.

Primary path

System architecture

Every ordinary invocation creates one gui_agent FunctionInvocation. Its Harness controller receives the original task, current capability availability, and the complete ordered capability history. It may call computer_use, browser_use, or vm_use, append that capability's exact input and full output, and then decide whether to continue, switch capability, or propose a terminal result. A hidden legacy surface value supplies only the initial preference; it does not create a second controller.

Task logic

Runner state machine and decision ownership

The runner controls iteration and terminal truth. The planner proposes one action or one terminal decision. The conclusion model produces user-facing prose only; it cannot change the terminal state.

01Observeone current screen or exact Page frame
02Verify previousdeterministic evidence before another action
03Plan one actiontyped action, done, or fail
04Execute onceone dispatch boundary; no backend fallback
05Record feedbackbounded latest eight outcomes
06Repeat or stopfour identical failed actions stop
07Summarizewording only; status already fixed
Planner owns

Next action

One validated action, done, or fail. Invalid protocols terminate rather than silently retrying.

Runner owns

Status and limits

Verification, step/time limits, cancellation, repeated-action detection, cleanup, and terminal normalization.

Conclusion owns

User-facing text

summary and handoff wording. It cannot convert a failure into success.

Built-in Browser

Exact Page lifecycle

Browser mode does not launch a separate browser engine and does not use the OS pointer. It uses the Page registry and WebSession state already owned by the OpenProgram worker.

Borrow an existing Page

  • Inventory is restricted to the originating OpenProgram window.
  • The selected exact Page becomes a binding with owner and revision checks.
  • Actions use DOM/CDP and screenshots use hidden capturePage.
  • Finalization releases the binding but never closes the user's Page.

Create a background Page

  • Only an empty usable inventory triggers creation.
  • The Page starts at the normalized Browser start URL and remains unselected.
  • The runner records agent_owned=true only from a trusted created response.
  • Every terminal path attempts exact close; rejection becomes takeover.

Exit semantics

One result contract, no ambiguous “completed” state

Desktop and Browser modes return the same core fields: status, success, reason_code, summary, and handoff_instruction. success is derived from status and is true only for succeeded.

succeeded · trueTask completion was verified. Function card: Succeeded.
infeasible · falseConcrete blocker requires user action. Function card: Needs takeover.
failed · falseRequest was not satisfied. Function card: Failed.
cancelled · falseHost cancellation propagated. Function card: Cancelled.
Transport state

completed

The worker returned a structured result and persistence finished. This is not a GUI task outcome and is not shown as the terminal task label.

Contract error

Error

A runtime exception, error node, or unrecognized GUI result is infrastructure failure. It is distinct from failed and infeasible.

Explicit exclusions

Background window boundary

The macOS backend supports window-only capture plus Accessibility press, text-value, and scroll actions. It does not synthesize background coordinate clicks, move the system pointer, activate the target, or control a minimized/off-Space window.

No automatic backend fallback

A backend failure cannot trigger a second backend and duplicate the side effect.

No benchmark pipeline exposure

Grounding benchmarks, crop/zoom experiments, and evaluation-only state remain internal to the Harness.

Reference adoption

Adopted, modified, and rejected choices

Adopted

GUI-Agent-Harness keeps its desktop observe → verify → plan → act loop, OCR/detector perception, component memory, VM adapters, and direct Python/CLI compatibility.

Adopted

An explicit macOS application/window target uses ScreenCaptureKit and Accessibility actions. A non-activating indicator follows the exact process/window, reports the current action bounds, hides when the target is unavailable or covered, and is reaped with the session.

Modified

OpenProgram wraps the raw Harness implementation so there is one public DAG node, adds surface routing, normalizes all terminal results, and bridges Browser work back to worker-owned Web Use state.

Modified

Browser control uses exact Page capabilities, DOM refs, WebSession ownership, and hidden native capture instead of applying desktop screenshots and coordinate input to a browser pane.

Rejected

Calling the decorated Harness wrapper from another decorated wrapper. It creates duplicate gui_agent nodes and two runtime boundaries.

Rejected

Using OS input for hidden Browser Pages, activating a tab before each action, or choosing the currently selected Page during Retry.

Rejected

Inferring success from conclusion prose, normal worker completion, or a truthy legacy field after status says fail/infeasible.

Observable acceptance criteria

Invocation and DAG
Function form, exact registered expression, and exact-node Retry each produce one ProgramRun. The expanded DAG contains one gui_agent root followed by gui_step; no nested duplicate root exists.
Terminal truth
Done, infeasible, failure, cancellation, exception, and cleanup rejection produce deterministic statuses. Fail/infeasible cannot return success=true; transport completion cannot display as task success.
Background Page behavior
An empty originating-window inventory creates exactly one hidden Page, continues the same run, performs observe/click/verify without changing visible selection or system frontmost application, and closes only that owned Page.
Background application behavior
An exact macOS process/window binding captures only that window and dispatches only supported Accessibility actions. The visible control badge and current action marker do not activate the target, receive input, move the system pointer, or survive the session.
Cleanup honesty
Every normal and abnormal terminal path attempts exact cleanup. A rejected close returns page_cleanup_failed and a manual takeover instruction rather than success.
