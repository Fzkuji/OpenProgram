OPENPROGRAM / COMPUTER USE

GUI Agent: complete computer-use design

An evidence-based design for complete input, persistent code execution, recovery and application acceptance.

TARGET DESIGN · NOT A COMPLETED IMPLEMENTATION Chinese edition

Purpose and completion contract

The product goal is sustained work in browser and native applications: combine UI interaction with permitted code/file tools, verify deliverables, and remain controllable. Coverage includes dense controls, custom canvases, multiple windows, dialogs, downloads, saving, recovery, and concurrent human use where the OS supports it.

This is the canonical GUI Agent engineering design, rewritten in place. The body specifies the target; the current-source audit and final status appendix separate existing capabilities from implementation and live acceptance still required. Product instructions remain in GUI Agent usage.

Acceptance means behavioral parity on a declared task suite, using the same model and comparable budgets. The pasted video description has no inspected end-to-end execution trace here. Neither its particular Blender/PCB method nor a quantitative Codex advantage is established.
  • One public gui_agent(task), standard Agent configuration and shared history.
  • Persistent code execution, complete UI primitives, browser/local desktop/VM adapters.
  • Target ownership, inherited permissions, bounded execution, cancellation, restart recovery and final verification.
  • Matched-model application tests. Foreground or VM operation does not satisfy a background-desktop criterion.

Foundation-model training, reproducing undisclosed OpenAI internals, bypassing app security and universal software compatibility are outside scope. Difficult background input remains a required workstream; it does not justify redefining the goal as Accessibility-only automation.

Current paths and verified gaps

The bridge registers one root and unwraps the Harness function. plan_next_capability serializes capability history into a prompt; call_capability selects the internal execution path.

gui_agent(task)
  -> plan_next_capability(task, history, availability)  # LLM
  -> computer_use(subtask)
       -> macOS window_session
       -> gui_step: observe
            -> verify_step(previous feedback)        # LLM, when feedback exists
            -> plan_next_action                      # LLM
            -> one registered action
  -> append inputs/outputs; choose again

browser_use(subtask)
  -> custom loop calling agent(tools=[browser_page], max_iterations=1)
  -> Page/frame checks, action, optional screenshot, terminal assertion

A desktop iteration with feedback normally has three model requests before optional localization/retry. This is a structural count, not measured latency. The first iteration omits prior-step verification. AX window actions bypass OCR/YOLO; other desktop/VM paths can use detection and localization.

The macOS window registry exposes only window_press, window_set_text, window_scroll and terminal markers. Global-input functions elsewhere do not expand this entry. Browser actions include click/type/press/hover/scroll/select, but no exposed drag or persistent script entry.

Runtime.exec already uses DAG-rendered history and gates inner tools under caller authority. A second context engine is unnecessary. execute_code starts a fresh Python subprocess and cannot preserve UI handles or variables across calls.

Target architecture and responsibility

One gui_agent FunctionInvocation owns one standard Agent execution lifetime. It resolves configuration, acquires resources, exposes tools, enforces limits and returns verified results. It is not another planner. The model chooses observation, UI, ordinary tools and terminal verification.

gui_exec(code) is a normal function tool. Its persistent Python child accesses scoped proxies; a trusted broker owns Page/window handles, permissions, leases, coordinate transforms and action receipts. Model variable assignments cannot change these. The desktop helper provides input/capture; the worker retains Page ownership and task control.

computer_use, browser_use and vm_use become compatibility boundaries/internal adapters without additional task planners in this path. Keep the simple public form; resolve advanced settings through normal Agent configuration: explicit, then ambient, then default. Preserve tools=None, tools=[] and selected-list semantics. Add GUI tools only within outer authority, and remove recursive gui_agent. No GUI call restores denied shell/file/network tools.

Persistent runner and code contract

Use Python first because Runtime, Harness and adapters already use it. One isolated child preserves a namespace per GUI invocation, including top-level await. The broker may use Playwright internally; model code receives scoped proxies, not raw browser/CDP/AppKit/OS-input objects. A JavaScript language adapter is optional, not required for code-driven operation.

Reuse backend process lifecycle and ToolReturn images, with a dedicated mandatory GUI isolation policy. Do not change execute_code's fresh-process contract. Python namespace restrictions and Node vm are not security boundaries.

Prototype limits: 30 seconds and 100 broker operations per script, 256 KiB text, four images per return plus provider pixel limits. These are starting values, not measured optima. Long application rendering returns an asynchronous handle; bounded polling yields control. Timeout revokes write capabilities before killing the child.

# Proposed SDK; not currently implemented.
page = await ui.browser.open("https://example.org", background=True)
obs = await page.observe()
field = page.get_by_role("textbox", name="Search")
await field.fill("bearing dimensions")
await field.press("Enter")
await page.wait_for_text("Results", timeout_ms=5000)
display(await page.screenshot())
# page and field persist into the next gui_exec call.

Return ordered text/image blocks and typed details: environment, generation, operation ID, status, effects, observation, error and timing. Record each primitive as a child execution event. Errors identify the last completed primitive and uncertain effects. An executor receipt proves an operation was applied, not that the task succeeded.

Broker protocol and observation schema

Use an invocation-local IPC connection with length-delimited JSON messages and separate bounded image payloads. The host assigns the owner and generation at connection setup; generated code cannot choose them. Requests include an operation ID, resource handle, method, arguments and observation token. The server rejects unknown methods and oversized messages before executing.

# Proposed broker message shapes
request = {
  "operation_id": "op-17",
  "resource": "window-handle",
  "method": "drag",
  "observation": "frame-token",
  "arguments": {"path": [[120, 90], [180, 120]], "modifiers": ["Shift"]}
}
observation = {
  "target": {"kind": "window", "handle": "window-handle"},
  "generation": 3, "frame_id": "f-21", "base_frame_id": None,
  "image": {"width": 1600, "height": 1000, "detail": "original"},
  "transform": {"origin_x": 0, "origin_y": 0, "scale_x": 2, "scale_y": 2},
  "controls": [], "capabilities": ["observe", "click", "drag", "keypress"]
}
receipt = {
  "operation_id": "op-17", "state": "applied",
  "last_applied_index": 1, "effect_uncertain": False,
  "observation_token": "new-frame-token"
}

The broker persists admission and completion through existing execution effects before reporting a successful receipt. Admission is not proof of a side effect. For native input, event posting often has no transactional acknowledgement: after a lost response, observe rather than replay. Lease generation fences old connections after recovery.

Receipt admission follows normalization and current authority checks, and is serialized with revocation under a short lock. A receipt admitted before revocation may finish persistence afterward because it records an already-completed primitive; it does not authorize further input. No adapter, validator or database call holds that lock. Dynamic validators are followed by renewed execution/attempt and cancellation checks. Broker dispatch uses a separate copy of the owning host Context for each operation.

For an unrotated window capture, desktop points are x = origin_x + image_x / scale_x, similarly for y. Crops first map to parent-image coordinates. General display transforms use a matrix and must be invertible; the source observation defines the convention. Browser coordinates are viewport CSS pixels after mapping from screenshot device pixels. Reject points outside allowed content and stale transforms. Do not multiply Retina scale twice.

SDK calls may hide protocol bookkeeping, but cannot hide changing authority. A locator revalidation may update geometry inside one known target; opening another app or executing on a new origin must pass its own policy check.

macOS: complete input and background feasibility

Retain ScreenCaptureKit and AX. Add a stably signed native helper for full input, bound to application identity, window and broker lease. Use AX for supported controls; investigate process-directed events for canvases and keyboard workflows.

The local SDK declares CGEventPostToPid; AXUIElementPostKeyboardEvent is deprecated. A PID is not a window ID. Prototype correct window routing, coordinate interpretation, event acceptance and foreground/pointer preservation. No claim is made that OpenAI uses this API.

The opt-in Harness probe tests/probe_native_input.py uses an owned AppKit fixture. On macOS 15.7.3 arm64, raw process-directed mouse events reach the application without a window association. NSEvent supplies the window association, but subsequent mouse coordinates are incorrect. An experimental CGEventSetWindowLocation annotation with the full window frame, including its title bar, produces the expected click and drag coordinates. This setter is undocumented: the experiment establishes a local feasibility result, not a supported production contract. The default probe retains the public-API control; the undocumented path requires --private-window-location.

The event fixture receives ordinary and Unicode key-down characters without clipboard use. The separate --controls fixture checks native text replacement, an NSButton action, local WebKit textarea replacement and a canvas drag using actual control values and DOM event positions. Command+A requires the fixture's standard Edit menu; without it, the initial experiment appends text and fails. Control geometry is measured after WebKit loads. These tests establish a small AppKit/WebKit control sample, not installed-app compatibility, IME, general shortcuts, multiwindow isolation or screenshot-coordinate correctness.

Stronger application-identity and two-window checks invalidate a general background-input conclusion from that single-window sample. A temporary signed bundle launched through LaunchServices satisfies the existing MacWindow launch-identity guard and yields an exact-window screenshot. With an initially key sibling window, ordinary mouse flags do not focus WebKit; subsequent web text goes into the native field. Explicit Command-modified mouse events reach the canvas, but keyboard text goes into the sibling. This is an unresolved routing/focus failure, not a transparent fallback. The probe records both conditions as failed control acceptance and checks the sibling's actual text on every receipt, including an explicitly requested final state after input. A production adapter must establish the intended focus and preserve requested modifier semantics before sending keys.

Foreground identity and pointer position are sampled before and after; this does not exclude transient changes. Keep background_input unavailable until the full implementation gates pass. The exploratory background-click analysis identifies the undocumented annotation as a candidate; its claims about other software are not adopted as verified facts.

First implementation gate: signed helper + owned AppKit/WebKit/Electron fixtures + installed canvas apps, with another app foregrounded. Record actual target state, screenshots, foreground identity, pointer and key state. Failure is an unresolved background requirement. Foreground/VM execution is not a substitute pass.

Advertise background_ax, background_input, foreground_input or unavailable. Background is default where verified; foreground requires a permitting task/session policy and visible control. Never silently activate an app. If public APIs cannot provide a required background behavior, evaluate a supported vendor integration or tested native approach and leave the criterion open.

Transform screenshot pixels using display identity, window origin, scale and crop metadata. Cover Retina, negative multi-display origins, moved windows and scale changes; reject stale geometry. Check capture and input permissions independently. Minimized windows, secure fields, lock state and permission dialogs have explicit outcomes.

Prefer AX replacement and verified key insertion. Default background and foreground text input never uses the global clipboard as an automatic transport. Use AX, Unicode/key events or an app-local insertion/import API. A clipboard change counter only protects restoration; it cannot prevent another process from replacing text before paste. Explicit system-clipboard tasks use host/pasteboard arbitration, preserve concurrent changes and do not carry a concurrent-user correctness guarantee. Browser-local paste is separately scoped. Serialize physical keyboard/pointer leases at host/session level, not merely per window. Bind modal sheets/menus as descendants or explicit new targets, never the frontmost window.

Browser: reuse ownership and extend operations

Reuse WebUseSessionRegistry, Page tokens, worker-owned WebContentsView/CDP, frame checks and cleanup. Attach to the exact submitted Page or open an owned background Page, never the currently active tab. Keep optional MCP adapters as execution adapters.

Expose scoped role/name, label, text, test-ID and relative locators plus frame entry. Reuse Playwright actionability and bounded waiting. Resolve each operation afresh; ambiguity or semantic/owner change returns a stale-target error. Numeric refs are observation-local.

Add drag, multi-click, modifiers, horizontal scroll, file chooser/download, iframes and popups. Bind popups by opener and exact identity, recheck destination authority, and verify transfers through approved paths. Arm download/popup waits before the trigger so events are not missed.

Do not expose raw page.evaluate, arbitrary CDP send, cookies, profile directories or browser launch in UI scripts. Trusted code may evaluate DOM for bounded observation. Ordinary shell/file/code tools stay available through normal gates; explicit developer-debug capabilities use the same policy. A UI SDK is not an unrestricted browser control endpoint.

Windows, Linux and VM boundaries

Windows requires an explicit active-desktop mode: capture the intended display/window and execute input under a foreground lease. Detect user takeover, desktop switches, lock and integrity-level restrictions. UI Automation handles standard controls; coordinate input covers custom canvases. Background Windows control is not claimed by the reference product and is not silently promised here.

Linux X11 and Wayland are distinct adapters. X11 can use existing input/capture infrastructure; Wayland requires an explicitly supported compositor/portal or remote desktop backend. Return an unavailable capability rather than assuming X11 permissions. The first Linux acceptance target is a declared isolated desktop/VM image, not every distribution.

Keep OSWorld-compatible screenshot/execute transport, but move target identity out of process-global monkeypatching. One environment object owns its transport, screenshot path, input state and lease. Credentials stay in the executor. Validate images and timeouts, distinguish read retries from uncertain writes, and test two independent VM targets. Docker is optional Linux infrastructure; local macOS and Windows-host use do not require it.

On macOS, lock-screen automation requires a separate reviewed design for OS authorization. Do not add a privileged unlock helper as a side effect of UI completeness. Locked use is a disclosed reference-only capability until that gate passes; the task pauses with a precise reason and resumes from a fresh observation after manual unlock.

[S8] [R2]

How context remains continuous

Use ordinary user/assistant/tool messages from the DAG as the sole model-visible history. UI code, every operation result and selected screenshots are recorded with the same invocation lineage. Remove duplicated JSON history injection after migration; preserve the legacy exported result history as a derived view of events, not a second source of truth.

Separate three lifetimes: Agent conversation, execution namespace, and external application state. A continued model response restores neither a Python object nor an application window. Record environment generation and resource bindings at safe points. Compaction retains the task, permissions, unresolved criteria, artifact paths, last verified state and uncertain effects. Never serialize live AX/CDP handles as portable checkpoints.

Return small AX/DOM diffs by default, with stable broker IDs and an explicit full-snapshot request. Missing or out-of-order base observations force a full snapshot. Images carry frame/target metadata and provider-compatible detail. Preserve the most recent relevant visual state, final evidence and failed-action observations under a declared retention policy; use the shared Context Engine for token budgets and summaries.

Crop on demand at original resolution. Each crop stores an affine transform back to its parent image; coordinate SDK calls require the crop's token or explicit parent frame. Reuse existing OCR/detector/zoom grounding as an optional tool for uncertain targets, not mandatory preprocessing or extra model calls on every native AX/DOM action. ScreenSpot-style localization measures one component, not long-task completion.

Latency, cost and verification strategy

Optimize measured end-to-end work. The current structural path repeats capability choice and per-step verify/plan. The target uses one Agent decision for a short deterministic group, returns state, then decides again. Do not remove outcome verification; move deterministic checks into the executor and reserve model verification for ambiguous visual states and milestones.

Change Reason Measurement / guard
Batch input and waits Avoid a model round trip for each low-level primitive. Operations/model call, p50/p95 wall time; batch must stop on target/permission changes.
AX/DOM diffs and lazy crops Reduce repeated pixels and text. Input/image tokens and wrong-target rate; force full observation when base is missing.
Reuse bindings and namespace Avoid reconnecting browsers and rebuilding handles. Connection/capture latency; generations prevent stale reuse.
Adaptive verification Use deterministic state checks and final artifact proof. False-success and recovery rates cannot worsen; inspect visual milestones.
Bounded progress policy Detect repetition without unrelated planner layers. Repeated fingerprint + unchanged state triggers new observation/strategy or explicit failure.
Model choice Use configured model; evaluate effort and smaller-model alternatives independently. Same task/budget paired trials; never infer quality from cost alone.

Report total time as model time + capture/encoding + broker/input + application waits + recovery. Count model requests, UI primitives, observations, image tokens, retries and manual interventions. An API call completed by the model is not an action applied by the executor.

Do not promise a speedup factor before measurement. Initial performance acceptance is no completion-rate regression and lower median model requests for the matched deterministic subset; publish latency distributions and failures for the whole suite. Dense visual tasks can reasonably spend more on images if completion improves.

Execution authority and isolation

Generated Python is arbitrary code, so OS isolation is mandatory. Launch the persistent child using a GUI-specific sandbox profile that intersects outer restrictions with an unconditionally enforced scratch/runtime/IPC-only policy. The ordinary Backend.spawn_spec path is not sufficient. Use a strict launch context that owns its scratch directory, fixes the interpreter and mandatory policy, requires the platform sandbox, and refuses fallback. Runtime bootstrap may read literal ancestor directory entries, but this does not permit descendant file contents. Neither danger-full-access, a broad inherited override, nor sandbox-unavailable may disable this per-tool isolation; in that case gui_exec is unavailable and ordinary separately gated tools remain unchanged. Deny direct network, desktop automation, arbitrary host-file access and raw CDP/native handles in this child. A filtered globals dictionary is not an isolation mechanism.

The trusted broker holds OS permissions and external handles. Authenticate the child connection using process identity and an invocation-bound channel; do not pass a reusable global bearer credential into generated code. Validate owner, generation, exact target, operation, current user grant, deadline and cancellation before each effect. A batch admission is not blanket authorization for future targets.

Ordinary Agent tools remain separately gated. If a script needs file or shell work, request the normal tool through an explicit brokered tool proxy, or return to the Agent to invoke it. Reuse the existing tool dispatcher and immutable outer request. Do not copy the legacy browser path's special bypass into a general code runner.

UI observations are untrusted data. Page text and screenshots cannot authorize new app access, alter system instructions or invoke restricted tools. Tool descriptions and app capabilities come from the trusted host. Preserve user approvals for the same authorized action; new apps or expanded effects follow current policy. Do not add a confirmation to every harmless click.

Revocation first fences new effects, releases held keys/buttons and stops the script; cleanup follows. Retain bounded private traces locally with explicit artifact retention. Redact secure fields and credentials, and never publish screenshots or user data as an automatic consequence of testing.

Failure, cancellation and restart recovery

Condition Required behavior Acceptance
Stale observation or moved window Reject before input; reobserve and rebind. No input at old coordinates.
Popup/modal or navigation Stop stale continuation; discover exact new target and check authority. No writes to another active tab/window.
Partial batch failure Return applied prefix and uncertain operation; no whole-batch replay. A completed save is not duplicated.
Timeout after input dispatch Mark effect uncertain; inspect external state before any retry. No claim of exactly-once UI input.
User takeover / pause Fence writes, release input state and lease as safe; preserve task state. Resume observes fresh state and respects new instructions.
Worker/helper death Invalidate environment generation; reconnect only owned resources; inspect last effect. Old scripts cannot act after restart.
Cancel during drag Stop new input, release mouse/modifiers, terminate/reap runner. No stuck button, orphan process or late write.
Cleanup failure Preserve primary outcome and separately report resource cleanup failure. Borrowed user windows/Pages are not closed.
Provider failure Use existing bounded retry; no replay of already executed tools. Retry model request without reapplying effects.

Reuse the existing execution-control safe points, cancellation and owner generations rather than creating a second scheduler. Persist serializable resource descriptors and last confirmed operation receipts. A crash destroys live namespace state: recover at a script boundary, rebind and reobserve; do not promise to resume a Python stack or replay a sequence of UI writes.

Public result semantics stay succeeded, infeasible or failed; cancellation remains the execution system's cancelled state. Pause/approval/takeover are resumable control states, not successful results. Include reason, unresolved criterion, last verified state and artifact evidence. Failed cleanup cannot rewrite an actual task failure as success.

[S11]

Default App experience and operation visibility

Keep the single GUI Agent form and registered-expression behavior. A whole registered function expression remains one ProgramRun without an extra chat reasoning turn; prose or fenced code remains an ordinary message. Capture submitting window/Page identity for both form and direct-expression entry.

The running card shows task, exact app/Page, background/foreground mode, current operation, last observed progress and elapsed time. Expand for screenshots, code batches and per-operation receipts; do not flood the normal conversation with every primitive. Preserve the native non-activating indicator from adapters/mac_indicator.py, including cleanup and ownership.

Stop immediately requests cancellation; the UI distinguishes stopping from stopped. Take over fences writes and shows what remains, with Resume doing fresh observation. App-access prompts name the exact app and access scope, save allowed decisions under normal policy and expose revocation. Missing permission identifies whether capture or input is unavailable.

Display verified artifacts and final criteria, not just a green function return. Support long tasks with visible milestones, user steering and bounded progress updates. These controls must work in /Applications/OpenProgram.app on default profile, port 18100 and ~/.openprogram. Alternate Electron instances do not count as acceptance.

Application suite and matched comparison

Two evaluation tracks prevent confounding: (A) same model through the current and new OpenProgram runners, isolating execution changes; (B) Codex product versus OpenProgram with matched model, task, OS/app versions, input files and practical budgets, measuring product outcomes. Tool capabilities and hidden prompts differ in B and must be reported. API-only results do not prove Codex parity.

Task family Concrete task and independent outcome Required perturbations
Browser form Fill local multi-step form from supplied data; local server confirms exact values. Delayed button, re-render, iframe, popup, same-name controls.
Browser files Choose an authorized fixture file and download a generated report; check contents and path. Cancellation and interrupted transfer; no external upload.
Native text Edit a fixture document, select/replace mixed-language text, save and reopen. Dialog, multiple windows, clipboard changed by user.
Native canvas Draw/move/resize shapes, drag with modifiers, export and reopen. Background/foreground, window movement, DPI changes.
Blender Create a specified small assembly with dimensions/materials, save blend and render. Inspect both artifact structure and rendered view; distinguish script-assisted from UI-only.

Start with two tasks per family, three independent reset runs per task: 48 runs per system/model condition. This is an initial diagnostic suite, not a statistically sufficient universal benchmark. Freeze inputs, output checks, budgets and failure categories before running. Record every attempt, including unsupported tasks and infrastructure failures separately; do not remove hard cases from the denominator.

Report completion and false-success rates, p50/p95 duration, model/image tokens, API cost when known, tool calls, interventions and recovery success. Use paired task outcomes and uncertainty intervals; expand the sample if a parity conclusion is statistically unresolved. Keep visual judgments separate from deterministic artifact checks and use a reviewer unaware of the runner when possible.

Mandatory release conditions: all deterministic ownership/cancel/stale-frame/isolation tests pass; every declared critical capability passes its real-app fixture; no false success in the acceptance suite; no completion-rate regression against baseline; documented product comparison and unresolved limitations. Numeric safety targets are proposed as broker admission cancellation within 500 ms and held-input release within 1 s on the same host; measure and revise only with explicit evidence, never retroactively to turn a failing run green.

Implementation sequence and bounded work packages

The dependency order is P0 → P1 → P2/P3/P4 → P5 → P6. Browser and native adapter packages can be developed independently after the broker contract is fixed, but integration acceptance uses one combined candidate. Each package requires a public-entry failing test, minimum implementation, affected checks, independent specification review, then quality review and exact-commit evidence.
