Chat transcript follow

Author: engineering Status: implemented on the web renderer Scope: web renderer (App and browser)

Sending a message does not reliably take the reader to the latest turn. Four overlapping scroll writers disagree about what “bottom” is and who may move the viewport (legacy scrollToBottom, unused useStickToBottom, live useChatAreaStick, and loadSessionHistoryWindow). This page collapses them into one React-owned follow policy: one attach/detach state, one at-bottom predicate, one follow-trigger table, and one padding-edge definition of latest. Chat handlers and the history loader do not pin latest onto an arbitrary viewport.

ownTurn identity

MessageList passes lastRole === "user" as ownTurn. That is true only while the last store row is the user bubble.

Send already lands an optimistic user row at 0ms: sendChatMessage calls appendLocalUserTurn after the socket accepts the frame (apps/web/components/chat/composer/submit/send-chat-message.ts). The assistant placeholder is not created in that update. handleAck in apps/web/lib/net/chat-stream.ts rekeys the pending user id, then ensureReply appends an empty assistant row. After ack, lastRole is "assistant" and ownTurn becomes false.

The unit contract in apps/web/scripts/chat/check-chat-ui.mjs is correct: own send follows from far up; an agent turn while scrolled up must not move. The gap is that ownTurn is inferred from transcript tail identity, not from the send gesture. If the send layout pass fails to latch stuckRef, the ack that appends the assistant row is treated as a foreign agent turn and the view stays put. Compaction / local_command / system rows that become last also flip ownTurn off.

docs/reference/design/ui/interaction-feedback.md still says the user bubble lands on chat_ack. The send path now appends at socket-accept time. Follow must start when that optimistic row (and the pending-reply indicator while lastRole === "user") lands, not wait for ack. This page does not redesign the send/ack pipeline.

Layout versus growth

The layout effect assigns scrollTop = resolveChatScrollTop(...), and on follow that value is area.scrollHeight, which the browser clamps to scrollHeight - clientHeight when clientHeight > 0 (the hook already skips clientHeight <= 0). That clamp is the same padding edge Jump already uses; it is not a distinct bug from last-message + 16px. The read can still run before the new row’s height is in the layout. ResizeObserver pin() would finish the job, but only if stuckRef is already true, the window has no after, Jump is not animating, and performance.now() - lastPointerRef > 600.

lastPointerRef is updated on pointer/wheel/keydown on the area. A composer click is not on #chatArea, so a send from a reader who was already at the bottom is not suppressed. A reader who scrolled up and then sent within 600ms is suppressed: the layout snap uses a too-small scrollHeight, pin does not run, stuckRef stays false, and the later assistant row does not follow.

The 600ms window exists to stop execution-strip / thinking-row clicks from yanking the clicked control upward. It must not suppress a take-latest gesture. The send latch is specified under Send latch sequence: force stuckRef = true before the first height read, snap now and on the next column resize this turn, and leave 600ms in place for unrelated in-transcript growth.

Two anchoring policies

.chat-messages pad is max(25vh, calc(var(--main-composer-height) + 24px)). The composer is absolutely overlaid. isChatAtBottom slack is pad - composer + 8 so “at latest” means the last bubble has not tucked under the composer. Jump and pin aim at the padding edge (scrollHeight - clientHeight). Legacy scrollToBottom aims last-message bottom + 16px, which pulls content toward the overlay and can hide a new user bubble under the composer. Those two targets fight when a WS handler still calls the legacy helper while React pins to scrollHeight.

Welcome first send

setWelcomeVisible(false) runs at 0ms, before appendLocalUserTurn. .chat-area:has(#welcome-mount > *) sets overflow: hidden. If the stick layout effect runs in the same frame as the welcome child, scroll assignment is a no-op. Stick dependencies do not include welcomeVisible. The adopted retry is specified in the send latch: main shell observes welcomeVisible or #welcome-mount children and snaps once when the lock lifts if the take-latest generation is still current. Peer is out of this path.

Peer pane composer slack

When areaRef is passed (peer pane), readComposerHeight() is forced to 0, so overlay is treated as 0 and slack is too loose by roughly the composer box. Peer publishes --peer-composer-h as measured composer root + 24px (peer-session-pane.tsx) and uses that same variable as .chat-messages padding-bottom (peer-session-pane.css). Main publishes --main-composer-height as overlay height only; pad is max(25vh, composer + 24).

Slack is max(0, pad - overlay) + 8. Treating --peer-composer-h as overlay would yield (h+24) - (h+24) + 8 = 8, 24px too tight. The variable is not analogous to --main-composer-height. Overlay and pad are separate inputs: pad from readBottomPadding(column); peer overlay from the composer root (or --peer-composer-h - 24, or a second CSS variable). Unit case: peer pad h+24, overlay h ⇒ slack 24+8.

Peer useChatAreaStick is keyed with scrollKey = sessionId ? \`peer:${sessionId}\` : null. Main uses activeChatKey. sendChatMessage only knows sessionId. A consume-once map keyed by either value races two hook instances or never matches a split pane.

Adopted, modified, and rejected choices

Adopted

One policy module in apps/web/lib/chat/chat-scroll.ts. One attached boolean per scroller. Send / queue-drain / first welcome send = take-latest, instant snap. Stream pins only while attached and on the latest history window. Jump to latest remains the explicit smooth re-attach. Session switch restores sessionStorage pixels and is not a send. Desktop App uses this same web renderer.

Modified

Take-latest is a generation-stamped note keyed by session id plus the submitting scroller’s chatKey, not a consume-once boolean and not lastRole alone. lastRole === "user" remains a fallback until the send-path note lands in the same merge train. Pointer 600ms suppression applies only to in-transcript clicks that resize content, never to take-latest or Jump. Peer overlay and pad are separate inputs; do not treat --peer-composer-h as --main-composer-height. resolveChatScrollTop keeps the whether-to-move decision; callers then assign latestScrollTop (the named clamped padding edge Jump already uses). Send while history.after is pending until latest loads; attached stays false on the stale page. The history loader never places latest; window anchor restoration remains in history-viewport helpers as specified below.

Rejected

A fourth stick file. Last-message + 16px as the follow target. Send as a second smooth animation. WS handlers calling a scroller. Global window / module stickToBottom. Persisting stickiness to disk. A virtual-list library. Auto-follow of every DAG expand. Rewriting the send/ack protocol. CLI ScrollBox in the web bundle. Turn-anchor-previous-reply-at-top as a parallel mode.

What “bottom” means

Latest is the padding edge of the scroller. latestScrollTop = max(0, scrollHeight - clientHeight) is the named form of the clamp Jump already uses and that assigning scrollTop = scrollHeight already produces when clientHeight > 0. Combined with pad max(25vh, overlay + 24) on main (peer pad is the published --peer-composer-h = overlay + 24), the last relevant content (user bubble, pending-reply indicator, streaming assistant, visible queued rows) sits in the visible band above the composer. Remaining slack is chatAtBottomSlack(pad, overlay) = max(0, pad - overlay) + 8. Overlay is the floating composer box, not the pad CSS variable.

Last-message + 16px is rejected because it measures against the scroller’s visible bottom, which is under the overlay, and because it ignores the pad that Jump already uses. Pinning to the padding edge without slack would hide Jump until the reader scrolled an extra ~25vh; that bug is already fixed in isChatAtBottom and is kept.

Send latch sequence

  1. sendChatMessage (or slash submit) calls appendLocalUserTurn when applicable, then noteTakeLatest({ sessionId, scrollerKey, turnSeed }). Default inside sendChatMessage: scrollerKey = background ? "peer:" + sessionId : sessionId. Interactive submit may pass scrollerKey explicitly. Do not read live activeChatKey at drain (that is the focused session, which may not be the draining session). Queue drain inherits because it already calls sendChatMessage with sessionId and background; send-queue.ts stays unchanged.
  2. The matching hook’s layout effect sees a note whose generation is newer than lastAppliedGeneration and whose scrollerKey equals this instance’s chatKey. Other panes do not latch. The note is not deleted on read (Strict Mode and two hook instances).
  3. If history.after is set, do not set attached, do not snap, keep Jump. Start the same async isCurrent await Jump uses. Layout effect must not await.
  4. When on the latest window (or after a successful latest load): set stuckRef = true regardless of the 600ms pointer window and regardless of current isChatAtBottom. Assign snapToLatest now.
  5. The next column ResizeObserver callback in this turn also snaps (late row height). That pin ignores 600ms because the take-latest generation is still current. Unrelated in-transcript growth still honors 600ms.
  6. Main shell only: subscribe to welcomeVisible or observe #welcome-mount children. When the overflow lock lifts, one retry snap if the same take-latest generation is still current. Peer sends use background: true and skip welcome.
  7. Ack that appends the assistant placeholder does not detach: attached is already latched, not derived from lastRole.

Gesture lifetime and cancellation

A note identifies a send, not permanent permission to scroll. Store notes independently by (sessionId, scrollerKey); peekTakeLatest(sessionId, scrollerKey) reads that pair. A main send and a peer send in the same session must not overwrite each other. Publishing a note must notify the matching view even when no transcript row changes (slash submit); reading a mutable map only during unrelated renders is insufficient. turnSeed identifies the accepted optimistic turn, not the current last row after ack.

  1. Each active follow operation captures session id, scroller key, generation, and a view interaction epoch. Every async completion, next-resize snap, welcome retry, and animation callback verifies all four before writing. A newer send replaces the older operation for that scroller. Jump replaces a pending send operation; send replaces Jump and stops its native animation before instant placement.
  2. Wheel, touch/pointer scroll intent, and scrolling keys in the transcript invalidate pending work before subsequent resize or network callbacks. They clear the forced next-resize/welcome retry. Geometry then determines attached after actual scrolling; clicking an execution control retains the existing temporary growth suppression. Programmatic scroll events alone are not cancellation. After send then user scroll-up, delayed growth never forces reattachment.
  3. Changing key or truly unmounting invalidates the outgoing operation. Returning to a chat restores pixels and must not replay a completed or cancelled note. Keep note data readable; do not delete it on read. Maintain explicit operation completion/cancellation and per-view applied-generation bookkeeping. Strict Mode effect cleanup cancels that effect's resources; setup must resume a still-valid pending operation, without a second logical send, lost retry, or an orphaned request. Do not mark a generation completed when merely starting a latest request.
  4. A first welcome send may publish before the transcript becomes visible. Preserve only that still-pending handoff until its matching view is ready; an initial subscription baseline must not discard it. Retry after visibility/layout readiness once, and cancel on a later user gesture or session departure. Existing provisional-to-real session binding must preserve the pending operation's identity without generating another send or replaying a completed one. Ack message-id replacement does not require turnSeed to remain the transcript's last id.
  5. While an older/around request is in flight, a send waits for a verified latest window even if the currently displayed page has no after yet. Use history.after || history.loading to enter asynchronous coordination, then verify the resulting latest page and operation identity. A cancelled/failed request leaves no forced retry and cannot hide Jump. A newer valid gesture may still succeed; an older completion must not detach or clear it.

One next-resize retry belongs to the operation, not to the entire assistant turn. After that retry, ordinary growth uses attached plus the normal interaction rules. Do not infer unlimited bypass from an unchanged generation. Each hook owns its resources and cleanup; no polling timer or persistent attached state is added.

Jump completion with changing content

On latest-load success, Jump starts smooth scrolling directly from the preserved position; no pre-animation snap is allowed. While Jump is active, resize records the changed target but does not instant-pin. At native settle, recompute latestScrollTop. If the target moved, stop the completed animation and perform one instant correction to the current padding edge, then verify placement. Hide Jump only after this verification and only if the same operation is still current. Reduced motion uses the same final verification with instant placement from the start.

The fallback timeout is a watchdog, not proof of arrival. At the timeout, a still-current operation stops native motion, corrects to the current target, verifies, and only then completes. Cancelling must stop browser motion as well as callbacks; removing a scrollend listener alone is not cancellation. No cancelled operation performs a correction. Subsequent growth resumes ordinary attached pinning. Accept a small geometry tolerance (2px); do not substitute the larger reattachment slack for exact Jump placement.

History restoration ownership

loadSessionHistoryWindow coordinates requests and publishes rows/window metadata. It never performs latest placement or examines send/jump notes. useChatAreaStick alone chooses and applies send snap or Jump smooth after a successful latest load. For older/newer/around replacement, existing history-viewport helpers own anchor restoration: capture a separate anchor, old top, and old height for each registered area before the update; restore only still-registered areas for that session after flushSync. Use each area's own chat key for height-cache maintenance. Do not reuse the first area's anchor or fallback delta.

History restoration is the explicitly retained scroll writer for window replacement, not another follow policy. It does not run a latest snap, and it must not overwrite an active, newer follow operation. Shared session data can replace rows in both main and peer panes; preserve each non-requesting pane's visible anchor when it remains available. If eviction removes that anchor, keep the existing bounded fallback and document it in acceptance evidence; scroller isolation does not promise independent history datasets.

Trust boundaries, data flow, failures

  • Follow is a view concern. Transcript identity, attached, and the last user gesture are enough. Frame type is not a scroll signal.
  • sessionStorage key chatScrollByKey remains pixel positions only. Do not persist attached. Hardened contexts already swallow write failures.
  • data-self-update-verification continues to skip persistence.
  • Failed latest-window load, or !isCurrent: remain detached, keep Jump visible, do not snap to a stale page, do not leave attached true from a pending take-latest. Jump already returns if loadSessionHistoryWindow is false.
  • Take-latest during an in-flight Jump: cancel the smooth ride and snap (only once latest is on screen). Send wins on 0ms feedback when already on the latest window.
  • Reduced motion: Jump snaps. Send already snaps.
  • Virtualization: recycle keeps measured placeholders so scrollHeight stays honest. Pin after recycle. Do not add react-virtuoso / react-window / @tanstack/react-virtual.
  • KaTeX: renderMathInChat stays a growth side effect inside the single pin path, not a second scroller.
  • No backend protocol change.

Compatibility and exclusions

  • App and browser share this web contract.
  • CLI TUI ScrollBox is out of scope.
  • Do not auto-follow DAG strip expand, compaction fold easeScrollBy / pinWhile, parent-return scrollIntoView, message-rail seek, or branch-checkout pivot (_postCheckoutScrollTo). Those remain explicit locators.
  • Do not rewrite occupancy, send-queue admission, or ack pairing except for a take-latest note at the existing appendLocalUserTurn call (and slash submit).
  • Do not keep send as a special-case policy beside stream pinning. Send latches attached (or pending-latest) and chooses instant motion.
  • Peer Jump keeps the existing header button: same attach policy, no #chatView portal, no live bars, no composer-offset positioning in this slice.
