用户发进来的文件和 agent 交出去的文件，在聊天流里各自是什么样子、能不能点开。四层：现状、八家对照、下一步、理想形态。附件怎么进模型上下文是另一个主题，写在 attachment-handling（图解版），本页只在需要时引用它的结论。

01我们现在怎么做的现状

附件的字节、正文里的标记、模型看到的内容、用户看到的东西，是四件独立的事。现在这四件在网页和渠道两侧走了两套不一样的规则，所以同一个附件在不同界面结局不同。

1.1 入站四条路，两种标记词法

入站的四条路都能把内容送进模型，四条路里只有一条能在聊天流里留下可读的痕迹。网页图片模型看得见、人看不见；渠道附件模型看得见、人看到的是一串路径。 openprogram/channels/_attachments.py · openprogram/channels/base.py:226-243 · openprogram/webui/ws_actions/chat.py:152-280 · web/components/chat/composer/use-chat-submit.ts:139-173

03我们计划怎么优化下一步

三件需求，三条改动，共用一条新路由。每条改动都落在已有模块上，没有新组件、没有新数据表、没有新依赖。

三条改动都是半天量级，因为每一层的目标模块都已经存在，改的是它们的入参和词法，不是它们的结构。共同前提那条路由先做，A 和 C 随后就能并行。

A · 用户发的图能点开看

  • 存储：网页图片今天不落盘，所以消息里没有任何可指向的东西。把它接进文档那条已经很完整的落盘路（sha256 去重、32MB 单文件与 64MB 单轮上限、路径回写），同时保留发给模型的 ImageContent 块。图片的 _count_and_preview 天然走 binary 分支返回空，不产生额外预览开销。
  • 渠道：attachment_notes() 改用网页那套词法，[attachment: 名字 (ext, N KB) @ 绝对路径]。发言人前缀加在正文最前、附件标记追加在正文最后，两者位置不重叠；前缀里的方括号已经被 _one_line 换成圆括号，标记的解析不受影响。
  • 前端：chip 正则里那段 (?:\s*@\s*[^\]]+)? 已经在匹配路径，只是不捕获。捕获它，ParsedAttachment 加一个 path，图片按扩展名直接渲染缩略图，其余保持 chip 但换成按钮。

B · agent 发文件给用户

  • 工具，不是裸的正文指令。send_file(path, caption) 不负责投递，只做三件事：校验路径、读大小、登记一条与入站完全同词法的标记。投递由各个界面按自己的方式完成，工具本身对渠道无知，加一个新渠道不用改工具。
    为什么不学 openclaw 与 hermes 的裸 MEDIA: 指令行：那条路线的失败模式是“抽不干净就当正文漏给用户”，而这个亏我们已经在渠道入站那侧吃过一次（第一层最后那条标记原样露出）。工具调用有存在性校验，也有地方给出“文件不在了”这种诚实反馈。
    为什么也不学 weclaw 的隐式扫描：模型在正文里提一句路径就会被当成投递意图，描述和意图分不开。
  • 安全闸是必需项，不是加分项。三家做正文指令的实现闸门长得一模一样：路径必须落在允许根内，符号链接先完全解析再判断包含关系。我们直接复用 _allowed_roots()（项目根加会话目录），拒绝时返回工具错误而不是静默丢弃。openclaw 还多一层，只有白名单核心工具能发本地路径，插件与 MCP 工具一律排除；等我们的插件工具能触发出站投递时再补这一层。
  • 渠道：base.py 拿到 reply_text 后先抽标记，逐个调已经写好的 self.send_file()，剩下的正文照旧走 send_text_full。WeChat 的 not_supported 学 weclaw 的做法，把那行标记原地改写成一句可读的中文说明，而不是把原始标记漏给用户，也不是静默吞掉。
  • 按渠道声明能力。学 hermes：系统提示里按当前渠道说明这个工具能不能用。CLI 与不支持文件的渠道明确写“这里没有附件通道”，省得模型调了才发现发不出去。
  • 网页：助手气泡复用同一个 chip 解析器。parseUserAttachments 已经是纯函数，挪到共享位置改个名即可，两侧共用一份词法是这条设计最大的收益。

C · 可读文件点开就能看

  • 复用 FileViewer，不复用 docs_site。docs_site 是构建期的静态站点生成器：输入是整棵 docs/ 树，产物是带导航壳的 docs/_site/，一次构建 408 页。聊天要的是运行期任意单个文件的即时渲染，输入、时机、产物三样都对不上。FileViewer 恰好已经覆盖图片、pdf、markdown 渲染、带行号代码、二进制下载卡这五类，正是需要的东西。
  • 入参：FileViewer 现在绑 projectId 加相对路径，两个出口分别是 rawFileUrl() 和 WS project_file_read。加一个二选一的绝对路径入参，两个出口切到 /api/file-raw 和已有的 /api/file-read，后者的文本语义与 1MB 截断跟 WS 那条一致。
  • 打开方式：默认开中心文件标签页，走 turn-files-chips 已经在用的 fileTabId 加 useCenterTabs；图片和小文件额外给一个灯箱，把组合器里的 FilePreviewModal 提到共享位置，它现在只服务未发送的文档，提出来两边都能用。
  • 点开的行为学 opencode 而不是 openclaw：openclaw 点缩略图开新标签页，opencode 点图开灯箱。灯箱不打断阅读位置，聊天流里更合适；需要长期停留的大文件再走中心标签页。两条路都留。
  • docs_site 唯一值得借的是它的 pygments 代码高亮。现在 FileViewer 的带行号 pre 够用，高亮等有人真的抱怨再说。
关于那条字节出口要不要签名票据：openclaw 给它的媒体端点加了五分钟 TTL 的签名票据。我们现在不加。web UI 只监听本地端口，前面已经有同源守卫，路由本身又校验允许根，票据在这个前提下买不到额外的东西。如果哪天 web UI 暴露到本地之外，这是第一件要补的事。

04理想状态目标形态

一句话：任何一个文件，不管从哪个渠道进来、谁产生的、什么格式，在任何一个界面里都能用同一套查看器打开；agent 交出来的文件和用户传进去的文件，除了一个来源字段之外没有区别。下面这张图不受当前实现约束，虚线部分是已知做不到或代价太高的，理由跟在图后。

第三层和第四层的关系：第三层做完，图里实线的部分基本成立，只是靠一句正文标记而不是一条记录来承载。第四层要的是把那句标记换成一个 id，剩下的界面全都不用改。
