Composer local paths

When a user drops or selects a local file, image, or folder in the Electron desktop app, the outgoing message must identify the original absolute path. The existing attachment tiles and byte-upload behavior remain unchanged.

Behavior contract

  • The desktop bridge is the only renderer-accessible source of a native path. The renderer does not receive Node filesystem access.
  • Every dropped or picker-selected File is queried once before asynchronous reads begin. Images and non-images retain the returned path.
  • A document with bytes keeps the current upload and preview pipeline. Its visible/model marker uses the original path; the backend may still persist a session copy.
  • A folder or unreadable local item with a source path is a valid path reference even when no bytes can be uploaded. It must not be marked “too large — not sent”.
  • An image keeps its multimodal payload and additionally receives one original-path marker.
  • Current path-bearing markers encode the path as a JSON string. This preserves brackets, quotes, backslashes, and trailing spaces; readers remain compatible with historical unquoted markers.
  • Each uploaded attachment carries its own optional source_path provenance. The backend preserves a frontend marker only when that attachment's exact source path is present, preventing same-name browser uploads from being conflated.
  • For local preview, the stored marker keeps the original path in @json for the agent and adds an immutable session-copy path in @previewjson for the UI. Older messages without a preview path remain readable. The raw-file endpoint does not add the source path's parent directory to the readable roots.
  • The backend removes source_path from image attachment metadata before provider dispatch. The path intentionally remains in the user-message marker.
  • Clipboard-created blobs and plain-browser files have no native path. They retain the existing upload/save behavior and generated session path.

Project and additional-directory controls

The environment-chip row contains two different path controls. The project chip chooses the draft's main working directory; after the first committed turn it becomes read-only because cwd, permission baseline, and session-repository placement are already fixed. The folder-plus control manages additional working directories and remains editable for an active session.

  • Choosing an existing project in a draft updates that draft only. Opening a new folder creates or resolves the project and immediately selects the returned project; a refresh without selection is not a completed picker action.
  • The additional-directory menu derives the effective main project from the draft's pending project choice when no session exists. It must not offer the main project path as an additional directory.
  • A connected backend reply remains authoritative. If project requests cannot be completed, controls retain their prior state instead of displaying a false successful selection.

Boundaries and rejected changes

Included files are the Electron preload bridge, bridge TypeScript contract, composer attachment state, submit marker construction, and the existing backend marker rewrite. Excluded are attachment tile styling, directory traversal, recursive browser uploads, arbitrary filesystem scanning, new IPC handlers, upload-size changes, Programs UI changes, and dependencies.

Rejected: using the non-standard legacy File.path; requesting Node integration in the renderer; replacing uploads with path-only messages for readable files; inventing a relative path in a normal browser; recursively enumerating a dropped directory.

Acceptance and verification

Focused checks must prove: preload returns the exact native path for the same File object; path capture handles an absent bridge, empty result, and exception; document, image, and unreadable-folder markers contain the full path; filenames with parentheses are display-safe; paths containing ], quotes, and trailing spaces round-trip through both parsers; path-less browser attachments retain their current marker; same-name browser and mixed-source attachments remain distinct; backend persistence does not duplicate a pre-path-marked attachment; TypeScript, desktop checks, web checks, backend attachment tests, build, documentation links, and diff whitespace checks pass.

Implementation status

Implemented and reviewed. The focused RED established the missing preload path boundary, absent composer provenance, and duplicate backend marker behavior. The final implementation preserves Electron paths for files, images, and folders; keeps plain-browser uploads unchanged; distinguishes same-name attachment sources; and uses a JSON-encoded path marker that round-trips legal delimiters and trailing spaces while reading historical markers. Focused Web and Python checks, TypeScript, full Web and Desktop checks, production build, documentation build/link check, Ruff, and diff whitespace checks pass. Independent specification and quality reviews pass. The preload boundary is exercised in a VM with the same File object; real-window manual dragging was not part of this verification.
