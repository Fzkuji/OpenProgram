Six ways to add an attachment

These are proposed OpenProgram behaviors. File type, input method, and the computer running the assistant all matter.

1. Paste a screenshot

Paste a screenshot and ask what an error means. Show a preview; send image content directly to the model without requiring a tool to find the screenshot first.

The clipboard may not retain the image, so save a copy with the chat. Chat memory needs a reference to the saved image, not the whole image encoded as text. Retrieve the image when it is needed again.

2. Drag in an existing image

Drag in a PNG to compare it with another picture. Send image content directly; an image coming from a file should not become just a filename.

Reference the existing original by default, with an option to save a chat copy. Moving or deleting a referenced image may prevent reopening it; reading it after an edit returns the new version. Save a copy to preserve the version sent. A thumbnail does not replace that copy.

3. Drag in text, code, or data

Drag in a CSV and ask for monthly sales totals. Add its path by default; let the assistant read, filter, or analyze it. Do not automatically insert the entire file into the request or copy the original.

The model initially knows the location, and learns the contents through tools. Reading after an edit uses the updated file. Choose “Save a copy to chat” when a fixed version is needed.

4. Drag in a PDF, Word document, or spreadsheet

Start with a local path. The assistant chooses how to inspect specific PDF pages, extract Word paragraphs, or calculate spreadsheet values. A path alone does not add format support; appropriate tools must be available.

A scanned PDF may require reading page images. Report the file and reason when reading fails. “Added” must not imply “fully read.” Automatic content previews are a separate feature choice.

5. Drag in a folder

Add the folder path. Let the assistant inspect its directory and read relevant files for the task, without recursively uploading everything. Later reads use its current contents.

6. Upload through a browser or use a remote assistant

A path works only when the assistant can access it. An ordinary webpage usually cannot obtain a usable full local path, and a remote computer cannot directly read files on your computer.

Upload the file or use an available transfer mechanism so the assistant can access it. Then send its image content or read it with tools. Retain the uploaded copy rather than recording an inaccessible local path.

When an image is too large

Check the selected model’s known format, dimension, size, and image-count requirements. Send compliant images directly. Otherwise scale proportionally or convert the image used for sending, preserving an available original. Explain that the sent image was resized and offer access to the original.

Not every model exposes a queryable image limit. Use configurable processing rules where limits are unknown. If sending still fails, explain why and retain the input. Cropping a relevant area can preserve small text. Prompt users to switch a model that cannot see images; identify any separate image-understanding tool used instead.

How other tools behave

Terminal code, desktop controls, and uploads through messaging channels are different surfaces. Evidence for one does not establish behavior across the whole product.

Codex: image input and ordinary file references differ

Official guidance covers pasting, dragging, and command-line image input. Public terminal code saves clipboard images as temporary PNG files. Selecting a decodable image attaches image input; selecting an ordinary file inserts its path. Images reach the model as image content, while ordinary files can be read later with tools.

Image preparation varies with capabilities and processing mode; there is no single resize rule for every model.

Feature to consider: direct image input and on-demand document reading. Clipboard persistence in public code does not establish permanent retention or the complete copying policy of the desktop app; those desktop details remain unverified.

OpenCode V2: supported text attachments are read automatically

Desktop and web controls accept supported attachments. Text files supply their name and text; folders supply an immediate directory listing. Supported images become image input and can be resized automatically.

This differs from passing only a path. The V2 guide lists PNG, JPEG, GIF, and WebP as image media and handles SVG as text. PDF, audio, video, and other binary attachments do not currently enter the model request directly; convert them first.

Feature to consider: make short text immediately available. Automatically including large files consumes context, so it is not proposed as our universal local-file default. The guide does not establish that every local file gets a retained chat copy.

OpenClaw: receive uploaded files, then process by type

Incoming channel media is downloaded to the runtime. A vision-capable primary model can see images; other configurations can produce descriptions through media understanding. Documents can yield text, and configured fallback can turn scanned PDF pages into images.

Files without direct extraction support, such as some Office documents, can be handed to tools only when their saved paths are actually accessible in the runtime. This does not establish that every locally dragged file should be copied.

Feature to consider: make browser, messaging, and remote uploads accessible to the assistant before processing them by type.

Features to choose for OpenProgram

Each feature can be selected separately and checked with a concrete user action. The order suggests priority, not approval to implement.

A. Paste an image and ask about it

Paste, preview, and send an image the model can see. Reopen the chat and view it again. Process images that exceed known limits; keep the input and explain failures.

Recommended first. Addresses screenshot submission and loss of pasted images.

B. Reference local files and folders

Dragging a CSV, PDF, or folder shows its name and location. The assistant reads it for the task, without automatically copying or loading everything. Report inaccessible paths immediately.

Recommended local desktop default. Images still follow the image-input behavior above.

C. Save a file copy when needed

Offer “Save a copy to chat” for existing files. The saved version remains available after the original changes or disappears. Otherwise show “Reference original file.”

Optional. Useful for preserving the evidence behind an analysis.

D. Include short text immediately

Offer “Include content directly” for text attachments. The current request contains the text without a preliminary tool read. Suggest on-demand reading when it is too long.

Optional. Inspired by OpenCode; useful for short notes or small code samples.

E. Upload for browser and remote use

When a local path cannot be used, show upload progress and save the file where the assistant can read it. Users do not need to find the remote path themselves.

Needed for browser uploads and remote sessions; separate from local references.

F. Keep input when sending fails

Retain text and attachments until sending is confirmed. Explain failures and allow editing before retrying. After a disconnect, check whether the previous send succeeded before repeating it.

Recommended alongside A. Verify with oversized input and a disconnected session.

Evidence and development notes

How current OpenProgram behavior differs

The current upload flow saves ordinary files too; B is not the current default. Image thumbnails do not resize outgoing images. Full image encoding counts toward the execution-input limit and can be rejected before the user message is saved. The composer clears before durable confirmation, which can leave a chat with only a title.

The target chat log records oversized input. The full original request is unavailable, so the responsible field is not established. A minimal local request reproduced image encoding exceeding the execution-input limit without a model call.

Handle chat persistence, image delivery, and file reading separately. Shrinking every image to fit the execution-input limit is insufficient; copying every local file should not become the default fix. Treat attachment text as supplied material, not automatically as new user instructions.

Limits of image-processing and retention evidence

Public Codex code supports several image-processing modes selected by capabilities and configuration. A utility’s default dimension is not every model’s limit. OpenCode’s configurable resizing does not guarantee compliance with every model. OpenClaw channel reception limits are not universal model limits.

Temporary storage, upload to a runtime, and long-term chat retention are different promises. Retention periods not established by the sources are not inferred here. If C is selected, specify copy handling for chat deletion, export, and migration in development notes.
