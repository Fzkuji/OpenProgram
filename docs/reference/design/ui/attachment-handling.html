Appearance and interaction

  • The first line shows the filename with single-line truncation. The second always shows format and size, independently of the name: PNG · 1.3 MB or PDF · 842 KB.
  • Images use proportional thumbnails without heavily rounded cropping. Documents, spreadsheets, and code use small format-labelled icons; color is not the only distinction.
  • For extensionless files, show a confirmed format or “File” when unknown. Folders show “Folder” without an invented total size.
  • Click the item body for a preview or details with the full name, location, size, and copy status. Keep removal visible. Implement separate keyboard-accessible actions rather than filling the composer with paths.
  • Images and files share a single layout region. Wrap uniformly in narrow windows; for many items cap the region at three rows and scroll it, keeping the text area available.
  • Preserve text and attachments while reading or after a failure. Explain why sending is unavailable; re-add or remove the failed item without selecting the others again.

Rules shared by all scenarios

Does the image need processing?

Process the sending version using known model requirements and preserve an available original. Use explicit rules for unknown limits; not every model exposes them.

Keep input after failure

Keep text and attachments until confirmed. Explain upload, read, or send failures; check the previous result after a disconnect to avoid duplicates.

Will the sent version remain available?

References are affected by edits, moves, and deletion. A saved copy preserves the version; listings and text excerpts are not original-file copies.

Recorded choices

The first five choices are saved in this document and persist on reload. This records design only and does not change the app.

Framework evidence and current implementation

OpenProgram file handling

When a file is added through the web interface, the backend receives and saves it for the assistant to read. The desktop interface references ordinary files at their original paths. Images retain a chat copy. Users add a file and state their task; they do not choose between upload and path handling.

Adding files · Storage and previews

Codex: public terminal behavior, not desktop UI

Verified: ordinary file selection inserts a path, decodable images become image input, and clipboard images are written to temporary PNG files. This does not establish the desktop app’s complete long-term copying policy. Copy controls and status labels in the panels are OpenProgram proposals.

File selection · Clipboard images · Official image guide · Image preparation

OpenCode V2

Supported text attachments include their text; directories include an immediate listing; PNG/JPEG/GIF/WebP become image media. SVG is text; PDF, audio, video, and other binary attachments currently do not directly enter model requests. Server-accessible files can be referenced. Configurable resizing does not guarantee compliance with every model.

Official attachment guide

OpenClaw

Channel media is downloaded to the runtime. Vision-capable primary models can receive images; other configurations can generate descriptions. Documents can yield text, with configured page-image fallback for scanned PDFs. Tool handoff requires an accessible saved path. Channel reception is not treated as equivalent to local desktop drag-and-drop.

Evidence and development notes

How current OpenProgram behavior differs

The current upload flow saves ordinary files too; path-only reference is not the current default. Image thumbnails do not resize outgoing images. Full image encoding counts toward the execution-input limit and can be rejected before the user message is saved. The composer clears before durable confirmation, which can leave a chat with only a title.

The target chat log records oversized input. The full original request is unavailable, so the responsible field is not established. A minimal local request reproduced image encoding exceeding the execution-input limit without a model call.

Handle chat persistence, image delivery, and file reading separately. Shrinking every image to fit the execution-input limit is insufficient; copying every local file should not become the default fix. Treat attachment text as supplied material, not automatically as new user instructions.

Attachment storage and message submission · Execution-input checks · Composer submission

Limits of image-processing and retention evidence

Public Codex code supports several image-processing modes selected by capabilities and configuration. A utility’s default dimension is not every model’s limit. OpenCode’s configurable resizing does not guarantee compliance with every model. OpenClaw channel reception limits are not universal model limits.

Temporary storage, upload to a runtime, and long-term chat retention are different promises. Retention periods not established by the sources are not inferred here. Image copies are selected for OpenProgram; implementation must specify copy handling for chat deletion, export, and migration in development notes.

Codex image preparation · Codex image input

Implementation status: the five selected behaviors and compact attachment composer are implemented and have passed independent review. Installed-App checks confirm mixed ordering, format and size labels, full-image preview, draft recovery, folder listing, original-image retention, and direct model image recognition. End-to-end document reading remains unverified because live executions wait after requesting a read; this is tracked separately from attachment delivery. Original images are retained up to 32 MiB. The model receives a send version up to 5 MiB; oversized images are resized proportionally. These are application limits, not automatically discovered model limits. Local documents remain path references; browser-selected files without a native path are saved by the backend. No remote connection feature is introduced.
