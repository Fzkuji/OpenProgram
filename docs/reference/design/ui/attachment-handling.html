当前问题有三个相互关联的部分

5 MiB

前端允许的图片大小

192 像素缩略图只用于界面，发送的仍是完整图片 base64；界面允许添加不等于后端能接收。

256 KiB

整个执行输入的上限

文字、规则、元数据和图片 base64 共同计量。执行准入失败发生在用户消息写入之前。

WebSocket.send

清空输入发生得过早

发出即清空文字和附件，尚未等到持久保存确认。错误只有短暂提示，重新打开可能只剩标题。

本地最小准入探针：100 KiB 二进制内容通过；200 KiB 和 1 MiB 被拒绝。该探针不验证图片格式，也不调用 Provider。实际空白会话另有同类错误日志，原请求各字段大小未保留。

一个会话附件存储，四个明确的阶段

  1. 上传和校验先检查归属、数量、编码和字节；不在聊天 WebSocket 中重复传完整文件。
  2. 保存不可变原件会话目录保存原件与摘要；工具可读副本不承担历史身份。
  3. 提交有序引用执行输入只含文字、引用和配置；仍受 256 KiB 限制。
  4. 按模型构造内容读取图片表示或有界预览；记录模型实际收到什么。

引用包含附件 ID、所属会话、摘要、实际字节数、检测 MIME 和文件名。原始 Desktop 路径保留为来源，客户端不能用路径字符串创建读取权限。旧路径标记与旧 inline 历史继续可读。

为什么不直接增大上限或把图片压到 192 KiB？

提高上限保留了重复序列化和庞大执行输入，也没有修复草稿恢复。压到约 192 KiB 仍需预留元数据空间，并可能使截图文字不可读。图片压缩服从 Provider 预算；执行输入通过引用控制大小。仅记录 Desktop 原始路径也不能保证文件被编辑或删除后的回放。

为什么不直接使用现有 execution state-blob store？

它要求已存在的 execution／attempt 所有权，而附件上传先于执行、又可能跨多次 attempt。复用摘要校验约定，不放宽它的所有权契约；不新增远程对象存储或多后端框架。

重放、分支、迁移和回收的约束

原件由引用 ID 和摘要标识；工具副本在按引用读取前校验，被修改则保留修改并从原件创建新副本。附件预览通过鉴权的附件 content 接口读原件，不依赖可变 file-raw 路径。历史、排队工作、checkpoint 和授权分支仍引用时保留；Archive 不删除。fork／attach／merge 复制字节并建立目标会话归属，导出／导入携带 manifest 和内容，项目迁移按会话位置索引解析。服务端持久草稿 claim 也属于保留依据；关闭浏览器不释放，明确移除或成功转为历史归属才释放对应 claim。只有无引用且经过宽限期的暂存数据能回收，不能删除共享项目目录来回收单会话附件。

PUT /api/session/{sid}/attachments/{upload_id} 接收单个上传；chat 携带提交 ID；GET /api/session/{sid}/submissions/{submission_id} 返回 not_found、pending、accepted、rejected 或 conflict。查询必须鉴权并检查会话读取权限，ID 本身不授予访问。这些是拟新增／扩展的公共契约，不是现有 API。

收到确认后，只清除对应提交快照；等待期间新增的文字和附件保留。SQLite 执行记录与 Git 用户消息不是同一事务，准入成功但消息保存失败也必须有可核对的结果。
