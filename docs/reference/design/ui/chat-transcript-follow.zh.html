聊天转录跟随

作者：engineering 状态：Web 渲染器已实现 范围：Web 渲染器（App 与浏览器）

发送消息并不能可靠地把读者带到最新一轮。四个重叠的滚动写入者对“底部”是什么、谁可以移动视口意见不一（遗留 scrollToBottom、未使用的 useStickToBottom、现场 useChatAreaStick、以及 loadSessionHistoryWindow）。本页把它们收成一份由 React 持有的跟随策略：一种附着/脱离状态、一个“在底部”判定、一张跟随触发表、以及一个以 padding 边缘定义的 latest。聊天 handler 和历史加载器不得把 latest 钉到任意视口上。

已采纳契约的交互预览

该视口完全本地，不发网络请求。它实现的是统一策略，不是当前产品行为。可以灌入长历史、向上翻、发送、模拟流式，并使用“跳到最新”。在最新窗口上，发送瞬间贴底并附着。正在显示更早窗口时，发送保持 pending、保留 Jump，latest 加载后再贴底。流式增长只在附着时跟随。“跳到最新”用原生平滑滚动重新附着（请求减少动效时改为瞬间）。

已附着 最新窗口 发送 = 瞬间贴底
随便问…然后发送，或在转录区按 Enter
策略日志：就绪。灌入历史，向上翻，然后发送。

键盘：Tab 到滚动区或按钮；在滚动区按 Enter 发送；“跳到最新”是真实按钮。呼吸垫为 max(25vh, composer + 24)。latest 是 padding 边缘，因此最后一条气泡落在输入框上方的可见带里，而不是被输入框挡住。Jump 在平滑行程落定前保持可见；滚动器上的指针或滚轮取消行程。发送仍然瞬间隐藏 Jump。本预览尚未覆盖本页新增的 generation 生命周期、异步取消及 Jump 动态目标完成验证，不作为这些行为的契约实现证据。本视口不模拟欢迎页 overflow、peer overlay 松弛、latest 窗口加载失败，或真实更早历史页（更早页控件只是一个标志）。

当前实现与已核实缺口

现场所有者是 React 的 useChatAreaStick（apps/web/components/chat/messages/use-chat-area-stick.ts），由 MessageList 和 peer-session-pane.tsx 消费。数学辅助已在 apps/web/lib/chat/chat-scroll.ts。旁边仍有三个旧的或并行的写入者。

所有者附着 / 底部跟随目标调用方核实状态
遗留 scrollToBottom / 模块级 stickToBottom（apps/web/lib/runtime-bridge/helpers.ts） 全局布尔，默认 true；在 #chatArea 上用 isChatAtBottom 听滚动 最后一条 .message 底边 + 16px，否则 scrollHeight chat-handlers.ts（compaction、local_command、status、follow-up）；conversations.ts 在非 _skipScrollToBottom 时 scrollToBottom({ force: true })；addSystemMessage 仍在运行。独立 stick 标志。最后一条 + 16px 与 25vh 垫冲突。MessageList 注释说 React 从不调用它，但 WS handler 仍会调用。
useStickToBottom（apps/web/lib/format-utils/scroll.ts） 同一套最后一条 + 16px 策略的 container-ref 副本 最后一条 .message + 16px 仅定义 无生产调用方。并行实现，尚未删除。
useChatAreaStick stuckRef 来自 isChatAtBottom + history.after；区域上 600ms 指针抑制；Jump 走 animateJumpToLatest ResizeObserver pin() 里 area.scrollTop = area.scrollHeight；发送跟随走 resolveChatScrollTop({ ownTurn }) MessageList（lastRole === "user" 当作 ownTurn）；peer pane 传入 areaRef / columnRef 预定所有者。下列缺口使发送跟随不可靠。
loadSessionHistoryWindow（apps/web/lib/runtime-bridge/session-history-loader.ts） 无附着状态。在 flushSync 之后为 latest / around / 高度差恢复写入 scrollTop，然后 dispatchEvent("scroll")。 latest → area.scrollHeight；around → restoreHistoryAnchor；否则 oldTop + heightDelta Jump、在 after 时发送、useHistoryWindow 自动加载。区域是 registered?.keys().next().value —— 主栏和 peer 都注册时是任意第一个视口。 第四个滚动所有者，纳入范围。可能贴错 pane，也可能在 hook 之前对过期页贴底。

压缩折叠的 easeScrollBy / pinWhile（message-list.tsx）、消息轨 scrollIntoView、父返回 scrollIntoView、分支检出 _postCheckoutScrollTo 也会写滚动。它们保持为具名排除（显式定位），不是跟随策略。

ownTurn 身份

MessageList 把 lastRole === "user" 当作 ownTurn。这只在 store 最后一行仍是用户气泡时为真。

发送路径已经在 0ms 落下乐观用户行：sendChatMessage 在 socket 接受帧之后调用 appendLocalUserTurn（apps/web/components/chat/composer/submit/send-chat-message.ts）。助手占位并不在同一次更新里创建。apps/web/lib/net/chat-stream.ts 的 handleAck 会重键 pending 用户 id，然后 ensureReply 追加空助手行。ack 之后 lastRole 变成 "assistant"，ownTurn 变为 false。

apps/web/scripts/chat/check-chat-ui.mjs 里的单元契约是对的：自己的发送即使远离底部也要跟随；向上翻时到达的 agent 行不得移动视口。缺口是 ownTurn 从转录尾部身份推断，而不是从发送手势推断。若发送那次 layout 没能闩上 stuckRef，追加助手行的 ack 会被当成外来 agent 轮，视口不动。成为最后一行的 compaction / local_command / system 行同样会关掉 ownTurn。

docs/reference/design/ui/interaction-feedback.md 仍写用户气泡在 chat_ack 落地。发送路径现在在 socket 接受时就追加。跟随必须在那条乐观行（以及 lastRole === "user" 时的 pending 指示）落地时开始，而不是等 ack。本页不重做 send/ack 管线。

布局与增长

layout effect 赋值 scrollTop = resolveChatScrollTop(...)，跟随成功时该值是 area.scrollHeight，浏览器在 clientHeight > 0 时钳到 scrollHeight - clientHeight（hook 已跳过 clientHeight <= 0）。该钳位与 Jump 已经使用的 padding 边缘相同；它不是相对最后一条 + 16px 的另一类缺陷。读取仍可能发生在新行高度进入布局之前。ResizeObserver 的 pin() 本可以补完，但前提是 stuckRef 已经为 true、窗口没有 after、Jump 不在动画、并且 performance.now() - lastPointerRef > 600。

lastPointerRef 只在区域上的 pointer/wheel/keydown 更新。Composer 点击不在 #chatArea 上，因此已经在底部的读者发送不会被抑制。先向上翻再在 600ms 内发送的读者会被抑制：layout 贴底用了过小的 scrollHeight，pin 不跑，stuckRef 保持 false，随后的助手行不再跟随。

600ms 窗口的目的是避免点击执行条 / thinking 行时把被点控件向上拽。它不得抑制 take-latest 手势。发送闩序列见 发送闩序列：在第一次高度读取前强制 stuckRef = true，现在以及本轮下一次列 resize 时 snap，600ms 仍挡住无关的转录区内增长。

在 history.after 置位时发送

if (seedChanged && ownTurn && sid && history?.after) {
  void loadSessionHistoryWindow(sid, "latest");
}
area.scrollTop = resolveChatScrollTop({ ... });

“跳到最新”已经用 isCurrent token await loadSessionHistoryWindow(sid, "latest")，然后再动画。发送却 fire-and-forget 这次加载，并立刻对过期的旧窗口做跟随。加载器本身也可能对任意已注册区域赋值 scrollTop（第四个所有者）。在 useLayoutEffect 里直接 await 不合法；fire-and-forget 会重现该缺陷。采纳路径使用与 Jump 相同的 isCurrent 异步回调，不对过期页 snap，并且在 latest 窗口到达之前不把 attached 设为 true。

两套锚定策略

.chat-messages 的垫是 max(25vh, calc(var(--main-composer-height) + 24px))。Composer 绝对覆盖在上面。isChatAtBottom 的松弛是 pad - composer + 8，因此“在最新”表示最后一条气泡还没钻进输入框下面。Jump 和 pin 瞄准 padding 边缘（scrollHeight - clientHeight）。遗留 scrollToBottom 瞄准最后一条底边 + 16px，把内容拉向覆盖层，可能把新用户气泡藏进输入框下。当 WS handler 仍调用遗留 helper、React 又 pin 到 scrollHeight 时，两个目标会打架。

欢迎页首次发送

setWelcomeVisible(false) 在 0ms 运行，早于 appendLocalUserTurn。.chat-area:has(#welcome-mount > *) 会设 overflow: hidden。若 stick 的 layout effect 与欢迎子节点同帧，滚动赋值是空操作。stick 依赖不含 welcomeVisible。采纳的重试在发送闩序列中：主壳观察 welcomeVisible 或 #welcome-mount 子节点，锁解开且 take-latest generation 仍当前时 snap 一次。Peer 不走这条路径。

Peer pane 的 composer 松弛

传入 areaRef 时（peer pane），readComposerHeight() 被强制为 0，overlay 当作 0，松弛大约偏松一个 composer 盒子。Peer 发布的 --peer-composer-h 是测得的 composer 根高度 + 24px（peer-session-pane.tsx），并且同一变量用作 .chat-messages 的 padding-bottom（peer-session-pane.css）。主栏的 --main-composer-height 只是 overlay 高度；垫是 max(25vh, composer + 24)。

松弛是 max(0, pad - overlay) + 8。把 --peer-composer-h 当 overlay 会得到 (h+24) - (h+24) + 8 = 8，紧 24px。该变量与 --main-composer-height 不是同类。overlay 与 pad 是分开的输入：pad 来自 readBottomPadding(column)；peer overlay 来自 composer 根（或 --peer-composer-h - 24，或第二个 CSS 变量）。单元用例：peer pad h+24，overlay h ⇒ slack 24+8。

Peer 的 useChatAreaStick 使用 scrollKey = sessionId ? \`peer:${sessionId}\` : null。主栏使用 activeChatKey。sendChatMessage 只知道 sessionId。按任一键做 consume-once 的 map 会让两个 hook 抢同一条记录，或永远匹配不上分屏 pane。

采用、修改与拒绝

采用

一份策略模块，位于 apps/web/lib/chat/chat-scroll.ts。每个滚动器一个 attached 布尔。发送 / 队列 drain / 欢迎页第一条 = take-latest，瞬时贴底。流式只在已附着且位于最新历史窗口时 pin。跳到最新仍是显式平滑重新附着。会话切换恢复 sessionStorage 像素，不是一次发送。桌面 App 使用同一套 web 渲染器。

修改

Take-latest 是带 generation 的记录，键为 session id 加上提交滚动器的 chatKey，不是 consume-once 布尔，也不单独靠 lastRole。lastRole === "user" 在发送路径记号进入同一合并列车之前仍是回退。指针 600ms 抑制只用于会改变尺寸的转录区内点击，从不用于 take-latest 或跳转。Peer overlay 与 pad 是分开的输入；不要把 --peer-composer-h 当成 --main-composer-height。resolveChatScrollTop 仍决定是否移动；调用方随后赋 latestScrollTop（Jump 已用的命名钳位 padding 边缘）。带 history.after 的发送在 latest 到达前保持 pending；过期页上 attached 保持 false。历史加载器不执行 latest 定位；窗口锚点恢复保留在 history-viewport helper，具体归属见下文。

拒绝

第四份 stick 文件。以最后一条 + 16px 作为跟随目标。把发送做成第二条平滑动画。WS handler 调用滚动器。全局 window / 模块 stickToBottom。把粘滞写到磁盘。虚拟列表库。自动跟随每一次 DAG 展开。重写发送/ack 协议。把 CLI ScrollBox 打进 web 包。并行的“把上一轮钉在顶部”模式。

“底部”指什么

latest 是滚动器的 padding 边缘。latestScrollTop = max(0, scrollHeight - clientHeight) 是 Jump 已经使用、并且在 clientHeight > 0 时把 scrollTop = scrollHeight 钳到同一位置的命名形式。主栏垫为 max(25vh, overlay + 24)（peer 垫是已发布的 --peer-composer-h = overlay + 24），最后相关内容落在输入框上方的可见带。剩余松弛是 chatAtBottomSlack(pad, overlay) = max(0, pad - overlay) + 8。overlay 是浮动 composer 盒子，不是垫的 CSS 变量。

拒绝最后一条 + 16px，因为它相对滚动器可见底边测量，而那条边在叠层下面，并且忽略了跳转已经使用的垫。pin 到 padding 边缘却不用松弛量会让跳转按钮直到再多滚约 25vh 才出现；该缺陷已在 isChatAtBottom 修好，予以保留。

目标架构

1
Composer 提交、队列排出、斜杠提交或 Jump 写入跟随手势。WebSocket 帧不滚动。历史加载器不得把 latest pin 到 registered.keys().next() 的 scrollHeight 上。数据发布后，匹配 hook 执行发送 snap 或 Jump smooth；窗口替换按各视口恢复，见 History 恢复的执行归属。
2
useChatAreaStick 是 DOM 施加器与状态机（stuckRef、jumpingRef、lastPointerRef、pending latest 加载）。MessageList 与 peer pane 传入滚动器、列、overlay 读取器和滚动器 chatKey。
3
原语在 chat-scroll.ts（latestScrollTop、take-latest 记录、overlay vs pad、snapToLatest、resolveChatScrollTop 作为是否移动）。hook 施加它们。没有 decideFollow 动作枚举。
4
列上的 ResizeObserver 只在已附着、位于最新窗口、且没有进行中的 Jump 时 pin。Take-latest 仅在已经位于最新窗口时，即使在 600ms 窗口内也强制 stuckRef 并 snap。当 after 置位时，take-latest 为 pending：保持脱离，保留 Jump，不对过期页 snap。600ms 仍挡住无关的转录区内增长。
5
遗留 scrollToBottom 先变成有文档的空操作垫片，再连同调用方删除。useStickToBottom 删除。同一次统一中，加载器停止把 latest 钉到任意第一个视口。

WS chat_response / compaction / status / follow-up / local_command 帧无—handler 不调用滚动、不记 take-latest行进入 store；视图只经 growth + attached 跟随，除非 composer 提交已经记过 take-latest。

发送闩序列

  1. sendChatMessage（或斜杠提交）在适用时调用 appendLocalUserTurn，然后 noteTakeLatest({ sessionId, scrollerKey, turnSeed })。sendChatMessage 内部默认：scrollerKey = background ? "peer:" + sessionId : sessionId。交互提交可以显式传入 scrollerKey。排出时不要读取现场 activeChatKey（那是聚焦会话，未必是正在排出的会话）。队列排出因已带 sessionId 和 background 调用 sendChatMessage 而继承；send-queue.ts 保持不变。
  2. 匹配 hook 的 layout effect 看到 generation 新于 lastAppliedGeneration 且 scrollerKey 等于本实例 chatKey 的记录。其他 pane 不闩。记录不在读取时删除（Strict Mode 与两个 hook 实例）。
  3. 若 history.after 置位：不设 attached，不 snap，保留 Jump。启动与 Jump 相同的异步 isCurrent await。layout effect 不得 await。
  4. 已在最新窗口（或 latest 加载成功）时：无论 600ms 指针窗口和当前 isChatAtBottom，设 stuckRef = true，立刻 snapToLatest。
  5. 本轮下一次列 ResizeObserver 回调也 snap（迟到的行高）。该 pin 因 take-latest generation 仍当前而忽略 600ms。无关的转录区内增长仍遵守 600ms。
  6. 仅主壳：订阅 welcomeVisible 或观察 #welcome-mount 子节点。overflow 锁解开时，若同一 take-latest generation 仍当前则重试 snap 一次。Peer 发送使用 background: true，跳过欢迎页。
  7. 追加助手占位的 ack 不脱离：attached 已闩上，不从 lastRole 推导。

手势记录的生命周期与取消

note 标识一次发送，不代表永久滚动许可。按 (sessionId, scrollerKey) 独立保存，使用 peekTakeLatest(sessionId, scrollerKey) 读取；同 session 的主栏与 peer 发送不能互相覆盖。发布 note 必须通知匹配的 view，包括没有新增转录行的 slash submit；不能只在无关 render 中读取可变 Map。turnSeed 标识已接受的乐观用户行，不要求等于 ack 之后的最后一行。

  1. 每个活动操作捕获 session id、scroller key、generation、view interaction epoch。异步完成、下一次 resize 重试、welcome 重试、动画回调写入前都验证这四项。较新发送替换本 scroller 的旧操作；Jump 替换 pending send；发送替换 Jump，并先停止原生动画再瞬间定位。
  2. 转录区中的滚轮、触摸/指针滚动意图、滚动按键，在后续 resize 或网络回调之前使 pending 操作失效，并清除强制 resize/welcome 重试。实际滚动后按几何位置确定 attached；点击执行控件仍保留现有的短暂增高抑制。程序触发的 scroll 事件本身不算取消。发送后用户上翻，迟到增长不得强制再附着。
  3. 切 key 或真正卸载使旧 view 的操作失效。返回 chat 恢复像素位置，不重放已完成或已取消的 note。记录保持可读，不在读取时删除；明确维护完成/取消状态与各 view 的 applied-generation。Strict Mode effect cleanup 清理该次 effect 的资源；setup 必须恢复仍有效的 pending 操作，不新增逻辑发送、不丢重试、不遗留请求。开始 latest 请求时不能直接把 generation 标为完成。
  4. 欢迎页首次发送可能早于 transcript 可见。只保留这次仍 pending 的交接，直到匹配 view 就绪；挂载时初始化订阅基线不能丢掉它。可见和 layout 就绪后重试一次，后续用户手势或离开 session 则取消。现有 provisional 到真实 session 的绑定应保留 pending 操作身份，不新增发送、不重放已完成操作。ack 替换 message id 后，不要求 turnSeed 继续等于最后一行 id。
  5. 已有 older/around 请求进行中时，即使当前页暂时没有 after，发送也要等待确认 latest 窗口。以 history.after || history.loading 进入异步协调，然后验证返回窗口和操作身份。取消/失败不遗留强制重试、不隐藏 Jump；后续新手势仍可成功，旧完成回调不得把新操作设为 detached 或清除它。

一次 next-resize 重试属于该操作，不属于整个助手回合。用完后恢复 attached 与正常手势规则；generation 未变不代表无限期绕过 600ms。每个 hook 管理自己的资源和清理，不增加轮询计时器或持久化 attached。

内容变化时的 Jump 完成条件

latest 加载成功后，Jump 直接从保留位置开始平滑滚动，禁止先 snap。Jump 期间 resize 记录目标变化，不瞬间 pin。原生滚动停止时重新计算 latestScrollTop；目标变动则结束原动画，瞬间补齐到当前 padding 边，并验证位置。只有位置验证通过且操作仍有效，才隐藏 Jump。reduced-motion 从开始就瞬间定位，使用同样的最终验证。

超时仅用于结束异常等待，不证明已经到达。超时后，仍有效的操作先停止原生运动，再补齐到当前目标、验证并完成。取消既要停止回调，也要停止浏览器动画；只删除 scrollend listener 不算取消。已取消操作不得补齐。后续增长恢复普通 attached pin。定位允许 2px 几何误差，不用更大的再附着 slack 代替 Jump 到达验证。

History 恢复的执行归属

loadSessionHistoryWindow 协调请求并发布行及窗口元数据，不执行 latest 定位，不检查 send/jump note。只有 useChatAreaStick 在 latest 成功后选择并执行发送 snap 或 Jump smooth。older/newer/around 窗口替换继续由现有 history-viewport helper 恢复锚点：更新前分别捕获每个 registered area 的 anchor、oldTop、oldHeight；flushSync 后仅恢复仍注册在该 session 的 area。高度缓存也使用各自 chatKey，不能复用第一视口的 anchor 或高度差。

窗口替换恢复是明确保留的滚动写入，不是另一套跟随策略。它不执行 latest snap，也不能覆盖较新的活动跟随操作。同 session 的主栏与 peer 共享历史数据，替换行可能影响两者；非请求方在原锚点仍存在时保留其可见位置。淘汰导致锚点消失时沿用现有有界回退，并在验收证据中说明；scroller 隔离不承诺独立历史数据集。

信任边界、数据流、失败

  • 跟随是视图问题。转录身份、attached 和最后一次用户手势足够。帧类型不是滚动信号。
  • sessionStorage 键 chatScrollByKey 仍只存像素位置。不要持久化 attached。加固上下文里写失败已经吞掉。
  • data-self-update-verification 继续跳过持久化。
  • 最新窗口加载失败或 !isCurrent：保持脱离，Jump 仍可见，不对过期页 snap，也不让 pending take-latest 把 attached 留在 true。Jump 在 loadSessionHistoryWindow 为 false 时已经返回。
  • 进行中的 Jump 遇上 take-latest：取消平滑行程并 snap（仅当 latest 已在屏上）。已在最新窗口时发送在 0ms 反馈上获胜。
  • 减少动效：跳转贴底。发送本来就是贴底。
  • 虚拟化：回收保留已测量占位，使 scrollHeight 诚实。回收后 pin。不要加 react-virtuoso / react-window / @tanstack/react-virtual。
  • KaTeX：renderMathInChat 留在单一 pin 路径里作为增高副作用，不是第二套滚动器。
  • 不改后端协议。

兼容与排除

  • App 与浏览器共享这份 web 契约。
  • CLI TUI ScrollBox 不在范围内。
  • 不自动跟随 DAG 条展开、压缩折叠 easeScrollBy / pinWhile、父返回 scrollIntoView、消息轨定位、或分支检出枢轴（_postCheckoutScrollTo）。那些仍是显式定位。
  • 除了在现有 appendLocalUserTurn 调用处（以及斜杠提交）记一条 take-latest，不改写 occupancy、发送队列准入或 ack 配对。
  • 不把发送做成流式钉住旁边的第二套策略。发送闩上 attached（或 pending-latest）并选择瞬间运动。
  • Peer Jump 保留现有标题栏按钮：同一附着策略，本切片不要 #chatView portal、live 条或 composer 偏移定位。

F16B指针/滚轮/滚动键取消 pending 或原生 Jump，无后续动画/补齐；Jump 中发送瞬间生效；减少动效时瞬间定位。
F17B两个位置不同的注册区域分别恢复 older/newer/around 锚点及回退高度差；latest 无加载器任意 pin。
F18C/D无 legacy 全局跟随 listener 或生产 scrollToBottom/useStickToBottom 引用；显式定位与自更新持久化保护仍有效。
