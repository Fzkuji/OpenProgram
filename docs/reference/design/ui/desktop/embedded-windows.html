Embedded application windows

A tab of kind window holds a window of another application. Each platform does it the way its window system allows; the tab, the worker requests and giving the window back are the same everywhere. A small chat preview can show the same window at the same time without moving it.

PlatformModeHow
WindowsnativeSetParent into the App's top-level window; frame styles swapped for WS_CHILD and restored on release. Rectangle in device pixels of the client area.
Linux, X11nativeXReparentWindow into the App's X window, as a window manager does with its frame, after withdrawing it so the window manager lets go (ICCCM 4.1.4); back to the root at the old place on release, where the window manager takes it again.

Decisions

DecisionWhy
The window system's own embedding on Windows and X11The window stays the application's real window: no latency, its own input, menus and accessibility. Window managers embed windows this way.
Capture plus posted input on macOSThe only way there; Codex Computer Use keeps the window it operates under a live capture the same way, and the input route is the one the computer_use backend already uses (after cua-driver).
On macOS the window sits behind the tab, at its sizeMenus, pop-ups and input-method panels are separate windows the application opens next to its window, so they appear over the tab where it shows the window. If the application raises the window, it covers the tab exactly.
Capture drawn at the window's size from the tab's top-leftWhat is shown lines up with the window behind it; a point in the tab maps to the window by the page zoom alone.
Input through one queue on one threadEvents reach the application in the order the user made them; moves and wheel turns are folded once a frame in the page, so the socket never backs up.
Keys go to a hidden text field firstAn input method can compose there; its finished text goes as text, every other key as a key with its physical code, so shortcuts keep working on any layout. Text that arrives without a key, from dictation or the emoji picker, goes as text too.
Capture source through getUserMediaNeeds no click, so a tab restored after a reload shows its window again by itself.
A view never moves the windowThe preview follows what the Agent or the user is doing; taking the window out of its place for a thumbnail would change what it shows. The reply's frame gives the view the window's aspect.
Windows view input posted in the backgroundThe route the computer_use backend takes for background clicks: mouse messages to the deepest child under the point in its client coordinates, the wheel in screen coordinates, keys to the thread's focus window, through one queue. Posted keys leave the keyboard state alone, so a printable key goes as its character and Ctrl with a letter as its control character, what TranslateMessage would make; shortcuts that read the keyboard state need the window in front.
computer_use finds embedded windows from the window treeAn embedded window is a child of the App window, so top-level walks miss it. The backends look for children of OpenProgram App windows owned by another process (Windows: process image openprogram*; X11: WM_CLASS openprogram*, XQueryTree) and list them under their application. No worker records are read, so a backend in an agentic subprocess sees them too; screen rectangles come from the window itself.
The App holds its close until windows are given backA child window would close with its parent. The page detaches them and answers; after 2 s the App closes anyway.

Following the window

A view looks at nothing on a timer. The operating system says when the window moves, resizes, is minimized or restored, is renamed or closes; the Worker signals embedded_windows keyed by the window id, and the view reads the window's state once, in the next animation frame.

ChangeSource
The window, macOSAn Accessibility observer per process: AXMoved, AXResized, minimized and restored, AXTitleChanged, AXUIElementDestroyed on the window; focused window changed, hidden, shown and activated on its application. A kqueue NOTE_EXIT catches a process that quits without closing its windows. One CFRunLoop thread
The window, WindowsSetWinEventHook on the window's process: location, name, show, hide, destroy, minimize and foreground, for the window object itself. One thread pumps them
The window, X11StructureNotifyMask and PropertyChangeMask on the window, from a connection of its own: configure, map, unmap, reparent, destroy, its name and state. One thread waits in select
The App windowElectron's move and resize, sent as embedded-window:host-changed; a page zoom is the page's own resize
The tab within the pageA ResizeObserver, an intersection observer cropped to the tab's own rectangle for a shift without a resize, scrolling and the page showing or hiding
A lost pictureTaken again when the window changes or the page shows or gets focus again

The Worker's thread starts with the first window a view shows and ends with the last. Where it cannot start (no Accessibility access), the attach reply has no follows, and that view reads the state every 1.5 s and retries a lost picture as often, only while it is open.

Requests

Socket actionDoes
embedded_windowsLists ordinary windows of other applications, without the App's own process
embedded_window_attachwindow_id, holder (default "tab"), place (default true), host when placing. Places or watches the window; answers its mode, title, frame (screen rectangle), placed, input: whether this holder forwards input, and follows when the Worker follows the window by its events
embedded_window_layoutholder, host: the tab moved, resized, hid or showed; ignored for a view
embedded_window_stateWhether it is still open, its title and frame; with holder, that holder's input
embedded_window_detachholder lets go; see the holder table
embedded_window_inputPointer, wheel, key, text and focus events, x and y from the window's top-left; no reply. Taken where input is true

Every reply is one embedded_window message carrying the request's request_id. When the worker stops it gives back every window it holds.

Implementation status

Placing is checked on a real desktop on all three: macOS in the App, Windows 11 (Arm64) with Notepad, and X11 under Openbox on Xvfb. Wayland stays unavailable. Holders, watching, Windows view input and computer_use finding embedded windows are covered by unit tests and not yet checked on a real Windows or X11 desktop.

Following by events is covered by unit tests on all three; its Windows and X11 sources, and the macOS observers' notifications, are not yet checked on a real desktop.
