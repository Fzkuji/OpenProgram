Phone app

On a touch phone, in the store app or a phone's browser, the UI is a phone app's screens instead of the desktop window. AppShell renders PhoneApp in place of the sidebar, tab strip and right panel when useTouchPhone() holds. A narrow desktop window keeps the phone layout of the desktop shell.

How it is built

PartHow
ControlsEverything common comes from Framework7 v9 (React), used as it ships. It was chosen over Konsta UI, which draws the controls but has no pages, navigation or sheets (each of those had to be built by hand and kept looking wrong), over Ionic, whose iOS look predates iOS 26, and over younger liquid-glass kits. One app of Framework7's draws iOS now and Material for the Android app later. Only the transcript, the composer's box and the data stay the app's own.
Framework7 and the app's stylesFramework7's stylesheet loads with the phone app only, and every rule of it is rewritten at build to reach only inside Framework7's root and not inside an area the app draws itself (data-not-f7: the transcript, a panel, a Next page), unless that area holds Framework7's parts again (data-f7: the composer's controls), and an app-drawn mark inside one of Framework7's parts is left out again (data-not-f7 on an agent mark in a chat row); its class names (.block, .grid, .card) would otherwise land on Tailwind's (apps/web/scripts/postcss-framework7-scope.cjs).
Font and dark modeFramework7's dark class follows the theme mode. The font is SF, with PingFang for Chinese.
Pages and BackWhere the app is stays in the address, which Next's router, the chat's navigation and the phone's links all change. Framework7's View follows it (phone-router.ts): a push pushes the page, going back goes back to it, a replace changes the page's address in place (a new chat getting its id) or shows another kind of page there. The other way, Framework7's Back and its swipe from the left edge go back in the View, and the history goes one entry back after it.
No half-drawn pageA conversation not yet read opens once its messages arrive (at most 700ms), so it never slides in as an empty New chat first.
DataNothing is fetched twice: the list reads the session store, and the app keeps the last list of chats and projects per computer and shows it at once, redrawing only what changed; the conversation is the split view's self-contained PeerSessionPane, and the details pages mount the right panel's own panels. The chat page's shell stays mounted out of sight, since it owns the connection and the load of the conversation in the address.
Shared with the desktopThe model, agent and session-action menus were split into hooks and bodies (useChatModel, useChatAgent, useSessionActions), so the phone's sheet and details page and the desktop's chips and menus run the same code.
Chinese, Japanese, KoreaniOS WebKit draws a character the system font lacks as a boxed "?" instead of trying the next family, so every font stack names PingFang SC, Hiragino Sans and Apple SD Gothic Neo before -apple-system (lib/prefs/appearance/font-stacks.ts).
MenusA choice is a Framework7 part: a smart-select page in the settings popup, the computer button's menu, an action sheet for a long press in a browser. iOS draws the long-press menus of chats and messages in the store app (lib/mobile/native-menu.ts, NativeMenus.swift): the page sends the items as soon as a finger lands, so the long press is ready; a pick comes back as an event.
Long pressA message's menu lists the buttons of its desktop action bar, which stays in the page hidden, and clicks them, so each action runs the same code (phone-message-menu.tsx). Text selection is off outside inputs.
HapticsThe store app's bridge plays a light, medium, selection or success tap (haptic() in lib/mobile/bridge.ts): long presses, switches and segments.
Permission cardIts choices stack as full-width 44pt buttons, the recommended one at the bottom near the thumb.
No zoomTwo quick taps on two controls would zoom the page: the screens use touch-action: manipulation, and the store app locks the viewport's scale.

Why a phone app, not the desktop restyled

The first phone version kept the desktop's structure (tab row, two drawers, chip rows) and restyled it; every fix still read as a computer squeezed onto a phone.

Three ways were drawn: restyle further (A), write the phone's screens inside the web UI (B), or write them natively (C). B was chosen: the screens follow phone conventions, while the data layer, the transcript renderers and the composer stay one codebase; C would mean a second UI to keep, which the phone app ruled out.
