Phone app

On a touch phone, in the store app or a phone's browser, the UI is a phone app's screens instead of the desktop window. AppShell renders PhoneApp in place of the sidebar, tab strip and right panel when useTouchPhone() holds. A narrow desktop window keeps the phone layout of the desktop shell.

Deleting returns to Projects.

How it is built

PartHow
Pages and BackEach screen is an address pushed with history.pushState, which Next keeps in step with usePathname. In the store app a swipe from the left edge goes one page back, the page following the finger (use-edge-swipe-back.ts): WKWebView's own back gesture does not take these entries. In a phone's browser, the browser's own gesture does it.
DataNothing is fetched twice: the list reads the session store, the conversation is the split view's self-contained PeerSessionPane, and the details pages mount the right panel's own panels. The chat page's shell stays mounted out of sight, since it owns the connection and the load of the conversation in the address.
Shared with the desktopThe model, agent and session-action menus were split into hooks and bodies (useChatModel, useChatAgent, useSessionActions), so the phone's sheet and details page and the desktop's chips and menus run the same code.
Chinese, Japanese, KoreaniOS WebKit draws a character the system font lacks as a boxed "?" instead of trying the next family, so every font stack names PingFang SC, Hiragino Sans and Apple SD Gothic Neo before -apple-system (lib/prefs/appearance/font-stacks.ts).
Long pressA message's sheet lists the buttons of its desktop action bar, which stays in the page hidden, and clicks them, so each action runs the same code (phone-message-menu.tsx). The press arms at 450ms with a haptic and cancels the user bubble's own rewind menu. Text selection is off outside inputs.
HapticsThe store app's bridge plays a light, medium, selection or success tap (haptic() in lib/mobile/bridge.ts): long presses, switches and segments.
Permission cardIts choices stack as full-width 44pt buttons, the recommended one at the bottom near the thumb.
No zoomTwo quick taps on two controls would zoom the page: the screens use touch-action: manipulation, and the store app locks the viewport's scale.

Why a phone app, not the desktop restyled

The first phone version kept the desktop's structure (tab row, two drawers, chip rows) and restyled it; every fix still read as a computer squeezed onto a phone.

Three ways were drawn: restyle further (A), write the phone's screens inside the web UI (B), or write them natively (C). B was chosen: the screens follow phone conventions, while the data layer, the transcript renderers and the composer stay one codebase; C would mean a second UI to keep, which the phone app ruled out.
