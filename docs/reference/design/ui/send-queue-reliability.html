OpenProgram / Web / Conversation input

Queue and active-turn steering

Queue is the default: each conversation sends one follow-up after its preceding turn ends. Steer adds text to the exact active execution at a supported safe point. Neither queue action cancels the active execution; cancellation belongs to the separate Stop control.

Reference and compatibility

Codex prompting separates queued follow-ups from active-turn input. Codex App Server binds steering to the expected active turn and does not accept runtime-setting overrides. OpenProgram uses its existing execution command service and safe points instead of adding a second session inbox or provider-specific steering transport.

Delivery

Queued text → execution identity and current version → durable execution.steer command → next safe point → persisted steering user message

The queue retains an entry until a matching applied receipt confirms that its user message is persisted. Accepted or applying commands are checked automatically with the same envelope. The command carries only the message, exact execution identity, version and an idempotency key. It does not change permissions, models, tools or the current running program. Unsupported or ended executions leave the entry queued; idle reconciliation drains normal follow-ups in FIFO order.

Before posting, the client retains the immutable command envelope. A lost acknowledgement leaves delivery unconfirmed: the row remains visible, normal drain cannot send it again, and retry reuses the same envelope. A confirmed stale-version rejection permits a new envelope against a fresh snapshot. Errors are visible; injected flags are always released after transport failure.

Ownership and UI

The active session and its running execution determine the target. Another session or related sub-Agent is never selected opportunistically. The queue exposes one non-cancelling action to add a message to the active turn, plus removal when delivery is not uncertain. The running-message preference remains queue or steer. Attachments retain their existing draft behavior; steering accepts text within the canonical command size limit.

Storage boundary

Queue entries remain local to this renderer. Pending steering entries cannot be drained as ordinary messages until a definitive acknowledgement resolves the command. Canonical acceptance persists the command on the server; application persists the user message. When an execution finishes, undelivered steering commands are rejected and their rows can resume ordinary queuing. A completed tool batch is never skipped merely because a steering message arrives. This change does not replace ordinary chat transport with a new message broker.

Acceptance

  • Queue two follow-ups: each starts only after the preceding turn ends.
  • Add text while a tool runs: the same execution and tool continue; the instruction reaches the subsequent model context.
  • Lost acknowledgement: retain the row and replay the same command without duplicate delivery.
  • Ended, unavailable and unsupported targets retain the input and report their state.
  • Scope switching cannot steer another conversation; Stop remains a separate explicit action.

Implementation status

The implementation uses canonical execution commands and non-cancelling queue controls. Agent command application confirms persisted user input in the active reply branch; safe-point admission alone remains applying. Owner expiry cannot authorize a late input write. Execution closure resolves undelivered commands even when the execution awaits effect reconciliation. Acceptance uses the default App and real request handling; static checks do not replace that runtime acceptance.
