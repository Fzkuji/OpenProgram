Review pane

The Review tab reads a set of changes and acts on it: four scopes, Revert and Stage on each block, line comments that wait and go out together, and a review by the conversation's own model. The layout follows the Codex app's review pane; where the change sets come from is in the chat turn spec.

  1. HeaderScope menu with its totals; … menu with Review with agent and File type
  2. Block headerRevert, Stage (Unstage in Staged)
  3. Your commentunder its line, which ends in a dot; Edit, Delete
  4. Agent findingunder its line; Dismiss, Fix
  5. Bottom barN comments, Discard, Send to agent

ItemBehaviour

… menuReview with agent (Stop review while one runs) and File type: All, Code, Tests, Docs, Large

Why one row: the pane usually sits in a split window about 580 px wide, where the old title row, scope-tab row and a third row for Review with agent took a quarter of the height. The layout follows Codex's Changes pane.

Scopes

ScopeShowsActs
This turnWhat one turn changed, from the mutation journalRevert a block
UnstagedWorking tree against the index, untracked files included, .gitignore honouredRevert a block; Stage a block or the file
StagedIndex against HEADUnstage a block or the file
BranchWhat the conversation's branch changed, from the mutation journalRevert a block
Why Unstaged and Staged
One "Workspace" diff mixed two segments a reader treats differently: what is about to be committed and what is not. Two scopes give each its own action (Stage, Unstage) and keep Revert on the side it writes, the working file.
Git chip
"N uncommitted files" opens Unstaged: the changes not yet in a commit or the index are the ones a person usually checks first.
Snapshot
Each scope is a pinned snapshot (HEAD, index blobs, working file identity). Stage, Unstage and Revert run only against the snapshot on screen; a newer one refuses and the pane reloads.

Stage and Unstage

ItemBehaviour
Blockgit apply --cached with that one block; Unstage adds --reverse. Git checks the block's context against the index, so a block the index no longer matches is a conflict and nothing changes.
Filegit add --all or git restore --staged, with the old path of a rename too
Only whole blocksA block cut by a page edge or ending without a newline has no Stage; a new or deleted file stages as a file
WhereOnly for a local Git project. Not a Git repository, or a conversation in an SSH environment: no Stage buttons, the same places the Git chip is absent, because the index there is not the one the agent works on.
During a turnWaits, like Revert
AfterThe scope reloads and the Git chip refreshes

Git does the patching. The same block that git add -p would stage is staged, with Git's own context checks, instead of a second patch engine.

Line comments

ItemBehaviour
WriteThe comment button on the hovered line; ⌘Enter saves, Escape cancels
PinnedA card under its line: "You", the text, Edit and Delete. The line ends in an accent dot.
KeptPer conversation in a client store, so a tab switch or a remount keeps them while unsent. A comment belongs to its scope and file.
Bottom barFloats over the diff while any wait: "N comments", Discard, Send to agent
SendOne user message in that conversation, each comment as file and line, the quoted line, then the comment. It takes the send queue, so during a turn it waits its turn. The comments clear.

Why a batch: comments on a change are read together. Sending each one as it is written starts a turn per line; dropping them into the composer mixed them with whatever was being typed. The Codex app collects inline comments the same way and sends them as one request.

Review with agent

ItemBehaviour
StartThe first item of the … menu. While it runs the header shows ✦ Reviewing, the time so far and a stop button, and the menu item reads Stop review.
Stop reviewEnds the review at once: the server cancels the model request, the answer is ignored and the header loses its Reviewing time. A review is named by its review_id; review_agent_cancel with that id cancels it.
InputThe whole diff of the scope on screen (up to 60 files and 120,000 characters), each under its path
CallOne structured-output request on the conversation's own model at low reasoning effort, through the runtime that writes conversation titles. It writes nothing to the transcript. Low effort reviewed a 400-line change in 82 seconds with one request; the default effort took nine minutes over two and found no more real problems.
FindingsPath, line, severity (low, medium, high), body. Findings on files outside the scope or with another severity are dropped.
ShownCards under their lines: ✦ in accent purple, "Agent review · severity", the body, Dismiss and Fix. A finding on no shown line sits above the diff. A new review of a scope replaces that scope's findings.
FixSends a message asking the agent to fix that finding, then removes the card
WaitingA review of a large change takes minutes (a 400-line change takes over a minute), so the pane waits up to 30 minutes. The Worker keeps each answer for an hour under its review_id; when the socket drops while the model works, the pane waits for it to come back and asks again with review_agent_wait, which answers at once, or when the review finishes.
FailureThe Reviewing time goes and Review with agent can be chosen again; no error page, no banner. A Worker that restarted no longer knows the review and answers UNKNOWN_REVIEW.
Wirereview_agent runs beside the connection's ordered frames, so a long model call does not hold other requests

Why the conversation's model: the review then reads with the same model and settings the person chose for this work, and no separate review model needs setting up. The Codex app's /review works the same way and puts its findings on the lines of the diff.
