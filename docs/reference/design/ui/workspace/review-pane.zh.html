审阅面板

审阅标签页读一组改动并对它操作：四个范围，每个块上的撤销和暂存，攒起来一起发送的行评论，以及由本会话自己的模型做的审阅。布局参照 Codex 应用的审阅面板；改动集从哪里来见聊天回合规范。

  1. 顶部范围菜单带增删行数；… 菜单里有让 agent 审阅和文件类型
  2. 块头撤销、暂存（已暂存范围里是取消暂存）
  3. 你的评论在所评论的行下面，该行末尾有圆点；编辑、删除
  4. Agent 审阅意见在对应的行下面；忽略、修复
  5. 底部条N 条评论、丢弃、发送给 agent

顶部

项目行为
范围菜单就是顶部的标题：范围名和它的 +/− 行数。菜单依次列出本轮，未暂存和已暂存，分支，最后一行是来源和文件数。
… 菜单让 agent 审阅（审阅进行中是停止审阅）和文件类型：全部、代码、测试、文档、大文件
审阅进行中✦ 审阅中、已用时间和停止按钮，在范围菜单和 … 菜单之间，只在运行时出现
文件头暂存（或取消暂存）和预览是图标，鼠标悬停或聚焦文件头时才出现；n / N 文件切换保留

为什么只有一行：面板通常在约 580 px 宽的分屏里，原来的标题行、范围标签行和单独放让 agent 审阅的第三行占去四分之一高度。布局照 Codex 的改动面板。

对象顶部
Codex一行：范围下拉当标题并带行数，一个 … 菜单；宽度不到 625 px 时按钮收进菜单；文件操作悬停才出现
Claude Code 标签页一行：范围下拉当标题；选项在面板菜单里
OpenCode、Antigravity范围下拉当标题；显示选项在图标或 ⋮ 菜单后面；Antigravity 悬停才出现暂存
agent 审阅这几家和 Copilot 都不放在差异面板头部

范围

范围显示操作
本轮一轮改了什么，来自修改日志撤销一个块
未暂存工作区对比暂存区，包括未跟踪文件，遵守 .gitignore撤销一个块；暂存一个块或整个文件
已暂存暂存区对比 HEAD取消暂存一个块或整个文件
分支会话分支改了什么，来自修改日志撤销一个块
为什么分未暂存和已暂存
原来一个“工作区”差异把两段混在一起，而读的人对它们的处理不同：一段马上要提交，一段还没有。分成两个范围，每个有自己的操作（暂存、取消暂存），撤销也只留在它真正写入的一侧，即工作区文件。
Git 胶囊
“N 个未提交文件”打开未暂存：还没进提交也没进暂存区的改动，通常是人最先要看的。
快照
每个范围是一个固定的快照（HEAD、暂存区 blob、工作区文件标识）。暂存、取消暂存和撤销只对屏幕上的快照执行；快照已经变了就拒绝，面板重新加载。

暂存和取消暂存

项目行为
块对这一个块执行 git apply --cached；取消暂存加 --reverse。Git 会拿块的上下文核对暂存区，暂存区已对不上的块算冲突，什么也不改。
文件git add --all 或 git restore --staged，重命名时连同旧路径
只限完整的块被分页切断或结尾没有换行的块没有暂存按钮；新增或删除的文件按整个文件暂存
在哪里有只在本地 Git 项目里。不是 Git 仓库，或会话运行在 SSH 环境里：没有暂存按钮，和 Git 胶囊不出现的地方一致，因为那里的暂存区不是 agent 工作的那个。
一轮进行中等待，和撤销一样
之后范围重新加载，Git 胶囊刷新

打补丁交给 Git。暂存的就是 git add -p 会暂存的那个块，用 Git 自己的上下文检查，不另写一套补丁引擎。

行评论

项目行为
写悬停行上的评论按钮；⌘Enter 保存，Escape 取消
固定显示所在行下面的卡片：“你”、正文、编辑和删除。该行末尾有一个强调色圆点。
保留按会话存在客户端存储里，切换标签页或重新挂载都不丢，直到发送。评论属于它的范围和文件。
底部条有待发送的评论时浮在差异上方：“N 条评论”、丢弃、发送给 agent
发送在该会话里发一条用户消息，每条评论写成文件和行号、引用的那一行、然后是评论。走发送队列，一轮进行中就排队。发送后评论清空。

为什么攒成一批：对一组改动的评论是一起读的。每写一条就发出去，会每行开一轮；放进输入框又会和正在写的内容混在一起。Codex 应用也是这样收集行内评论，作为一个请求发出。

让 agent 审阅

项目行为
开始… 菜单的第一项。运行时顶部显示 ✦ 审阅中、已用时间和停止按钮，菜单项变成停止审阅。
停止审阅立即结束审阅：服务端取消模型请求，结果不再采用，顶部的审阅中计时消失。每次审阅用 review_id 命名，带这个 id 的 review_agent_cancel 取消它。
输入屏幕上这个范围的全部差异（最多 60 个文件、120,000 个字符），每个文件放在它的路径下
调用用本会话自己的模型、以低推理强度发一次结构化输出请求，走生成会话标题的同一个运行时。不写入对话记录。低强度审一个 400 行的改动用了 82 秒、一次请求；默认强度用了九分钟、两次请求，也没多找出真正的问题。
审阅意见路径、行号、严重程度（低、中、高）、正文。不在本范围文件里的、或严重程度不合规的意见丢弃。
显示对应行下面的卡片：强调紫色的 ✦、“Agent 审阅 · 严重程度”、正文、忽略和修复。不在任何显示行上的意见放在差异上方。对同一范围再审阅一次，替换该范围原来的意见。
修复发一条消息请 agent 修复这条意见，然后移除卡片
等待审阅大的改动要几分钟（一个 400 行的改动要一分多钟），面板最多等 30 分钟。Worker 按 review_id 把每次的结果留一小时；模型还在审时连接断了，面板等连接恢复后用 review_agent_wait 再要一次：已完成就立即回答，否则审完时回答。
失败审阅中计时消失，可以再选让 agent 审阅；没有错误页，没有提示条。重启过的 Worker 不再认识这次审阅，回答 UNKNOWN_REVIEW。
协议review_agent 在连接的有序帧之外运行，耗时的模型调用不会挡住其他请求

为什么用本会话的模型：审阅用的是这个人为这项工作选的同一个模型和设置，不需要另外配置审阅模型。Codex 应用的 /review 也是这样，并把意见放在差异的对应行上。
