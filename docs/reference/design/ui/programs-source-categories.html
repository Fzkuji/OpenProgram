Reference comparison and decisions

ReferenceRelevant modelDecision here
OpenProgram registryRegular functions and agentic functions register into one callable surface while retaining source-layer metadata.Adopt the unified runtime catalog; add read-only source filters only in the management UI.
Hermes toolsetsNamed toolsets represent selection, not source ownership.Keep tool profiles separate from source categories.
Claude CodeThe official repository does not publish the product's internal tool implementation tree, so its visible UI cannot establish a source-layout contract.Do not copy an unverifiable one-folder-per-tool assumption.
OpenAI CodexThe public tool implementation uses both handler files and submodules.Adopt the same complexity-based distinction, without copying Rust-specific names.

Adopted: purpose directories are ordinary Python packages. A Function with one implementation file is a module; a Function or subsystem with providers, prompts, actions, workers, shared state, or several cooperating entry points is a package. A source package can register several callables, so packages such as agent and memory remain cohesive. Rejected: forcing every callable into a directory, forcing every source into one file, frontend-only categories, a second category registry, compatibility copies at old import paths, raw source-file browsing, and duplicating external MCP tools in Programs.

Behavior, compatibility, and failures

  • The explorer expands the installed directory hierarchy lazily; it never invents category paths in the browser.
  • A singleton module or package is rendered directly as its registered callable; it does not add an extra source-wrapper row.
  • A package that registers several callables expands to those callable names while retaining one shared source boundary.
  • Refreshing Programs rescans Programs and reloads the same explorer endpoint.
  • Rows whose source is mcp never appear in Programs; MCP Servers remains their only management page.
  • Agentic Functions use their public callable names; their source path is used only for static call analysis when available.
  • Workflows, Applications, favorites, chat launch, call tree, and graph behavior remain unchanged.

Application import compatibility

Applications loaded from openprogram/programs/applications must import built-in Agentic Functions through the canonical openprogram.programs.workflow namespace. The removed openprogram.programs.agentic_functions namespace is not restored as a second compatibility package.

Acceptance: the packaged gui_agent public entry can begin a desktop run without a module-import error; the GUI, research, and wiki application packages contain no production import of the removed namespace.

Application function calls

The Application view reads current package source on each request. It starts at decorated public functions and follows local function calls and package imports, rather than treating every repository import as an execution edge. Tests, benchmarks and unrelated files do not enter the graph.

Conditional calls are labelled as conditional, not as a fixed execution sequence. The existing tree and graph share the same source-derived nodes. Unresolved calls and analysis limits are reported; the analyzer never executes package code to discover relationships. The visible page refreshes its analysis while open. The call tree initially expands the first three levels, keeping capability functions visible and their internals collapsed. Branch rows toggle with a click, Enter or Space. Expansion choices survive source refreshes for the selected Program; leaves and repeated references have no toggle.

Implementation status

Source tracing, conditional edges and visible-page refresh are implemented. Regression tests cover source edits, entry selection and unresolved callable aliases. Installed-App visual acceptance remains unverified. No Archify integration or Harness execution changes are included.

Direct function replies and input

A manually invoked function retains its execution tree and renders its persisted final answer as a separate Markdown body below the tree, visible even when the tree is collapsed. This adds no model call or persisted conversation node. Summaries and takeover instructions remain readable; other values use text or JSON. Nested calls retain their current presentation. The same selected execution detail follows incoming status updates without opening the sidebar.

Empty function forms size from visible fields. Closed Advanced sections contribute only their summary row, not hidden parameter labels. Explicit expansion remains available. Regression and default-App checks verify these presentation contracts.
