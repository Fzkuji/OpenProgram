Programs source categories

The Programs explorer is a logical catalog, not a mirror of Python files. It combines registered built-in Functions and Agentic Functions with source-backed Workflows and Applications. MCP servers and their tools remain exclusively in the existing MCP Servers page.

Reference comparison and decisions

ReferenceRelevant modelDecision here
OpenProgram registryRegular functions and agentic functions register into one callable surface while retaining source-layer metadata.Adopt the unified runtime catalog; add read-only source filters only in the management UI.
Hermes toolsetsNamed toolsets represent selection, not source ownership.Keep tool profiles separate from source categories.
Claude Code and OpenClaw referencesRegistration and policy decide callable availability; neither reference exposes OpenProgram's three-directory source tree as a Programs sidebar.Do not infer source categories from policy, permissions, enabled state, or profile membership.

Adopted: reuse the existing built-in runtime groups. Modified: the file-tree visual language represents logical catalog folders rather than physical directories. Rejected: duplicating MCP tools in Programs, a second category registry, persisted user categories, moving Python files, a new dependency, and displaying raw source files.

Behavior, compatibility, and failures

  • Search indexes every loaded logical folder and callable name.
  • Refreshing Programs re-fetches all three catalog endpoints.
  • Runtime-only built-in functions render a valid single-node detail instead of requesting nonexistent source paths.
  • Rows whose source is mcp never appear in Programs; MCP Servers remains their only management page.
  • Agentic Functions use their public callable names; their source path is used only for static call analysis when available.
  • Workflows, Applications, favorites, chat launch, call tree, and graph behavior remain unchanged.

Task brief and gate manifest

Production files: one pure Programs catalog builder and the existing Programs page. Test files: the existing Programs UI contract plus one direct catalog-builder test. Excluded: registry changes, new API endpoints, moving Python files, agent-profile behavior, card restyling, dependencies, and release operations.

Acceptance: the Programs tree contains every non-MCP built-in row returned by /api/tools, every Agentic Function returned by /api/programs, existing Workflows, and existing Applications; built-ins retain their functional groups; no MCP server or MCP tool is duplicated in Programs; selecting every displayed leaf produces a valid detail.

Verification: focused catalog-builder RED/GREEN, Programs UI contract, TypeScript compile, production build, default 18100 packaged-App DOM and screenshot, and git diff --check.

Application import compatibility

Applications loaded from openprogram/programs/applications must import built-in Agentic Functions through the canonical openprogram.programs.functions.agentic namespace. The removed openprogram.programs.agentic_functions namespace is not restored as a second compatibility package.

Acceptance: the packaged gui_agent public entry can begin a desktop run without a module-import error; the GUI, research, and wiki application packages contain no production import of the removed namespace.

Implementation status

Implemented and packaged: Programs owns built-in Functions, Agentic Functions, Workflows, and Applications only. The default 18100 App exposes 60 vanilla Functions, 11 Agentic Functions, Workflows, and Applications, with no MCP or connected branch; the backend still reports MCP tools for the dedicated MCP Servers page.
