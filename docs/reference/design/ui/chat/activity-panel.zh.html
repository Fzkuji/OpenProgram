运行时开出的（runtime_started）不是 agent：它不是用户分出来的分支。它的运行算在已检出分支上。没有别的分支时，整个会话就是一个“主代理”。常驻代理或任务在当时的头部发的报告，读者走开后留下的那一段也算：没有提示词，只有 report_… 消息。
定时任务写的（scheduled_task）不是 agent：它的运行属于它的任务。任务的分支记录会这样标，自身那一段只有调度器写的提示词的线也算，这就涵盖了旧运行被截断时留下的末端。已检出的分支不会是它。

事实来源
属于哪个任务运行保存的回合写着它的任务（scheduled_task，来源 scheduler）。回合还没写任务时保存的运行，取它那条线的任务：一个任务的运行在一条线上前后相接，所以后来的运行、它的分支记录和分支条目为前面的运行指明任务（task_activity.run_tasks）。GET /api/session/{id}/executions 在每个顶层运行上以 scheduled_task_id 发出。
结果任务记录（task_runs，最近 20 次）里有这次运行时以它为准；否则看执行的状态和回答，判断方式与 run_finish 在运行结束时相同。结束了的运行只判断一次并保留。
原因由运行的 reason_code 和运行时长生成，中英文各一份：agent_runner_error、time_limit、owner_lost_before_checkpoint、unfinished_before_session_logs、scheduled_run_start_failed，其余是简单的“失败”“被停止”或“运行 … 后被截断”
花费记在运行的执行和它的助手 Job 上的模型调用。调用还没记执行时保存的那些，算给当时这个对话里正在进行的运行。
页面读取GET /api/session/{id}/activity/tasks/{task}?filter=all|unfinished|notified&offset=&limit=：计数、最近 24 次、花费和一页运行。在有 177 次运行的对话上，对话已在内存时约 26 ms；对话还没载入时第一次约 0.6 秒。进入页面、收到 op:execution-update 和 op:job-status 时，以及收到 runs 和 work 变化帧时读取；刷新按 ID 替换最新的几行。

为什么一行：每小时运行的任务有几百次运行，每次一行、或者每条线一行，会把读者真正在用的代理埋掉。常驻设计对比的同类产品都是一个任务列一次、历史放在它自己的页面：

  • Claude Code 列出 routines。
  • Codex 列出 automations。
  • DeepSeek Harness 有任务页和每个任务的投递记录。

这里的行多给了最近一天跑得怎么样，用一条色条表示；历史留在任务页，分页，并能只看没完成的。

它和提醒、命令一起列在定时任务里：三者都是 Scheduler 为这个对话做的事，一个任务只在一处。它的行不一样，是因为它的运行是 agent 做的。

概览的读取

概览先画出这个会话上次读到的内容，同时在后台重新读取；新结果在原处替换，不出任何提示。

情况做法
首次打开各组按上次读到的内容画。agent 在工作图的运行读到之前什么都不画：读到后是工作图，对话没有运行时是主代理那一行。
再回来四项读取（执行、程序和调用、助手名单、会话事务）按会话保留到页面关闭（lib/execution/activity-reads.ts），回到这个 tab 或切回这个会话时第一帧就画出来。执行和助手名单在新鲜时不重读：期间连接一直在、读取开始后没有 op:execution-update、op:job-status 或 processes 变化，与读了多久无关。会话事务每次都重读。
显示期间执行在上述事件、重连、获得焦点和窗口重新显示时读取，最多每秒一次，不按定时器读。读取失败后隔 2、4、8 …… 秒重试，最长 30 秒。
失败什么也不说。已读到的内容保留；从没读到的运行记录位置留空，同时继续重试（等待不配文字）。
服务端GET /api/session/{id}/executions 每次请求对每个会话只读一次 Job（jobs.store.session_jobs_reader），每一行的 Job、包括助手用量都从中查找；前台轮次没有 Job，不再逐条去查。会话目录来自位置索引，索引文件变了才重新解析。一个有 203 次运行的会话，响应从 4–6 秒降到约 0.2 秒，三个请求同时到达也不再在会话锁上排队 18 秒。

分支、运行和等待

术语含义
子代理显示类型为 job_agent 的执行；挂在上方最近的子代理下，否则挂在主代理下
分支每个执行属于一个：子代理的分支包含其下没有更深子代理拥有的一切；其余属于主代理
运行一条消息及为它做的一切，通常是一个顶层执行，其执行树包含子执行、未返回的函数调用和托管程序。较早的运行只以消息形式存在。是代理页里的一行，不在总览中出现。
等读者处理只有暂停在提问或授权上的运行（模型的 issues 过滤出暂停的执行）
已中断被重启截断的调用或运行。属于历史，无需处理：概览里不列出。
状态未知监管进程已消失的程序。属于历史，无需处理：概览里不列出，它所属的代理也不会因它显示“运行中”。
已结束仅缺模型响应记录的执行（provider_response_incomplete）

agent 调用与子代理的配对

服务端从转录读调用，不读 effect，因为其元数据带着完整的 provider 载荷。Job 记录派生它的回复（spawn_caller）和提示词。

  1. 调用方和提示词相同的调用启动了它；未失败的调用优先配对，因为失败调用可能和重试共用提示词。
  2. 提示词对不上时，若某调用方只剩一个 Job 和一个未失败的调用，就配对这两者。
  3. 没有 Job：调用启动失败（结果为 [agent error] … 或结局为 failed）或未启动。

调用方决定分支：j_… 回复是子代理的，其余是主代理的。

页面

总览里的一行打开一页。页面不再通向别的页面：属于某行的内容在它下面原地展开，直到被收起。顶部的“运行记录”、焦点在面板内时按 Esc、或点侧栏轨道上的“运行记录”都会返回，并恢复总览的滚动位置和焦点。

页面像手机上那样移动，用的是 Launchpad 的弹簧；开启减少动效时直接切换。

一张竖着的时间图，最新的在上面，每一层一列：话题、消息、步骤、步骤里面。侧栏宽度决定显示几列，视野里的每一列都是完整的。

侧栏宽度列

544（第二个吸附点）两列，各 256

两个吸附点之间取较少的列数，拉宽填满

列数是图表宽度除以 256 向下取整，至少一列、最多三列（columnsFor）。宽度变化的那一帧就生效，所以拖动拖动条时，松手会落到的列数在拖动过程中就显示出来。

每一块悬停都抬成卡片，都能点；被截断的标题或文字悬停时显示全文。下面还有内容的块往右移一列。只是一次调用、一次失败或没有步骤的消息的块原地展开：输入和结果，或者提问和回复，用运行列表里的写法。

展开的块变高，下面的块往下让，左边几列里它的色条跟着变长。再点一次收起。展开和收起是一段 240 毫秒的标准曲线，收起时内容留到块合上为止。还在运行的调用没有可展开的内容。

视野以读者去过的最深一列结尾，放得下时从话题开始。点开一块时，如果它的下一列已经在视野里，什么都不移动。列数少于层数时，视野一次移动一列：

动作发生什么
点击一块它的下一列滑进来，这一块在屏幕上的位置不动
返回、Esc、在块上按左方向键退回一列；已在第一列时回到总览
左右滑动图表跟着手指走，最多一列。移动途中再滑也会从当前位置接住。
抬手已经滑过 48 像素或是一次甩动，就继续到手指前往的那一列；否则退回。两种情况都只有一次移动，抬手后的惯性不再移动任何东西。
滑过最后一列图表最多让出 44 像素，随落定一起回来
滑过第一列整个页面跟着走：这就是返回
横向转动的鼠标滚轮每一格移动一列
键盘焦点落到视野外的块它所在的列移进视野

一次移动只是各列轨道靠 transform 滑动一次：

  • 整列 240 毫秒，剩下的一段更短（不少于 120 毫秒），曲线是 --ease-standard；开启减少动效时直接切换。
  • 移动开始前，条目按终点排好，只排一次。滑进来的列已经是最终尺寸；被点的块或视野顶上的块在屏幕上保持不动。
  • 屏幕上位置或高度变了的块，随滑动一起过渡过去，时长和曲线与滑动相同：块用 transform 移动，竖条从顶部缩放，贴在视野顶上的文字走它自己的路径。这些动画不在主线程上跑，播放时不会重新排版。
  • 移动前离得太远、没有画出来的块，从旧布局里的位置移进来；移出范围的块先移走再消失：旁边的块还在动时，没有块原地出现或消失。
  • 比终点那一列更深的列不绘制，滑出途中也一样。
  • 滑动结束后没有任何东西再变高、淡入或落定。
  • 实测：一个 3 个话题、约 40 条消息的对话，左右移动时每一帧约 9 ms，加过渡前后一样。处理器降速四倍时，打开后的第一次移动有一帧约 45 ms，加不加过渡都一样；之后的移动保持 9 ms。
  • 图表容器从不横向滚动，只上下滚动。离视野上方超过一屏、下方超过两屏的条目不在布局里。
  • 视野外的列的条目也不在布局里：只有正在显示的列，以及移动途中两侧各一列，才有条目。移动带进来的列，在显示之前就有了条目。
  • 有焦点的那一行所在的列留在布局里，焦点和按键不会丢；方向键只在布局里的行之间移动。
  • 实测：一个 8 个任务、约 440 行的对话，处理器降速四倍，三列宽度下左右移动，一帧里最慢的任务从 252 ms 降到 45 ms，一次样式计算从 2,545 个元素（52 ms）降到 313 个（7 ms）。
  • 一个条目的位置变了才写入，它显示的内容变了才重画，所以有东西在运行、图每隔几秒重建一次时，只重画几个条目。

原因：这张图以前靠横向滚动翻列，每块的高度按滚动位置插值。三件事让移动不对劲：

  • 两段动画：高度在一列 256 像素的前 64 像素里就变完，过阻尼的弹簧还拖着长尾在滑，滑入的一列又按自己的曲线淡入。
  • 卡顿：每一帧都写所有块的 top 和 height、重设纵向滚动、改变哪些块绘制，等于每帧一次完整布局。
  • 半列：任何宽度下列都是 256 像素；不是滑动手势的横向滚动停下 160 毫秒后还要吸附到列边。
规则做法
高度由视野里最深的一列决定。父块盖住子块，所以各列同一高度是同一时间。
时间每块顶上写这一块最晚的时刻：话题和消息到分钟，步骤到秒。长时间空闲和换天是横跨各列的一行虚线：换天时每一列的时间列都写日期，长时间空闲在第一列注明空了多久。
颜色颜色只表示属于哪个话题，不表示结果好坏。每个话题按首次出现的顺序取一个主色，隔了很久回来的话题还是这个颜色。消息取主色下的不同色号，步骤和步骤里面继续往下延伸。没人发起的运行是灰色。失败和运行中写在文字里。
步骤连续调用同一个函数合成一行，每次调用在最后一列。失败的步骤单独一行，错误写在下面。子 Agent 自己的步骤在最后一列。下面的行都没有下一层的一步（一组调用、子 Agent 的步骤）最多四行高，它的行在自己的格子里滚动。
按钮最多一个，只在等读者或已暂停的消息上：Answer 或 Continue。
数据activity/runs?chart=true 返回这一页，带每个事件的简短形式（输入截断，结果只在步骤失败时保留）和每次运行的话题。已结束的运行按修订缓存。

话题

用户发的每条消息属于一个话题，存在会话消息旁边的 topics.json 里：话题按首次出现的顺序排列，以及每条消息的话题。不往消息里写任何东西。

  • 每轮结束后，后台任务给还没有话题的消息分类，用和聊天标题相同的后台模型，只看用户说的话。
  • “继续”这样的短回复跟着上一条消息，不调用模型。
  • 旧会话第一次打开时间图时，同一个任务给它的消息分类，每次调用 40 条。在此之前它们的话题块只占位置，什么都不画。
  • 调用失败或没有可用模型时，消息保持未分类，画在上一条消息那里。下一条消息会再试；打开时间图要等上一轮结束 10 分钟后才再试，所以一轮自己发出的变化通知不会再启动一轮。

openprogram/host/processes/progress.py 从输出读取进度，可信度从高到低：

  1. ##progress 45/100 samples 行（bash 工具要求模型在长循环里打印）
  2. OSC 9;4 终端进度序列
  3. tqdm 和 pip 进度条
  4. Epoch 3/10、step 120 of 1000、[45/100] 这类计数

更可信的来源出现后，较低的来源被忽略，内层每批进度条不会覆盖样本计数。速度和剩余时间取进度条自身的，或从开始计数起测量。重绘的进度条只占 2,000 行上限中的一行，读取后台命令的代理每次重绘只收到一次。
