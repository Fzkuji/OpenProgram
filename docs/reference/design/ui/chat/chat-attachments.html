Chat attachments

One text marker carries every file in a message:

[attachment: notes.txt (txt, 18 KB, 4210 lines) @json "/abs/path/notes.txt"]

Written only by format_marker in openprogram/state/attachments.py; a fifth source calls it too. Read on the web only by parseAttachments. An optional @previewjson names a saved preview. The older @ /abs/path spelling stays readable. How content enters model context: Attachment handling.

Channel text is prefixed with [display name (id)] and markers follow. _one_line removes brackets from the name so a prefix cannot be forged. Unnamed pasted images get an extension from their media type.

A card is drawn only for an attachment the server put on the message: a send_file file or a file the turn produced. The browser derives no card of its own.

When the turn's final text is assembled (with_attachments), a marker the model typed for a file the turn did not record becomes the file's name, in the content and the text blocks: no card, path or automatic preview, live or after a reload. Upload and mention markers in the person's message stay.

  • A marker stays only when its path and any @previewjson path were both recorded.
  • The text a reply stores while streaming, kept by a reply a restart cut off, and an always-on report get the same treatment.
  • parseAttachments reads only the forms the server checks.

A script the reply links ([build.py](/abs/build.py)) or a file the agent only read stays a link in the prose (Paths in a reply).

When a reply finishes in the focused chat, its first attachment not already shown in the reply opens in the preview beside it: the deliverable the turn just made.

Below the preview: file-type icon, name, type and size (plus page or file count), then Open and Reveal in Finder (File Explorer, File Manager by platform). A file the app cannot show puts Download in the open slot; when the worker is not on the user's machine, the reveal slot downloads. Previews load as the card nears the screen.

HTML sandbox and archives
  • GET /api/file-page serves only .html and .htm, with sandbox allow-scripts and no allow-same-origin. A srcdoc frame would inherit the app's script-src 'self' and a script-drawn page would be blank.
  • The page has an opaque origin: no access to the app or its storage, its Origin: null requests are refused, it cannot navigate or open windows. Relative files are missing from the strip because the strict cookie is not sent; the page opened in a browser tab has them.
  • FileViewer sends a zip or tar to ArchivePreview: full tree on the left, the selected member on the right through the same FileViewer. Nothing is extracted to disk.

Paths in a reply

A file the reply only names, as `exports/plan.pptx` or [plan](/Users/me/exports/plan.pptx:3), is a link to that file. A click opens it in the preview beside the chat: an office file in the document editor, a PDF in the PDF viewer, a web page as a page.

StepRule
CandidatesInline code spans and markdown link targets of a settled reply (never code blocks, never while it streams). A path-shaped string: a folder separator or a name with an extension, absolute, ~ or relative; a :12 or #L12 suffix is dropped. Commands, web addresses and links to the app's own pages (/s/…, /settings) are not candidates
Confirmed by the workerGET /api/file-paths answers which candidates are files: absolute and ~ paths against readable_roots, relative ones joined to the chat's working directory first. Only confirmed paths become links, so a code span that looks like a name never turns into a dead link
CostThe candidates of every reply on screen go out in one request per chat (64 paths each, stat only), answers are kept five minutes (a missing file twenty seconds, since the agent may still make it). The text is drawn first and never waits
Not a routeA markdown link that can only be a local path (/… that is not an app page, ~/, ./, ../, file://, a drive) is stopped before the shell's router, which would take /Users/… for a page. Not confirmed yet, it is looked up on click; a file that is not there says so. A bare target (notes/plan.md, or docs.example.ai, a web address without its scheme) becomes a file link only once confirmed, and until then keeps its own click
LookDrawn as the app's rendered-markdown links are (the file preview's): the link colour over a faint underline that turns solid on hover. A code span keeps its chip and takes the colour and the underline, so it is told apart from plain code at rest even where the link colour is close to the code colour. Only decoration changes, so the paragraph keeps its layout when a path becomes a link. Enter opens it

Files the turn produced

A model that builds a deck with a script and answers “done, it is at exports/plan.pptx” has attached nothing. At turn end, produced_files attaches such files itself, with the same marker, so the same card appears and a channel uploads them.

StepRule
CandidatesPaths the reply names: markdown link targets (also <…> and %20), code spans and bare tokens; absolute, ~, or relative to the project and then the session workdir; a :12 or #L12 suffix is dropped. Plus files write wrote and image_generate saved
Kept whenA regular file inside sendable_roots, at most 32 MB, modified at or after the turn started (one second of slack); a resumed turn uses its user message's time. Not a file the user sent in (workdir/attachments/, steer-images/): its mtime falls inside the turn too
FormatsOffice and other documents, PDF, images, audio, video, archives; and HTML, Markdown, CSV, TSV, SVG and notebooks unless the edit tools changed them, since the edit card already shows those with their diff. The rule is the same for every candidate, whether the reply named it or write or image_generate saved it, so the script that built a deck stays out. Source code and logs never, nor .key, which is also a private key's extension
LimitsAt most 64 candidates looked at with stat only, at most 8 attached, each once, after the send_file files. Any failure attaches nothing and never reaches the turn
WhereOnly where send_file exists (not cli or tui) and for a speaker with fs.read

The modification time is the guard: a file the model only read or mentioned is older than the turn and stays put.

The base guide asks the model to name each file it produced as a markdown link to its absolute path and to attach deliverables with send_file; the send_file description says it is for any file the user should see, office files a script made included.

resolve_within resolves symlinks before testing containment, so a link to ~/.ssh fails. Every session is auto-bound to the default project, so only non-default bindings count as a project. Channels are globbed down to the attachments leaf because credentials.json is a sibling.

A chat with no project

Such a chat works in the default project's folder, often the home directory, so a deck it builds lands there. That folder is a root only as a WorkdirRoot, for a conversation that exists and has no real project. A folder that is the filesystem root is never one, or the whole disk would be a root. The rules:

SurfaceRule
Preview, path links, file cards, reveal (readable_roots)Allowed for that chat's own requests. These are local to the owner's App
send_file and turn-end attach (sendable_roots)Allowed while the conversation does not deliver to a chat platform. An owner chat bound to one (its meta names a channel), or one that arrived from a platform contact (its meta names a peer_id, kept after unbinding since the contact's next message returns there), keeps the narrow roots: the tool refuses a home file, and the turn-end check refuses it again, so nothing from home is uploaded to WeChat or Telegram
Always refused under that folderAny path through a dot-folder or dot-file (~/.ssh, ~/.aws, ~/.openprogram*, .env); any path through a folder named Library or AppData, where macOS and Windows keep keychains, browser profiles and cookies; key and keystore files (.key, .pem, .p12, .kdbx and similar); names such as id_ed25519, credentials.json, token; and the state directory, whose conversation folders are roots of their own. Uploads and steer images stay out of turn-end attach as before
ChoiceWhy
Not a plain rootThe folder may be $HOME, and send_file can reach a chat platform
Not left outA chat with no project could neither send, link nor open what it built. Claude Code desktop, Codex, Hermes, MiniMax Code and KimiCode all open files the turn wrote from the reply, wherever the working directory is
No per-file journalFiles the turn's tools wrote outside every root are not opened: the working folder covers where they land, and a journal would be a second rule
RouteContract
GET /files/rawProject and relative path for the file panel and center tabs. Always refuses absolute paths; keep this invariant
GET /api/file-rawAbsolute path against readable_roots; nosniff, CSP sandbox, PDF exempted from it for the browser viewer
GET /api/file-readText. A relative path under a root, or an absolute path against readable_roots
GET /api/archive-listEntries from the zip central directory or tar headers, at most 5000, flagged when cut
GET /api/archive-memberOne member up to 32 MB with /api/file-raw's headers. The name is only looked up in the archive index, so ../ reaches nothing
POST /api/file-revealSelects the path in the worker's file manager after the same check. Never opens or runs it; opening in the default app is the desktop app's, which checks the file itself (File menu)
GET /api/file-pathsMany path parameters, at most 64; each mapped to the absolute file it names inside readable_roots or null, without saying whether it was missing, a folder or outside. Relative paths are joined to the chat's working directory. stat only
On the event loop/api/file-paths, /api/file-search and /api/file-resolve find the chat's working directory under its conversation lock, and the search walks folders. That lookup runs in a worker thread in that conversation's lane, so a turn holding the conversation delays only these requests, never the Worker. The search's folder walk runs in a plain worker thread after it, outside the lane, so an @-mention typed while a large folder is walked never queues a Send or Stop of the same chat

Both archive routes take an absolute path or a project id and relative path. FileViewer has one abs switch, so image, PDF, Markdown, line-numbered code and download-card rendering stay in one implementation.

Target design

Any file, from any source, opens through the same viewer in every interface. User and agent files differ only in their source field.

CapabilitySolvesTodayWhy deferred
One attachment record (id, SHA-256, name, MIME, location, count, source, session, message); text holds only [attachment:<id>]Rename, dedup and cross-session references become queriesA text marker holds everythingNeeds a schema change and history migration; wait for cross-session references
One parser, every interface, including inline terminal images (iTerm2, kitty; file card elsewhere)One rendering decision per resourceTrue on the web. The TUI has no attachment concept and cannot paste imagesIndependent of the web. Peers show the practical gain is modest
Full symmetryOne data model and UI for user and agent filesGrammar, parser, chips and viewer are shared; only fallbacks differPartly done; all four platforms upload
Output as a live pageWatch a document developcanvas writes Markdown blocks with ids; no panel renders themWire format settled. The most valuable next addition; three peers built it

Excluded: global content-addressed blob storage. Each session workdir is committed every turn and stays replayable, so large binaries staying in git history is the accepted cost.

Delivering produced files: peers and choices

Among the 21 harnesses on frontierharness.org/live, none of the strong ones relies on the model remembering to attach every file. They layer a host step, actionable paths in the reply, and a prompt line, with the send tool as a backup.

PeerWhat it does
Claude Code desktop, CoworkPresents files Write and Edit produced by itself; SendUserFile is for files a script made. A setting opens HTML, images, PDF and video it writes
hermes Deliverable ModeScans the reply for absolute or ~ paths ending in .pptx, .docx, .xlsx or .pdf and uploads them; its docs admit the agent does not reach for files by default
Codex app, MiniMax CodeOpens a generated file after the task; lists files generated or referenced as results
Codex, Antigravity promptsAsk the model to write file paths as clickable links and never to say a report is ready without its link
ChoiceWhy
Attach at turn end, not only through the toolClaude Code desktop's split. Office files and PDFs come from scripts, which no edit journal records, and a model whose attachment was refused stops trying
Require a modification during the turnhermes' scan has no such test, so naming an input file sends it back. The time test is one stat and separates a result from a mention
Accept relative paths and linksModels write exports/plan.pptx and markdown links more often than bare absolute paths, which are all hermes reads
Same roots as send_fileThe host step must not reach further than the tool. A file outside the roots is still opened from the link in the reply
fs.read, not replyAttaching is replying, but it shows a file's bytes. reply would let a paired speaker, who may not read the owner's files, have them sent

Other techniques

  • Output as a page: openclaw serves canvas documents embedded with [embed ref=…]; Codex materialises ::codex-inline-vis{ in a sandboxed viewer (2 MB, strict CSP); pi-mono's /share publishes a session as a private gist.
  • Signed tokens: openclaw's mediaTicket, v1.<payload>.<signature>, five-minute TTL.
  • Chips as editing units: claude-code sends an image only while its [Image #N] stays in the text.
  • Hermes rewrites host cache paths to container paths. Codex has view_image.
