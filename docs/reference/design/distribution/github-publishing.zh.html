发布源码到 GitHub

GitHub 只承载 main。它的历史永不和 dev 合并，也没有东西把 GitHub 的 main 拉回来。本机的稳定版 App 就是发布出去的 Release，和每个用户拿到的是同一个构建。

分支

线作用
dev接收每个提交，来自主 checkout 或 worktree。开发版（/Applications/OpenProgram Dev.app，端口 18200，~/.openprogram-dev）运行它，提交后由 openprogram dev deploy 或 scripts/local-instances/refresh-dev-instance.sh 更新
mainGitHub 承载的线，有自己的历史。只有 scripts/publishing/publish-github.sh 往上加：一次同步一个提交，内容是接在上一个 main 提交之后的 dev 文件树

worktree 分支合入 dev 后删除，放弃时也删除。想留着的放到 refs/archive/，任何命令都不会把它列为分支，也不会推送。

每天同步，偶尔发布

步骤发生什么
同步publish-github.sh -m "summary"大约每天一次，dev 有新提交时。GitHub 拿到当天的源码，不运行任何工作流
发布publish-github.sh -m "summary" --tag vX.Y.Z版本准备好时。先推同步，再推标签，标签启动 Release 工作流

推送 main 不启动任何东西，所以每天同步不花 Actions 时间：

工作流何时启动
release.yml推送 v* 标签时，或手动给出 tag；rehearse 构建并检查全部内容但不发布
ci.yml、docs-pages.yml、contributors-readme.yml、linux-release-smoke.yml、windows-install-smoke.yml只能手动（workflow_dispatch）

本机的稳定版 App

/Applications/OpenProgram.app（端口 18100，数据在 ~/.openprogram）就是官方 Release：从它的 DMG 安装一次，之后只由 App 自己的更新程序更新：后台下载下一个 Release，显示 New，点 Restart to update 换上。

本机没有任何东西构建或安装它，所以所有者当稳定版用的，正是用户下载的那一个。

同步

scripts/publishing/publish-github.sh -m "Sidebar run status, Launchpad, Agent cards" --dry-run
scripts/publishing/publish-github.sh -m "Sidebar run status, Launchpad, Agent cards"
python scripts/release/release-version.py set 1.3.0
scripts/publishing/publish-github.sh -m "Office editor" --tag v1.3.0 --office-archive /path/to/OfficeAssets-….zip --dry-run
scripts/publishing/publish-github.sh -m "Office editor" --tag v1.3.0 --office-archive /path/to/OfficeAssets-….zip
参数作用
-m "summary"这次同步带来什么；来源和 main 不同时必填
--source <ref>改为压缩 dev 上的另一个提交；默认 dev
--dry-run显示提交说明和检查结果，不做改动
--no-push第 7 步后停止
--tag vX.Y.Z第 9 步；不能和 --no-push 同时使用
--office-archive <file>配合 --tag：本地的 Office 归档，按固定值校验；GitHub 上没有时放到这个 tag 的草稿 release 上
  1. 把 hook 装进共享的 .git/hooks，每个 worktree 都有。
  2. 拒绝不在 dev 上的来源。main 已是该来源的文件树时没有要同步的，直接到第 8 步。
  3. 来源的文件树或摘要提到停用账号时拒绝，并列出每处 path:line。每次调用都检查，dry run 也一样。
  4. 扫描新增行中看起来真实的凭据（GitHub token、Anthropic API key、AWS access key、私钥块），命中就拒绝。AWS 文档里的示例 key 和测试里的单行 PEM 字符串不算。
  5. 在来源提交的临时检出上跑 scripts.docs_site.check --all，失败就拒绝。
  6. 写提交说明：摘要、距上一次同步的本地提交数、Local-Source: trailer。
  7. 用 git commit-tree 创建提交：来源的文件树，上一个 main 提交是唯一父提交（第一次同步没有），作者和提交者都是发布身份。移动 main，把来源记入 refs/publish/last，下一次同步从这里开始计数。
  8. 确认 GitHub 的 main 是本地 main 的更早位置后推送 main，所以只会 fast-forward。要上传的提交里有任何一个的作者或提交者不是发布身份，或提交说明提到停用账号时，拒绝推送。
  9. 给推上去的提交打标签并推送标签。在移动任何东西之前，带标签的运行拒绝：
    • 已经存在的标签；
    • 任何一处版本位置写着别的版本的源提交，逐处列出；
    • 缺少 .github/release-notes/vX.Y.Z.md（开头必须是 # OpenProgram X.Y.Z Release Notes）的源提交；
    • 用 --office-archive 给出、却不是固定 Office 归档的文件；
    • 真正运行时，最新 release 和这个 tag 的草稿都没有归档（用 gh 询问）且没有给文件。给了文件就改为 seed 草稿。
    --dry-run 离线运行这些检查，只跳过询问 GitHub 那一步，说明有没有给本地归档、是否一致，并显示标签。

其他拒绝情况
条件结果

发布身份

仓库是 Fzkuji/OpenProgram，项目最初的仓库：main 上先是到 0.9.8 为止的历史，之后从 1.0.0 起是压缩提交。

每个同步提交署名 FuzzyKuji，9404270+FuzzyKuji@users.noreply.github.com，也就是上传它的账号，GitHub 上新提交不再带主账号的邮箱；不论检出用什么身份提交，脚本都写这个署名，并拒绝上传含有其他署名的同步。只检查 GitHub 还没有的那一段 main，因为更早的历史有很多作者。

上传本身走协作者账号 FuzzyKuji，不管 gh 当前切到哪个账号：脚本从 gh 取这个账号的令牌，并让 git 向 gh 要凭据，主账号的令牌不会用来上传。没有登录 FuzzyKuji 时，脚本在动任何东西之前就拒绝。

1.0.0 到 1.3.0 是在 FuzzyKuji/OpenProgram 构建的，安装包留在那里，它们的发布说明也链接到那里。从 1.4.0 起，版本在 Fzkuji/OpenProgram 构建：

  • 下载链接、安装脚本和 App 的更新检查都从它读取，和源码链接一致。
  • 1.3.0 及更早的 App 检查的是构建它的那个仓库，所以要手动覆盖安装一次 1.4.0 或更新的版本。
  • pyproject.toml、apps/desktop/package.json 的作者和 README 的许可证一行保留 1.x 版本发布时的名字。

网站

落地页和文档由 docs-pages 工作流发布为 Fzkuji/OpenProgram 自己的 GitHub Pages 站点，地址 https://fzkuji.github.io/OpenProgram/，文档在 docs/ 下。放在另一个账号下的独立站点仓库会随那个账号一起失效，所以站点和代码放在一起。地址只有一处设置：openprogram/operations/project_site.py 里的 SITE_URL。

要点决定
不用 openprogram.ioGitHub 不肯把这个域名接到站点仓库：一个已停用的 Pages 站点仍占着它。这个域名的每个路径都返回 GitHub 的 404，所以不再有任何地方链接它
在代码里推导canonical 和语言链接、sitemap、Markdown 副本、llms.txt、robots.txt、社交卡片地址、IndexNow 的主机和密钥、更新源及其主机。docs/_static_root 里的文件写 {{SITE_URL}}；只有自定义域名时构建才写 CNAME
挂载路径构建写出的链接以 OPENPROGRAM_DOCS_BASE 开头：worker 里是 /docs/，工作流里是 project_site.DOCS_PATH。它们保持从根开始的绝对路径，因为站点脚本换页时保留侧栏、按路径匹配。放在站点根的文件（如 favicon.ico）通过这个路径的上一级链接，所以在地址自带的路径下也能找到
相对链接文档页之间手写的链接，包括指向 ../latest.html?<name> 的最新版下载链接，以及落地页上的所有链接。latest.js 只读 GitHub 和页面自己的查询串
写明地址README、发行说明、安装脚本、落地页的 canonical 和社交地址、桌面 App 的更新源。tests/unit/config/test_site_address.py 在任何受跟踪文件写了别的网站地址时失败，文档页之间用了绝对链接时也失败
运行时读取站点根下的 install、install.ps1 和 install.cmd；update-source.json，可选，只在 GitHub 失败时读

一次发布构建什么

Release 工作流由推送的标签触发。每个平台分支彼此独立。

标签不会移动，所以发版前可以先演练。不带 --tag 发布 main，再运行 gh workflow run release.yml -f tag=vX.Y.Z -f rehearse=true：每个分支都从 main 构建，跑同样的检查，什么都不发布。

gh workflow run windows-install-smoke.yml -f tag=vX.Y.Z -f run_id=<演练运行> 在 Windows runner 上安装那次运行的 Windows 文件。有分支失败就修根因，再演练一次。

两者都通过后，scripts/publishing/publish-github.sh --source refs/publish/last --tag vX.Y.Z 给同一个提交打标签，最早在演练通过 12 小时之后。不带 --source 时，这期间 dev 上的新提交会作为一次没演练过的新同步上传。

项目行为
失败的分支只缺自己的文件；发布任务上传成功的部分
薄 App 缺更新文件该平台的更新文件没构建出来时，Windows 或 Linux App 分支在构建前先报错，但仍然构建并检查 App，同一次运行就能看到其他问题；发布时去掉这个 App 并写明原因
Windows 检查App 分支：先跑 scripts/release/windows-contracts.txt 里的平台契约测试，再用安装包安装、启动到 worker 健康、做一次工具调用、卸载并保留数据。契约测试失败不会拦住构建和安装检查，由上传前的一步把这个 App 去掉。运行时分支：安装好的命令做一次工具调用。失败只缺这一个包。Windows 分支失败时把日志存为 diagnostics-windows-* 工件，不会发布
release-manifest.json只列实际存在的文件
发布说明多出 “Not in this release” 一节，写明缺什么、为什么缺
计划内的包缺失发行版公开之后，发布任务失败并逐个列出，运行结果不会看起来完整
拒绝发布只有 wheel 或 Office 归档缺失，或者 macOS 和 Linux 的命令行运行时一个都没有时

证书只决定安装包的形式，不决定它有没有。

Office 归档

可选的 Office 编辑器从一个 zip 安装，约 699 MiB，文件名、大小和 SHA-256 固定在 openprogram/programs/applications/office_editor/install.py；safe_http.py 里 office.assets 的下载上限就是这个大小。从 1.3.0 起每个版本上传一份；1.0.0 到 1.2.0 都没有。

要点行为
App 去哪里找先找自己版本的 release，再找 releases/latest/download/；后者给没有自己 release 的构建用，前提是固定值没变。两处的文件都按固定的大小和 SHA-256 校验
为什么不只放最新版本最新版本上的固定文件名，会在某个版本换掉资源包那天让所有已安装版本装不上；每个 release 各带一份，只要那个 release 在，那个版本就能装
没有任何 release 带它安装返回 office_release_missing：1.3.0 之前的版本提示更新到 1.3.0 或更高，其他版本提示更新到最新版。不把重试当作解决办法
发布时从哪里拿CI 里重建不了：有授权的字体和固定的编辑器构建是所有者手里的输入（Office README）。office 任务下载最新已发布版本的那一份，没有就取这个 tag 草稿 release 上的那一份，并校验字节
第一个带它的版本publish-github.sh --tag vX.Y.Z --office-archive /path/to/OfficeAssets-….zip 校验文件，在移动任何东西之前把它放到这个 tag 的草稿 release 上（office-archive.py seed）。之后每个版本都沿用上一个版本的那份，不用手动上传
两处都没有office 任务失败，写出文件名、大小、SHA-256 和 seed 命令。所有构建都等它，所以什么都不会构建或发布
发布之后对公开 latest release 的检查也要求归档恰好一份
新的资源包必须换文件名，不能在旧名字下放新字节，因为已安装版本按名字固定了字节。office-archive.py pack 把它命名为 OfficeAssets-<editor>-<patch>-<pack>.zip，最后一段取自资源包自己的清单摘要，字节不同名字一定不同

重建归档

在所有者的机器上、dev 检出里进行。同一个准备好的资源包，pack 每次做出同样的 zip。已安装的那份就是准备好的资源包：~/.openprogram/cache/office/<source>-<patch>/versions/<manifest> 能通过 office_editor/assets.py 里固定值的校验时，把它拷出来直接做 pack 这一步，不构建也不下载。

  1. 准备 Office README 列出的输入：agentbridges-ai/onlyoffice-browser 在 d15d12b6945be4d8b0f3aa1806120e740d2950ee（包版本 0.3.34）的 git 检出；有授权的字体输入，以及用 font-generation.mjs 和 Document Server 9.3.0 生成器从它生成的字体包，其清单摘要必须等于 office_editor/assets.py 里的 OFFICE_FONT_MANIFEST_DIGEST；npm ci 需要能访问 npm registry。
  2. 把 office_editor/assets.py 里的 OFFICE_LOCK_SHA256 设为 scripts/release/office/package-lock.json 的 SHA-256，也就是 prepare.py 构建用的审核过的 lock；资源包最后一步校验拒绝其他 lock。
  3. python scripts/release/office/prepare.py --source … --font-pack … --font-input … --output /path/to/prepared-office
  4. python scripts/release/office-archive.py pack /path/to/prepared-office /path/to/out 写出 zip，并把文件名、大小和 SHA-256 写进 install.py，把下载上限写进 safe_http.py。
  5. 跑受影响的测试，在 dev 上提交并部署。
  6. scripts/publishing/publish-github.sh -m "…" --tag vX.Y.Z --office-archive /path/to/out/OfficeAssets-….zip --dry-run，再去掉 --dry-run 运行一次。

Hook

Hook拒绝放行
scripts/git-hooks/pre-push没有 OPENPROGRAM_GITHUB_PUBLISH=1（脚本设置）或发送的不是本地 main 的 refs/heads/main 推送；任何其他分支的推送，那会上传工作历史；不是脚本推送或不指向本地 main 的标签，因为推送标签会启动 Release 工作流删除远端分支或标签
