Mobile app

A phone uses OpenProgram through an app from the store, not a browser tab. The app carries the whole UI, so opening it reads nothing over the network but data; it pairs with a computer once and stays signed in. Conversations, files and accounts stay on the computer, as in remote web access.

  1. Computer: Add deviceA one-time QR code with every address of this computer
  2. App: scanRedeems the code for a device credential, kept in the Keychain
  3. App: openUI from the app, data from the first address that answers

Why an app, and why this shape

Opening the web UI through Tailscale Funnel took 10 to 20 seconds on a phone: about fifty requests at 0.7 to 1 second each, the UI's own files included, before the conversation list arrived. Every peer that is fast on a phone ships its UI on the phone and sends only data.

The app reuses the web UI instead of a second UI written for the phone (Paseo's way): one UI to keep, and the phone gets every feature the computer has. It is restyled for the phone (layout) rather than shown as the website.

The shell

apps/mobile/ios is a SwiftUI app around one WKWebView. It does not use Capacitor or Cordova: what it needs is one scheme handler and a few native calls, and a framework would sit in the way of the one part that matters, the request path.

PartHow
UI filesThe static export of apps/web (output: "export") is copied into the app at build time and served at openprogram://app/ by a WKURLSchemeHandler. Nothing of the UI crosses the network.
HTTP to the computerThe same handler takes /api/, /hooks/ and the other server paths and forwards them through one shared URLSession, so requests reuse its connections instead of paying a TLS handshake each, to the current address, adding Authorization: Bearer opd1.… and no Origin. Responses stream back chunk by chunk, so server-sent events work. To the page every request is same-origin: images, file previews and downloads need no change.
WebSocketA custom scheme cannot carry WebSockets, so the page opens wss://<address>/ws itself. The app tells the page where (window.openprogramMobile.socket), and the credential goes in the handshake as a subprotocol, APP_BEARER_PREFIX followed by the credential, next to APP_SUBPROTOCOL (both in openprogram/interfaces/server/owner_auth.py), because a browser WebSocket cannot set headers. The server accepts this only from the app's origin openprogram://app, answers with APP_SUBPROTOCOL, and never echoes the credential.
CredentialThe device credential of paired devices, unchanged: redeemed once, revoked from Settings → Devices, forgotten after 30 idle days. Kept in the Keychain, readable only after the first unlock.
Native callsScan a code (VisionKit), list, add, choose and forget computers, and haptics. The page calls them through one WKScriptMessageHandler; the app hands the page the paired computers (window.openprogramMobile.computers) for its picker, which asks the app to switch (selectComputer) or pair another (addComputer).

Pairing and addresses

  • The first screen is one action: scan the code from Settings → Devices → Add device on the computer, or paste its link with the system paste button, which asks no permission.
  • The app redeems the code with POST /api/auth/pair and no Origin, which returns {"device_id","token"} instead of a cookie.
  • The link names every open address of the computer (Same Wi-Fi, Anywhere). The app keeps them all, asks every one /api/auth/session at once and uses the first that answers; a local answer within 300ms of a remote one still wins.
  • It starts from the address that answered last time and asks again when the network changes or the app comes back. A 401 means revoked only when no address answered. Nobody picks an address.
  • An address change keeps the page: requests read the current address, and the page is told the new socket address (openprogram-mobile-address). Coming back from the background, a socket that does not answer a ping within 2s is replaced at once.
  • The page keeps the last chat list per computer and shows it at start, before the socket is up (lib/mobile/session-list-cache.ts); until the first paint the view shows the page's own background, not white.
  • A request that fails on the network is retried on the next address and never shown as a sign-in problem. Only a 401 from a reachable computer means the device was revoked; the app then returns to the scan screen for that computer.

Layout

The app's screens are a phone app of their own, built inside the web UI from its data and renderers (phone app): Projects first, then a project's chats, with a docked new-chat field; a conversation with Back and ⓘ, one sheet for the turn's settings from the composer, and a details page for changes, files, activity, resources and the chat's actions. A swipe from the left edge goes one page back.

The first version restyled the desktop's three columns as two drawers around the chat; it still read as a computer on a phone and was replaced.
