Distribution architecture · stable channel

正式版本自动更新

OpenProgram 只把完整、稳定、经过 manifest 验证的 GitHub Release 视为可安装更新。Desktop 自动发现并校验平台 installer：macOS 使用 DMG，Windows 使用带 Authenticode 签名的 EXE；managed CLI/server 验证完整 runtime 后原子切换。仓库出现新提交不构成用户更新。

Question

如何让正式安装发现和应用新版本，同时不跟踪 main、不降级产品功能，并保证失败时保留可用版本？

Audience

维护 Release、Desktop、CLI/server、设置页和安装文档的开发者与发布人员。

Scope

macOS/Windows Desktop，macOS/Linux/Windows managed CLI/server，以及 source checkout 的明确分流。

Exclusions

Windows 沙箱、macOS 签名、Linux Desktop、PyPI 产品安装、后台替换运行中的应用。

01

必须保持的产品合同

平台动作不同，但版本来源、完整产品定义和验证结果必须一致。

Release unit

更新单位是完整产品

不单独更新 wheel、Web、Program、OCR、Browser 或模型。每个受支持产物都满足统一 capability manifest，并包含固定 CPython。

Desktop

自动检查，校验后打开 installer

主进程选择当前平台与架构的 DMG 或 EXE，验证 bytes 与 SHA-256；Windows 再验证 Authenticode。renderer 不能提供 URL、hash 或文件名。

CLI / server

显式命令，原子切换 runtime

openprogram upgrade 验证 Release、runtime、capabilities 和 cold start，最后替换 current；不自动重启现有 worker。

Development

源码安装保留 Git 流程

source checkout 继续使用显式 ref、preflight、build 与 probe，不把开发分支伪装成 stable Release。

02

从 GitHub Release 到平台动作

两条用户路径在严格验证后分开。任何缺失、重复或不一致都在进入下载或安装前停止。

1 · GitHub latest
只接受 non-draft、non-prerelease、vX.Y.Z。
2 · Release + manifest gate
验证唯一资产、版本、bytes、SHA-256 和平台架构。
3A · Desktop
校验平台 installer；Windows 额外验证 Authenticode；随后由用户确认安装。
3B · managed CLI
验证完整 runtime 与 cold start，最后原子切换 current。
metadata / Desktop完整 runtime 安装信任边界

renderer 从未获得资产 URL、文件名或 hash；CLI 子进程只继承安装所需的最小环境变量。

03

Desktop 与 CLI 的完成边界

“检查”“下载”“安装”分别对应可验证的动作。两个平台不使用同一套替换机制。

macOS Desktop

自动发现 + 完整下载 + 明确安装交接

  1. 启动调度packaged app 启动 30 秒后首次检查；开发模式不自动检查。
  2. 严格选择仅匹配当前 process.arch 的完整 unsigned DMG。
  3. 安全保存用户选择目标；随机 exclusive 临时文件；流式 size/hash 验证。
  4. 打开安装介质校验成功后打开 DMG。应用不后台替换运行中的 .app。

Windows Desktop

自动发现 + 完整下载 + 签名验证 + 明确安装交接

  1. 启动调度packaged app 启动后自动检查；开发模式不自动检查。
  2. 严格选择只接受精确命名的 OpenProgram-<version>-win-x64.exe。
  3. 双重校验流式验证 size/SHA-256，落盘后要求 Authenticode 状态为 Valid。
  4. 打开 installer校验成功后打开按用户安装的 NSIS 向导，不静默替换运行中的应用。

macOS / Linux CLI & server

显式执行 + 完整 runtime 验证 + 原子激活

  1. 检查openprogram upgrade --check 只读报告当前与最新版本。
  2. 版本化 installer从已验证的不可变 tag 读取脚本，并固定 repository/version。
  3. 隔离验收checksum、capability manifest、version probe、worker cold start 全部成功。
  4. 激活准备 launcher 后以 os.replace 切换 current；用户显式重启 worker。

05

调度、持久化与恢复

自动检查只影响发现，不触发无人值守安装。手动检查始终强制刷新。

启动 + 30spackaged app 首次调度；已有缓存时先计算 due time。
检查成功 + 24hlastSuccessAt 决定下一次自动检查。
检查失败 + 6hlastAttemptAt 提供失败退避，不连续访问 GitHub。
resume / 设置变化清除旧 timer，最多立即检查一次，然后重新排程。
Persisted schema 1

update-state.json

保存 automaticChecks、lastAttemptAt、lastSuccessAt 和最近一次经过验证的 release metadata；使用临时文件加 rename。POSIX 可指定文件 mode，Windows 沿用当前用户目录 ACL。

Repair

损坏状态不能控制调度

无效 JSON、未知 schema、未来时间、版本/架构不匹配和缺失 release 都被归一化并重写。写入失败时不提交隐藏的内存设置变化。

06

信任边界

验证发生在获得权限的进程中；低权限界面只接收用于展示的投影状态。

Remote metadata

GitHub 响应默认不可信

HTTPS、固定 host、最多 5 次重定向、逐跳验证、大小与 body idle timeout；再次要求 draft === false 和 prerelease === false。

  • tag 必须是 vX.Y.Z
  • asset name 与 manifest basename 唯一
  • GitHub size 与 manifest bytes 一致
Renderer IPC

renderer 不能选择远端目标

preload 只暴露 getState、check、布尔设置、download、openRelease 和状态订阅。

  • 不接受 URL、path、hash、repository 或命令
  • 公开状态剥离 asset name/URL/SHA-256
  • 窗口关闭不能中止检查或下载
Downloaded files

完成校验前不激活

Desktop 使用随机 exclusive 临时文件并处理 short write；Windows 沿用目录 ACL 并额外验证 Authenticode。CLI 在新版本目录验证完整 runtime 后才替换 current。

  • 大小/hash/签名不符立即删除临时文件
  • archive path traversal 被拒绝
  • launcher 准备失败保留旧 current
Child process

版本化 installer 使用最小环境

managed upgrade 固定 repository 和目标 version，只传 PATH/HOME/temp/locale/proxy/XDG/OpenProgram state 等允许项。

  • 不继承 provider/API 凭据
  • 不继承 archive/checksum source override
  • --json 始终输出单一 JSON 文档
07

失败语义

每个错误都说明停止位置和保留内容，不用模糊的“更新失败”代替事务边界。

离线、超时、GitHub 限流
自动检查记录错误并按 6 小时退避；手动检查显示可重试错误。
应用和当前版本继续运行
Release / manifest 无效
拒绝响应，不下载；不回退 wheel、source archive、其他架构或旧版本。
最近一次有效 metadata 可保留
Installer body stall / size / hash / Windows 签名错误
中止 response，关闭文件，删除随机临时文件，恢复可重试动作。
未校验文件绝不打开
CLI archive / cold start / launcher 失败
installer 非零退出；不执行最后的 current 替换。
旧 runtime 仍为 current
切换成功但 worker 仍运行旧版本
命令明确报告 active runtime 已更新，并打印显式 restart 指令。
运行中请求不被隐式中断
08

安装类型决定更新路径

安装检测只回答当前运行方式，不创造功能不同的产品版本。

managed_release
→
正式 GitHub ReleaseDesktop bridge 或 complete runtime installer；immutable marker 优先。
source_checkout
→
显式 Git ref pipelinepreflight、checkout、依赖/构建、probe，必要时按开发合同重启。
unknown
→
稳定错误不猜测 PyPI、binary 或 Git 路径；提示使用正式 installer 或源码 checkout。

pip_wheel 不属于正式产品安装类型。开发者 wheel 可以作为构建输入，但不提供功能不完整的普通用户版本。

09

参考实现与采用方式

参考用于确定平台限制和状态模型；最终方案服从 OpenProgram 的 unsigned Desktop 与完整 runtime 合同。

采用

GitHub Releases API

latest stable metadata、Release Notes 和 assets。客户端仍对 stable 字段、tag、唯一资产和 manifest 做独立验证。

修改采用

Electron update lifecycle

采用 check / available / download / error 状态模型；Desktop 完成边界为校验后打开平台 installer，不调用自动替换。

当前不采用

Electron autoUpdater

macOS 原生自动安装要求签名，Electron 不提供 Linux 内置 updater；与当前产物和平台合同不匹配。

不新增依赖

electron-updater

现有 Release manifest、Node/Electron API、Python 和 shell 已覆盖本阶段；新增包不能改变当前 Desktop 安装边界。

Release-visible acceptance

v0.7.0 stable Release

v0.7.0 已以 non-draft、non-prerelease 发布；四平台 runtime、四个 CLI installer、两种 macOS Desktop、manifest、checksums 与 latest endpoint 门禁全部通过。

Installed-client acceptance

真实客户端更新交互

尚未操作当前用户窗口验证版本发现、平台 installer 打开、长时间运行与 sleep/resume 排程；这些交互不由发布资产 smoke 代替。Windows 还必须在正式 release runner 使用真实证书通过 Authenticode gate。

Compatibility acceptance

v0.6.6 及更早版本的一次性过渡

Desktop 需要手动安装首个含 updater 的 v0.7.0 DMG；CLI/server 重新运行一次公开 installer。安装 v0.7.0 后，后续版本才使用更新 UI 和 managed upgrade 命令。

发布后的明确状态

v0.7.0 是首个包含 updater 的正式 GitHub Release，完整资产、唯一 release-manifest.json、stable 字段与 Release workflow gate 均已验证。v0.6.6 及更早 Desktop 不含该 updater，仍需手动安装 v0.7.0；当前证据不包含前台客户端更新交互。
