Stable and development instances

Stable is the official App from a GitHub Release, changed only by its own updater. Commits go to dev and run on the development instance. A deploy does not restart stable, so a stable conversation can deploy and check http://127.0.0.1:18200.

Deploying to the development instance

openprogram dev deploy [ref] (default dev) checks the commit out into the detached worktree ~/.openprogram-dev/source and runs scripts/local-instances/refresh-dev-instance.sh there. Nothing of stable is stopped or written.

  1. Refuse uncommitted or untracked files. One deploy runs at a time; a second waits.
  2. Sync the Git hooks and report docs findings since the last deploy, without stopping. Build the Web assets and the OpenProgram wheel; a page that breaks the format becomes a visible error page.
  3. The Web export is built only when a tracked file other than Python, the documentation and the tests changed since the last deploy; otherwise the last export is staged again.
  4. Install a full CPython 3.12 into the runtime once (uv python install --install-dir), sync the locked dependency set a release installs, reinstall the wheel.
  5. macOS: build the helper OpenProgram Dev.app (ai.openprogram.runtime.dev) and point runtime-manifest.json at it. The worker gets its own identity, so Screen Recording, Accessibility and similar grants are separate from stable.
  6. Set the dev profile's port and bind the Program catalog.
  7. Install or restart only the dev worker as a login service (launchd or systemd; a plain stop and start elsewhere). Wait up to 300 seconds for /healthz, then record the commit in runtime/source-revision.
  8. macOS: run scripts/local-instances/install-dev-app.sh.

Signing in

The worker mints a new owner token on every start, so a deploy signs out browsers. The development App fetches its new token itself.

CommandResult
openprogram dev openOpens the default browser, signed in; the sign-out message names this command
openprogram dev auth-urlPrints a sign-in link for another browser

From a conversation

In the development instance (the dev profile, with a source repository that has a dev branch), self_update(action="prepare") uses the dev_deploy backend: a change is a commit on dev, and deploying it is the whole update. The call saves the request and starts a detached controller; the rest runs after the calling turn is saved.

StepWhat happensPhase
1Wait for the calling turn to be savedpreparing
2Rebase the candidate onto dev in its worktree, then git merge --ff-only in the primary checkout. A moved dev or a held index.lock retries up to 10 times with backoffbuilding
3openprogram dev deploy <sha>, which restarts the worker the request came from; skipped when the instance already serves the commitbuilding
4System probe against port 18200 and the dev state directory, then a browser probe: open the signed-in Web app until the message box appearsbuilding
5The result reaches the origin conversation through the ordinary delivery and follow-up turn on the restarted workersucceeded

The probe compares the doctor rows with the instance's own before the change, so a row already failing, such as a login development lacks, blocks nothing. The stable App is never waited for or touched.

Ends asWhen
succeededThe development instance serves the landed commit and passes both probes
abortedThe calling turn never ends; a rebase conflict or a dirty file in the way (lists the files); the deploy or a probe fails. A commit that landed stays on dev, and the result says so: the fix is the next commit, made and deployed like any other

In the official App the same call is refused before any request is saved: the App is Developer ID signed and cannot be rebuilt here, so the refusal points to Check for updates in Settings.

Publishing

Neither instance pushes anything. See Publishing source to GitHub.

Source checkout

openprogram dev and the self-update controller find the repository through OPENPROGRAM_SOURCE_REPO, else ~/.openprogram-dev/source-repo, which scripts/local-instances/refresh-dev-instance.sh writes with the main checkout, not the build worktree.
