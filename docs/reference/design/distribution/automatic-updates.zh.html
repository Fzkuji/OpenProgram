自动更新

用户只安装一次，用最新 vX.Y.0 的安装包。之后的每次更新都在 App 内到达：检查到新版本时侧栏标志旁显示 New；点下载更新只下载变了的文件，构建并试运行新版本；点重启以更新就切换过去。

只有 GitHub Release 会到达已安装的 App；main 的每日同步不会。

发布了什么

所有文件都在 Fzkuji/OpenProgram 的一个滚动 GitHub 发行版上，标签 updates：预发布，永不标为 latest，也不匹配 v*。客户端只通过 https://github.com/Fzkuji/OpenProgram/releases/download/updates/<name> 读取，这个地址只在一处定义：official/channel.py 的 UPDATES_URL。

文件内容
channel.json最新的已宣布发行版。已安装的 App 读它
latest.json每次发布，包括每日同步。只在设置 OPENPROGRAM_UPDATE_POINTER=latest 时读取：开发版和测试
pack-<12 hex>.pack对象首尾相接，没有文件头，以自身 sha256 的前缀命名。发布后永不改变
runtime-<platform>-<base>.jsonRelease 工作流构建并连同包一起上传的运行时层，等待引用它的那次发布
shell-<platform>-<version>.jsonApp 外壳层的同类文件，由所属 vX.Y.0 的 Release 工作流上传
指针字段

指针文件是 {"signed": "<pointer JSON>", "signature": "<hex>"}。签名的文本里有 schema（2）、pointer（channel 或 latest，一个不能冒充另一个）、sequence、published_at、version（三段或四段）、announce、build（提交，12 位十六进制）、notes、commit、shell_compat、layers（{name: {manifest, pack, offset, length}}；外壳层另有 App 的 version）和 packs（{name: {bytes, sha256}}）。

channel.json 的 announce 必须为 true。sequence 在两个指针之间统一递增。签名是对签名文本的十六进制 Ed25519 签名，密钥在 RELEASE_PUBLIC_KEYS 中（official/signing.py；update-service.js 里是同一把）。

格式

单位是什么
对象一个文件的字节，以其 sha256 命名，存为独立的 zstd 帧（级别 19）
分片1 MiB 及以上的文件按固定偏移切成 256 KiB 的分片发布，每片是一个对象。重签名的二进制只改文件头和末尾的签名，中间的分片名字不变
包对象一个接一个。一次发布每个变动的层最多写一个包，tree 放在最后；每个对象的位置记在 tree 里
Tree一个目录，Git 的做法，本身也是以 sha256 命名的对象：{"entries": [...]}，每项是文件 {name, mode, size, sha256, at}（分片的文件用 chunks: [[sha256, size, at], ...] 代替 at）、链接 {name, symlink} 或目录 {name, tree, at}。at 是 [pack, offset, length]，tree 自己所在的包写作 ""。代码源文件还带 Git blob id
层格式根 tree 里的 schema 3。客户端遇到别的格式的层，报出层名后拒绝。发布端整个重写代码层，运行时层和外壳层重建之前一律拒绝
层清单根 tree，另外带 schema、layer 和 meta。内容没变的目录沿用原来的 tree，客户端只读通往改动的那几个 tree
层内容元数据
code所有平台共用。提交的全部跟踪文件放在 source/ 下，构建好的 Web、文档和终端界面放在 frontend/ 下提交、Git tree、版本、base id、shell_compat
runtime-<platform>base：Python 和锁定的包、Playwright、Node、Git、uv，以及 bin/ 里的 Tailscale 边车base id、平台
shell-<platform>macOS arm64 和 x86_64、Windows x86_64、Linux x86_64 和 arm64：构建、签名、公证后的 App 原样：OpenProgram.app、安装目录，或作为单个文件的 AppImage，保留权限位和链接平台、App 版本、可执行文件、shell_compat 范围、Python 小版本、空目录
  • 不带扩展属性：macOS 包的签名在 Mach-O 文件、_CodeSignature 和装订的票据里，都是普通文件。客户端校验前会清掉所有扩展属性。
  • deb 继续用安装包：它装在只有 root 能写的 /opt 下。
  • 外壳只随功能版本变化，而功能版本总带着新提交。客户端仍按外壳层本身比较，所以当时不能替换自己、先取了代码的 App，之后也会取到外壳。

base id 是 uv.lock、pyproject 依赖、product-runtime.json 和 apps/tailnet 的 Git tree id 的哈希；提交里没有这个目录时不计入它。

已安装的 App 上

步骤规则
检查启动约 30 秒后一次，之后每小时一次，失败的也一样。update-service.js 读取 channel.json；检查只发现并显示更新。下载更新运行 openprogram upgrade --prepare --json，由它完成其余步骤
指针先对签名文本验签。序号低于已见过的最高值（<runtime>/channel-seen.json）就拒绝，重放的旧指针不能把 App 带回旧代码。指针正好处在替换它的删除和上传之间而缺失时，这次检查当作没有新内容，不提示；下一次每小时检查会读到
Tree读代码层的；本平台运行时层的只在它的 base 在本机是新的时候才读。本机已有的 tree 不再下载。单个 tree 上限 16 MiB。树或文件所在的包不在指针列表里就拒绝：指针列出它各层的文件和树所在的每个包，包括沿用在旧包里的，垃圾回收保留的也正是这些包
App 外壳在能替换自己的 App 上（没被转移、所在文件夹可写、macOS 上有 Developer ID 团队、Linux 上是 AppImage 而不是 deb），本机的外壳层版本比运行中的 App（OPENPROGRAM_SHELL_VERSION）新时读取它，代码已经在本机时也一样
谁来判断App 能不能替换自己只在这里判断：每份 upgrade --json 报告都带 shell_swap，App 记住这个答案，不能替换的 App 每次检查都拿到安装包
需要新外壳的代码只在新 App 里运行。普通的 upgrade 拼好 App 就停下（prepared）；只有 upgrade --prepare 把拼好的外壳当作已安装的来构建和试运行，已安装的外壳容纳不了时也不会切换到保留的更新。新 App 第一次启动时切换过去
无事可做仓库已有发布的提交时为 up_to_date。外壳、启动器和本机的外壳层都容纳不了时为 waiting_for_shell；本平台的运行时还没发布时为 waiting_for_runtime。两者都不改动任何东西
缺什么仓库里没有对应 Git blob 的源文件；运行中版本或 base 里不存在同路径同大小文件的前端和运行时文件，存在的经哈希校验后直接收用；运行中的 App 里不存在同路径同大小文件的外壳文件
分片的文件只下载本机旧版本（同路径，大小不限）在同一偏移处没有的分片。分片在对象库里拼回整个文件，校验整个文件的 sha256，然后删掉分片
下载对每个包的下载地址发 HTTP Range 请求。GitHub 重定向到支持 Range 的 CDN；每个包只跟随一次重定向，每一跳都检查主机。相距不到 64 KiB 的范围合并，每个包最多 32 个请求，6 个并行。中断后从 <runtime>/objects/ 里已保存的对象续传
上限每个响应以该范围的大小为上限；服务器回 206 以外的任何状态就不再请求它，只有连接中断、5xx 和过期的 CDN 地址才重试。每个对象经过以 tree 给出的大小为上限的流解压，不管帧头声称多大，再按 sha256 校验
组装在更新控制器下进行。用运行时层写出 base（文件系统支持写时复制就克隆，否则复制）。缺的 blob 写进 Git，用临时索引重建 tree，必须等于发布的 tree id，再以固定元数据提交到 refs/heads/release；refs/openprogram/official/<github sha> 记下它对应的 GitHub 提交
新 App试运行之前，在 App 旁边的隐藏文件夹 .<App 名>.update/ 里拼出新 App，和 App 在同一个盘，不管数据在哪个盘：重建链接，文件取自对象库，或从运行中的 App 复制并校验哈希，Windows 卸载程序一并带上
它的检查macOS codesign --verify --deep --strict、运行中 App 的团队和版本；Windows 与运行中 App 主体相同的 Authenticode，未签名的 App 要求 NotSigned；Linux 是可执行的 ELF 文件。之后移到那里的 staged/，记入 <runtime>/shell/staged.json；失败不改动任何东西
链接按 tree 解析，指向 tree 之外的一律拒绝，只写一层的一部分时也一样
构建用这个提交和预构建的前端构建版本，不跑 Web 构建。version.json 记录 official: {commit, sequence, code_layer}
收尾重放、试运行、保留或切换、回滚，见下文。成功后清理当前各层不再用到的对象；外壳的文件不留作对象，只留它的 tree
带新外壳重启重启以更新会退出 App；一个脱离的脚本（sh，Windows 上是 PowerShell）等 App 退出，在同一个盘上用两次改名换上新 App（第二次失败就撤回第一次），再打开它。只有换成功后，各自单独 try，Windows 上把卸载项的 DisplayVersion（HKCU，按 InstallLocation）改成新版本。调换后留下写着更新键的 shell/activate；新 App 启动时切换到准备好的版本

openprogram upgrade --from DIR 从本地副本读取同样的文件（channel.json 和包）。upgrade --check --json 报告 published_days_ago，仅供参考；文本输出在指针超过 60 天时加一句说明。

重放、试运行与切换

从版本库运行的安装把所有者自己的提交带到每个新的官方提交上。

项目规则
官方线每接受一次更新，在 refs/heads/release 上加一个本地提交。不需要 GitHub 的历史：只需要新的官方提交，以及 local 上它不包含的提交
重放所有者的提交是 release..local。从旧到新在 work/official-<release> 里 cherry-pick。冲突的提交存到 unreplayable/<release>/，其余继续。release 已包含的提交跳过。候选基于官方版本构建，没动过的 Web 包直接克隆
失败构建或试运行失败时保存最新的提交并尝试其余的，最多重试 5 次，然后直接试未修改的官方版本。磁盘不足不丢弃提交。切换失败不重试
先准备，重启时切换App 的下载更新运行 openprogram upgrade --prepare --json。它下载、构建并试运行候选版本，然后停在 ready，标记为 held 并记下目标，App 于是显示重启以更新，什么都不切换。检查从不下载，下载由用户发起。worker 启动、看门狗和队列都不会推进被保留的更新
被保留的更新对同一目标再次准备什么都不做；更新的目标会先取消保留的那个。下一次 upgrade --json 在保留的更新仍是应安装的版本时（离线也一样）切换到它（结果 activated）；如果 local 在这之后移动过，就取消它，按常规方式安装。任何需要更新槽的其他更新（包括 self_update 工具）都会先取消它。upgrade --check --json 在 prepared 下列出它

发布

代码不经过 GitHub Actions。scripts/publishing/publish-github.sh 把 dev 压成一个提交同步到 main（GitHub 发布），再运行 scripts/release/publish-updates.py run。

  1. 读取通过下载地址读取线上的指针
  2. 构建在本机构建代码层。前端在发布端自己的版本库里构建，没变就复用
  3. 打包新对象写成一个包。RUNTIME_PLATFORMS 里的每个平台（macOS arm64 和 x86_64、Linux x86_64 和 arm64、Windows x86_64）都需要代码 base id 对应的运行时层：线上已有的、Release 工作流上传的，或本机构建的

    缺任何一个平台：拒绝，什么都不发布。拒绝信息列出缺的平台和 gh workflow run release.yml -R Fzkuji/OpenProgram --ref main -f runtime_layers_only=true

  4. 上传先上传新包，再对每个指针删一次、传一次。指针自带签名，读者看到的是旧的、没有、或新的。发行版上丢失的指针由发布端从本地历史补回
命令作用
publish-updates.py plan说明发布某个提交会做什么；被拒绝时退出码为 3。publish-github.sh 在推送前运行它
publish-updates.py run发布 latest.json；带 --release vX.Y.Z 时同时发布 channel.json
publish-updates.py announce vX.Y.0在 channel.json 中宣布功能版本。vX.Y.0 的 GitHub Release 发布、所有运行时层都在、Release 发布的每个能替换自己的 App（从它的 release-manifest.json 读）都有该版本的外壳层且既能容纳新代码也能容纳之前宣布的代码之前，一律拒绝。没有外壳层的平台（例如 AppImage 构建失败）继续用安装包
publish-updates.py upload-runtime-layerRelease 工作流按平台执行的步骤：从 base 构建运行时层，上传它的包和 runtime-<platform>-<base>.json。不移动指针，不需要密钥
publish-updates.py upload-shell-layerRelease 工作流对每个已签名的 macOS App、Windows App 和每个 AppImage（带 --seed，说明它的 Python 版本线）执行的步骤：用用户安装到的那个 App 构建外壳层，上传它的包和 shell-<platform>-<version>.json。带 --no-upload（演练时）只构建
publish-updates.py build-runtime-layer在本机把现有的 base 目录做成运行时层，随下一次 run 发布
publish-updates.py release-page用一次 API 调用创建只含代码的发行版的 GitHub Release 页面
publish-updates.py gc删除已不可能被读取的包；线上的包大部分已失效时重新打包。读不了的指针从历史补回，但只有 404 算缺失：其他连不上发行版的情况一律中止

一次每日发布约调用 GitHub 5 次：读一次发行版及其资产，上传一个包，latest.json 删一次传一次，再删除失效的包。

什么会通知用户

发布效果
每日同步不带 --tag只移动 latest.json。已安装的 App 看不到
功能版本--tag vX.Y.0publish-github.sh 推送 main 和标签，只派发 Release 工作流（先演练，再等 12 小时）。工作流构建安装包、全部运行时层和全部外壳层。然后由 publish-updates.py announce vX.Y.0 宣布，所以 channel.json 最后才动。只有这一种可以改变运行时或外壳

release.yml 只由 workflow_dispatch 启动。带 runtime_layers_only 时只构建并上传运行时层。

垃圾回收

线上的 latest.json、线上的 channel.json、发布端历史里最近 3 个指针、或等待发布的运行时层（本机构建的，或已上传的 runtime-*.json）还引用的包保留，其余删除。

线上包的字节有一半以上不被两个指针的层（含 tree）使用时，gc 把用到的对象重新写进一个新包。存储量有上限，也没有增量链。

实测

情况大小
代码层，首次发布9,106 个文件，原始 170 MB；包 59 MB
改一行 Python新包 9.5 KB：5 个 tree 共 5.8 KB（根 330 B），加 3.7 KB 的文件。客户端连指针约下载 11 KB
重签名的 macOS 外壳，代码不变已签名的 1.5.1 App（1,463 MB，18,878 个文件）对比一份把 305 个 Mach-O 文件和 15 个 bundle 全部重签名的副本：168 个文件不同。按整个文件算是 929 MB，压缩后 291 MB
同样的改动，按分片压缩后 21 MB（原始 60 MB）：119 个 1 MiB 以下的改动文件 7 MB，49 个更大文件的分片 14 MB。Electron 和 Chromium 两个框架从 73 MB 降到 3 MB
分片的代价整个都变了的文件分片后压缩得更大：Electron Framework 整个 66.5 MB，256 KiB 分片 78.1 MB，1 MiB 分片 73.7 MB。如果从 4 MiB 起切 1 MiB 分片，重签名的外壳要 47 MB，因为 29 个 1 到 4 MiB 的改动文件仍是整个

用一份扁平清单时，同样的改动客户端要下载约 644 KB；按目录的 tree（和 Git、OSTree 的 dirtree 对象一样）只留下通往改动的那条路径。

为什么这样设计
决定理由
文件以哈希命名和 OSTree、Steam depot 一样：任何版本已有的文件都不再下载，不管客户端从哪个版本跳过来
源码树，而不是 Git bundlebundle 需要一个前置提交，跳过几次更新的客户端可能没有。带 blob id 的源码树让任何客户端都能用手头的 blob 重建出发布的那棵 tree
没有增量链Codex 桌面 App（Sparkle）把增量链限制在 5 层。按内容寻址加重新打包，根本不需要增量链
签名的静态指针和 Claude Code 的签名清单、magpie 的签名校验和列表一样：一个小文件决定信任什么，序号防止重放
用下载地址，不用 APIGitHub REST API 未认证时每小时 60 次，按 IP 共享。发行版下载没有这个限制，并且支持 HTTP Range
代码在本机构建，运行时在 CI 构建GitHub 上的活动只有每天一次推送和几次上传；CI 完整构建一个发行版约一小时，所以只在运行时变化时才跑 CI。每个平台的运行时要在那个平台上构建
拒绝，而不是降级新的运行时或外壳需要只有功能版本才带的原生文件；拒绝能让每个安装都停在能运行的版本上
App 作为一层，重启时调换和 Chrome、Sparkle 增量更新对同一个包的做法一样：签好名的 App 是更新单位，运行中的 App 已有的文件直接复用，调换是 App 关闭时的两次改名。签名在拼好的副本上检查，拼装出错到不了用户手里

安装包

安装包仍然装着整个产品。没有版本库的 App 或终端安装按下面的方式从最新的稳定 GitHub Release 更新；不能替换自己的版本库 App（deb、只读或被转移的 App），更新需要更新的外壳时，也从这里取 App 文件。

安装类型路径
managed_release上图路径。不可变标记优先
source_checkout明确的 Git ref：预检、检出、依赖与构建、探测、重启。不显示成稳定 Release
unknown稳定的错误，指向官方安装器或源码检出。不猜 PyPI、二进制或 Git 路径

openprogram upgrade 应用更新；--check 只读报告当前和最新版本；--dry-run 打印计划。pip_wheel 不是安装类型：开发者 wheel 只作构建输入。

信任边界

边界规则
GitHub 响应不可信。HTTPS、固定主机、最多 5 次重定向且每跳校验、大小上限、30 秒请求超时、60 秒下载空闲超时。要求 draft === false、prerelease === false、tag 为 vX.Y.Z、资产名和 manifest 基名唯一、GitHub 大小等于 manifest 字节数。
网络路径走 Chromium 网络栈，因此使用系统代理。API 返回 403、429、5xx 或无响应时，改用 releases/latest 重定向加 release-manifest.json。仍失败时，用可选的 update-source.json，只有带内置密钥的 Ed25519 签名才生效
渲染进程 IPC只暴露状态、检查、布尔设置、下载、打开发行版、订阅。不接受 URL、路径、哈希、仓库或命令。公开状态去掉资产名、URL 和 SHA-256。关窗口不中止任何操作
下载文件随机排他临时文件，处理短写，任何不符都删除。CLI 在新版本目录校验并拒绝归档路径穿越。启动器失败保留旧 current
新的 App 外壳它的文件在指针签名覆盖的层里按哈希命名。拼好的 App 还要先通过平台自己的检查才放进暂存：macOS 上 codesign --verify --deep --strict 和运行中 App 的团队，Windows 上与运行中 App 主体相同的 Authenticode。调换脚本只用 staged.json 里、位于 App 自己的 .<App 名>.update/staged/ 下的路径
已签名的 Windows 线已签名的 App 只接受 Authenticode 签名有效、且发布者与自己相同的安装器：同一张证书，或续期后主体名相同。发布者取自 App 自身的文件。读取失败、超时或 App 的签名已损坏时，比较前会再读一次；仍然读不到发布者，就拒绝该安装器
未签名的 Windows 线未签名构建的 App 接受状态为 NotSigned、大小和 SHA-256 与 release-manifest.json 一致的安装器。这能发现损坏、截断或被调换的下载。它不能证明发布者：该清单没有签名，只靠到固定主机的 HTTPS 取信，能在那里发布发行版的人就能发布安装器。已签名的 App 不走这条线
更新签名覆盖什么channel.json 里的签名覆盖指针，指针按哈希列出每份层清单和每个包，所以版本库更新取用的每个对象都在覆盖范围内，外壳层也一样。它不覆盖 App 安装器，也不覆盖 release-manifest.json
安装器子进程固定仓库和版本。只放行 PATH、HOME、临时目录、语言、代理、XDG、OpenProgram 状态。不继承 provider 或 API 凭据，不继承归档或校验和覆盖项。--json 只输出一个 JSON 文档

失败

发生了什么结果
离线、超时、限流先回退到网页路径。自动检查：到下一次每小时检查时再试。手动检查：可重试的错误，并用平实的话说明原因。App 继续运行
Release 或清单无效下载前拒绝。不退回 wheel、源码归档、其他架构或旧版本。可保留最近的有效元数据
卡住、大小、哈希或 Windows 签名错误下载中断时重试，并通过 .part 文件续传，重启后也能继续。大小、哈希或签名不符时删除文件并恢复重试。未验证的文件绝不打开
CLI 归档、冷启动或启动器失败在最后切换前非零退出。旧版本保持选中（macOS 和 Linux 上是 current，Windows 上是启动器）
