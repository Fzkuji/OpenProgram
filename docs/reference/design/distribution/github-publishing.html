Publishing source to GitHub

GitHub carries main and nothing else. Its history never merges with the other lines, and nothing pulls GitHub's main back.

Branches

Locally there are exactly these three. A worktree branch is merged into dev and deleted, or deleted when abandoned. One worth keeping goes under refs/archive/, which no command lists as a branch and nothing pushes.

  1. Install the guards into the shared .git/hooks, so every worktree has them.
  2. Refuse a source not on dev. When main already holds the source's tree there is no new version; go to step 8.
  3. Refuse a source whose tree, or a summary, names a retired account, listing each path:line. This runs on every call, dry runs included.
  4. Scan added lines for live-looking credentials (GitHub tokens, Anthropic API keys, AWS access keys, private key blocks) and refuse on a hit. AWS's documented example key and one-line PEM strings in tests do not count.
  5. Refuse if scripts.docs_site.check --all fails on the source commit, read from a temporary checkout of it.
  6. Write the message: the summary, the number of local commits since the previous version, and a Local-Source: trailer.
  7. Create the commit with git commit-tree: the source's tree, the previous main as only parent (none for the first version), author and committer the publishing identity. Move main and record the source in refs/publish/last, where the next version starts counting.
  8. Push main after checking GitHub's main is an earlier point of local main, so the push only fast-forwards. Refuse when any commit on main has another author or committer, or its message names a retired account.
  9. --tag vX.Y.Z also labels that commit on GitHub, which triggers Release. Before anything moves it refuses:
    • a tag that already exists;
    • a source where any version place says another version, naming each one;
    • a source without .github/release-notes/vX.Y.Z.md starting with # OpenProgram X.Y.Z Release Notes;
    • a given --office-archive that is not the pinned Office archive;
    • a real run when neither the newest release nor the tag's draft has the archive (asked with gh) and no file was given. With a file, it seeds the draft instead.
    --dry-run runs these checks offline, skipping only the question to GitHub, says whether a local archive was given and matches, and shows the tag.

Publishing identity

The repository is Fzkuji/OpenProgram, the project's first repository: main carries its history up to 0.9.8 and then one commit per version from 1.0.0.

Each version commit is signed FzKuji, fzkuji@gmail.com, the signature of the earlier history; the script sets it whatever identity the checkout commits with and refuses to upload a version holding any other. Only the part of main GitHub does not have yet is checked, since the earlier history has many authors.

Versions 1.0.0 to 1.3.0 were built in FuzzyKuji/OpenProgram, where their installers stay. Download links, the installer scripts and the App's update check read releases from there until a version is released from Fzkuji/OpenProgram; source links already point at Fzkuji/OpenProgram. Author lines in pyproject.toml, apps/desktop/package.json and the README licence line keep the name the 1.x versions shipped with.

What a release builds

The Release workflow runs on the pushed tag. Every platform leg is independent.

A tag never moves, so a release can be rehearsed first. Publish main without --tag, then run gh workflow run release.yml -f tag=vX.Y.Z -f rehearse=true: every leg builds from main, the same checks run and nothing is published.

gh workflow run windows-install-smoke.yml -f tag=vX.Y.Z -f run_id=<rehearsal run> installs that run's Windows files on a Windows runner. When both pass, scripts/publishing/publish-github.sh --source refs/publish/last --tag vX.Y.Z tags the same commit; without --source, a promotion made in between would become a new, unrehearsed version.

The Office archive

The optional Office editor installs from one zip, about 699 MiB, whose name, size and SHA-256 are pinned in openprogram/programs/applications/office_editor/install.py; the download limit for office.assets in safe_http.py is the same size. Every release from 1.3.0 uploads it once; 1.0.0 to 1.2.0 carry none.

PointBehaviour
Where the App looksIts own version's release, then releases/latest/download/, which serves a build that has no release of its own while the pin is unchanged. Both copies are held to the pinned size and SHA-256
Why not only the newest releaseA fixed name on the newest release breaks every installed version the day a release changes the pack; a copy in each release keeps each version installable for as long as its release exists
No release has itThe install answers office_release_missing: a version before 1.3.0 is told to update to 1.3.0 or newer, any other to update to the newest version. A retry is not offered as the fix
Where a release gets itIt cannot be rebuilt in CI: the licensed fonts and the pinned editor build are the owner's inputs (Office README). The office job downloads the newest published release's copy, or else the one on the tag's draft release, and checks its bytes
First release to carry itpublish-github.sh --tag vX.Y.Z --office-archive /path/to/OfficeAssets-….zip checks the file and, before anything moves, puts it on the tag's draft release (office-archive.py seed). Every later release carries the previous one's copy with no upload by hand
Neither copy existsThe office job fails with the file name, size, SHA-256 and the seed command. Every build waits for it, so nothing is built or published
After publishingThe check on the public latest release also requires exactly one copy of the archive
A new packNeeds a new file name, never new bytes under an old one, because installed versions pin the bytes behind each name. office-archive.py pack names it OfficeAssets-<editor>-<patch>-<pack>.zip, the last part from the pack's own manifest digest, so different bytes always get a different name

Rebuilding the archive

On the owner's machine, from a dev checkout. The pack step makes the same zip from the same prepared pack. An installed copy is a prepared pack: when ~/.openprogram/cache/office/<source>-<patch>/versions/<manifest> validates against the pins in office_editor/assets.py, copy it out and go straight to the pack step; nothing is built or downloaded.

  1. Gather the inputs the Office README names: a git checkout of agentbridges-ai/onlyoffice-browser at d15d12b6945be4d8b0f3aa1806120e740d2950ee (package 0.3.34); the licensed font input and the font pack made from it with font-generation.mjs and Document Server 9.3.0's generator, whose manifest digest must equal OFFICE_FONT_MANIFEST_DIGEST in office_editor/assets.py; npm registry access for npm ci.
  2. Set OFFICE_LOCK_SHA256 in office_editor/assets.py to the SHA-256 of scripts/release/office/package-lock.json, the reviewed lock prepare.py builds with; the pack's last validation refuses any other lock.
  3. python scripts/release/office/prepare.py --source … --font-pack … --font-input … --output /path/to/prepared-office
  4. python scripts/release/office-archive.py pack /path/to/prepared-office /path/to/out writes the zip and pins its name, size and SHA-256 in install.py and the download limit in safe_http.py.
  5. Run the affected tests, commit on dev, deploy and promote.
  6. scripts/publishing/publish-github.sh -m "…" --tag vX.Y.Z --office-archive /path/to/out/OfficeAssets-….zip --dry-run, then the same without --dry-run.
