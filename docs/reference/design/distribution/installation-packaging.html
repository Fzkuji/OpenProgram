OpenProgram 安装、打包、发布与升级设计

本文是 OpenProgram 安装与分发的规范来源。它分别定义用户类型与平台支持，覆盖 macOS 和 Linux 桌面包、命令行与服务器安装、浏览器访问、Python 运行时归属、Program 扩展环境、版本、升级和卸载。实施任务单独记录，不与概念设计混合。

1. 已确定的设计约束

  1. Python 是 OpenProgram 后端、CLI、Runtime 和 Program 执行的核心运行时，不允许以删除 Python 的方式简化安装。
  2. macOS 桌面版通过 DMG 分发，Linux x86_64 桌面版通过 AppImage 分发。两个桌面包都包含固定 CPython、OpenProgram、核心 Python 依赖、预编译 Web 资源和基础运行组件。
  3. 桌面用户不需要预装 Python、Node.js 或 Git；首次基础启动不依赖网络。
  4. 签名后的 OpenProgram.app 在运行期保持只读。配置、会话、Program 源码、Program 依赖和缓存写入 ~/.openprogram。
  5. 桌面、命令行和开发安装使用同一个 OpenProgram release version，但安装介质和更新方式不同。
  6. stable 表示已发布、已验证的版本，不表示 origin/main。main 只属于开发安装。
  7. 正式安装不使用 editable checkout，不在用户机器上构建 Web 或 Ink，不依赖仓库目录。
  8. PyInstaller、Briefcase 和 py2app 只作为参考实现，不替换现有 Electron 桌面应用。
基础安装完整性：安装 DMG 或执行 AppImage 后，在没有系统 Python、Node.js、Git 和网络的条件下，桌面窗口、Python worker、Web UI、配置页面、基础 CLI 接口和默认内置能力能够启动。可选 Program、模型和非默认浏览器组件不属于该条件。

2. 当前实现与已验证缺口

范围当前实现与本设计的差异
安装脚本scripts/install.sh 克隆仓库，创建或复用 Python 环境，执行 editable install，并在本机运行 npm 构建。这是开发安装行为，不能作为正式 release installer。
Python wheelpyproject.toml 定义 CLI entry point 和 package data；release staging 会把预编译 Web 资源写入 wheel。已完成 Web 资源的 clean-wheel 验收；Ink bundle 仍仅属于源码开发界面。
Web UIfrontend.py 在 release wheel 中优先读取包内 _frontend；源码 checkout 仍使用 web/out。基础分发路径已消除用户机器上的 npm build；正式 release 仍需 CI 重复验收。
TUIcli_ink.py 从仓库根目录定位 cli/dist，缺失时调用 npm。正式 CLI 必须有不依赖 Node.js 的基础界面；Ink 只作为开发安装中的增强界面。
Program 安装protected_paths.py 把源码目录定义在 Python 包内部；programs.py 使用当前解释器执行 pip install。签名应用和普通 site-packages 不能承担可变 Program 源码及依赖。
Electrondesktop/main.js 在 packaged mode 从 resources manifest 解析包内 CPython，并以隔离模式启动 worker；desktop/package.json 声明 DMG、ZIP 和 AppImage。macOS unpacked app 已本机验证；Linux AppImage 已在原生 x86_64 runner 和 Debian 11/glibc 2.31 断网容器中验证。签名 DMG 仍必须由 macOS release runner 验收。
版本pyproject.toml 是规范版本来源；Electron metadata 保留构建工具要求的副本。release gate 必须拒绝 tag、Python metadata 和 Electron metadata 的任何不一致。
发布tag workflow 已定义 wheel、DMG、ZIP、AppImage、checksums、release manifest、GitHub Release 和 PyPI 发布；独立 Linux smoke workflow 可在无发布凭据时执行原生产物验收。Linux 预发布产物证据已经成立；受保护凭据、macOS 签名/notarization、GitHub Release 和 PyPI 状态只有实际 tag workflow 执行后才能成立。
升级upgrade.py 只处理 source checkout，并把 stable 映射到 origin/main。正式 release 安装需要版本化、分阶段验证和失败恢复；source checkout 只属于开发通道。

3. 官方规范与工具比较

本设计采用 Apple 的直接分发要求作为 macOS 规范来源，以 Electron 和 electron-builder 作为 macOS/Linux 桌面打包工具，以 Python 打包工具验证应用内置 Python 的可实施性，以 uv 管理命令行安装和 Program 依赖环境。

参考提供的能力缺少或不适用的能力OpenProgram 采用方式
Apple distributionDMG、PKG、ZIP 的适用边界；Developer ID 签名；嵌套代码签名；notarization。不负责 Python 或 Electron 的项目级组装。采用：DMG 直接分发，所有嵌套可执行代码签名，DMG notarize 并 staple。
Electron distribution / electron-builder signingElectron 资源打包、macOS 签名、发布和自动更新集成。不提供 Python runtime 或 Python dependency resolution。采用并扩展：继续使用 Electron；增加签名的 CPython、Python 包和默认运行组件。
electron-builder Linux targets / AppImageAppImage、deb、rpm、Snap 和 Flatpak 等 Linux 产物；AppImage 是无需 root 的单文件产物。不解决 Python runtime、不同 glibc 基线或 OpenProgram 功能验收。采用并限制：Linux 桌面首个正式产物只提供 x86_64 AppImage；deb/rpm 和 Linux arm64 桌面包在有独立验收环境后再增加。
BeeWare BriefcasePython 应用、CPython support package、签名 app、DMG/PKG/ZIP 和 notarization。它本身生成应用容器；与现有 Electron 应用职责重复。采用结构原则：Python 和依赖进入 app bundle；不采用 Briefcase 作为顶层构建器。
PyInstaller把解释器、应用和依赖组装成无需预装 Python 的产物。独立可执行打包不适合 OpenProgram 的 Python 库入口、动态 Program 发现和可变扩展依赖。拒绝：不采用 PyInstaller；保留标准 CPython 与 wheel 语义。
py2app创建包含 Python.framework 和 Mach-O 依赖的独立 macOS app。同样会形成第二套 app 构建层，不能替代 Electron shell。参考：用于核对 Python.framework、Mach-O 和 app bundle 布局，不直接采用。
uv environments不依赖 Python 的独立二进制、虚拟环境、固定解释器安装目标、Python 下载与依赖同步。uv tool 环境不应被 pip 直接修改，与当前 Program 安装行为不兼容。采用并限制：CLI 安装和 Program 环境使用受控 uv；不把 uv tool install openprogram 作为正式安装方式。
PyPA packaging / PyPI Trusted Publishingwheel/sdist、entry point、构建隔离和基于 OIDC 的发布。wheel 不包含 CPython，也不是 macOS 桌面安装器。采用：wheel 是所有安装形式共用的 Python 代码产物；PyPI 使用 Trusted Publishing。

4. 用户类型与平台支持

三类用户描述安装目的，平台矩阵描述产品承诺。两者分别维护，不能以用户类型代替平台覆盖。

DESKTOP

桌面用户

macOS 下载对应架构的 DMG；Linux x86_64 下载 AppImage。桌面包内置 CPython、核心依赖和 Web，不读取系统 Python、Node.js 或 Git。

macOS 与 Linux 命令行用户

运行固定 release installer。installer 使用固定版本 uv 创建 OpenProgram 管理的 CPython 环境，安装已发布 wheel，不克隆仓库，不执行前端构建。

克隆仓库，使用 uv sync 和项目构建命令。editable install、Node.js、Web/Ink 本地构建和 main 更新只出现在这一安装类型。

5. 一个版本与一组发布产物

pyproject.toml 中的项目版本是规范版本来源。Electron metadata 由于构建工具要求保留副本，release gate 验证它、release manifest、Python wheel 和 tag 完全一致。tag 必须指向被构建的 commit。

一次 release 构建vX.Y.Z
固定源码、lockfile、CPython、uv、Node 与 Electron 版本
→
共用 Python 产物wheel + sdist
预编译 Web 资源
依赖 lock 与 artifact manifest
→
分发产物macOS arm64/x64 DMG + ZIP
Linux x64 AppImage
PyPI wheel/sdist + checksums

每次 release 至少生成：

  • openprogram-X.Y.Z-py3-none-any.whl 和 sdist；
  • macOS arm64 DMG 与 ZIP；
  • macOS x64 DMG 与 ZIP；
  • Linux x86_64 AppImage；
  • 包含版本、文件路径、文件大小和 SHA-256 的 release manifest；
  • GitHub Release 和 PyPI 中可对应验证的版本。

首个正式版本分别构建 arm64 和 x64，不先生成 universal2。Python native wheels、浏览器组件和 Electron helper 都具有架构差异；分架构构建更容易验证每个二进制的来源和签名。只有全部 native dependencies 提供可靠 universal2 产物后，才重新评估 universal2。

6. macOS 与 Linux 桌面包

6.1 逻辑内容

macOS: OpenProgram.dmg → OpenProgram.app/Contents/
Linux: OpenProgram-X.Y.Z-linux-x86_64.AppImage → squashfs-root/resources/

桌面资源目录
        ├── MacOS/
        │   └── OpenProgram                 # Electron launcher
        ├── Frameworks/
        │   ├── Electron Framework.framework
        │   └── signed helpers
        └── Resources/
            ├── app.asar                    # Electron main/preload
            └── runtime/
                ├── python/                  # 固定 portable CPython + wheel 内容
                ├── bin/uv                   # 固定 uv
                ├── wheel/                   # 构建时 wheel 证据
                └── runtime-manifest.json

macOS 和 Linux 的 portable CPython 都来自固定 uv 版本所索引的 python-build-standalone 产物。runtime manifest 记录 OpenProgram、Python request 和 uv 版本；release manifest 记录最终 artifact hash。不允许从打包机系统 Python 复制任意运行时。

6.2 启动

  1. Electron 读取 app 内的 release manifest，并验证所需文件存在。
  2. Electron 使用 app 内的 Python worker launcher，调用明确的绝对路径，不查询 PATH。
  3. Python 使用 -I -B 启动，忽略系统 PYTHONPATH、用户 site-packages 和系统 Python 配置，并禁止向已签名 app 写入 bytecode。
  4. launcher 先装入只读核心包路径，再按已验证的 Program manifest 添加扩展路径。
  5. worker 监听本机端口并通过 /healthz 返回运行状态；版本与 runtime ID 字段补齐后再纳入发布 gate。
  6. Electron 获取认证 URL 后加载 Web UI；启动失败时显示错误类别、日志位置和修复动作。

6.3 不允许发生的行为

  • 不调用 PATH 中的 openprogram、python、node 或 git。
  • 不修改 /Applications/OpenProgram.app。
  • 不在首次启动时下载基础 Python、核心 wheel、Web 资源或默认基础组件。
  • 不从仓库目录读取 web/out 或 cli/dist。
  • 不在用户机器上执行 npm build。

7. Program 源码与依赖环境

只读核心

OpenProgram.app 中的 CPython、OpenProgram 核心包、内置依赖、Web、Electron 和默认基础组件。它们由 release 构建、Developer ID 签名和 notarization 保护。

用户允许的扩展

~/.openprogram 中的 Program 源码、Program dependency environment、配置、会话和缓存。Program 是用户明确安装并允许执行的 Python 代码。

~/.openprogram/
├── programs/
│   ├── src/<program-id>/
│   ├── manifests/<program-id>.json
│   └── environments/
│       └── <runtime-id>/
│           ├── releases/<generation>/
│           └── current -> releases/<generation>
├── config/
├── sessions/
├── logs/
└── cache/

runtime-id 至少包含 CPython minor version、CPU architecture 和核心 dependency lock hash。只要其中一项改变，Program environment 就重新创建，不能继续使用旧环境。

Program 的 install、upgrade 和 remove 都执行同一事务：

  1. 解析 Program 来源和声明，写入临时目录；
  2. 使用 app 内的 uv 和 CPython 创建 staging environment；
  3. 从全部已启用 Program manifest 解析并安装依赖，记录精确版本和 artifact hash；
  4. 执行 import probe、Program 注册检查和 worker cold-start probe；
  5. 全部通过后原子切换 current；失败时删除 staging environment，继续使用原环境。
信任边界：Program 及其 native dependencies 不属于 OpenProgram 核心签名内容。它们只能由显式 Program 管理命令写入，不能覆盖 openprogram 核心模块。Python worker helper 需要针对动态 native extension 加载设计最小 entitlements，并通过签名和实际启动验证；不能为方便安装而关闭整个应用的 hardened runtime。

8. 安装、升级和卸载

8.1 桌面安装

  1. macOS 用户下载对应架构的 notarized DMG，由 Gatekeeper 验证后把 OpenProgram.app 放入 /Applications 或其他应用目录。
  2. Linux x86_64 用户下载 AppImage，验证 SHA-256，增加当前用户执行权限后直接启动；不要求 root。
  3. 首次启动只创建 ~/.openprogram 的配置和状态目录，不安装基础 runtime。
  4. worker 从桌面包内置 CPython 启动。

8.2 CLI / Server 安装

  1. bootstrap 脚本通过 HTTPS 获取固定版本的 uv 官方 installer；installer 校验其下载的 uv archive。
  2. uv 安装固定 CPython，创建 ~/.openprogram/runtime/cli/releases/X.Y.Z。
  3. 安装同一 release 的 OpenProgram wheel；依赖锁定文件进入发布流程后，再把依赖解析升级为完整可复现安装。
  4. 安装器使用 runtime 的绝对路径执行版本 probe，并 cold-start worker、验证 /healthz、停止 worker；全部成功后才原子切换 current。
  5. 在 ~/.local/bin/openprogram 创建由 OpenProgram 管理的启动入口。通用 doctor 还检查 provider、持久 worker 和开发工具，不作为基础安装切换条件。

8.3 开发安装

开发文档使用仓库 checkout、uv sync、Web build 和 Ink build。现有 source installer 改名并明确标记为开发用途。开发安装允许跟随 main，但不能称为 stable。

8.4 升级

  • 桌面：先以手动下载新 DMG 或 AppImage 为正式机制；签名和更新元数据完成跨版本验收后再启用 electron-updater。macOS 自动更新需要签名应用和 ZIP 元数据；Linux AppImage 更新必须验证发布签名与 hash。参见 electron-builder auto update。
  • CLI / Server：在新的 version directory 安装、probe 后切换 current；失败时保留旧版本。
  • 开发：保留 source checkout 的 fetch、build、doctor、probe 和 restart 流程，目标 ref 必须显式。
  • 命令：openprogram upgrade 是统一公开命令；旧 update 先作为兼容别名，再按弃用策略移除。

桌面应用升级后，如果 Program runtime ID 不兼容，应用先以核心模式启动，再重建 Program environment。Program 重建失败只停用受影响 Program，不阻止核心界面启动，也不修改新 app。

8.5 卸载

  • 删除 OpenProgram.app 只卸载桌面应用，默认保留 ~/.openprogram。
  • CLI uninstall 删除启动入口和 OpenProgram 管理的 CLI runtime，默认保留状态。
  • 只有显式 purge 操作删除配置、会话、Program 和缓存；执行前必须显示精确目录并要求确认。

10. 公共入口验收标准

10.1 wheel

  1. 从 sdist 构建 wheel，并在不包含源码 checkout 的空环境中安装。
  2. openprogram --version 和 worker cold-start 成功；配置 provider 并启动持久 worker 后再把通用 doctor 作为完整环境验收。
  3. /healthz、/chat 和至少一个 hashed Web asset 返回成功。
  4. 验证过程中不安装 Node.js，不访问仓库的 web/ 或 cli/。

10.2 macOS DMG

  1. 分别在未安装 OpenProgram、Python、Node.js 和 Git 的干净 arm64 与 x64 环境验证。
  2. 断网后完成首次启动、初始化、worker health check、Web UI 加载和基础对话页面访问。
  3. codesign --verify --deep --strict、spctl、stapler validation 和 DMG verification 全部通过。
  4. 首次启动前后，OpenProgram.app 的签名资源没有变化。
  5. Electron 启动的 Python 路径位于 app bundle，不是 PATH、conda 或系统 Python。
  6. 默认浏览器能力如果被归类为基础能力，在断网验证中能够创建一次浏览器会话。

10.3 Linux AppImage

  1. 在无系统 OpenProgram、Python、Node.js 和 Git 的干净 x86_64 Linux 环境启动。
  2. 断网后完成 worker health check 和 Web UI 加载。
  3. Electron 启动的 Python 路径位于 AppImage resources，不是 PATH、conda 或系统 Python。
  4. 验证 AppImage SHA-256、desktop metadata、可执行权限以及至少一个 glibc 基线环境。

10.4 Program

  1. Program 安装只修改 ~/.openprogram/programs 和明确的状态文件。
  2. 安装、升级、删除失败不会破坏当前可用 Program environment。
  3. Program 不能通过依赖声明替换 openprogram 核心包。
  4. 桌面 app 升级后，兼容 Program 能够重建并继续注册；不兼容 Program 不阻止核心启动。

10.5 CLI / Server

  1. 一条 release installer 命令可以在干净 macOS/Linux 用户环境安装固定版本，不克隆仓库。
  2. 安装器内部始终调用明确 runtime 路径；新 shell PATH 尚未刷新时也能完成验证。
  3. 升级在新目录完成并验证后切换；失败时旧版本仍能启动。

10.6 release

  1. tag、Python package、Electron package、manifest 和 health endpoint 报告相同版本。
  2. GitHub Release 包含两种 macOS 架构的 DMG/ZIP、Linux x86_64 AppImage、checksums 和更新元数据。
  3. PyPI wheel 与 GitHub Release wheel hash 相同。
  4. 已发布 tag 不允许移动；修复使用更高 patch version。
