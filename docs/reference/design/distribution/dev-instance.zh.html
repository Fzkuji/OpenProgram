稳定版与开发版实例

稳定版是来自 GitHub Release 的正式版 App，只由它自己的更新器改动。提交进 dev，在开发版上运行。部署不重启稳定版，所以稳定版里的对话可以部署并查看 http://127.0.0.1:18200。

规则在 openprogram/operations/worker/dev_instance.py。openprogram dev status 显示稳定版 App 的发布版本和健康状态、开发版的提交和健康状态，以及 dev 上还没部署的提交。

部署到开发版

openprogram dev deploy [ref]（默认 dev）把提交检出到 detached worktree ~/.openprogram-dev/source，在那里运行 scripts/local-instances/refresh-dev-instance.sh。稳定版不会被停止或写入。

  1. 拒绝未提交或未跟踪的文件。同一时间只跑一次部署，第二次等待。
  2. 同步 Git hooks，报告上次部署以来的文档问题，但不中止。构建 Web 资源和 OpenProgram wheel；违反格式的页面变成可见的错误页。
  3. 只有 Python、文档和测试以外的已跟踪文件自上次部署后变了，才重新构建 Web 导出；否则再次使用上次的导出。
  4. 在运行时里安装一次完整的 CPython 3.12（uv python install --install-dir），同步到发布版使用的锁定依赖，重装 wheel。
  5. macOS：构建 helper OpenProgram Dev.app（ai.openprogram.runtime.dev），让 runtime-manifest.json 指向它。worker 有自己的身份，屏幕录制、辅助功能等权限与稳定版分开授予。
  6. 设置 dev profile 的端口，绑定 Program 目录。
  7. 只安装或重启 dev worker，作为登录服务（launchd 或 systemd；其他系统直接停止再启动）。最多等 300 秒 /healthz，再把提交记入 runtime/source-revision。
  8. macOS：运行 scripts/local-instances/install-dev-app.sh。

登录

worker 每次启动都生成新的 owner token，所以一次部署会让浏览器掉登录。开发版 App 自己取新 token。

命令结果
openprogram dev open用默认浏览器打开，已登录；掉登录的提示会写出这条命令
openprogram dev auth-url打印登录链接，给其他浏览器用

数据与模型

凭据库的根目录是当前 profile 的数据目录，所以 dev profile 不读取也不刷新默认 profile 的登录。openprogram dev copy-models 复制模型配置：

复制不复制
配置项 providers、last_used_model；每个厂商的 API keyOAuth 登录：refresh token 会轮换，两个实例会互相挤掉登录。需要时重新登录。
API key 和 CLI 委托凭据（按引用读取其他工具的登录）对话、Agent、记忆

ChatGPT 登录是共享的：开发版读取 Codex CLI 的 ~/.codex/auth.json，稳定版把同一账号的登录同步进这个文件。两边都采用对方写入的更新登录，不去花已经用过的 refresh token（一台机器一个 ChatGPT 登录）。

从对话里

在开发版里（dev profile，源码仓库有 dev 分支），self_update(action="prepare") 走 dev_deploy 后端：改动就是 dev 上的一个提交，部署它就是整个更新。调用保存请求并启动脱离的控制器，其余步骤在发起调用的那一轮保存之后才开始。

步骤做什么阶段
1等发起调用的那一轮保存preparing
2在候选的 worktree 里 rebase 到 dev 上，再在主 checkout 里 git merge --ff-only。dev 移动或 index.lock 被占用时退避重试，最多 10 次building
3openprogram dev deploy <sha>，它会重启发起请求的 worker；开发版已经在服务该提交时跳过building
4对端口 18200 和 dev 状态目录做系统探测，再做浏览器探测：打开已登录的 Web 应用，直到消息框出现building
5结果经常规投递和后续轮次，在重启后的 worker 上回到发起的对话succeeded

探测把 doctor 各行与该实例改动前的结果比较，本来就失败的行（比如开发版没有的登录）不挡更新。稳定版 App 不会被等待，也不会被改动。

结束状态条件
succeeded开发版在服务落地的提交，并通过两项探测
aborted发起调用的那一轮一直不结束；rebase 冲突或挡路的脏文件（列出文件）；部署或探测失败。已经落地的提交留在 dev 上，结果会说明：修复就是下一个提交，和其他改动一样提交、部署

在正式版 App 里，同一调用在保存任何请求之前就被拒绝：App 是 Developer ID 签名的，本机无法重新构建，拒绝信息会指向设置里的检查更新。

控制器
项目行为
后端openprogram/operations/self_update/control/backend.py 选择，这个是 control/dev_deploy.py
位置<state>/self-updates/<id>/controller 下的运行时私有副本，在开发版运行时之外：部署会替换那份运行时，而代码是懒加载的
运行方式macOS 上是 launchd 任务，其他系统是脱离的会话，环境里既没有会话也没有 profile。挂掉时由 worker 启动拉起
重启步骤幂等。更新目录里的日志记录落地的提交，重启后从所在阶段继续
撤销self_update(action="undo", target=<提交>) 在 dev 的 worktree 里 git revert，作为普通 prepare 提交
重试self_update(action="retry") 不适用，修复就是新的 prepare

发布

两个实例都不推送任何内容。见发布源码到 GitHub。

源码 checkout

openprogram dev 和自更新控制器通过 OPENPROGRAM_SOURCE_REPO 找到仓库，否则读 ~/.openprogram-dev/source-repo。scripts/local-instances/refresh-dev-instance.sh 写入它，记录的是主 checkout，不是构建 worktree。
