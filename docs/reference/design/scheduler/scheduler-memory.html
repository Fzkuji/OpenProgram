OpenProgram Scheduler 与 Memory 接口

Scheduler 负责时间、执行、状态和结果；Memory 负责长期语义事实。两者通过稳定引用和现有 Memory 工具连接，但不共享状态文件或写入事务。Agent 可以在规划、执行和关闭任务时显式维护关联的 Memory 记录。

1. 目标与边界

一次性任务

保存带时区的 run_at，到期后只执行一次。旧的有日期 Commitments 迁移为此类型。

周期任务

复用现有五字段 cron 解析、owner 签名、冻结 sandbox policy 和非交互执行边界。

监控任务

使用 cron 周期执行观察 prompt。首版记录执行日志和状态，不承诺跨渠道 exactly-once 通知。

明确排除

Memory writer 不推断任务；Memory 页面不显示 Commitments；Scheduler service 不隐式创建或修改 Memory；不新增跨 Scheduler 与 Memory 的联合事务、外部 token 权限模型、已删除记录的占位对象或 ID 转发、第二套执行器、项目管理、任务依赖或子任务。

2. 目标数据关系

1 创建owner Web、Agent tool 或外部 API 创建 Scheduler task。
2 冻结Runtime 签名 prompt/command、cwd、权限、sandbox 与 MemoryRef。
3 唤醒常驻 OpenProgram worker 每分钟判断 once/cron 是否到期。
4 解析执行前按 workspace_id + memory_id 读取当前 Memory 内容。
5 执行在冻结的非交互权限边界中执行，并写 Scheduler 日志与状态。

Worker tick 异常边界

初始 @reboot tick 和后续普通 tick 抛出 Exception 时，daemon 以 warning 和完整 traceback 写入 stderr，在下一分钟边界继续；不立即重放、不补偿，初始失败后后续 tick 使用 reboot=False。常驻 OpenProgram worker 重定向后的 stderr 进入全局 worker 日志；独立前台 scheduler-worker 则显示在当前终端。两者都不是某个任务的 execution log。run_once、KeyboardInterrupt、SystemExit 与其他 BaseException 保持 fail-fast。

3. MemoryRef 公共契约

字段规则失败
workspace_id必须等于当前 Memory workspace 的稳定 ID。拒绝跨 workspace 隐式读取。
memory_id创建和更新时必须解析到唯一 Topic block；内容在每次执行时重新读取。写入时拒绝缺失、重复、跨 workspace 或格式错误的引用；执行前引用失效时任务失败，不回退到旧快照。
写入能力MemoryRef 本身不授予编辑权。由本地 owner 创建的 prompt task 可以使用 memory_status、memory_get 与 memory_update，所有修改仍走现有 revision、格式校验、派生视图和 Git 事务。缺少当前 revision、Topic 格式错误或并发更新时，Memory 事务独立失败；Scheduler 状态不回滚。

4. Agent 生命周期协议

阶段Agent 行为边界
规划或创建仅当任务本身值得长期保留时，Agent 使用 memory_update.create_record 创建任务记录，再把返回的 memory_id 作为 memory_refs 附到 Scheduler task。普通临时提醒可以不写 Memory。两个调用顺序执行，不伪装成一个原子事务；任一步失败都明确返回给 Agent。
执行或状态变化Prompt task 在执行时收到当前 MemoryRef 内容。若该记录描述本任务，Agent 先读取 revision 和原记录，再使用 update_record 写入当前状态、结果或下一次仍需保留的信息。Scheduler 不能使用 shell、文件写入、网络发送等其他副作用工具；新增写能力只限现有 Memory 事务工具。
关闭仍有长期价值时，把关联记录更新为已完成、已关闭或最终结果；完全没有保留价值时，使用 delete_record 删除。交互 Agent 可同时禁用或删除 Scheduler task。删除后当前 Memory API 不再解析旧 ID，仍引用该 ID 的 Scheduler task 会在下次解析时失败，因此应先移除或关闭任务。

Git 恢复边界

删除记录前的提交仍可从同一 Memory Git 仓库的可达历史中检索和恢复；这要求相关变更已经提交、仓库未丢失且历史未被重写或清理。当前 memory_get 只查询 HEAD，因此 Git 历史可恢复不等于旧 memory_id 可由当前 API 直接查询，也不构成绝对的 100% 保证。

5. 旧 Commitments 迁移

  • 只迁移 open 记录；有日期记录成为启用的一次性任务，执行时间为本地日期 09:00。
  • 无日期记录成为暂停的一次性草稿，保留文本和 provenance，等待 owner 设置时间。
  • 迁移成功后把原始 commitments.jsonl 移到 Scheduler migration archive；重复启动不得重复创建。
  • Memory writer 删除 record_commitments 工具与提示，旧 runtime parser 只作为一次性迁移兼容代码保留。

6. UI 信息结构

独立 /scheduler 页面复用 Chats、Memory、Programs 与 MCP 的管理页结构：64px topbar 只显示一次页面标题，搜索和 Create 作为右侧工具；topbar 下方固定为左侧分类栏和右侧内容区。页面不设置第二个大标题或宣传式说明区，避免与 OpenProgram 其他管理页产生不同的字号、留白和操作层级。

Scheduler 自动写 Memory拒绝在 service 层隐式双写。采用 Agent 显式组合两个现有工具，并以 MemoryRef 保存关联，避免新增跨存储事务和重复 CRUD。

8. 实施 brief 与验收

本轮修改限定为 Scheduler prompt task 的内部 Memory 生命周期：保留现有 Scheduler service、REST、UI 和 Memory 数据格式；允许 Scheduler 来源调用 memory_status、memory_get 与 memory_update，补充 Agent 工具说明和执行上下文提示。公共 RED 必须证明上述三个工具可执行，同时 shell、普通文件写入、网络发送和 Scheduler 自修改仍被硬约束拒绝；Memory 写入继续经过现有 authority、revision、transaction 与 Git 路径。外部 API 权限不在本轮实现；记录删除后，旧 memory_id 的当前查询按最终语义返回 NOT_FOUND。

独立的 worker reliability 修改隔离 run_forever 的完整 tick 异常，并让 scheduler-worker 与 cron-worker 绕过仅供 Ink TUI 启动的 stdio 重定向；不改变 Scheduler service、REST、任务状态格式、claim、spawn 或 run_once。
