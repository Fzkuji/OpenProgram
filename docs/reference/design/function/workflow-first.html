全面workflow化：把什么收进代码，把什么留给模型

三层的区别只有一个：控制流握在谁手里。工具握在模型手里，技能也握在模型手里（散文只是建议）， @agentic_function握在Python手里。所谓“全面workflow化”，就是把重复出现的工作模式的控制流从模型那边收到代码这边。 收的是顺序、扇出宽度、验收闸门、产出契约；留的是判断、抽取、措辞、修复。这一页把四层现状按这条线画出来。

两个真做成了的，它们各自的形状

两家的取法不同但结论一致：固化层要么给出一份“每步返回什么”的契约（openclaw），要么给出一个“每个流程实现什么”的接缝（codex）。 我们两样都已经有了：@agentic_function就是那个接缝（DAG节点、expose、注册成工具都是白拿的）， 返回值就是那份契约。缺的是有人去用，以及缺一样东西：断点续跑。

03我们计划怎么优化

先把线划清楚：代码持有什么，模型持有什么

推论一条，很容易搞反：workflow里大多数步骤不该是decision.make。 一个到处是decision.make的workflow，只是把模型的自由度换成了一份菜单，没有真的收进代码。 闭集分支（下一步走哪条路）用decision.make，应该少见；开放产出（这一步交出什么内容）用runtime.exec加输出契约加代码侧结构检查，那才是常态。

04理想状态

05几个设计问题的回答

workflow是第四层，还是取代技能层？

都不是。它是@agentic_function这一层第一次被用满。 再造一个@workflow装饰器只会是同一机制的第二个名字：DAG节点、expose／render_range的上下文裁剪、注册进共享registry让模型能直接调、重试与墙钟预算，这些@agentic_function全都给了。 变的是写法约定（一个形状），不是机制。
技能不消失，变薄。技能有workflow没有的一件事：按描述可寻址。name加description进系统提示，模型在还不知道该干什么的时候能找到它；workflow函数按工具名寻址，模型得先认得这个名字。 所以技能从“步骤清单”退成路由：什么情况下跑哪个workflow、参数怎么填。今天那些两百行的步骤型技能，该变成二十行技能加一个函数。
distill声称的两条路，只有SKILL.md那条真铺到底了：§3给了判断标准，§5只写了怎么写SKILL.md，函数那条留一句“去加载agentic-programming技能”就转走。现有4个agentic函数没有一个是distill产出的。要补的就是这条断头路。

decision.make现在的形态够不够表达“让模型判断哪条值得抄”？

现在的形态：选项是dict或list，每项可以是callable（选中就跑，返回值直接当结果）、任意值（原样返回）、或("说明", schema)（模型填schema，返回{"decision": name, **字段}）。 菜单渲染成带Call:示例的文本，回复里逐个花括号试着抠JSON，按类型／枚举／嵌套结构校验，失败让模型重挑（重挑本身也是一次exec，也进DAG），耗尽后抛DecisionError。
不够，而且方向不对。“哪条值得抄”不是从固定菜单里选一项，是产出一个开放列表。decision.make是闭集选择器。 要分清两种口子：闭集分支（下一步走哪条路）用它，在workflow里应该少见；开放产出（这一步交出什么内容）用runtime.exec加输出契约加代码侧结构检查，那才是常态。 第二种现在没有便利入口，exec(response_format=)零使用，三个地方各手写一遍JSON解析。补一个exec_json(prompt, schema)就够，约25行，不是新层。

跑了半小时的workflow中间失败了怎么办？session.py管不管？

不管。Session是ask_user在CLI下的文件信箱：uuid键目录，meta.json加一个answer触发文件，原进程wait_for_answer轮询，run_with_session在finally里cleanup()删目录。跑了半小时崩掉，它什么都不留。
真正落盘的是DAG：create_pending_call_node进入时写status=running、output=None的节点，_update_function_call_exit退出时补上输出和耗时，进git支撑的会话库。 每个已完成步骤的输入和输出已经在磁盘上了，只是没人读回来。
最省的补法：once(key, fn)，跑一步之前查本会话下有没有同名同参且已完成的节点，命中就返回它记录的输出。约30行，不新增写入方、不新增文件格式。 天花板必须说清：只对“输入决定输出”的步骤正确，写文件的步骤是被跳过不是被回放，所以要显式选择加入。openclaw那套SQLite flow_runs加revision对我们是重复造DAG。

agent()那套是不是workflow的天然执行底座？并行步骤该不该就是派几个agent？

是，而且不用建任何东西。agent(run_in_background=True)立刻返回task_id，task_output(task_id)阻塞取结果，task_stop(task_id)取消且取消沿血缘级联，派生深度／扇出／消息数三个预算已经在配置里（默认depth 1、fanout 8、messages 8）。 并行步骤就是派一批再逐个收。有个旁证：goal需要“带工具的一次判断”时，绕开了exec(tools=)，改用run_agent_turn派子agent，说明子agent本来就是更顺手的那条路。
唯一要建的是：start_from="clean"意味着prompt就是子agent看到的全部，所以并行步骤必须构造每个子提示。这正是今天手写四遍的东西，而且四个共用同一个模型覆盖，一起撞上配额上限同时死，然后靠我手工重发。写成代码，模型降级重试就是fan_out里的一个清单，不是人的记性。

成本可预测是不是主要收益之一？

是，但要说准：固化之后不是每次调用次数固定，是次数有上界且上界写在代码里、看得见。 survey_references固化后，顶层是仓库数次派发加空格子重问加一次合并；每个子agent内部的循环次数仍然不定，但被max_iterations和自身预算兜住。 今天手写同一件事，顶层调用次数完全取决于当时怎么想的，跑两遍能差好几倍。
排在成本前面的收益其实是另外两个：漏步骤变得不可能（清单是代码，不是记性），结论可核实（出处检查是闸门，不是礼貌）。 今天三次真实事故里，两次是漏步骤和没核实，一次是两个agent撞同一个文件，都不是成本问题。
