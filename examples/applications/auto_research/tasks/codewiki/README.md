# codewiki tool

`code_wiki` writes module-level architecture docs for the paper's code and ties the paper's method subsections, equations and algorithms to the functions that implement them (`tasks/codewiki/`). It takes the project's Git repository as `paper_dir` (anything else raises `ValueError`), writes into `<out_dir>/<timestamp>/` with a trail (`run.json`, `run.md`), and returns JSON with `status`, `report` and `run`. The report is in Simplified Chinese; the wiki itself is in English, as repository docs are. Plain code reads the code and the paper and checks every link; the roles only choose links and write prose.

Learned from DeepWiki (Cognition: a browsable wiki generated from a repository, with module pages, diagrams and source citations) and paper-to-code mapping tools (each part of a method linked to the code implementing it).

## code_wiki

| Item | Contract |
| --- | --- |
| Signature | `code_wiki(paper_dir, code_dir="", out_dir="")` |
| Purpose | A contributor finds, for every equation and method subsection of the paper, the function that implements it, and for every module what it does and how data flows through it, each statement cited by a line that exists. The parts with no code are listed: not implemented, or the paper claims more than the code does. |
| Input | `paper_dir`: the project's Git repository; the paper is `rules.json`'s `main_tex`, else the top-level `.tex` with `\documentclass`, with `\input`/`\include`/`\subfile` inlined. `code_dir`: the code; empty uses `rules.json`'s `code.repo` when it is a local folder, else `paper_dir` (as `paper_agent`). `out_dir`: default `<paper_dir>/drafts/code_wiki`. Not a Git repository, a `code_dir` that is not a folder, code without a source file, or a paper without a main `.tex` or `\begin{document}` raises `ValueError`. |
| Code index (plain code) | Up to 400 source files; `.git`, `drafts`, `workflow`, `docs`, virtualenvs, `node_modules`, build folders, hidden files and `.env` skipped; tests (`tests/`, `test_*.py`) indexed and marked. Python by `ast`: module docstring, imports (relative, absolute, sibling-script and suffix matches resolved to project modules), classes with bases, functions and methods with spans, signatures, docstrings, and the top-level statements as the pseudo-function `<module>`. Calls between project functions: local and imported names, `module.func`, `Class.method`, `self.method`, `self(...)` (the class's `forward`/`__call__`), `self.layer(...)` where `__init__` assigned `self.layer = ProjectClass(...)` (also inside `ModuleDict`/`ModuleList` keywords), and a class constructed means its `__init__`. `.js/.ts/.cpp/.cu/.c/.h/.rs/.go`: function and class names by regex (spans end at the next definition; calls by name within the file). Entry points: a `__main__` block, argument parsing (`argparse`, `fire`, `tyro`, `hydra`), file names like train/eval/main/run/sample, console scripts from `pyproject.toml`, `setup.py`, `setup.cfg`, and `package.json` bins and scripts. Config files (`.json/.yaml/.yml/.toml/.cfg/.ini/.conf`) in the top two levels or a `config(s)`/`conf` folder, with their top-level keys. |
| Paper parts (plain code) | deep_read's LaTeX structure (`deepread.structure`). Method sections: top-level sections titled like method, approach, model, architecture, framework, algorithm, training, objective, inference (and not introduction, related work, background, experiments, results, conclusion, appendix, why). Parts: every section under them with text of its own (a method section's own overview is skipped when it has subsections; a method section without subsections is a part itself); every numbered display row in a method section and every display row with a `\label` anywhere (`eq:<number>`); every `algorithm` float with its caption, label and body (`alg:<n>`). |
| Model calls | `mapper` (`map_parts`, schema `paper_code_map`): one call per 8 parts, with the numbered source of the most central non-test modules (80k characters), an outline of the others and the config files' text (4k each, 12k in all). Per part: `implemented`, `partial` or `not_found`, a note, and at most 4 links (function `path::qualname`, line, code quote, paper quote, how). `writer` (`write_page`, schema `module_page`): one call per module, at most 24 (modules implementing a part first, then by functions, calls across modules and entry points), with its numbered source (30k), outline, calls in and out and its checked links: purpose, at most 8 key functions and 8 data-flow steps (each with a line and a quote), and how it implements each of its parts. |
| Check | A link is kept when its code quote (8 or more non-space characters, whitespace runs compared as one space) is on a line of the named function (nearest to the line given), or else anywhere in the named file, where it is re-attributed to the function holding that line; and its paper quote (12 or more characters) occurs in that part's text or LaTeX (citation markers, case and whitespace ignored; spaces ignored for LaTeX). A key function is kept when its quote is on a line of that function of the module; a data-flow step when its quote is on a line of the module; a paper item only for a part this module's checked links implement. Everything else goes to `dropped` with the reason. `function:path` written with one colon is accepted. A reply that is not valid after the retries leaves those parts unmapped or that page with the outline only, and is noted. |
| Output | JSON with `status`, `report`, `run`, `site`, `md`, `code`, `modules`, `functions`, `parts`, `mapped`, `unmapped`, `links`, `pages`, `dropped`, `notes`. `PASS`: every part has a checked link. `PASS_WITH_NOTES`: some part has none, or the paper has no part. `FAIL`: there are parts and none has a link. Files: `docs/code_wiki/index.html` (counts, entry points, the module tree with each module's purpose, the module call graph as inline SVG, the paper-to-code table with code and paper quotes, config files), `docs/code_wiki/callgraph.svg`, `docs/code_wiki/modules/<path>.html` (purpose, paper parts implemented, key functions, data flow, the function call graph with other modules' functions dashed, every class and function with lines and docstring), `docs/code_wiki/src/<path>.html` (the source with `#L<n>` anchors every citation links to), `code_wiki.md`, `wiki.json` (everything, including what was dropped and why), `report.md` (the table by part, the unmapped parts with the mapper's note, and a `cp -R` command that would copy the site into the code's `docs/`). |
| Site | Plain HTML and CSS, no script and no external file; light and dark by `prefers-color-scheme`. The SVG is laid out in code: columns by longest path from the callers (an edge closing a cycle is drawn dashed below), barycenter ordering, at most 60 nodes. |
| Effects | Model calls as above. Reads the code and the paper; writes only the run folder. The code and the paper are never modified or executed. |
| Tests | `tests/codewiki/`: a fixture repository with a package (relative and absolute imports, a layer assigned in `__init__` and called in `forward`), a script with argparse and `__main__`, a console script, a config, a test file, TypeScript, Go and Rust files and an ignored `drafts/` file; the index, the call edges, entry points, configs, quotes over several lines; the paper parts (subsections, a labelled equation, an algorithm, the unlabelled experiments equation left out); the SVG layout with a cycle; a full run with scripted roles (a link re-attributed to the function holding its quote, a paper quote from another part, a missing file, a key function quoted outside its span, a made-up step), the site's pages and anchors, PASS, PASS_WITH_NOTES and FAIL; `code_dir` elsewhere and every `ValueError`. |
| Not covered | Languages other than Python get names and spans only (no imports, no calls across files, no docstrings); calls through variables whose type is not visible (`model(x)` with `model` a parameter) are not edges; equations in PDFs (LaTeX only); copying the site into the repository (the report proposes the command). |
| Usage | `from auto_research.tasks.codewiki import code_wiki` |
